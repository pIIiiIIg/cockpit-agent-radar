一、先说结论

P0：MaAI —— 追踪表上第一个"中文可用 + 代码 MIT + 可纯 CPU 运行"的实时判停/应答制品

这一条的形状与以往都不同：核心价值在制品，论文只是发现通道。 本轮通过 cat:cs.HC 查询命中论文 2608.19527《Does Listening Matter? Backchanneling and Nodding in AI Clone》（京都大学 Inoue/Kato/Kawahara + Sony CSL Kasahara，2026-08-20T00:53:25Z 投稿，v1，5 页，cs.HC，ICMI 2026 Late-Breaking Results track）。论文本身是一份小规模人因研究，但它使用的预测组件指向一个此前从未进入过本项目追踪表的开源软件：github.com/MaAI-Kyoto/MaAI。

一手核实结果（全部通过 GitHub / Hugging Face API 直接核对，非转述论文）：

  • 仓库存在，MIT（LICENSE 文件 1,078 字节，逐字读为标准 MIT，版权方 "MaAI Development Team"，2025 年），created 2025-07-04T07:12:01Z，pushed 2026-08-19T08:02:06Z，224 个 blob 合计 88,247,753 字节，120 stars，最新 tag v0.2.15。
  • 功能覆盖四类：判停（Turn-Taking，VAP）、语音活动检测（VAD）、应答预测与应答检测（Backchannel prediction / detection）、点头预测（Nodding）。
  • 语言覆盖含中文。 主 README 自述 "Currently available for English, Chinese, and Japanese languages"。
  • 可纯 CPU 运行。 主 README 自述 "Thanks to its lightweight design, MaAI operates efficiently, even exclusively on CPU hardware"。
  • 帧率是用户可设的参数，因而算法块长可直接换算：判停与应答模型支持 5 / 10 / 20 Hz（CPC 编码器，model_type="normal"）或 12.5 Hz（Mimi 编码器，normal-ver2）；VAD 支持 10 / 20 / 50 Hz（CPC）或 12.5 Hz（Mimi）。
  • MaaiMultiple 让多个模型共享同一个音频编码器，官方说明为"（相对昂贵的）编码器每音频帧只运行一次"。

编辑判断：这正是项目 probe_turn_end 负面结果所指向的那种结构，而且是第一个不需要 GPU 的。 项目已实测"主模型自己判停"不可行；X2-Turn（08-20 的并列 P0）给出的替代路线是"判停头与 ASR 头并行、不回灌解码"，但那是一个 4B 模型、要占 GPU。MaAI 给出的是更彻底的解耦：它完全不做 ASR、不做语义，只从声学流连续预测非语言行为，因此可以整个搬到 CPU 上，与被 MoE 主模型占满的 GPU 互不争抢。对一个 GPU 已经是瓶颈的车机，这个属性的价值可能高于精度本身。

但开放状态是本轮最需要小心的一条，因为它是"代码一个许可证、权重三个许可证"的拼盘。 详见第 1 节。一句话结论：中文应答预测权重 vap_bc_ch 是 MIT，可商用；而中文判停主力权重 vap_ch 是 CC-BY-NC-ND-4.0，不可商用且不可衍生；其 MIT 替代品 vap_ch_kyoto 存在但能力严格更少（只有 5Hz 与 10Hz 两个文件，无 Mimi 12.5Hz、无 20Hz、无短上下文变体）。"MaAI 是 MIT 的"这句话是错的，必须逐模型看。

P0（同一条脉络）：2608.19527 的真正价值是一条倒 U 型约束，不是那三个显著性

论文事实。 N=35 名日语母语者（本科/研究生），被试内设计，AB/BA 配衡，单尾配对 t 检验。加入应答与点头后显著改善的是三项：注意感 5.29 对 4.80（p=.018）、真实感 4.77 对 4.29（p=.006）、共在感 4.60 对 3.94（p=.002）；亲近感（p=.081）与参与感（p=.089）为边缘显著；其余四项无显著优势。九项量表内部一致性 Cronbach's α 为 .77 / .81。顺序效应检验九项全部 p>.21。

论文事实（本条最重要）：注意感与应答次数呈显著的倒 U 型关系，二次项 p=.009，在中等数量处达到峰值。 论文原话是 "simply providing more was not necessarily better"。点头与其余各项均未出现显著曲线关系。系统实际产生的量为：每段对话应答 27.29 次（SD 7.55）、每条用户话语 2.25 次（SD 0.92）；点头 21.83 次（SD 6.10）、每条话语 1.76 次（SD 0.62）。

同等重要的负面结果，论文自己报了：用户的行为一点没变。 用户话语条数 12.89 对 13.11（p=.516）、平均话语长度 7.30 对 6.93 秒（p=.195）、对话时长 4.90 对 4.83 分钟（p=.300），全部 p>.19。论文自己的解释是"主观评价的改善反映的是用户对交互的感知变化，而不是他们自身外显对话行为的变化"。

编辑判断：这两条合起来，给出了一条项目可以直接执行的设计约束和一条不可用的论证。 可用的是：应答频次必须设上限，且"更多"会反向伤害注意感——这是目前唯一一条把"应答不是越多越好"变成显著性检验结果的一手证据，项目若要做座舱应答，这条应当在第一版就写进参数表，而不是上线后靠投诉发现。不可用的是：不能用它论证应答能提升任务效率或缩短交互，因为论文自己的行为数据在这一点上是零效应。

P1：Thinkingbox —— 它挑战的正是项目现在的头条指标

论文事实。 2608.19741《One Success Isn't Reliability: Thinkingbox, a Sandbox and Benchmark for Agents in Stateful Business Workflows》，微软，2026-08-20T07:37:57Z 投稿，v1，45 页，cs.CL，论文许可证 CC-BY-4.0。507 个任务、每任务独立 20 次尝试、12 个模型，即每模型 10,140 次试次。GPT-5.4 的 pass@20 达到 91.12%，而 pass^20（20 次全中）只有 25.25%。

编辑判断：这一条直接指向项目的 80.49% 严格工具名召回。 论文的核心主张是 "tool-call-level signals are not clear proxies for end-to-end task completion"（工具调用层面的信号不是端到端任务完成的清晰代理）。项目当前的头条数字恰恰是一个工具调用层面的单次运行指标。加上 08-20 从 ComponentBench 记下的"两次运行聚合完全相同（52.5%）却有 17.3% 的逐条翻转"，现在有两条独立证据说明单次运行的聚合数字会系统性高估可靠性。 本轮的建议因此是具体的：把 452 条自建判定改报 pass@k 与 pass^k 一对数字。

同等重要的正面记录，而且是 08-20 那批的干净反例。 08-20 记录的三篇（SemaPLC、ComponentBench、2608.18351）判定器或真值都由作者或 LLM 造，人工一致性统计全部为零。Thinkingbox 反过来：它的主判定是确定性的哈希断言，比对终态数据库与任务特定的黄金态，LLM 只用于给失败轨迹打归因标签。论文自己把这个取舍写明了：

"We accept this asymmetry to keep the primary metric deterministic; extending LLM-judged rubrics to every task would reintroduce judge variance into the verdict."（我们接受这种不对称，以保持主指标的确定性；把 LLM 评判的评分细则扩展到每个任务，会把评判者方差重新引入判定。）

这正是项目"判定链路不得引入 LLM 判定器"这条既定规则的第一份外部同向证据，此前记录的都是反面教训。

P1（并列）：ReCache 命中了项目的成本结构，但它的 TTFT 定义正是 08-20 记下的那个陷阱

论文事实。 2608.19662《ReCache: Efficient KV Cache Reuse and Compression for Tool-Augmented LLM Agents》，2026-08-20T05:57:24Z 投稿，v1，17 页。摘要给出：资源级注意力在 Inv-F1 上 82.3% 对 Dense 的 82.4%（差 0.1 个百分点）而 TTFT 加速 3.655×（26.319ms → 7.200ms）；完整框架把已分配 KV 张量显存降低 92.43%、注意力加速 1.423×。规模扩展上：Dense 的 TTFT 随资源上下文增长"从几十毫秒涨到 5,000 毫秒以上"，而其 Ω_full 维持在 50ms 以下，ReCache 近乎平坦、略高于 5ms；TPOT 方面 Dense 与 Ω_full 约 11ms 而 ReCache 略高于 6ms；注意力时延 Dense 与 Ω_full 约 5ms 而 ReCache 低于 0.2ms；显存 ReCache 封顶在 0.03 GiB 而 Dense 与 Ω_full 逼近 8 GiB。

为什么它值得记：项目已经有一条相关的账。 08-19 记录 2608.14036 的结论是技能"每任务多花 93.8K 输入 token"。ReCache 处理的正是这笔开销的结构——把工具/资源 schema 的编码与实际资源访问分开，schema 部分预先编码、跨请求复用。

但两条边界让它不能进入候选，第一条尤其重要：

  1. 它的 TTFT 明确定义在"缓存命中"之下。 原文："We use time-to-first-token (TTFT) to quantify online prefill latency under a cache hit, including request-local KV materialization but excluding offline cache construction."（在缓存命中下量化在线 prefill 时延，包含请求局部的 KV 物化，但排除离线缓存构建。）这与 08-20 从 Qwen3TTS-Streaming README 记下的 prefix-cache 命中 是同一个陷阱，而且这次是论文在指标定义里自己写明的。车机的第一句话永远是冷的，因此这组数字对项目最关心的那一次请求不成立。
  2. 代码仓库存在但没有许可证。 详见第 4 节。

P1（并列）：本轮的方法学收获——制品通道找到了论文通道结构上看不见的东西

1. MaAI（MaAI-Kyoto/MaAI）

  • 仓库：https://github.com/MaAI-Kyoto/MaAI（源码 MIT）
  • 模型：https://huggingface.co/maai-kyoto（34 个模型，许可证不统一，见下）
  • API 文档：https://maai-kyoto.github.io/MaAI/
  • 关联论文（本轮发现通道）：https://arxiv.org/abs/2608.19527
  • 上游依赖：VAP 原始实现 https://github.com/ErikEkstedt/VoiceActivityProjection；Mimi 编码器 https://huggingface.co/kyutai/mimi（CC BY 4.0）；CPC 预训练模型来自 https://github.com/facebookresearch/CPC_audio

它是什么

一个实时、连续、轻量的非语言行为预测软件包，定位是给口语对话系统与交互机器人做"什么时候该接话、该应答、该点头"的判断。它的方法基座是 Voice Activity Projection（VAP） 及其扩展。名称取自日语"間 / 間合い"，指人在交互中用各种模态调节的细微时机与间距。

必须先说清它不是什么：它完全不做 ASR、不做语义理解、不生成文本。 它只从声学流输出概率。这一点决定了它在项目里的位置——它是一个旁路信号源，不是一个对话模型，这正是项目 probe_turn_end 负面结果之后应当走的方向。

核心方法（或核心架构）

四类模型，逐条记录官方说明：

  • 判停（Turn-Taking）：直接使用原始 VAP，预测"下一刻哪一位参与者会说话"。分三个变体：基础 VAP、噪声鲁棒 VAP（官方标注为"Recommended"）、单通道 VAP。
  • 语音活动检测（VAD）：官方说明写明它与判停模型的区别是"不预测未来：它检测每位说话人此刻是否在说话"。关键机制是跨通道注意力联合处理两个通道，官方原话："even when one speaker's voice leaks into the other speaker's microphone (crosstalk), the model can still decide who is actually talking."（即便一位说话人的声音泄漏进另一位的麦克风即串音，模型仍能判断实际是谁在说话。）训练时加入了噪声与混响（RIR）增强，官方因此说明"噪声鲁棒配方就是默认配方……vad 本身就是多条件模型"，故没有单独的 vad_mc 模式。输出为每通道 [0.0, 1.0] 的概率；二值化默认阈值 0.5，官方另注 0.54 在训练所用开发集上取得最佳 F1。
  • 应答（Backchannel）：分两类。预测模型输入 2 通道 16kHz 音频（ch1 用户、ch2 系统），输出应答后验概率 p_bc；另有两类型版本。检测模型则判断"当前正在说的这句话本身是不是一个应答"。
  • 点头（Nodding）：三类点头的预测，另有带运动学参数的版本。

一条直接可借的工程设计：MaaiMultiple 让多个模型共享同一个音频编码器，官方说明为"当多个 Maai 模型需要跑在同一条音频流上时，MaaiMultiple 类在它们之间共享单个音频编码器，因此（相对昂贵的）编码器每音频帧只运行一次"。源码侧可佐证这个"相对昂贵"的说法：src/maai/encoder.py 为 71,539 字节，是全包最大的单个源文件之一。

对 StreamingModelHarness 的帮助

第一，它是追踪表上第一个可以不占 GPU 的判停制品。 项目的 GPU 已被 110ms/token 的 MoE 主模型占满，而 X2-Turn 那条路线要再加一个 4B 模型。MaAI 自述可纯 CPU 运行，且提供 5–50 Hz 的帧率档位让使用方自行权衡 CPU 占用。这使得"判停旁路"第一次成为一件不需要先解决显存与调度冲突就能试的事。

第二，中文应答预测权重是 MIT，可以直接用在商业车机上。 maai-kyoto/vap_bc_ch（created 2025-11-19T08:08:42Z，非门控、非私有，license:mit）含四个权重文件，覆盖 5 / 10 / 20 Hz 的 CPC 版本与 12.5 Hz 的 Mimi 版本，上下文均为 20,000 毫秒。这是本轮唯一一个"中文 + 判停/应答方向 + MIT + 非门控"的权重。

第三，双通道 VAD 给了"扬声器泄漏"这个长期空白一个可用的下游制品，但必须严格限定它解决的是哪一半。 项目的 AEC 空白已连续九轮，而 AEC 要解决的是"把自己播放的声音从麦克风信号里减掉"。MaAI 的 VAD 不做这件事。 它做的是在串音已经存在的前提下，判断此刻说话的是用户还是系统。沿用既定判别式：ANC = 副扬声器 + 误差麦克风；AEC = 自身播放信号的参考/回环抽头；而 MaAI VAD 属于第三类——串音条件下的归属判定。 这一条对项目仍然有用（打断判定需要知道"现在这段声音是不是用户在插话，还是我自己的播报漏回来了"），但任何把它写成"AEC 有进展了"的表述都是错的。

第四，MaaiMultiple 的共享编码器设计可以直接照搬到项目的多头旁路上。 项目若同时需要判停、应答时机与串音归属三个信号，天真做法是跑三个模型三次编码。官方给出的做法是编码器每帧只跑一次、多个轻量头共享。这与项目在 MoE dispatch 上"每层固定代价"的推理是同一类工程思路，且这里有可读源码。

第五，2608.19527 的倒 U 型给了一条可以立刻写进参数表的约束。 应答频次要设上限。论文的实测量级是每条用户话语 2.25 次应答、每段 5 分钟对话 27.29 次，但项目不能直接抄这个数——它是日语、实验室、平板、非驾驶场景。可抄的是形状：单调递增假设是错的，参数表里应当有上限而不是只有下限。

2. Thinkingbox（2608.19741）

  • 论文：https://arxiv.org/abs/2608.19741（v1，2026-08-20T07:37:57Z 投稿，45 页，cs.CL）
  • 代码：https://github.com/microsoft/thinkingbox（MIT）
  • 论文许可证（arXiv 元数据 /License）：creativecommons.org/licenses/by/4.0/
  • 作者：Zhuochun Li、Youngmin Ko、Ali Keramati（三人共同一作）、Nicola Ferri、Susana Palmaz Lopez Pelaez、Liang-Chun Tsai、Calvin Wang、Mirco Milletari、Tuhin Kundu、Vadim Smolyakov、Kjartan Olafsson、Tommy Guy。论文注明"共同一作；工作完成于微软实习期间"。

它是什么

一个有状态业务工作流下的 agent 沙箱与基准。它跑的是"模拟用户 ↔ LLM agent ↔ 隔离的 MCP 兼容工具"三方多轮交互，然后用终态、副作用与对话三类可执行检查来判定，而不是判定一个最终答案。五个业务域：零售（Retail）、预订（Booking）、保险（Insurance）、新型银行（Neobank）、咨询（Consulting）。

它的出发点用论文自己的话说是："Thinkingbox is motivated by a limitation of many function-call-oriented tool-use..."，而结论句更直白："tool-call-level signals are not clear proxies for end-to-end task completion."

核心方法（或核心架构）

（一）确定性判定，LLM 只用于归因。 主评估把最终数据库状态与黄金期望状态用确定性的、基于哈希的断言比对。原文："The agent succeeds only when it produces the exact required side effects without introducing incorrect additional effects."（agent 只有在产生了确切要求的副作用、且没有引入错误的额外副作用时才算成功。）解码失败、测试执行失败、API 错误与其它系统错误一律计为失败试次。LLM 评判者只用于给失败轨迹打归因标签，不进入判定。

（二）试次隔离是硬要求。 原文："Two attempts of the same task must not share database rows, cached tool state, or side effects, otherwise pass@k and training rewards become unreliable."（同一任务的两次尝试不得共享数据库行、缓存的工具状态或副作用，否则 pass@k 与训练奖励会变得不可靠。）

（三）两个指标必须成对报。 论文的定义：pass@k 是"k 次中至少一次成功"的概率，pass^k 是"k 次全部成功"的概率。原文的区分句："pass@k measures whether retries can *discover* a successful trajectory, whereas pass^k measures dependable repeated execution."（pass@k 度量重试能否发现一条成功轨迹，而 pass^k 度量可靠的重复执行。）另报 95% 的任务簇自助置信区间（重采样 507 个任务、保留每个被采样任务内的全部 20 个结果）。

（四）任务筛选规则值得单独抄。 剔除的类别包括：工具损坏、初始状态不一致、目标含糊、结果不可核验、检查依赖于工具调用轨迹、以及在 LLM agent 下反复无法终止的交互。原文要求"被接受的任务必须至少存在一条有效的完成策略，同时保有清晰的正确性判据"。"剔除依赖工具调用轨迹的检查"这一条与它的头条主张是自洽的：既然主张工具调用层面的信号不是完成度的代理，判定就不能建立在轨迹上。

（五）失败归因是确定性优先级，且论文自己给它降级。 论文用固定的优先级顺序给每条失败轨迹指派唯一的主导特征，并自述这些特征"是可观测的诊断，而不是唯一的因果解释"。

第一，它给项目的头条指标提出了一个必须回答的质疑。 项目当前对外的数字是单次运行的严格工具名召回 80.49%，这既是工具调用层面的信号，又是单次运行的聚合值——恰好同时踩中论文批评的两点。加上 08-20 从 ComponentBench 记下的"聚合完全相同却有 17.3% 逐条翻转"，两条独立证据同向。本轮的具体建议：把 452 条自建判定改报 pass@k 与 pass^k 一对数字，并在聚合值旁并列逐条翻转率。

第二，pass@k / pass^k 的取舍对座舱有一层特殊含义。 论文场景是业务工作流，重试是允许的，所以 pass@20 有意义。车控场景没有这个奢侈：用户说"打开空调"，系统没有第 20 次机会。 因此对项目而言，pass^k 才是那个对齐业务语义的指标，pass@k 只用于诊断"能力存在但不稳定"与"能力不存在"的区别。这一条项目应当在采纳时明确写下，否则容易照抄论文的呈现顺序而误导。

3. ReCache（2608.19662）

  • 论文：https://arxiv.org/abs/2608.19662（v1，2026-08-20T05:57:24Z 投稿，17 页）
  • 代码：https://github.com/EIT-NLP/ReCache（存在，但全仓库没有任何 LICENSE 文件）
  • 论文许可证（arXiv 元数据 /License）：arxiv.org/licenses/nonexclusive-distrib/1.0/
  • 作者：Yichu Fang、Sitong Wei、Haozhe Hu、Xiaoyu Shen（通信邮箱分别为 sjtu.edu.cn 与 eitech.edu.cn）

它是什么

一个面向工具增强型 LLM agent 的资源级 KV 复用与压缩框架。核心主张写在摘要里：把可复用的 schema 编码与选择性的资源访问分开，从而"大幅降低 agent 推理成本，且有效性损失有限"。

核心方法（或核心架构）

三层，逐层叠加：

  1. 资源级注意力（Ω_full）：让资源表示以共享前缀预先编码、跨请求复用，配合资源局部的位置重索引。这一层单独就拿到了 3.655× 的 TTFT 加速。
  2. 结构剪枝（Ω_{20,3}）：按层与头组的贡献做 Top-K 选择（论文的敏感性分析用了 Top-K 层 KL 与 Top-K 头组 KG 两个维度）。
  3. 语义剪枝（SMP）：进一步削减语义字段的 token。

对 StreamingModelHarness 的帮助

它命中的是项目一笔已经记过账的开销。 08-19 从 2608.14036 记录的是技能"每任务多花 93.8K 输入 token"，而 ReCache 处理的正是这笔 token 的结构——工具 schema 是跨请求高度重复的内容，理应只编码一次。若项目的座舱工具 schema 规模可观，这条思路在方向上成立。

但本轮的结论是"记录方向，不采纳数字"，理由见下。

局限与开放状态

第一，也是决定性的一条：它的 TTFT 定义在缓存命中之下，且明确排除离线构建成本。 原文："We use time-to-first-token (TTFT) to quantify online prefill latency under a cache hit, including request-local KV materialization but excluding offline cache construction." 这与 08-20 从 Qwen3TTS-Streaming README 里挖出的 prefix-cache 命中 条件是同一个陷阱，只是这次它出现在论文自己的指标定义里而不是藏在附注里。 车机上电后的第一句话必然是冷的，因此 26.319ms → 7.200ms 这个对比对项目最关心的那一次请求不成立。论文没有给出任何冷启动或缓存未命中的数字，也没有给出离线构建一次要多久。

第二，开放状态是一个此前未记录过的形态：代码可读但无许可证。 EIT-NLP/ReCache 确实存在（created 2026-08-19T03:12:43Z，pushed 2026-08-19T05:42:28Z，size 1,881 KB，1 star），论文摘要写 "The code is available at https://github.com/EIT-NLP/ReCache."。但 GitHub API 的 license 字段为 null，且全树递归列举确认没有任何 LICENSE / LICENSE.txt / COPYING 文件。 按 GitHub 默认条款，未附许可证的公开仓库保留全部权利。"公开可读"不等于"开源可用"，这一条应当加入开放状态判据：许可证缺失是一种独立状态，不能与"已发布可核"合并。

第三，仓库结构显示它包含相当规模的训练基础设施，与"纯推理期优化"的读法不符。 全树含 capsule/main/train.py、FSDP 与 DeepSpeed 的 stage2/stage3 配置、以及 capsule/data/config/slimpajama.json。论文侧也写明主模型是"训练"出来的（"We train the primary Qwen3-4B model on an NVIDIA A800 GPU"）。因此不能把它归入"叠加在现成模型上的推理期改动"这一类，它至少需要一次训练才能得到论文报告的效果。

第四，批大小从未在正文中给出。 本报告不据此触发"最小可评估批大小"这条否决规则——规则要求写出到底是"从未在 1 上评测"还是"收益随批变小而缩水"，而本篇是"批大小根本没有报告"，这是第三种情况，按未知记录。

综合判断：REJECT 为候选，TRACK 为方向。 决定性理由是缓存命中口径，次要理由是无许可证。可带走的一条是它的指标拆分方式：把 TTFT、TPOT 与"注意力时延"分开报，论文自己解释了为什么——注意力上的收益"会被 TPOT 里未变化的投影与前馈计算所掩盖"。这条拆分纪律对项目诊断 110ms/token 同样适用。

4. 术语与同名/同源辨析（本轮新增）

  • 12.5 Hz 在本轮第三次出现，但这一次不是矛盾。 08-19（VoiceChat-TTS）与 08-20（Qwen3-TTS 生态）记录的是同一模型的两种说法互相打架；MaAI 这里 12.5 Hz 明确对应 Mimi 编码器、5/10/20/50 Hz 明确对应 CPC 编码器，是两类不同模型。记录在案是为了防止日后把三处并列成"同一个生态问题"。

  • Interrupting the Loop（2608.19893）里的 "interrupting" 与语音打断无关，它讲的是在基座语言模型里周期性更换话题对"判定惊讶度与连接感"的影响，属 cs.CL 文本方向。"interrupt" 词根的第三个假阳性来源（前两个是并行机排程与统计学的 "Interrupted Time Series"）。

5. 今日建议路线

第一阶段（零 GPU，可立即做）

  1. 把 MaAI 的许可证拼盘做成一张项目内部表，并按"可商用 / 不可商用 / 未知"三分。 这一步必须在任何技术评估之前完成，否则可能在不可商用的 vap_ch 与 vad_ch 上投入工作。结论已经清楚：中文应答预测（vap_bc_ch，MIT）可用；中文判停只能用能力更少的 vap_ch_kyoto（MIT）；中文 VAD 与中文应答检测目前不可商用。
  2. 把"应答频次设上限"写进座舱交互参数表。 依据是 2608.19527 的倒 U 型（注意感对应答次数的二次项 p=.009）。抄形状不抄数值——论文的 2.25 次/话语来自日语实验室平板场景。
  3. 把 Thinkingbox 的 pass@k / pass^k 一对指标引入项目 452 条自建判定的报告口径，并在聚合值旁并列逐条翻转率（后者的依据是 08-20 的 ComponentBench）。先只改报告口径与最小子集试算，不急于跑满 20 遍。
  4. 在跑任何重复试次之前，先验证项目评测的试次隔离。 依据是 Thinkingbox 的硬要求：两次尝试不得共享数据库行、缓存的工具状态或副作用。隔离不成立时 pass^k 会被系统性高估，这一步不能跳。
  5. 判定器处理不变性检查（优先级仍为最高，来自 2608.12880）。本轮第一次有了完整可抄的量具：照搬 StateMemBench Table 8 的四格转移表——选一个与行为无关的拨杆、判定器固定不变、报四个转移计数而不是那个差值。这是本轮全部内容里工作量最小、收益最大的一项。
  6. 把 452 条判定改造成封闭选项池，并公布确定性份额。 构造时同时算出金标准、一个已知坏基线会给出的具体错误答案、以及 2–3 个中性干扰项，提问时不展示池；随后报告"纯字符串匹配能定下多少条、判定器在该子集上的一致率是多少"（对照值 28% 与 94.1%）。同时写几个可执行的座舱"坏读者"基线（永远取最新槽位、取提及最频繁的槽位、不重算派生值、过早丢弃约束），只保留至少一个坏基线与确定性重放不一致的条目——这一步同时完成选样与失效标注，并使注入故障召回率按构造成立。另加一类"反陷阱"样本，用来抓住奖励过度作废的判定器。
  7. 补两个泄漏扫描器：条目侧（断言每条承重事实出现在其指定会话中，且逐条禁用短语不泄漏到渲染面，失败则重渲染）与特征侧（审计高权重特征里是否出现来源或批次标记）。
  8. 只读审阅 envharness/harnesses/rules.py（8,274 字节，Apache-2.0），把四条动作门规则与 ABSTAIN_ERROR 第三状态写进动作门设计文档。 不运行该仓库任何代码。
  9. 给 452 条判定各打上"标注强度 × 证据类型"两条正交轴的标签，并写死"弱档证据永不用于设定阈值"，同时预先声明一个 llm 证据档，使 LLM 标注在表里可见而不被悄悄提升。

第二阶段（单卡或纯 CPU 可做）

  1. 用 vap_bc_ch（MIT）在项目 452 条基准音频上做离线应答时机预测，只做旁路观测。 记录三组数字：不同 frame_rate（5 / 10 / 20 Hz）下的 CPU 占用、每帧耗时、以及应答触发点相对项目已有标注的分布。不接入播报路径，不改生产链路。
  2. 离线复现 X2-Turn 的 EasyTurn-zh 判停指标（08-20 的既定项，本轮未动，权重与代码仍是开放非门控的 Apache-2.0）。做完第 10 项后，两条判停路线第一次可以在项目自己的音频上直接对比：一条要 4B + GPU，一条可纯 CPU。

7.1 FlashPrefill V2（2608.19758）—— REJECT，但它的基准硬件恰好就是项目的 H20

先说为什么值得单独写：这是追踪表上第一篇基准硬件明确写成 H20 的论文。 2608.19758v1，中科院自动化所 + 国科大 + 微信/腾讯，2026-08-20T08:02:55Z 投稿，20 页，cs.CL。原文："All methods are evaluated under identical hyperparameter settings on NVIDIA H20 GPUs"；算子级为单张 H20，端到端为 TP=4、四张 H20。

论文结果。 128K 上下文下相对 FlashAttention-2 为 27.19×（BF16）/ 47.26×（FP8）；相对 FA3/4 对齐的稠密算子为 17.5× / 30.5×（后者才是诚实的基线）。RULER 平均 87.79 对满注意力 88.82（Llama-3.1-8B）。密度随长度下降是全部收益的来源：4K→128K 为 76.0% → 4.6%。端到端 TTFT，Qwen3-30B-A3B（MoE）、批大小 1：4K 为 0.10 s（FA3/4）对 0.09 s（本文 BF16，1.02×）；128K 为 13.78 s 对 4.17 s（3.30×）。

否决理由，按决定性排序，且必须写准以免日后按错误理由重新评估：

  1. 它按构造只管 prefill。 论文原话："The two-stage pipeline runs in the extend (prefill) phase, while decode falls back to dense attention, since a single query token per step leaves no room for block-level sparsity."
  2. 项目的上下文整个落在它评测区间之下。 项目 KV 约 2,500 token，而论文最短的一列是 4K；在 4K 处 BF16 只有 1.01–1.09×，密度仍有 70–76%。
  3. 其官方仓库的出厂默认值直接把项目排除在外。 flashprefill_min_sparse_q_len 默认 4096，文档写明低于该值整批走 FA3。这是一手核实的仓库默认值，不是论文陈述。
  4. FP8 路径在 RTX 5090 上不存在。 README 要求 "NVIDIA Hopper GPU (H20 / H100, sm_90a)"；451 个 kernel 实例化文件中 sm90 有 310 个、sm80 有 140 个、sm100 仅 1 个（且只有 BF16）、sm120 为 0，全部 80 个 FP8/e4m3 实例化都是 sm90 专属。

明确不以批大小否决。 该论文真的评测了批 1（1/4/8/16），且收益在批 1 处基本不衰减（128K 上 MoE 从批 16 的 3.40× 到批 1 的 3.30×，仅缩水 3%）。按错误理由否决会导致日后重新 litigate。 但需记一条口径：其头条的 47.26×/27.19× 是批 4 的算子数字（Fig. 2 图注明写 "All results are measured with a batch size of 4"），只有端到端 TTFT 表下探到批 1。

开放状态：第二档，已发布可核，且许可证逐字读过。 github.com/qhfan/FlashPrefillv2，created 2026-08-19T09:56:38Z，3,595 个 blob 合计 52,782,993 字节，Apache-2.0。LICENSE 文件 11,357 字节，与 apache.org 标准文本逐字比对完全一致、版权行仍是占位符。注意 GitHub API 的 size: 7968 与 blob 字节和 52,782,993 是两个不同的量，本报告两个都写出来。

但它出现了一处新的不一致形态，且是本轮最严重的一处：论文与它自己的官方仓库在头条方法学声明上互相矛盾。 论文 §4.1 写："every model shares a single configuration without per-model tuning ... α = 0.1"。而仓库 flashprefill_ops/flashprefill/prefill.py 的注释写："Paper-calibrated values (block size 128): Llama-3.1-8B 0.18, Qwen2.5-7B 0.08, Qwen3-30B 0.12."，server_args.py 的帮助字符串重复了同样说法。这是逐模型调校的三个值、被仓库明确标为"论文校准"，而其中 Qwen2.5-7B 这个模型在论文里根本没出现过。 本报告不替作者选择，两边原样并存。同时仓库还暴露了一个论文全文从未提及的开关 --flashprefill-full-attention-layers（README 示例传 4，代码默认 0），因此论文 Table 4/5/6 用的是哪个取值无法从论文得知。

这也第三次印证了缓存口径这条筛查项。 全文 20 页对 radix、prefix cach、cache hit、warm、cold 的命中数全部为 0，而它的头条指标是在 SGLang（默认开启 radix/prefix 缓存）中对同一批提示重复 30 次测得的 TTFT。测量条件缺失本身就是发现，必须记。

值得带走的五条原语，全部与项目的 CUDA Graph 与无同步 MoE dispatch 直接相关：

  1. 靠"各自重算"消除分歧，而不是靠"互相通信"。 原文："Producer and consumer evaluate the same sequence {n(t)} independently, so their control flows are identical by construction and the pipeline advances in lockstep without any synchronization for block skipping."这正是项目在 MoE dispatch 上想要的形状。
  2. 用掩码跳过，不用分支跳过。 todo = valid & ¬selected，两侧 identically 跳过，固定形状、无主机分支，可被图捕获。
  3. 把不规则工作折叠成一次固定形状的额外迭代，"reusing the same MMA pipeline and online-softmax rescaling without any additional kernel launch"。
  4. 项目自身根因的第二条外部佐证，且这次来自一套跑得起来的代码。 原文："the index stage reuses a per-stream workspace cache whose capacity-matched reuse avoids any host synchronization or allocator round trip in steady state." 第一条是 08-20 记录的 FreeToken。
  5. 按工作量而不是按位置切分负载："the CSR list is partitioned by selected-block count rather than by position range"。

一条负面结果值得单独留：分块 prefill 会侵蚀稀疏收益。 实测 Qwen3-30B-A3B 上 P50 TTFT 加速从不分块的 2.2× 掉到 8K 分块的 1.2×，原因是"the index selection is re-run on every chunk and the mandatory tail blocks raise the effective density of short chunks"。推广：任何按块重建索引的机制都有一个由其强制块决定的收益下限。

7.3 AV 边缘调度（2608.19557）—— REJECT，但它把"模型调用不能进快路径"证成了不可能性论证

否决理由三条同时成立：仿真器结果（原文自述 "Results are from a simulator with deterministic channels and a single primary workload size"）、全文零硬件声明（gpu|cpu|nvidia|hardware 命中数为 0，而 GPU 在其代码里只是一个带 speed 标量的类）、多机前提（4–6 台异构服务器）。

但最锋利的否决理由来自它自己的消融：全部优势都归于一个 40 个待处理任务的批处理视野，而座舱在任一时刻只有一个人在说话。 其 Table III：TC-first + EFT 在 W=200 时 0.942、W=40 时 0.896、W=1 时 0.795——而 0.795 与朴素 EDF 完全相同。论文自己写："Ordering does nothing at W=1, since a window of one task cannot be reordered." 注意这里正确的表述是"收益随视野缩小而消失"，不是"未在批 1 上评测"——它评测了。

  1. "模型调用不能放在每任务路径上"被写成了不可能性论证，措辞可以直接引用。 原文："A model call takes seconds, whereas an admission decision must be taken in the time it takes a PU to free; placing a language model on the per-task path is therefore not a tuning choice but an impossibility."这是项目 PACE 式"慢推理通道绝不可门控快音频通道"设计的一条独立外部佐证。
  2. 必须有陈旧策略回退，且理由是推导出来的而不是断言的。 原文："Because control-plane latency is not bounded by the window duration, a deployment cannot assume a policy update will arrive before the window it was requested for. 第二条：一条反对"静态韵律预设"作为产品功能的负面证据。 固定的非自适应基频偏移没有产生可测的情绪收益，作者自己的诊断是"stable pitch manipulations ... may not reflect how pitch modulation is naturally used throughout a session... Moreover, pitch rarely operates in isolation"。日后若有人提议做"舒缓语音模式"预设，这是反对把它做成静态偏移的引用。

7.5 EEG 听觉注意解码 ASIC（2608.20198）—— REJECT，理由是 1 Hz

2608.20198v1，德累斯顿工大 + 埃尔朗根-纽伦堡大学，BioCAS 2026 已接收，2026-08-20T15:54:35Z 投稿，5 页，cs.AR。GF22FDX 22nm，已流片。

它不是关键词假阳性——它真的是脑电驱动的目标说话人选择。 但否决理由是决定性且单一的：注意力判定每秒只更新一次。 原文："only eight correlation coefficients are maintained in a circular buffer and updated once per second using a moving-average scheme."一个每秒刷新一次的控制信号无法参与打断仲裁，因为打断的全部预算比一个更新间隔还小。

必须防一个误读：7.34 ms 不是判定时延。 那是每次推理的算力耗时，被设计成塞进 125 Hz 脑电流的 8 ms 采样周期内。把它读成"7 毫秒完成脑电注意力解码"是错的。 另注该论文从未声明自己的判定窗长度（"decision window" 全文只出现一次，且在一条参考文献的标题里）；8 个系数的缓冲区若是 8 次连续的 1 秒更新则积分时间约 8 秒，若另有结构则更短，论文没有给出判别方式，此处记为待核。但最有利的读法也已经是 1 Hz，两种读法都不通过。

第二个独立的否决理由是传感前提：31 通道头皮电极、面向人工耳蜗使用者、且权重需按人在 listening sessions 之间经串行 SRAM 接口重载——即每位乘员都要戴电极并做个体标定。另注全文没有给出任何 AAD 准确率，所有相关表述都是定性或转引其合作论文。

但它带回两条价值很高的佐证：

  1. "身份/注意力判定必须是音频通路之外的控制信号"这条架构约束拿到了第二篇独立佐证，且来自完全不同的子领域。 原文："The decoded attention information can provide a control signal for a hearing-assistance system to select or enhance the attended speech stream."第一篇是 08-19 的 2608.17972。两篇互不相关的论文在不同子领域收敛到同一条约束，其价值高于任何单篇。
  2. "空间编码不是多乘员的正确路线"拿到第三条独立佐证，而且论据类型是新的。 原文："many of these approaches rely on spatial cues or predefined speaker configurations, which may limit their robustness in practical acoustic environments. In contrast, stimulus reconstruction-based AAD remains independent of speaker locations."前两条佐证讲的是渲染成本（DiffM2A 的 2.66 s/4 s、Meta/Aalto 自述"适合离线"），这一条讲的是线索本身的鲁棒性——一个做实硅的团队出于鲁棒性主动放弃了空间线索。

另有一条可迁移的工程技巧：把皮尔逊相关从需要缓存全部历史的中心化形式改写为原始矩形式，从而"enabling on-the-fly accumulation, eliminating the need to buffer complete signal histories"。项目任何想在流上计算的在线指标（预测与实际 token 速率的滑动相关、首音频时延的漂移监控、流式 CER 代理）都可以用同一替换把状态从增长缓冲降为 O(1)。

一处必须并存的不一致：同一个术语在 5 页论文里指两个不同的数。 摘要写 "a total silicon area of 2.09 mm² (1264µm x 1654µm)"，正文写 "The total silicon area is 76048µm²"（= 0.076 mm²）。两个数各自算术自洽（1264×1654 = 2,090,656 µm²），但约 2.01 mm² 的差额全文从未交代。两个都记，不合并。

  1. 报告评分者间一致性，并且在系数很低时去解释它而不是藏起来。 他们用 Krippendorff's α（理由是"it accommodates nominal categories and incomplete response matrices"），然后把准确率约 90% 下 α 近零解释为基率悖论而非分歧："when the marginals are highly skewed ... the expected (chance) agreement approaches the observed agreement, so α collapses even though raw percent agreement exceeds 90%. Krippendorff's α therefore measures consistency, not correctness, and must be read jointly with the accuracy metrics." 并把它与边缘分布均衡时的真歧义情形区分开（ElevenLabs α = 0.155："here low agreement does reflect genuine perceptual ambiguity"）。这条同时能防止项目在自己偏斜的评测集上把低 α 误读成评分者不可靠。
  2. 把准确率拆成敏感度与偏倚，因为聚合准确率把两者混在一起。 报 d′ 与判据 c：本文 d′ 为 2.75 / 2.88 / 0.73，而在真实音频上的虚警率是 17.5%——这正是原始准确率会掩盖掉的量。
  3. 用配对的、逐被试的非参数检验，并用按被试重采样的 cluster bootstrap 置信区间，因为每位听者贡献了许多相关的判断。项目 452 条评测集正好是这种聚簇结构。
  4. 在解释任何指标之前先算出它的随机水平。 他们算出 All-OK 的随机水平是 6.25%、Over-50-Percent 约 31%、逐句 50%，然后发现 33% 的得分"sits essentially at its chance level"——朴素读法会把它当成正面结果。 项目报告的每个指标旁边都应当写上它的随机水平。
  5. 用一族严格度递进的指标，并说明何时某一个失效。 其中 All-OK（全部片段都对）是最值得抄的一个：正是它暴露了整段 F1 掩盖掉的定位失败，包括检测器的 0.00。
  6. 在结果之前先声明自己的设计引入了哪些人为效应（本文声明了三条：合成条目的高先验比例、剔除"不确定"回答、以及可能的非随机流失）。

另有一条负面结果值得带走，而且它与项目最高优先级事项同源：六个源基准 EER 只有 0.57–5.34% 的成熟检测器，在没见过的现代商用合成上崩到 F1 0.09——比未受训练的人类（0.48）还差，且在部分伪造上的严格定位率是 0.00。推广的教训不是那些数字，而是：一个检测器在自家基准上的 EER 几乎不能预测它在未见生成器上的行为。 这与 2608.12880 的构造效度失效是同一个模式，却来自完全不同的子领域，并且适用于项目任何打算凭已发表基准分数就直接接入链路的预训练分类器——VAD、打断检测、说话人归属都在内。

8.2 StateMemBench（2608.19652）——协议 P0，但开放状态是四栏全部第三档

  • 论文：https://arxiv.org/abs/2608.19652（v1，2026-08-20T05:41:23Z 投稿，23 页，cs.AI）
  • 作者：Xinyi Fan\*、Miri Liu\*（共同一作）、Ruozhen Yang、Siru Ouyang、Jiawei Han，全部为伊利诺伊大学厄巴纳-香槟分校
  • 论文许可证（arXiv 元数据 /License）：arxiv.org/licenses/nonexclusive-distrib/1.0/

它的构造方式是本节最值得抄的部分。 每个场景是一段符号化事件程序（规则声明、取值更新、带作用域的例外、承诺、撤回），正确答案由确定性求解器重放该程序算出，而不是人工标注。然后是关键一步——可执行的"坏读者"基线：论文实现了一族 lazy reader 策略，每一个都对应记忆系统的一种可能失效（只信最近一次提及、只信出现最频繁的取值、直接返回已陈述值而不重算、过早丢弃已锚定的决定），而陷阱场景恰好取自"至少一个策略与完整重放不一致"的那些，那些不一致的策略随即构成该场景的失效模式签名。这等于让每一条评测样本自带一个已知的错误答案，即注入故障召回率按构造成立。

封闭选项池评分： 在生成时就构造好一组可信答案（含金标准、被针对策略算出的漂移答案、以及 3–4 个中性干扰项），但在提问时不展示。因此判定器唯一的工作是把自由文本映射到池上——一个严格更简单且可审计的任务，并且能把"跟踪错了"与"完全答错"分开。论文还写明"Gold and drift are computed before rendering, so the renderer cannot alter trap semantics."

它还有一个项目目前完全没有的东西——泄漏扫描器： "we programmatically verify that the load-bearing facts appear, and appear in the correct assigned session, as well as that no banned phrases appear in the final scenario. Any scenarios that fail are re-rendered until they pass."

它是本项目筛过的第一篇把 LLM 判定器的验证工作真正做完的论文，而它给出的结论对项目至关重要。 论文把确定性份额直接量化了："a deterministic word-boundary matcher decides the 28% of answers that name exactly one pool option verbatim and agrees with the judge on 94.1% of those; the judge maps the rest"。判定器间一致性（Table 7）则给出一条必须写死的规矩：

"Mode κ (which drift sub-mechanism) is near zero on every benchmark (0.00–0.09) while binary κ is fair-to-substantial: **judges agree on *whether* a failure is drift but not on *why* the wrong fact won. This is the empirical basis for … mechanism must be fixed by construction rather than inferred post hoc.**"

编辑判断：这条应当直接成为项目的硬规矩——判定器最多只能向 LLM 索取一个二元判定；失效类别必须由构造固定，LLM 事后归因的机制标签在统计上等于噪声（κ = 0.00–0.09）。 这同时给 08-20 记录的三篇（SemaPLC / ComponentBench / 2608.18351 的 LLM 归因）提供了一个量化的否定依据：它们的归因标签之所以不可信，不是因为没做人工核对，而是因为这类标签本身就没有可复现的信号。

它的人工锚定同样值得抄，因为设计上防住了范畴被表格强加。 Track A（结构化，n=12）让标注者回答固定子问题、由回答推导出类别，"so the taxonomy cannot be imposed by the form"；Track B（盲测，n=6）让标注者在看到分类体系之前先用自由文本描述失效。结果：二元漂移判定 83.3% 原始一致、κ=0.43；完整类别标签只有 50.0% 原始一致；盲测的表层观察标签 κ=0.80，且 12 条盲测描述全部落进已有类别、无需新增。而最该记住的一个数字是人机对比：两名标注者与判定器的二元一致率只有 58.3% 与 41.7%，且两人给出的漂移都比判定器少（8.3% 与 25.0% 对 50.0%）——因此论文自称其漂移率是"judge-labeled upper bounds"。

开放状态是本轮最遗憾的一条：论文写"We release StateMemBench"、并写"The annotation kit (forms, keys, and the analyzer) is released with the benchmark"，而 23 页全文没有给出任何 URL。 超链接注解只有一条 arXiv 自链接；全部五条裸 URL 均为第三方引用（microsoft/STATE-Bench 是被引用的他人基准、OpenAI 与微软的博客、Qwen 博客、Instacart 数据源）。代码、数据均为第三档 unverifiable，许可证未知。 编辑判断：那套标注工具包（表单、答案键、分析器）是本批次里对项目最直接可用的制品，而它现在拿不到——列入追踪，是追踪表上价值最高的第三档条目。

两处摘要级不一致，按原样记录。 其一，摘要的"1.6×"只有在把 GraphRAG（0.224）归类为"graph-RAG 系统"而非"记忆系统"时才成立，而正文自己的检验说两者持平："McNemar over the 322 shared probes: 38 vs 35 discordant, p=0.82"。其二，摘要没有提一个消融比头条方法更好：DeepSeek 上"w/o dep.-propagation"为 0.373，高于完整 StateMem 的 0.363；正文如实披露了，但表注把消融排除在加粗竞争之外。另注全文未声明任何硬件、无墙钟、无 token 计数，且主表每个配置只跑一次，因此 Table 8 是全文唯一的翻转率测量。

8.3 EnvHarness（2608.19880，Google Cloud AI Research）——协议 P1，且带回项目一直缺的那个动作门形状

  • 代码：https://github.com/google-research/envharness（Apache-2.0，LICENSE 11,357 字节，逐字为未修改 Apache 文本；242 条目，9 stars）
  • 项目页：https://www.envharness.com

它对项目的价值集中在一个源码文件上，而不是论文。 envharness/harnesses/rules.py（8,274 字节，Apache-2.0，已一手读过）提供三个纯函数式的逐步钩子：filter_action(action, env_state)、modify_transition(action, response, env_state)、filter_observation(obs, env_state)。这是本项目找到的第一个"播报前确定性动作门"的真实形状，而且它是一个运行时而不是一个 LLM 审阅者——正是 08-20 从 SemaPLC 得出的"唯一可能塞进时延预算的形状"。 四条可直接搬：

  1. 拒绝必须返回实时状态加理由，绝不能是一个光秃秃的拒绝。 拦截返回一个带类型的 Blocked(reason=...)，且拦截路径保持环境不变、重新观测、把当前状态连同理由一起交回。源码注释解释了为什么："A bare [blocked] Observation would strip env-critical obs.data … and strand or crash format-specific policies on their next act()." 座舱对应物：动作门拒绝一次工具调用时，必须把当前车态与拒绝理由一起返回，否则模型的下一轮无法恢复。
  2. 层次信任分离由结构强制，而不是靠约定。 Rules 在结构上碰不到初始状态（那是独立的 Setup 层）也碰不到奖励/判定（那是验证器）。论文侧的表述是："Because all interventions remain external, the ground-truth evaluation logic is preserved, ensuring the original verifier still can score the episode." 编辑判断：把这条作为项目 452 条判定的硬不变量——动作门可以拒绝或改写一个动作，但永远不得触碰评分器。
  3. 生成出来的门代码在隔离子进程里运行，"so a bad mutation becomes a recorded trace instead of a dead run"。
  4. 跨进程边界传递的必须是数据，不能是句柄（get_env_state()）。若项目为保住时延预算而把动作门放到进程外，这条直接适用。

论文本体的结果与项目无关（ALFWorld / WebArena / SWE-bench / SpreadsheetBench），但它的 Table 12 是 8.0 节列的第四条佐证。 另需记一条方法学正面记录：它的 LLM 只做提议者、不做评分者——设计智能体诊断弱点并写出真正的 Python 组件，而原基准的验证器原封不动地裁决。这与 Thinkingbox 的"判定确定性、归因才允许用模型"是同一条纪律的第二个正面先例。

开放状态：第二档，但有一处经文件级核实的缺口。 论文 Table 4 报告了 ALFWorld 与 WebShop 两个 RL 结果，而 242 条路径中 webshop 出现 0 次，README 也从未提及 WebShop。即 Table 4 的整个 WebShop 列（Score 79.2 对 75.6、SR 67.4 对 66.0）没有任何已发布的桥接或实验。 这是"仓库存在 ≠ 论文声称的制品存在"这条规则的又一次生效。另有两处不一致按原样记录： OfficeQA 的 F1 增量论文写 +1.96 而 README 写 +1.97（57.73 − 55.77 = 1.96，README 是错的那个）；摘要说"为强化学习提供了更优的优化信号"，而 Table 4 四项里有一项退化（ALFWorld OOD 88.8 对 89.6）且该表全表没有任何标准差——正文诚实地写了这条退化，属摘要层面的省略。

另记一条对项目开放问题的否定回答：它没有回答"缩小可达工具集能否提升准确率"。 EnvHarness 是在训练期限制动作集，然后在标准的、不受限的实例上评测；因此它证明的是"训练期限制能改善不受限的评测"，而不是"推理期限制"。 08-19 从 2608.14036 推出的那条假设在第三次尝试后仍然开放。

8.4 MaliciousSkillBench（2608.19901）——协议 P1，且是本轮第二篇完全干净的论文

  • 论文：https://arxiv.org/abs/2608.19901（v1，2026-08-20T11:13:00Z 投稿，49 页，cs.CR）
  • 代码：https://github.com/protectskills/MaliciousSkillBench（Apache-2.0，LICENSE 11,358 字节）
  • 数据：https://huggingface.co/datasets/ProtectSkills/MaliciousSkillBench（CC-BY-4.0，非门控非私有，primary.parquet 28,600,360 字节；模型卡 arxiv: 标签为 arxiv:2608.19901，指向正确）

它的 skill 用的正是 08-19 记录 2608.14036 时的那个义项——可安装的指令包。 规模：13 个公开来源、8,414 条原始恶意记录 → 7,562 条精确去重 → 7,539 条归一化去重 → 4,588 个结构族；最终 9,740 条 = 7,505 恶意 + 2,235 良性，四套评测协议在同一份冻结条目集上跑。

四条可直接搬的纪律，其中两条直接作用于动作门：

  1. 证据分档门控——目前可见的最便宜的判定器升级。 该基准把"标注强度"与"证据类型"做成两条正交的轴，并明确"evidence type must not be interpreted as an ordinal confidence score"；然后设一条硬门：仅有扫描器证据的记录永不进入主要真值，据此把 182,699 条注册表记录中的 169,676 条仅凭证据类型就排除在外。它甚至预先声明了自己没有用到的档位（human、llm、unknown）。编辑判断：项目应当给 452 条判定各打上这两条轴的标签，并写死"弱档证据永不用于设定阈值"；同时预先声明一个 llm 档，使得凡是 LLM 标注的东西在表里是可见的，而不是被悄悄提升。
  2. ABSTAIN_ERROR 作为第三种状态——这一条应当立刻写进播报前动作门。 原文："Technical failures remain a third state, ABSTAIN ERROR, and are never silently converted to benign predictions. Primary binary metrics therefore use successful scans while reporting coverage separately."座舱对应物：动作门自身出错时绝不可退化成放行；且门的覆盖率必须与门的准确率分开报告。 这是一行不变量，但安全后果是实质性的。
  3. 一个作用在模型特征侧的泄漏扫描器，与 StateMemBench 那个作用在条目侧的互补：审计导出的高权重线性特征里是否出现来源 ID、基准 ID 或数据集名标记，记录到零命中，且来源标识按构造被排除在检测器输入之外。同时它对自己的结论作了正确的限定："This reduces the likelihood of a trivial metadata leak but does not establish source invariance."
  4. 它明确拒绝给单条误报/漏报打语义"错误成因"标签，原文："Automated keyword summaries are used only as inspection aids and have no human-verified causal-annotation status … We therefore report frozen counts and source concentration without … promoting those keywords to ground truth."这与 StateMemBench 的 mode-κ 结论指向同一处，且是一条可以在日后引用的先例——作者对自己的工作守住了这条线。

它是本项目筛过的论文里少有的把"少数类指标必须给召回"当成论文主张本身的一篇：每一个工作点都同时给出召回与良性误报率——95.6% / 62.4%、2.5% / 1.1%、0.0% / 0.55%、25.3% / 49.9%。并且它给出了一条对项目动作门选型直接有用的结论：在跨来源的分布漂移下，一个学出来的文本门只能用 62.4% 的良性误报率去买 95.6% 的召回，作者的总结是"no detector occupies the desired high-recall, low-FPR regime on held-out sources"。编辑判断：这是"播报前动作门必须是确定性的 schema/车态校验，而不是学出来的分类器"这一选择的最强外部论据。

另有一条存在性证明值得记：确定性方法的重复运行翻转率可以真正等于零。 种子 42/43/44、划分冻结，"standard deviation 0 in the frozen result table"——因为 TF-IDF 加线性模型本身就是确定性的。即"重复运行不稳定"不是评测的固有属性，而是方法选择的后果。

它是本轮第二篇完全干净的论文，且它主动交代了七处上游不一致而不是抹平。 摘要的 0.932/0.916/0.665 与 Table 2、README 三处逐位一致；95.6%/62.4% 与 340/545 = 62.39%、802/839 = 95.59% 精确对得上；9,740 = 7,505 + 2,235 成立。附录 A.4 逐条列出上游来源的自相矛盾（例如 SRC005 的 README 报 350 行而固定修订版只有 347 行，"The three missing malicious records are not reconstructed"），并给出一条规矩："'Paper-reported size' 与 'artifact-level samples available for a frozen evaluation snapshot' 是两个不同的量"。它对硬件的处理同样是本项目见过最好的："The frozen run package does not record an exact host Python version, operating-system build, CPU model, RAM size, or GPU model, so we do not invent those fields here."

但许可证有一处被聚合标签掩盖的实质风险，必须点名。 仓库层面是 Apache-2.0（代码）+ CC-BY-4.0（数据），但 THIRD_PARTY_NOTICE.md 写明："Third-party Skill artifacts included or referenced by this project are not relicensed under Apache-2.0 or CC BY 4.0. Those artifacts retain their respective upstream terms." 而其 Table 6 列出的上游许可证里有三个对商业车机是问题：SRC001 为 academic-research-only、SRC006 为 terms not provided、SRC010 为 CC-BY-NC-SA-4.0。编辑判断：聚合的 CC-BY-4.0 只清理了基准自身的元数据层，对这三个来源什么都没清理。 另有一处经文件级核实的缺口：附录 G.6 声称冻结包保留五类制品，而 GitHub 56 条目与 HF 18 文件里对 joblib|seed|estimator|minilm|embedding 的命中数全部为零——五类里有四类（逐种子指标表、seed-42 序列化估计器、MiniLM 嵌入矩阵、嵌入方法学清单）两处都不存在。

一处该论文没有说明的来源独立性问题，值得单独记： 其局限一节写 SRC002/SRC004 使用"author-provided historical artifact snapshots"，而 SRC002 就是 ProtectSkills 这个组织自己的 HF 数据集，与本论文的发布方是同一个组织。即 8,414 条原始恶意记录里有 236 条依赖于非公开快照，且其中一部分的上游就是发布方自己，而"author-provided"这个措辞没有披露这层关系。

8.5 术语：harness 现在有五个义项，且有一篇论文同时使用其中两个

在既有三义（训练脚手架 2608.03571 / 执行脚手架 Evo-Bench 2608.09096 / 普通动词 2608.19013）之外，本轮新增两个：（四）环境脚手架——EnvHarness 自定义为 "a programmable layer that wraps an existing, static environment"，并与执行脚手架并列成 "Agent = Model + Harness" 对 "Customized Env = Static Env + EnvHarness"；（五）可执行测试运行器制品——MaliciousSkillBench 只在这个窄义上使用。EnvHarness 一篇之内同时使用义项（二）与（四），且专设一张对照表说明，属有意为之而非混用。 StateMemBench 全文从不使用这个词。

风险提醒

  1. 不要说"MaAI 是 MIT 的"。 代码是 MIT，权重是四个许可证家族的拼盘，其中中文判停主力 vap_ch、中文 VAD vad_ch、中文应答检测 bc_det_ch 全部是 CC-BY-NC-ND-4.0，既非商业又禁止衍生；两个模型（vap_bc_2type_jp、bc_det_en）完全没有许可证标签，按未知处理。可商用的中文权重目前只有 vap_bc_ch（应答预测）与能力更少的 vap_ch_kyoto（判停）。
  2. 不要把 MaAI 的双通道 VAD 记成 AEC 的进展。 它不消除自身播放的回声，它在串音已存在时判断谁在说话。AEC 的计数是连续第九轮为零。
  3. 本轮没有从一手来源核实到 MaAI 的任何精度数字。 论文 2608.19527 只有主观量表，仓库 README 把精度全部指向四篇未核实的外部论文。在自测之前，项目文档里不得出现 MaAI 的任何准确率。
  4. 2608.19527 的基础管线是按键说话，不是全双工。 它证明的是"半双工主通道 + 并联的连续倾听旁路"有感知收益，不提供任何关于打断、抢话或重叠语音的证据。
  5. 不要用 2608.19527 论证应答能提升效率。 它自己的行为数据（话语条数、话语长度、对话时长）全部无显著差异，p 值分别为 .516 / .195 / .300。
  6. 应答不是越多越好，这已经是显著性检验结果而不是直觉。 注意感对应答次数的二次项 p=.009 且呈倒 U 型。但该分析是探索性的、N=35、单一语言场景，可信的是方向不是数值。
  7. 不要把 ReCache 的 7.200ms 当成项目可获得的 prefill。 它明确定义在缓存命中下且排除离线缓存构建成本，而车机上电后的第一句话必然是冷的。这是 08-20 记录的 prefix-cache 陷阱的第二个独立实例。
  8. ReCache 的仓库存在但没有任何许可证文件，按 GitHub 默认条款保留全部权利。"公开可读"不等于"开源可用"。
  9. Thinkingbox 承诺发布两件制品，只交付了一件。 507 个任务与黄金终态不在仓库里，仓库里只有沙箱框架与一个 cloud_drive 演示场景。且其 README 中 arxiv / 507 / pass@ / 五个业务域名称的出现次数全部为 0——这是 08-20 记录的"发布产品不发布实验"形态的第二个独立实例。
  10. 对座舱而言 pass^k 才是对齐业务语义的指标。 用户说"打开空调"没有第 20 次机会。照抄论文以 pass@k 为主的呈现顺序会误导。
  11. 在验证试次隔离之前不要报 pass^k。 两次运行若共享任何状态，pass^k 会被系统性高估。
  12. 不要按错误理由否决 FlashPrefill V2。 它确实评测了批 1 且收益在批 1 处几乎不衰减，因此"最小可评估批大小"这条规则在它身上不触发。正确的否决理由是：按构造只管 prefill（解码回退到稠密注意力）、项目上下文低于其评测区间下限、其仓库默认 flashprefill_min_sparse_q_len = 4096 让它对项目直接失效、以及其 FP8 kernel 只有 sm90 实例化、RTX 5090（sm120）为 0。
  13. 不要引用 FlashPrefill V2 的 47.26×/27.19× 作为批 1 数字。 那是批 4 的算子数字，只有端到端 TTFT 表下探到批 1；而在项目所处的 4K 以下区间，它自己的表给出的是 1.01–1.09×。
  14. 缓存命中口径本轮出现第三例，且第三例是"完全没提"。 ReCache 写在指标定义里、Qwen3TTS-Streaming 写在 README 条件里、FlashPrefill V2 则是 20 页全文对 radix/prefix cach/warm/cold 零命中，而其头条 TTFT 是在默认开启前缀缓存的 SGLang 中对同一批提示重复 30 次测得的。测量条件的缺失本身就是发现。
  15. 任何音色或韵律 A/B 必须先做响度归一化。 2608.19826 的作者是在第一轮问卷跑完并得到零结果之后，才发现变调操作意外改变了响度。不归一化的对比是被混淆的，其零结果不可解释。
  16. 不要把 EEG 听觉注意解码的 7.34 ms 当成判定时延。 那是每次推理的算力耗时；该系统的注意力判定每秒只更新一次，最不利读法下积分时间约 8 秒。
  17. 不要把 2608.19959 当成 TTS 自然度的纵向趋势数据。 它的标题写"Tracking the Trend"，而正文三处明确否认可以据此得出趋势（每个发布期只有一个系统，且唯一的商用系统与"最新"完全混淆）。这是"标题断言正文自我否认"这一新形态的第一例。
  18. 不要凭已发表基准分数直接接入任何预训练分类器。 六个源基准 EER 仅 0.57–5.34% 的语音深伪检测器，在未见过的现代商用合成上崩到 F1 0.09，比未受训练的人类（0.48）还差，部分伪造的严格定位率为 0.00。这条同样适用于 VAD、打断检测与说话人归属。
  19. 判定器最多只能向 LLM 索取一个二元判定。 StateMemBench 的判定器间一致性显示：二元漂移判定的 κ 可以达到 fair-to-substantial，而"是哪一种失效机制"的 mode-κ 在每个基准上都是 0.00–0.09。因此 LLM 事后归因的机制标签在统计上等于噪声，失效类别必须由构造固定。 这条同时为 08-20 记录的三篇（SemaPLC / ComponentBench / 2608.18351）的 LLM 归因提供了量化的否定依据。
  20. 不要把判定器的漂移率当成真实值，它是上界。 该论文的人工锚定显示两名标注者与判定器的二元一致率只有 58.3% 与 41.7%，且两人给出的漂移都比判定器少（8.3% 与 25.0% 对 50.0%）。项目自己的 LLM 辅助判定同理，一律按上界记。
  21. 动作门自身出错时绝不可退化成放行。 MaliciousSkillBench 的 ABSTAIN_ERROR 第三状态："Technical failures … are never silently converted to benign predictions"，且门的覆盖率必须与门的准确率分开报告。这是一行不变量，但安全后果是实质性的。
  22. 播报前动作门不能是学出来的分类器。 在跨来源分布漂移下，一个学出来的文本门只能用 62.4% 的良性误报率去买 95.6% 的召回，作者结论是"no detector occupies the desired high-recall, low-FPR regime on held-out sources"。动作门必须是确定性的 schema 与车态校验。
  23. MaliciousSkillBench 的聚合 CC-BY-4.0 不能当成整份数据可商用。 其 THIRD_PARTY_NOTICE.md 写明第三方 Skill 制品不被重新许可、保留各自上游条款，而 Table 6 里 SRC001 为 academic-research-only、SRC006 为 terms not provided、SRC010 为 CC-BY-NC-SA-4.0。这是本轮第二个"聚合许可证掩盖了成分许可证"的例子，第一个是 MaAI 的逐模型拼盘。
  24. StateMemBench 声称发布了基准与标注工具包，而全文 23 页没有任何 URL。 那套标注工具包（表单、答案键、分析器）是本批次对项目最直接可用的制品，现在拿不到，属第三档 unverifiable。
  25. EnvHarness 的 Table 4 里整个 WebShop 列没有对应的已发布实验。 242 条仓库路径中 webshop 出现 0 次，README 也从不提及。仓库存在不等于论文声称的制品存在。
