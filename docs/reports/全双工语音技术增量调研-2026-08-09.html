与前一日报告相比，什么发生了变化

8 月 6 日报告的主线是 VAmoS/MIST/Audio2Tool 的车态验收、NAC Streaming Endpointer、Stream RAG、QIANGDA、M* 和 Lychee-FD。今天没有出现能替换这些结论的 新 AEC/降噪、在线语义判停、空间听觉、多乘员因果前端、原生全双工模型或 TTS 首包 结果；持续跟踪项保持不变。

真正新增的是三组互补能力：

  1. HarnessOpt-Bench 与 OneDayAgent 把 harness 改动、隐藏测试、预算、最终产物

    2. 验证和定点修复变成可审计协议。

  2. RestoreKV 与 OmniScope 分别处理“激进 KV 驱逐后的质量恢复”和“已知查询后的

    3. 音视频 prefill 压缩”；两者都不修复当前约 110ms/token 的 HF MoE 同步瓶颈。

  3. OPPO 与 LS-MOPD 分别提供多模态证据依赖和多语 ASR 专家蒸馏证据，但都是训练

    4. 级路线，不是可直接接入的实时控制模块。

Sparse Event-KV 已在 8 月 5 日报告纳入，本次不重复建立条目。RestoreKV 与它不是 改名或修订关系：前者学习恢复被驱逐缓存的行为，后者研究已服务事件 KV 是否隐式携带 被删除源事件的信息。

StreamingModelHarness 当前事实与新增实验

本次 main 没有提供新的 StreamingModelHarness 状态快照，因此沿用前一日报告中 已经实测的项目事实，不把论文结果写成项目收益：

  • A/B 在同一 100 条语音上的完成率均为 100%，严格工具召回/执行成功率为

    • 80.49%/79.27%，整体任务成功率为 84.0%/约 83.0%；样本置信区间高度重叠。

  • B 的首文本 P50/P90 为 131/141ms、首动作为 700/850ms；A 分别为

    • 758/1,006ms、1,094/1,440ms。A/B 首音频 P50 为 2,918/3,491ms，主要瓶颈仍是 Edge TTS。

  • B 版持久 KV 累积曾损失约 22 个百分点；光场屏/副驾屏上下文引力仍未根治。
  • 单 token 解码约 110ms；项目剖析指向 48 层约 816 次 GPU→CPU 同步/token。

    • DynamicCache.update() 在 KV=2500 时约 0.2ms，不是同量级瓶颈。

一、结论与优先级

P0：先收紧变更与最终状态契约

  1. 先实现 HarnessOpt-Bench 风格的隐藏集、预算和候选版本协议。 当前项目已经有

    2. 多次阴性优化和回滚；新的价值不是让模型自动改代码，而是让任何 harness 改动都不能 看到最终测试分，并把重复运行噪声、调用量和最终车态纳入发布条件。

  2. 先移植 OneDayAgent 的 verification-only，而不是完整长任务框架。 论文自己的

    3. 消融中 verification-only 与 decomposition-only 得分相同，但增加的平均时间少得多； 对当前严格工具成功率约 80% 的链路，先验证最终车态和口播一致性比增加更多工具调用 更稳妥。

P1：有条件地做缓存与多模态压缩

  1. RestoreKV 是 B 路径约 22 点损失的直接研究候选。 但它必须在完整 KV 仍存在时

    2. 运行，并为具体 backbone 和驱逐器训练 adapter；先做离线、同预算、同长会话回放。

  2. OmniScope 只适合 endpoint 后 prefill。 它依赖已知 query，而 Harness 的工具

    3. schema 又是晚注入；若在 query 成熟前剪 token，可能恰好删掉工具消歧所需的音频或 乘员证据。

P2：训练级持续跟踪

  1. LS-MOPD 证明共享、冻结声学前缀的多教师蒸馏可以改善其多语 streaming ASR，

    2. 但基座、教师和学生均未公开，训练依赖内部大规模数据；当前只借鉴语言分桶和路由 评测。

  2. OPPO 只作为低优先证据忠实度旁线。公开模型是离线情绪推理 Thinker，没有

    3. 流式、延迟、轮次、打断或工具事务证据；当前最多复用反事实遮蔽协议。

  3. 今日没有直接命中 AEC、TTS 首 PCM、空间听觉或 HF MoE 同步的新候选。继续执行

    4. NAC/QIANGDA、CosyVoice 和无同步 index_select+bmm fast path 的既定实验。

1. HarnessOpt-Bench：把 Harness 优化变成隐藏集上的受控实验

来源：论文正文 / arXiv:2608.06301v1； Hugging Face 论文页； Scale 官方 VeRO / Harness Engineering Bench 仓库。

论文事实：问题与方法

HarnessOpt-Bench 评估一个“优化器模型+编码 harness”能否修改目标 agent 的提示词、 工具、控制流、记忆和编排代码，并在不可见测试集上真正提高目标 agent，而不是记住 可见评分。

  • 开发集公开逐案例结果和轨迹；验证集只公开聚合分；测试集在最终候选提交前不可见。
  • 目标模型、环境和 verifier 固定；候选只能修改目标 harness。
  • 每次候选评测在隔离、非特权 sandbox 中运行；网关统一限制模型、资源和目标评测

    • 预算，每个候选保存为不可变版本。

  • 最终用 normalized gain 衡量候选填补了 seed 到满分之间多少 headroom；每个测试案例

    • 重复三次。

论文事实：明确结果

  • 论文共评估 5 个优化器模型、4 个下游任务和 111 个 scored runs。
  • 在固定任务与编码 harness 时，更换优化器模型使 gain 平均变化 0.142；固定模型而

    • 更换编码 harness 平均变化 0.079，前者约为后者 1.8 倍。

  • 开发中探索八类 harness lever 的覆盖率与 held-out gain 的 Spearman 相关在四任务上

    • 为 +0.34 到 +0.88；这是相关性，不证明扩大修改范围必然增益。

  • 详细 trace 只在 111 个 cell 中被 7 个 cell 共请求 16 次；读取评测输出的动作占比与

    • gain 负相关，但论文明确不据此断言 trace 诊断无用。

  • 正文 §3.1 写“每个 partition 最多 100 次 evaluation calls”，§5.3 又写 200 次；

    • 两处不一致。四次完整 case pass 的预算口径一致，因此本报告不擅自选择 100 或 200。

  • 主实验每个配置只有两轮，论文给出的范围不是置信区间；小于各任务 resolution band

    • 的差异被视为未分辨。

开放状态

  • Scale 官方 scaleapi/vero 仓库已公开四项 harness-engineering benchmark 的 seed、

    • development/validation/test manifest、构建与评测文件，仓库为 MIT。

  • 论文所用外部数据集、模型与服务仍服从各自许可；MIT 不能覆盖这些依赖。
  • 论文没有训练或发布专属模型权重。

编辑判断：对 StreamingModelHarness 的帮助

把现有 A/B/C 回归升级为三层发布门：

开发集：逐条音频、phase、候选、typed call、车态和失败轨迹
验证集：仅聚合工具/参数/最终车态/延迟与预算
隐藏测试集：发布时一次评估，候选全程不可见

同时固定目标模型、工具 schema、CarSim 初态、TTS 和硬件，把每个 harness 候选保存为 commit；调用次数、音频秒数、目标 token、P50/P95 和未授权动作均计入预算。先由人工 提出候选，不启用自动递归修改。

局限

  • 四任务是文档问答、检索、终端和通用 agent，不含语音流、打断、车控或物理状态。
  • seed 有意留出明显 headroom，其中 GAIA 甚至是不可用 stub；不能外推到成熟 harness。
  • 可信边界降低了泄漏风险但并非 hackproof；固定 verifier 仍可被长期适配。

2. OneDayAgent：优先借鉴最终产物验证，而非增加规划层

来源：论文正文 / arXiv:2608.05013v1； 官方仓库； 官方轨迹数据页。

论文事实：问题与方法

OneDayAgent 面向跨网页、文件、计算和图像的长任务，联合处理目标漂移、状态丢失和 上下文溢出：

  • 原始请求始终作为 global intent，planner 最多拆成六个顺序子任务。
  • 子任务在统一 ReAct 工具空间执行，以摘要、证据和文件句柄提交状态。
  • 128K 上下文达到 90% 时生成技术摘要并保留原任务与最近三轮，接近硬上限时再做

    • 确定性裁剪。

  • synthesis 后，verifier 对照原请求、子任务答案和附件检查最终产物；失败时最多三次

    • 定点 repair。

论文事实：明确结果

  • AgentIF-OneDay 含 104 个任务、767 个 rubric 点。GLM-5.2 后端 overall 为 0.821；

    • 五个后端使用相同 harness 均完成 104/104，overall 范围为 0.613–0.821。

  • DIRECT、仅 decomposition、仅 verification 和 FULL 分别为

    • 0.771/0.804/0.804/0.821；平均耗时为 27.6/38.1/29.7/53.6 分钟。

  • 95/104 项首次验证通过；9 项进入 repair，其中 6 项修复成功、3 项仍失败。
  • 35/104 项触发上下文压缩；最高压力任务累计约 350K token。压缩次数与分数近零相关，

    • 但这不是隔离的因果实验。

  • 官方基线与本文结果使用不同版本的 Gemini judge；作者在同一 run 上测得新 judge

    • 低 3.12 个百分点，跨表比较仍有混杂。

开放状态

  • 官方 GitHub 仓库有 MIT LICENSE，但截至本次核验仍只有 README 和图片，harness

    • 源码与 prompts 未发布；不能把仓库存在写成实现已开源。

  • 官方 HF 数据页公开约 8.24GB 的九组轨迹、产物和 judge 分数，但数据卡没有

    • license metadata；轨迹和产物许可记为未知。

  • 无专属模型权重。

编辑判断：对 StreamingModelHarness 的帮助

只先接 verification-only：执行器完成后读取原始请求、授权结果、参数、最终 CarSim 状态和准备播报文本；若不一致，最多一次有界修复，并重新查询最终车态。验证器不得发 车控，只能拒绝、请求澄清或生成新的待授权候选。

局限

  • 论文没有 ASR、endpoint、音频 KV、TTS、重叠说话或实时交互结果。
  • execution memory 在所有消融中始终开启，无法单独归因。
  • 论文明确当前实现没有 workspace isolation；网页提示注入还可能经压缩记忆进入

    • verification/repair。

3. RestoreKV：在固定 KV 预算内学习恢复被驱逐信息

来源：论文正文 / arXiv:2608.01247v1； 作者项目页； 官方 KVPress 实现； 官方 adapter 模型页。

论文事实：问题与方法

查询无关 KV 驱逐需要在未来问题未知时压缩一次上下文。RestoreKV 不只选择保留哪些 原始 KV，而是在完整 prefill 后让 8 个 restore token 通过 rank-8、alpha=16 的 LoRA 前向读取完整缓存，生成上下文相关恢复 KV。基础驱逐器再填满剩余槽位，总预算 保持不变。LoRA 仅在这一次恢复 pass 开启，后续 query 和 decode 使用冻结原模型。

恢复模块以 full-cache 模型为教师做对称 KL 自蒸馏；每个模型和驱逐器都需要匹配训练。

论文事实：明确结果

  • Qwen3-4B、5% KV 预算下，KVzip 的 RULER-4K 为 38.2，RestoreKV 为 73.2；

    • QASPER 18.0→28.7、QuALITY 46.3→52.4、LongHealth 61.0→67.5。

  • 五种驱逐方法、四任务、三预算的 60 个配对设置中改善 59 个；唯一退步是

    • SnapKV/QuALITY、10% 预算的 53.0→51.8。

  • 5% 预算消融中，仅学习 restore embedding 为 42.1，固定 embedding 加 LoRA 为

    • 71.9，只适配 q/k/v 为 72.4，完整配置为 73.2。

  • Llama-3.1-8B、32K 上下文在 RTX PRO 6000 上的恢复 pass 增加 0.03–0.04 秒、

    • 峰值显存增加 84MB；论文将其报告为总压缩时间和峰值显存的约 0.5%/0.4%。

开放状态

  • RestoreKV 推理支持已进入 Apache-2.0 的 NVIDIA KVPress。
  • 官方 HF 页公开 Llama-3.1-8B 与 Qwen3-8B 的 KVzip/KVzip+ adapter，模型卡明确为

    • CC BY-NC 4.0，只限研究/非商业使用。

  • 论文训练代码、精确训练样本和 Qwen3-0.6B/4B adapter 未核验到公开版本。

编辑判断：对 StreamingModelHarness 的帮助

它适合作为 B 路径持久 KV 损失的离线恢复对照，但必须训练 Qwen3-Omni 专用 adapter， 并与实际驱逐器匹配。验证顺序应为“无压缩 full cache→当前压缩→同预算 RestoreKV”， 同时检查工具名、参数、最终车态、no-op 和长会话。

局限

  • 必须在完整 KV 尚未丢弃时运行，不能恢复已经在线删除的历史。
  • 只验证文本 decoder，没有 Qwen3-Omni 音频、晚注入工具或车控实验。
  • 它恢复 full-cache 行为；如果 full cache 本身造成上下文引力，恢复缓存也可能保留

    • 这种偏差。

  • 保持相同 query-time KV 成本不等于降低 MoE 每 token 同步，不能解释当前

    • 110ms/token。

4. OmniScope：音频与视觉分别估计显著性的查询后压缩

来源：论文正文 / arXiv:2607.23193v3； Hugging Face 论文页； 官方代码仓库。

论文事实：问题与方法

OmniScope 观察到同一查询下音频和视觉的关键时刻经常错位，因此以 query 为共享语义 锚点，但分别估计两种模态显著性和预算。视觉执行 Anchor–Delta 空时剪枝，音频按秒 聚合相关性并在秒内做 bipartite soft matching。方法免训练，作用在送入 OmniLLM 前的 输入 token。

论文事实：明确结果

  • DailyOmni 的 1,197 个 query-video 对中，78.3% 的音频/视觉显著性 Spearman

    • 相关满足 |rho|<0.3。

  • Qwen2.5-Omni-7B 在 25% token 保留时，四项 benchmark 平均分为

    • 51.35→51.00；OmniZip 为 49.80。

  • 同一 7B/25% 设置下，峰值显存 28.31→24.00GB，prefill

    • 6,299.90→1,784.45ms（3.53×），端到端 10.965→4.792 秒。

  • 45% 保留时平均分 51.35→51.65；这只是该离线 benchmark 结果，不代表压缩普遍提高

    • 质量。

开放状态

  • 官方仓库公开推理和评测代码，Apache-2.0；方法无专属权重。
  • 仓库只含 WorldSense 格式 JSON，不含完整 benchmark 媒体；外部 Qwen、CLIP 和数据

    • 许可需分别遵守。

编辑判断：对 StreamingModelHarness 的帮助

只有在 endpoint/commit 后完整 query 已知时才进入首轮实验；迟到工具 schema 应作为 新查询条件触发重新选择，不能直接复用旧显著性。当前项目没有连续视频主链，先只测 音频压缩并保存未压缩控制组。

局限

  • 只验证 Qwen2.5-Omni 3B/7B 和四个离线 QA benchmark。
  • query 必须预先存在；没有持续更新、barge-in、工具注入或多轮持久 KV。
  • 外部 CLIP 有固定成本；论文的离线 prefill 加速不等于生成阶段 token 加速。

5. OPPO：低优先复用模态遮蔽，不作为全双工核心进展

来源：论文正文 / arXiv:2606.25325v2； 官方代码仓库； 官方模型页。

论文事实：问题与方法

OPPO 面向多模态情绪推理：模型可能遗漏音频/视觉线索，也可能在对应模态被遮蔽后仍 编造该模态证据。方法先把参考推理拆成视觉、音频和情绪线索，以嵌入匹配给生成子句 计算覆盖奖励；训练时随机遮蔽 70% 视频或音频，只在对应证据 token 上约束完整输入与 遮蔽输入的分布差异，并在 SFT 后执行 GRPO。

论文事实：明确结果

  • MER-UniBench 九数据集平均分为 81.05，论文复现的 AffectGPT-R1 为 75.60。
  • MEP-Bench 上 Baseline→OPPO 的线索 Recall 为 58.00→70.44，视觉遮蔽

    • Acc@V 为 59.20→76.40，音频遮蔽 Acc@A 为 33.00→50.60。

  • 只加感知奖励平均为 79.45；加入定向 Omni-Perception Loss 后为 81.05。

开放状态

  • 论文正文为 CC BY 4.0。
  • 官方仓库公开 SFT、GRPO、奖励、推理和评测代码，顶层为 Apache-2.0。
  • 官方 HF 页提供 Qwen2.5-Omni Thinker 权重，但模型卡没有 license 字段，权重许可

    • 记为未知。

  • 完整音视频训练数据和 MEP-Bench 许可未闭合；MER-Caption+ 另有非商业/审批约束。

编辑判断：对 StreamingModelHarness 的帮助

不直接训练 OPPO，先复用其反事实思想：分别遮蔽音频、视觉、用户身份和工具回执， 检查回答中的每项主张及每个车控候选是否仍然出现。若证据缺失，预期行为是澄清、拒绝 或降低置信度，而不是保持同样的动作。

局限

  • 任务是情绪识别，不是工具调用或车控；MEP-Bench 只有 300 个样本。
  • 训练和评分依赖多个外部模型，只验证 Qwen2.5-Omni 单一主干。
  • 没有流式输入、首 token、打断、TTS 或实时资源结果；公开权重也不是完整语音双工

    • 模型。

6. LS-MOPD：多语 ASR 的按语言专家蒸馏

来源：论文正文 / arXiv:2608.03610v1。

论文事实：问题与方法

LS-MOPD 针对普通话、中文方言和英语联合训练时的优化冲突。未公开的 2.3B NIM4-ASR 由 0.6B FireRed Conformer、4× 下采样 adaptor 和 Qwen3-1.7B decoder 组成。三名 语言专家和一名 generalist 分别用 DAPO 训练；学生在自己的 on-policy 转写轨迹上按 输入语言选择验证集排名靠前的教师，并最小化多教师 token 分布的加权 reverse-KL。 论文的 streaming 设置使用 640ms chunk，并保留前四个 chunk 作左上下文。

论文事实：明确结果

  • 共享冻结声学前缀的三教师方案，offline 平均错误率为 4.45%；基座、generalist RL

    • 和 best-teacher oracle 为 4.70%/4.65%/4.59%。

  • 对应 streaming 平均为 5.18%；基座、generalist RL 和 oracle 为

    • 5.74%/5.43%/5.37%。

  • streaming 随教师数增加由 5.25%→5.21%→5.18%；允许教师分别更新声学前缀的动态

    • 方案不单调，最终 streaming 为 5.30%。

  • 这些平均数混合 CER 与 WER，不能与项目当前 micro CER 直接横比。

开放状态

LS-MOPD/NIM4-ASR 代码、2.3B 基座、教师、学生、训练清单和路由划分均未核验到官方 发布；论文专属制品许可证未知。

编辑判断：对 StreamingModelHarness 的帮助

短期只建立普通话、粤语/方言、英语和 code-switch 分桶，并比较 A/B 两路径的 ASR、 工具、参数和最终车态。只有出现稳定、语言特异的梯度冲突证据后，才讨论专家训练。

局限

  • 只验证一个未公开基座；复现依赖约 56 万小时内部预训练和多个 RL 教师。
  • streaming 指 640ms chunked encoder ASR，不代表同步听说、语义判停或 TTS。
  • 方法不直接改善工具事务、打断、多乘员身份或车态安全。
