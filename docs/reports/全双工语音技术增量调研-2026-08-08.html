    2. 重复 resume 会重复副作用的确定性证据。它直接补前一日 VAmoS/MIST 的执行轨迹， 应优先转成 StreamingModelHarness 的 crash/retry/并发恢复回归。

  2. OneDayAgent 的 verification-only 路径比整套长任务分解更适合当前车控：论文中

1. Resume Contract：把恢复语义变成可机测的 Action 契约

来源：论文正文 / arXiv:2608.03836v2。

论文事实

论文针对 checkpoint、interrupt 和 resume 后“哪些已发生副作用可以再次执行”的歧义， 提出六个属性：

  • Prefix Continuation（PC）：恢复只能继续耐久前缀之后的工作。
  • Effect Exactly-Once（EO）：同一分支内已提交副作用不能重复。
  • Fork Determinism（FD）：从旧 checkpoint 建立的新分支必须使用该分支自己提供的值。
  • Checkpoint Validity（CV）：无效状态不能静默持久化。
  • Consume-Once（CO）：同一等待中的审批只能被消费一次。
  • Recovery Determinism（RD）：相同耐久日志必须产生相同恢复决定。

作者用 TLA+ 检查参考语义；扩大边界后遍历 740 万个 distinct states，六个安全属性和 活性要求仍通过。确定性、无 LLM 的探针覆盖 LangGraph 1.2.9、LlamaIndex Workflows 2.22.2、CrewAI 1.15.2、pydantic-graph 1.107.1 和 AutoGen AgentChat 0.7.5。

主要实测包括：

  • LangGraph interrupt 路径保持 exactly-once，但 crash 恢复会重跑已持久化任务；

    • SIGKILL 后外部副作用账本由 1 变为 2。

  • 对同一个 interrupt checkpoint 先后提交不同 resume 值，LangGraph 会再次服务第一

    • 个值；第二个值虽被持久化却没有用于分支决定。

  • CrewAI CheckpointConfig 声称不重跑已完成工作，但实测恢复会重复执行已完成方法；

    • 框架内最终状态仍可能看起来正确，只有外部副作用账本显示重复。

  • 两个进程同时消费同一 LangGraph interrupt 时，SQLite 和 PostgreSQL 两种 saver

    • 均在 10/10 次重复中执行两次 gated effect。扩到 40 个并发配置时，36/40 个配置的 所有 racer 都成功消费。

论文给出 Remit 参考 sequencer、追加式 effect ledger、分支键和读路径修复设计，但正文 同时说明论文 artifact 与源码在发表前仍为私有、仅供审稿；因此本报告把可公开核验的 代码和许可证记为未知，不依据第三方包索引改写。

编辑判断：对 StreamingModelHarness 的帮助

在现有 VAmoS/MIST 证据账本外增加执行器外部、追加式 action ledger：

request_id / branch_id / action_id / idempotency_key
→ approval value → typed call → effect accepted
→ final CarSim state → spoken acknowledgement

回归不能只测试正常 interrupt；必须覆盖异常退出、同值重复、冲突值、跨进程并发和 旧 checkpoint fork。副作用的“恰好一次”由执行器外部账本和最终车态联合判断，不能由 Harness 自己的 state 字段判断。

局限

  • 论文测的是特定版本与特定路径，不证明所有 saver、版本和嵌套图都有相同行为。
  • TLA+ 证明参考模型，不证明被测框架；Remit 也没有端到端 refinement proof。
  • 它不处理语音判停、AEC、TTS 或模型工具选择正确率，只约束已决定 Action 的恢复语义。

建议优先级：P0。

2. OneDayAgent：优先借 artifact-level verification，不搬整套长任务 Harness

来源：论文正文 / arXiv:2608.05013v1； Hugging Face 论文页。

论文事实

OneDayAgent 把开放任务拆成有界子任务，在统一 ReAct action space 中使用 Web、文件、 计算和多模态工具；它将原请求保持为全局意图，把工具输出压缩成证据，在上下文达到 阈值时总结旧轨迹，并在最终交付前做全局验证和定点修复。

AgentIF-OneDay 含 104 个任务、767 个 instance-level 评分点。论文主结果使用 GLM-5.2：

  • 完整 OneDayAgent 总分 0.821，104/104 完成，平均延迟 3,216.8 秒。
  • DIRECT（无分解、无验证）为 0.771、27.6 分钟。
  • 只加 DECOMP 为 0.804、38.1 分钟；只加 VERIFY 为 0.804、29.7 分钟。
  • 完整方案为 0.821、53.6 分钟。VERIFY 相对 DIRECT 只多 2.1 分钟，却取得与

    • DECOMP 相近的分数。

  • 95/104 个任务首次验证通过，9 个进入修复，其中 6 个修复成功。
  • 同一 Harness 在五个后端上均完成 104/104，但总分为 0.613–0.821，延迟和工具调用

    • 风格差异明显。

论文称会开放 Harness 和轨迹，但当前允许来源中只核验到通用作者组织链接，没有定位到 本工作的精确公开仓库、版本或许可证，因此代码与许可证记为未知。

编辑判断：对 StreamingModelHarness 的帮助

当前语音车控不是小时级开放任务，最合适的是 verification-only：

  1. 保留原始用户话语与授权边界。
  2. 执行 typed call。
  3. 读取真实 CarSim 最终状态。
  4. 检查参数、终态和口播是否一致。
  5. 只对可补偿、幂等的失败执行定点修复；不可逆动作直接失败并告警。

这比把每条车控拆成多代理子任务更接近当前低延迟需求，也能与前一日 VAmoS/MIST 的 最终状态契约合并。

局限

  • 论文任务平均耗时以分钟计，不能支持座舱首动作或首音频门槛。
  • 主结果由 LLM judge 评分；论文更换 judge 后同一运行平均低 3.12 个百分点，说明

    • 跨基线比较仍受 judge 漂移影响。

  • 所有 ablation 都保留 execution memory，没有隔离其因果贡献。
  • 当前实现没有 workspace isolation，正文明确提示安全风险。

建议优先级：P0（仅 verification-only）；完整 Harness 为 P2。

3. RestoreKV：修复激进压缩质量，不修当前 MoE 同步

来源：论文正文 / arXiv:2608.01247v1； 作者官方项目页。

论文事实

RestoreKV 面向 query-agnostic KV eviction：上下文只压缩一次，后续不同查询复用同一 缓存。它不只选择保留哪些原 KV，而是在删除前让默认 8 个 restore token 通过一次 LoRA 适配前向读取完整缓存，生成小型 context-conditioned restore cache，再与保留的 原 KV 合并，总 KV 预算不变。LoRA 只在恢复缓存生成时启用，之后查询和解码仍用冻结 骨干。

训练通过完整缓存教师做 self-distillation，只更新 restore embedding 和 LoRA：

  • Qwen3-4B 可训练参数为 0.4%，训练集含 6,200 个 context-query 对、2,500 个独立

    • context；单张 RTX PRO 6000 约两小时。

  • 在四个骨干、四个长上下文 benchmark、五种 eviction 方法上测试。
  • Qwen3-4B、5% KV 预算时，KVzip 的 RULER-4K 由 38.2 提至 73.2；59/60 个匹配

    • 预算配置得到改善。

  • KVzip+ 在 KVPress Benchmark 的 16× 压缩下达到 86.4 RULER accuracy。
  • 32K 上下文中，8-token 恢复前向增加约 0.03–0.04 秒、低于总压缩时间 0.5%，峰值

    • 显存增加 84MB；后续 attention latency 和 KV 预算与基线匹配。

作者项目页公开了方法和结果，但本轮没有从允许来源核验到精确代码仓库与许可证，因此 代码和许可证记为未知。

编辑判断：对 StreamingModelHarness 的帮助

它只与“B 版持久 KV 累积损失约 22 个百分点”相关。建议先在纯文本 Qwen3 路径上复现：

  • full cache；
  • 当前 B 版持久/压缩 cache；
  • 相同总 KV 预算的 RestoreKV；
  • 每组报告 52 组近义工具、聚合意图、光场屏/副驾屏干扰和长会话。

如果质量可追回，再评估 Qwen3-Omni adapter。恢复前向仍需先看到完整 cache，因此还要 记录峰值显存和 prefill，不得只报告压缩后显存。

局限

  • 实验是 0.6B–8B decoder-only Qwen/Llama，不是 Qwen3-Omni MoE，也不含音视频流。
  • 任务是文档问答、摘要和合成长上下文，不是车控或全双工对话。
  • 需要按骨干训练 adapter；论文没有证明跨架构即插即用。
  • 它不减少当前约 816 次 GPU→CPU 同步/token，不能替代无同步 fast path 实验。

建议优先级：P1。

4. StreamArena/StreamMind：小时级因果流评测，不是低延迟全双工后端

来源：论文正文 / arXiv:2608.05703v1。

论文事实

StreamArena 含 243 个 60–134.2 分钟视频，平均 88.8 分钟；3,646 个经三阶段人工校验 的开放问答覆盖：

  • 实时音视频感知 263 项；
  • 历史回忆 877 项；
  • 外部工具 1,732 项；
  • 主动监控/提醒 774 项。

每个查询和证据都有时间戳，查询只能访问当时及之前的流。StreamMind 将延迟敏感的 Front/Monitor workers 与异步 Memory Writer、Router、Recall、Search workers 分离， 以事件、实体关系和关键帧构建持久多模态记忆。

论文报告：

  • StreamMind 在四类能力上的 accuracy 为 44.5/34.9/56.1/11.6；相对各自最强流式

    • 基线提高 58.4%/53.7%/228.1%/54.7%，但不同基线和骨干规模并不完全受控。

  • 与同一 Qwen3.5-397B-A17B 的 query-triggered 离线推理比较，三类响应的加权平均

    • 延迟由 81.4 秒降至 27.5 秒，保留 89.7% pooled accuracy。

  • 诊断子集上，实时感知的 ASR-only/visual-only/visual+ASR accuracy 为

    • 4.2/26.8/32.4。

  • StreamMind 的历史回忆从 L2 到 L4 仍下降 63.4%，长时记忆远未解决。

论文称 annotation 以 CC BY 4.0 发布，评测 Harness、baseline adapter 和 StreamMind 代码以 Apache-2.0 发布；原 YouTube 视频不再分发，只给视频 ID。当前正文转换未暴露 首屏精确仓库 URL，本轮也没有从作者官方入口独立核验资产，因此将“论文声明已发布” 和“当前可下载地址已核验”严格分开。

编辑判断：对 StreamingModelHarness 的帮助

借评测协议，不借 27.5 秒服务延迟：

  • 建立 30/60 分钟真实或合成座舱回放，视频、用户音频、系统播放参考、车态和 Action

    • 都使用统一时钟。

  • 同时测即时感知、过去事件回忆、主动提醒和只读检索。
  • 查询时冻结可见前缀，禁止未来帧泄漏；保存触发时刻和支持证据时间段。
  • 实时前端只做 endpoint、授权和紧急提醒；长时摘要/检索异步运行，不能阻塞首动作。

局限

  • 所谓“实时”最终回答仍以十几至几十秒计，远超当前 700–1,440ms 首动作区间。
  • 视频来自公开视频，不含真实车内 AEC、阵列、多人授权和有副作用车控。
  • 主要评分由单一 Gemini judge 完成，并非全人工最终判定。
  • StreamMind 使用 397B-A17B 骨干；对较小流式基线的相对提升不能全归因于架构。

建议优先级：P1（评测），服务架构为 P2。

5. C-SuiteBench：更多视觉证据会让受约束 Action 更差

来源：论文正文 / arXiv:2608.05864v1。

论文事实

C-SuiteBench 在 50 个场景上构造完全配对的 text-only 与 multimodal 条件，覆盖诊断、 证据排序、资源分配、风险预测和说明五类任务；九个模型形成 2,250 组配对比较。视觉 材料由同一底层数据渲染，包含财务、增长和运营三个通道。

主表给出的九模型平均变化为：

  • 诊断 +0.07；
  • 证据排序 +0.10；
  • 受约束资源分配 −0.08，九个模型全部下降；
  • 风险预测 +0.24；
  • 说明 +0.17。

正文叙述另把后两项写为 +0.27/+0.21，与主表不一致；本报告采用主表并明确保留此 冲突。资源分配中，visual-grounding proxy 平均约 +0.42，但 constraint validity 和 strategic fit 同时下降。单通道消融中，每个通道都优于全通道；九模型最佳单通道相对 text-only 为 +0.052，而三通道合并为 −0.08。结构化数字而非图表也重现约 60% 的下降， 说明问题更接近并发证据负载，而不只是视觉格式。

论文称场景、rubric、prompt、输出和 scorer 将发布到匿名 GitHub 地址；当前没有可核验 的官方仓库，因此代码、数据许可证均为未知。

编辑判断：对 StreamingModelHarness 的帮助

这与项目已有的光场屏/副驾屏上下文引力相符，但不是对该项目现象的直接证明。可以借其 配对设计：

车控请求
→ 仅文本
→ +当前车态
→ +主屏视觉
→ +副驾屏视觉
→ +全部通道

每一对都检查工具名、参数、硬约束、授权和最终车态。视觉描述更充分不能抵消约束失败。 若全通道下降，应先做 query-dependent evidence gate，而不是继续加 prompt。

局限

  • 场景是合成商业决策，不是座舱；没有音频、流式输入或真实 Action 执行。
  • 主结果 temperature=1、每 cell 单次推理；自动 scorer 虽有规则约束，仍不能替代

    • 车态执行器。

  • 论文存在主表与文字结果不一致，开放资产也尚未核验。

建议优先级：P1（配对评测协议）。

6. HarnessOpt-Bench：用隐藏测试和预算约束自动改 Harness

来源：论文正文 / arXiv:2608.06301v1； Hugging Face 论文页。

论文事实

HarnessOpt-Bench 把 prompt、工具定义、控制流、上下文、记忆和编排代码都视为可编辑 Harness。优化器可以读开发/验证反馈并提交多个候选，但模型、环境、verifier 和隐藏 测试集固定；所有候选在隔离 sandbox 中运行并版本化审计。

论文在 OfficeQA、BrowseComp-Plus、Terminal-Bench 和 GAIA 上测试五个优化器模型， 共享/原生 coding harness 共 111 个 scored runs：

  • 固定任务和 Harness 时，更换优化器模型带来的平均 gain 变化为 0.142；固定任务和

    • 模型时，更换 coding harness 为 0.079，约相差 1.8×。

  • 20 个共享/原生配对中，共享 Harness 胜 11、原生胜 9，没有一致的原生优势。
  • 八类可修改杠杆包括 prompt、context、step cap、retry/timeout、tool schema、

    • answer extraction、retrieval 和 reasoning effort；探索广度与 gain 的 Spearman 相关为 +0.34 到 +0.88，但论文明确说这不是因果证据。

  • 详细 trace 只在 111 个 cell 中请求 16 次；可见验证最好分数通常高于隐藏测试，

    • 支持保留不可见测试集。

预算口径在正文内部存在不一致：协议段写每个 partition 最多 100 个 evaluation calls， 结果段写 200 个 invocations；两处都写开发/验证各最多四次完整 case pass。本报告不 自行猜测正确值。

论文称发布 benchmark，但本轮没有在允许来源中核验到精确公开仓库和许可证，均记未知。

编辑判断：对 StreamingModelHarness 的帮助

先把现有 400 条文本、1,566 条语音、52 组近义工具和多人/回声/改口桶划成：

  • 开发集：允许读取逐条轨迹；
  • 验证集：只返回分桶指标和有限失败；
  • 隐藏测试：最终候选只跑一次，禁止优化器读取；
  • 固定安全不变量：未授权执行为 0、完成率 100%、最终车态不低于当前基线。

优化器只能改 Harness，不能改 CarSim 初态、grader、音频或成功定义。所有候选保存 diff、token/调用预算、均值与重复测量差异。只有隐藏集增益超过噪声带且安全桶不退化， 才允许人工审阅。

局限

  • 四个任务都不是实时语音或多模态车控，candidate 只允许 Python。
  • 每个任务只有一个固定 target model，跨模型泛化没有验证。
  • seed Harness 有意较弱，不能把可用 headroom 外推到成熟 StreamingModelHarness。
  • trusted sandbox 仍非绝对防作弊，固定 evaluator 可能被优化器过拟合。

建议优先级：P2，前置条件是 P0 verifier 和安全不变量稳定。

7. SmartMage：按查询选择模态，再分配专家

来源：论文正文 / arXiv:2608.05137v1； 作者官方项目页。

论文事实

SmartMage 处理 RGB、depth、BEV、point cloud 和 voxel。SMART router 联合：

  • 从问题文本估计模态先验；
  • 计算 text-modality 对齐；
  • 用激活强度、稀疏度和稳定性估计模态质量；

在固定保留 RGB 的同时选择辅助模态。随后 MAGE 把模态先验加入 sparse MoE gate， 引导 token 分配到不同专家。

论文报告五个 3D benchmark 的 SOTA；相对 Ross3D，ScanRefer Acc@0.5 提高 5.1， Multi3DRefer F1@0.5 提高 6.4。作者项目页列出 ScanQA 32.6、SQA3D 66.8、 Scan2Cap 88.7、ScanRefer 59.5 和 Multi3DRefer 60.7。项目页没有提供代码、权重、 数据下载或许可证链接，因此开放状态均为未知。

编辑判断：对 StreamingModelHarness 的帮助

短期只借“先选择证据，再生成 Action”的原则：根据当前请求、模态质量和授权座位， 决定是否让主屏、副驾屏、车态、声纹或空间音频进入模型上下文。长期如果训练专用模型， 再比较固定全模态与 query-dependent gate。

局限

  • 它使用完整 3D 场景表示，没有因果流、端点、打断或实时延迟结果。
  • RGB 始终保留，不适合直接表达隐私关闭或摄像头失效。
  • MAGE 增加 sparse MoE 路由；当前项目已经受 HF MoE 同步影响，不能直接移植热路径。
  • 结果针对室内 3D QA/grounding，不证明车控约束更可靠。

建议优先级：P2。
