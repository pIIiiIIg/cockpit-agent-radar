一、先说结论

P0：直接命中当前工程短板

  1. StaticCache 该不该上，此前是按“拷贝开销”算的账；今天出现了一个完全不同的理由——它是 CUDA Graph 捕获的前置条件。 项目快照的原判断没有错：KV=2500 时 DynamicCache.update() 的 torch.cat 只有约 0.2ms，按“省掉这 0.2ms”来算，StaticCache 确实不值得。但 FlashDrive 的论文事实是：它把 static KV cache、算子融合、以及对整个解码循环做 torch.compile 与 CUDA Graph 捕获打成一个“系统层优化”捆绑，在不改任何算法的前提下，10B 模型的解码段从 271.7ms、56.4 tok/s 降到 170.6ms、89.5 tok/s，整机从 716.9ms 降到 513.3ms。编辑判断：这条证据的价值不在那 1.59×，而在于它把 StaticCache 从“省一次拷贝”重新定位成“让解码循环形状固定、从而可以被图捕获”的结构前提。而 CUDA Graph 捕获恰恰要求区间内没有依赖数据的主机同步——项目诊断出的 .nonzero() + GPU 标量比较 + torch.where 正是会破坏捕获的那类操作。所以正确的顺序是：先落项目自有的无同步 index_select+bmm fast path（这是快照里已有的既定计划），再把图捕获作为第二个独立变量测。这两步必须分两次测，因为它们的收益来源不同，合在一起测就再也分不清是谁贡献的。
  2. ASR 段第一次有了“无损加速”的一手依据，同时它自带一条对项目已有负结果的解释。 arXiv:2608.12703 的论文事实：在贪心验证规则下，投机解码返回与目标模型贪心解码相同的序列；给目标模型挂一个轻量 draft 头并让它每步都能交叉注意到冻结的音频编码，Qwen 1.7B 达到 1.41–1.55× 端到端加速、Voxtral-Mini 3B 达到 1.42–1.69×，WER 接近自回归。更重要的是它的反例：换一个完整的同族 0.6B 识别器来 draft，restart 与 continuation 接受率几乎完美，端到端却只有自回归速度的 0.59–0.70×——“有用的提案必须省下足够多的目标模型工作来抵掉自己的成本”。编辑判断：这与项目 2026-08-03 把投机预取改回默认关闭的负面结果是同一个成本条件在不同层面的两次显现，但两者不是同一件事，必须分清：项目否决的是“提前预取工具候选”这一应用层动作，本文讲的是“逐 token 无损投机解码”，验证规则保证输出不变。本轮不把它变成候选——它没有公开代码或权重，且需要训练 draft 头。
  3. 判定器本身需要先被审计一次，这件事的优先级高于再去修任何 +1/+4。 arXiv:2608.12880 是作者对自己前一轮 MCP agent 安全评测的自审，论文事实非常硬：判分器把 treatment 元数据直接接进了 ATTACK_SUCCESS 的分支条件，于是固定住已执行的行为证据、只改元数据，类别就会翻转；按只依赖行为证据的判定重建后，180 条模型绑定请求里 ATTACK_SUCCESS 从 70 条历史标签变成恰好 0 条，其中 58 条重建为“授权内的正常完成”。作者写下的那句“可复现没有阻止这个错误，它让错误可以被精确复现”值得原样抄进项目的评测规范。编辑判断：项目的 452 条判定链路里同样存在可疑的元数据入口——方案名（A/B）、候选集版本、音色、SNR 档位标签都可能被判定逻辑读到。做一次处理不变性检查的成本极低（冻结执行证据、只改无关元数据、重算），而它能挡住的错误是系统性的。

P1：适合形成下一阶段架构

  1. 降噪前端的“流式代价”今天第一次可以估个量级。 HybridSB-MoE 的论文事实：在 VoiceBank+DEMAND 上 PESQ 3.88、STOI 0.96、CSIG 4.82、CBAK 3.85、COVL 4.82，全部指标自测最好，K=8 步、top-k=2 路由、RTF 0.28、自报 35ms 时延，训练用 2× RTX 5090。而 08-13 记录的 RT-SEMamba 在同一份语料（VCTK-DEMAND 与 VoiceBank+DEMAND 是同一个数据集的两种叫法）上，全因果流式实现的 8 层教师 PESQ 3.32、蒸馏 1 层学生 3.18。编辑判断：把这两个数放在一起，可以给出一个粗略但有用的先验——在这份语料上，坚持“能因果地逐帧出音”大概要付出 0.5–0.7 PESQ。但必须同时写死三条免责：两篇的评测协议不同（HybridSB 自称所有基线都由其重训重测，其复现的 SEMamba 是 3.55），所以不能直接相减；HybridSB 全文没有任何因果性或逐帧算法时延的声明，其 35ms 是整句口径而不是 08-13 定的“1 帧进 1 帧出”口径；两者都只有英文单通道 PESQ 类指标，没有中文、没有车内、没有下游 CER，也都没有 AEC。所以 08-13 写下的前端选型硬要求一条都不放松。
  2. Luna-TTS 的官方项目页从 404 变成了可访问，这是对昨天记录的一处直接更正。 08-13 报告与记忆都记为“项目页 2026-08-13 复核返回 HTTP 404”。2026-08-14 复核该地址返回 200，页面标题 Luna-TTS Family，含完整的 Seed-TTS-Eval 表与推理性能表。新增的一手信息有三条：一是推理表比论文多两行（16 步 2×H20 并行 CFG 首音频 63.8ms / 整句 451.4ms / RTF 0.0426；32 步全网格 419.6ms / RTF 0.0410）；二是 Seed-TTS-Eval 表里 OmniVoice 0.6B 记为 zh CER 0.84 / zh SIM 77.7 / en WER 1.60 / en SIM 74.1，且明确标注“取自该系统自己的报告”，正好与 08-13 记录的“Luna 作者用官方工具在 CV3-Eval 上重测 OmniVoice 得到四语平均 6.88”形成同一候选的两套外部数字；三是页面自身存在一处内部不一致（见下）。仍然没有代码、权重或许可证——整页唯一的外链是 arXiv。所以 omnivoice-local-tts-16step-v1 的处置不变。
  3. 候选流程可以直接借用一条成文的“单变量 + 留出门”协议。 AutoDesign 的论文事实：外层每次迭代只允许修改五个组件中的一个；接受条件是 J_train(H') > J_train(H) 且 J_dev(H') ≥ J_dev(H)；且 dev 分数从不展示给作为优化器的编码 agent。同一篇还给出一个对项目更有价值的警告：它自己的基准分与 933 条人评判断的 Pearson 相关只有 r = 0.34（95% CI [0.22, 0.44]），按分差分层，0–3 分差时人机一致率只有 51.9%（约等于抛硬币），要到分差 ≥20 才升到 74.4%。编辑判断：项目的 452 条自动判定与 +1/+4 量级差异正落在“分差极小”的那一档，这条外部证据说明小分差区间的自动判定基本不携带信息，必须靠零退化逐条比对而不是靠总分。

P2：长期研究与明确的边界

  1. “局部都对、组合起来不对”今天有了一篇自报失败的对照。 arXiv:2608.13228 把 agent harness 的组合失败建模成一个有限层（capability sheaf）：各子系统各自都能给出合格答案，但它们对共享状态（文件路径、API 版本、源提交、测试标识）的取值对不齐。它在受控实验里证明了自己的不变性机制有效，然后在 20 个真实仓库、160 个 issue、875 个候选补丁的发现集上诚实地报告失败：解决 118 个 issue vs 匹配基线 116 个，跨仓库符号翻转检验 p=0.75；弃权门 127/160，只比匹配门多 1 个，p=1.0；作者据此宣布“发现门未通过，确认集保持封存”。编辑判断：对项目最有用的不是它的数学，而是这套预先声明门槛、未达标就封存、不做事后挑选的纪律，以及“+2 不构成证据”这个具体量级。

1. FlashDrive: Flash Vision-Language-Action Inference for Autonomous Driving

论文（arXiv v1，2026-08-13 08:10:54 UTC 提交，本轮 2026-08-14 检索发现）：https://arxiv.org/abs/2608.12932

官方项目页：https://z-lab.ai/projects/flashdrive

官方代码仓库：https://github.com/z-lab/flashdrive

官方模型页：https://huggingface.co/z-lab/Alpamayo-1.5-10B

它是什么

UC San Diego、Princeton 等作者的一篇推理加速论文。它解决的问题是：面向自动驾驶的视觉-语言-动作（VLA）模型推理太慢，而慢的原因不是单一瓶颈，而是四段串起来的级联——视觉编码在滑窗里重复编码已见过的帧；语言模型 prefill 重算上一时刻本可沿用的上下文；推理链的 token 逐个自回归生成，尽管驾驶域推理链短且可预测；动作侧的流匹配去噪对一个非均匀的速度场施加均匀算力。作者的论点是“单独优化任何一段，其余三段原封不动”。

核心方法

分成系统层与算法层两部分。

系统层（论文与仓库 README 都列为“不改模型行为”的一档）：把每个流水线阶段编译成 CUDA Graph，记录完整的 kernel 序列；融合 attention 与 MLP kernel；仓库 README 把这一档写作“static KV cache、融合 expert projections、以及对完整解码循环做 torch.compile 与 CUDA graphs”。

算法层三条：

  • 流式推理：利用驾驶视频的时间重叠，只编码新帧并复用此前帧的 KV cache，把有效序列长度砍掉约 75%；因为这会带来分布偏移，另配一段轻量流式微调来适配动作专家。
  • 投机推理：利用驾驶域推理链“逐 token 熵低、块内相关性强”这两个性质，用 DFlash（一个块扩散并行 drafter，本身是 arXiv:2602.06036，2026-02-05 首投、2026-05-28 修订的前作，不是本轮新工作）一次提出整块候选，由目标模型一次前向验证。
  • 自适应步长流匹配：去噪速度场在两端变化剧烈、中段近似恒定，于是缓存中间速度，八步里复用四步。

对 StreamingModelHarness 的帮助

一条直接的、可执行的帮助，和一条必须写死的边界。

直接帮助是：它给出了“static KV cache 是 CUDA Graph 捕获的前置条件”这个此前项目没有采用过的理由。项目快照对 StaticCache 的判断是按拷贝开销算的——KV=2500 时 DynamicCache.update() 的 torch.cat 只有约 0.2ms，所以不值得。这个算法是对的，结论在它自己的口径下也是对的。但图捕获需要区间内张量形状与显存地址固定，动态增长的 KV 缓存会直接让捕获失败；而项目诊断出的每 token 约 816 次同步（.nonzero()、GPU 标量比较、torch.where）同样是图捕获的破坏源。所以三者的关系是有顺序的：先用 index_select+bmm 消掉数据依赖的主机同步（项目既定计划），再上固定形状的 KV 预分配，最后才谈整循环图捕获。FlashDrive 的价值是给这条链路提供了一个已被别人量到过的量级：不改任何算法，10B 模型的解码段能从 271.7ms/56.4 tok·s⁻¹ 到 170.6ms/89.5 tok·s⁻¹。

必须写死的边界，按重要性排：

  • 它不是 MoE 证据。 仓库 README 里的“融合 expert projections”容易被误读成 MoE 专家融合。复核 z-lab/Alpamayo-1.5-10B 的 config.json，其 expert_cfg 是 {head_dim:128, hidden_size:2048, intermediate_size:8256, num_attention_heads:16}，配合 action_in_proj_cfg/action_out_proj_cfg/diffusion_cfg，指的是动作专家这一独立模块，不是 MoE 路由专家。项目的 110ms/token 根因是 HF MoE 的路由实现，FlashDrive 没有针对这一点的任何证据。
  • 系统层那 1.59× 是一个捆绑（static KV cache + kernel 融合 + torch.compile/CUDA Graph），论文没有把 CUDA Graph 单独拆出来消融。项目若要用，必须自己拆成单变量测，不能引用 1.59× 当预期。
  • 领域与模型都不同：驾驶 VLA、10B 稠密骨干 + 动作专家 + 流匹配，与 Qwen3-Omni 的音频原生全双工路径没有架构可比性。它的 token 吞吐基线 56.4 tok/s（约 17.7ms/token）与项目的 110ms/token 也不是同一个量级的问题。
  • 按项目既定边界，不运行该仓库代码。本节全部结论只来自论文正文、仓库 README 与模型页元数据。

2. Alignment Drift in Single-Model Speculative Decoding for ASR: Mechanism, Correction, and Cost

论文（arXiv v1，2026-08-13 01:34:38 UTC 提交，本轮 2026-08-14 检索发现）：https://arxiv.org/abs/2608.12703

它是什么

Boson AI 与 McGill 的论文。它研究的问题是：把“单模型自投机解码”（draft 不是另一个模型，而是挂在目标模型上的轻量模块）用到 ASR 上时，会多出一个文本任务没有的困难——draft 每一步都能读到整段编码后的音频，但它仍然必须知道下一个 token 该对齐到哪一帧。作者的说法是“能访问不等于能定位”（access is not localization）：已接受的文本前缀明确记录了转写位置，而音频位置需要 draft 自己在两次目标模型验证之间维持，且因为每个 token 的时长不同，音频位置每步前进的帧数是变化的。他们把 draft 注意力峰值与真实对齐帧之间不断变大的距离称为对齐漂移。

核心方法

先定位失败发生在哪：把每个投机轮拆成 restart（验证之后的第一个提案）与 continuation（下一次验证之前的后续提案）。然后做三件事：

  • 用受控对照隔离音频位置：固定可见窗口宽度、只改窗口中心，看 continuation 是否恢复。
  • 两种纠正。运行时纠正：从目标模型验证时的音频注意力读出一个新鲜的位置估计（在开发集上选定层，本文中两个独立训练的 1.7B draft 都选中第 21 层），用它对齐下一轮 draft 窗口；该实现只读已有 cache，不做强制对齐，不增加目标模型前向。训练期纠正 AnchorDraft：对 draft 的第一层音频注意力施加高斯引导注意力目标，损失为 L = L_tok + 0.5·L_feat + λ·L_anchor（选定 λ=0.1、σ=5），推理图完全不变。
  • draft 架构沿用 EAGLE-3 的直接 token 预测与多层特征设计，额外加上每个 draft 步到冻结音频编码器的交叉注意力。

对 StreamingModelHarness 的帮助

三条，按可用性排。

5. Labels Are Not Endpoints: Treatment Leakage and Construct Validity in MCP Agent Security Evaluation

论文（arXiv v1，2026-08-13 06:44:40 UTC 提交，本轮 2026-08-14 检索发现）：https://arxiv.org/abs/2608.12880

它是什么

作者对自己前一轮 MCP agent 安全评测的自审。核心指控是：安全评测常把存下来的标签当成行为事实，而他们的历史判分器把 treatment 元数据直接接进了 ATTACK_SUCCESS 这一类的门控条件，于是固定住已执行的行为，只改 treatment 标注，类别就会变。论文自我限定为“一次以本次实验为界的测量审计，而不是攻击率、模型排名、防御有效性或因果估计”。

核心方法

  • 单元重建：把 10,200 条执行记录按内容哈希绑定回身份（stimulus、delivered content、semantic request、model authority、template authority、model-bound request），并以“数量不符即失败”的方式 fail closed。

论文（arXiv v1，2026-08-13 17:59:57 UTC 提交，本轮 2026-08-14 检索发现）：https://arxiv.org/abs/2608.13560

官方代码仓库：https://github.com/Yaxin9Luo/AutoDesign

它是什么

美团、MBZUAI、华科、北大、清华等作者的论文。它把“把多模态素材变成结构化媒体产物”视作一个围绕模型-harness 系统展开的长时程 agent 过程，主张在模型参数固定的前提下优化 harness 本身，并在“论文转学术海报”这一任务上实例化。对项目而言，它的价值几乎全在优化协议，而不在海报。

核心方法

两层嵌套循环。内层是设计 harness：设计模块与批评模块交替，产物保持为可编辑 HTML，渲染成 PNG/PPTX/MP4 后再批评，最多 K=12 次精修，然后回退选择与定稿；批评由规则校验器（阻断性检查）加视觉语言模型批评器（设计契约、美观、版式、可读性）组成。

外层是元 harness，这一层才是对项目有用的部分：

  • harness 被拆成恰好五个功能组件（上下文与记忆、工具与规格、执行运行时、编排、评测与反馈），每次外层迭代只允许修改其中一个。
  • 接受门是 Accept(H') ⟺ J_train(H') > J_train(H) ∧ J_dev(H') ≥ J_dev(H)，即训练集严格提升且开发集不退。
  • 开发集分数从不展示给优化器。
  • 只维护单一活跃 harness，作者明确说明“不在 harness 变体上做树搜索”；优化记录作为持久上下文。

7. Capability Sheaves for Compositional Agent-Harness Repair

论文（arXiv v1，2026-08-13 13:31:09 UTC 提交，本轮 2026-08-14 检索发现）：https://arxiv.org/abs/2608.13228

它是什么

独立研究者的单作者论文。它要刻画的失败模式，用它自己的例子说最清楚：一个仓库补丁 agent 里，一个子系统能定位到属主文件，另一个能取回声明的 API 版本，第三个能保住源提交，验证器能选出公开契约测试——每个子系统看起来都称职，但它们给出的路径、版本、提交与测试状态对不齐。作者称之为“可执行行为的局部到整体失败”。

核心方法

用有限的层（cellular sheaf）建模：五个已登记的需求（定位、契约、次序、保持、验证）各是一个顶点，每个顶点带一个有类型的行为签名 stalk，边表示共享字段的重叠，限制映射是字面的字段投影。可接受性由一个精确的有限 CSP 定义（每个顶点的取值落在其“良好子集”内，且每条边上两端的限制相等）；另外用 F₂ 上的线性相对上同调类作为诊断与搜索特征。作者明确说明“层的表述不消除组合难度，它把局部存在性与粘合分开，并给出跨候选的类型化线性诊断”。

论文结果

受控实验（20 个任务簇，人为引入隐藏的内部中介，其原始状态是冗余变量）：对其上边界做商可把每簇候选预算从 2,000 降到 1,000；对齐隐藏状态则该差距消失；精确 CSP 与商的结果一致——作者据此说“这证明的是对陈旧代表元的不变性，而不是优于精确推理”。

真实仓库压力测试（PatchFuseBench 的 SWE-bench Multilingual 发现集）：20 个仓库、160 个 issue、875 个真实候选补丁、2,579 个源码感知编辑原子、153 个新执行的补丁。结果是自报失败：

  • 第一种池级构造是常数（因为 [δx] = [0]），因此根本无法对配置排序。
  • 候选索引式修复在 848/875 个候选上非平凡、在 120/160 个 issue 内有变化；解决 118 个 issue vs 匹配的非上同调选择器 116 个，但跨仓库精确符号翻转检验 p = 0.75，即该差异未获支持。
  • 留一仓库的弃权门达到 127/160，与强锚点持平，比其匹配门多 1 个，p = 1.0。
  • 作者结论：“发现门因此未通过，确认集保持封存。本研究支持受控的不变性机制与一个可识别性修正，但不支持真实世界中的上同调优势。”

对 StreamingModelHarness 的帮助

不是技术，是纪律。三条：

  1. 它把项目 composition queue 的前提用一个具体例子说清楚了：局部各自合格不等于共享状态一致。项目的对应物是——RAG 候选、模型的 typed call、确定性执行器的参数校验、最终车态判定，这四者对“到底操作的是哪一块屏、哪一个座位、哪一个温度目标”必须取值一致；任何一处对不齐，四个组件各自的通过率都不下降，而整体失败。项目已有的“组合前必须做 interaction/zero-regression”正是防这个，本文给了它一个可引用的失败模型。
  2. “+2 不构成证据”有了一个具体的外部量级。118 vs 116 在跨仓库分层下 p = 0.75；弃权门 127 vs 126，p = 1.0。项目的 +1/+4 在 452 条上是同一量级甚至更小。这与第 6 节 AutoDesign 的 r=0.34 同向。
  3. 值得直接借用的做法是“预先声明门槛 + 未通过就封存确认集”。项目在跑 full H20 之前先把通过判据与样本量写死落盘，达不到就封存、不做事后挑选，也不把“换个分层看就通过了”当作通过。这一条与项目已有的“冻结 414 canary 零退化 + 动态 full gap 14”规则是同一精神，本文是它的外部背书。

必须写明的边界：任务域是代码补丁融合，不是语音也不是车控；它的核心贡献是数学结构，项目不需要也不应该引入层上同调；本文自己宣布真实世界优势未被支持，因此不存在“值得复现”的技术。它只作为方法论参照，不进候选。

8. vToken: Token-Level Virtualization for Reclaimable KV Caches

论文（arXiv v1，2026-08-13 14:01:21 UTC 提交，本轮 2026-08-14 检索发现）：https://arxiv.org/abs/2608.13263

它是什么

国防科大与北大作者的系统论文。问题是：KV cache 随序列长度与 batch 增长；PagedAttention 用固定大小的块降低分配器级碎片，但近期的 KV 驱逐算法工作在比块更细的 token 粒度上，这个粒度错配造成块内碎片，使已分配的 KV 显存有很大一部分无法回收。

核心方法

在驱逐策略与块级显存管理之间插入一层 token 级虚拟化：通过 token 表间接寻址，向上暴露稳定的逻辑 token 视图，向下通过异步重打包存活 token实现物理回收（论文称之为惰性压实）。设计上明确保持 PagedAttention kernel 与 CUDA Graph 兼容性。实现在 vLLM 上，用 H2O、Random、Scissorhands 三种驱逐算法评测。

论文结果

相对配对的 Naive-Evict 基线，把满足 SLA 的吞吐提升最多 1.37×。开销分解显示规划器侧的机会检查主导 CPU 可观测开销。作者自己给的适用范围写得很清楚：“vToken 是一个压力触发的扩展而非原生全 KV 服务的替代；当 KV 显存不是瓶颈时，原生路径仍然更可取”。

对 StreamingModelHarness 的帮助

判为不适用，并作为一条边界清晰的记录留档，理由有三：

  • 项目是 batch=1 的单请求座舱场景，KV 约 2,500，快照已明确“当前 KV 规模下影响可忽略”。KV 显存根本不是瓶颈，论文自己的适用条件就把项目排除在外。
  • 它优化的是 SLA 约束下的吞吐，而项目的门是单请求的 ms/token 与首音频时延。这与 08-12 记录的 OasisKV 属同一类反例（收益需要大 batch/长上下文，低 batch 下 TPOT 反而更差），不需要重新论证。
  • 它引入的是一层间接寻址与异步重打包，在单请求下只有开销没有收益。

唯一可转移的一点，与本报告第 1 节同向：它把“保持 PagedAttention kernel 与 CUDA Graph 兼容性”当作硬性设计约束写在方法里。加上 FlashDrive 把整个解码循环做图捕获，可以归纳出一条选型筛子——推理侧的任何改动都要先问“它是否破坏图捕获兼容性”。项目的 .nonzero() + GPU 标量比较 + torch.where 正是破坏项，这条筛子恰好指向项目已经决定要做的那件事。

9. StreamTTT: Reconciling Real-Time Perception and Long-Term Memory in Streaming VLMs

论文（arXiv v1，2026-08-13 16:10:33 UTC 提交，本轮 2026-08-14 检索发现）：https://arxiv.org/abs/2608.13416

它是什么

NUS 与 KIT 作者的论文，首页自标“仍在进行中的工作”。问题是：流式视觉语言模型常在“实时感知当下”与“记住很久以前”之间二选一；已有工作显示缩短上下文能提升当前场景感知却损害长程回忆，注入历史则相反。作者把原因归为注入的历史挤占了注意力上下文，于是把长程历史移出注意力上下文。

核心方法

在 Qwen3-VL 上，把每个自注意力块改成混合层：保留预训练的滑窗注意力路径，并联一条测试时训练（TTT）分支，由一个初始化接近零的逐通道可学习门 o = o_SWA + tanh(α) ⊙ o_TTT 融合。TTT 分支把历史写进一组快权重（写入是对 ‖f_W(k) − v‖² 做一步梯度下降，读出是 f_W(q)），用 LaCT 的大块 TTT 并采用“先应用后更新”的次序以保证因果流式；与原始 LaCT 不同，它用带输入相关衰减的动量。每层状态为 (W, M, 卷积前缀, 部分块缓冲)，全部固定上限大小，因此状态大小与已处理 token 数无关；部分块缓冲至多 C−1 个 token，衰减与动量门保持在对数域，使分块多趟运行能复现单趟连续运行。流式推理按墙钟时间把帧切成窗口，每个窗口后把 KV cache 裁剪到最近 L 个 token，而快权重状态不驱逐地向前携带；位置用全局连续的 M-RoPE。

论文结果

OVO-Bench 两轨 + StreamingBench RTVU：StreamTTT-4B（2 fps）RTVU 80.48，实时感知均值 78.9，回溯均值 58.3，两轨平均 68.59。对照：SimpleStream-4B（16 帧）77.5 / 54.6 / 66.06；SimpleStream-8B（4 帧）RTVU 80.59、81.4 / 54.0 / 67.70；HERMES-7B RTVU 79.44、69.0 / 49.4 / 59.20；人类 91.46、93.2 / 92.3 / 92.77。

记忆架构消融（Qwen3-VL-4B，同调度同种子；实时均值 / 情节回忆 / 平均）：冻结的最近窗口（4 帧、无训练）78.66 / 51.25 / 64.96；仅滑窗 KV + 联合训练 68.19 / 49.58 / 58.89；混合 + 仅离线训练 65.08 / 57.50 / 61.29；混合 + 仅实时训练 78.15 / 57.00 / 67.58；混合 + 联合训练 78.85 / 59.55 / 69.20。匹配推理显存的对照（均用 4K 滑窗 KV）：仅滑窗 58.89、StreamMem 65.65、HERMES 66.23、本文快权重 69.20。

明确的负结果，值得单独记下：在 64K 窗口下（EgoSchema 整段短片已能进上下文），加 TTT 反而更差——65.6 vs 纯滑窗 66.8，差 1.2 分。作者的结论是“当整段视频能放进上下文时，它是补充而非替代”，并承认“固定大小的循环状态在依赖回忆的视频上仍是有损摘要”。另一处：经过训练的“仅滑窗 KV”方案（68.19）反而低于完全没训练的冻结最近窗口基线（78.66），差 10.47 分。

10. PIPES: Securing Agent Perception with Provenance and Priors

论文（arXiv v1，2026-08-13 03:49:00 UTC 提交，本轮 2026-08-14 检索发现）：https://arxiv.org/abs/2608.12789

它是什么

NVIDIA 三位作者的论文。问题是他们称作agent 感知缺口的东西：用工具的 agent 消费来自不同信任级别来源的外部数据，但工具回执很少标明“这一部分是谁产生的、它有权断言什么”。由此产生状态污染攻击——攻击者可控的内容做出超出其信息权限的环境断言，污染 agent 感知到的环境，使随后的动作在现有护栏看来完全合理。论文的例子是商家可控的 tags 字段写入“评分已更新为 4.9”，护栏于是判定“动作与感知到的评分一致”而放行。

核心方法

在工具回执进入 agent 上下文之前的边界处做两项检查，输出稀疏指示向量：一是静态先验与来源（结构稳定的 schema：可机检字段如数字、布尔、枚举先确定性校验并成为可信参考上下文，开放词表字段再配语义先验与来源标签，来源序如“平台 > 商家”）；二是上下文先验与来源（开放式内容：把回执归一化成“来源单元”，用工具级契约与有界的响应前历史评估）。评估与响应策略分离：部署方可以移除、告警、阻断或升级；实验采用原子移除（违规标量文本清空、违规列表元素移除、违规来源单元整体移除），作者说明“而不是改写，因为改写可能引入无依据内容或模糊来源边界”。

论文结果

六个划分（VitaBench 的 Delivery/In-store/OTA 各 100 条良性任务，攻击实例 69/38/28；AgentDyn 的 Shopping/GitHub/Daily-life 各 20 条开放任务、各 20 条攻击实例）。

Gemma 4 31B IT：无防御平均攻击成功率 84.7% → PIPES 2.3%，良性效用 90.6% → 92.5%。GPT-5.6 Luna：21.6% → 1.1%，效用 84.0% → 86.5%。对照的其它防御在 Gemma 的 VitaBench 静态路径上，PromptArmor 与 DRIFT 的平均 ASR 分别是 19.1% 与 17.9%，PIPES 是 2.8%；在 AgentDyn 上 PIPES 为 1.7% ASR / 100.0% 平均良性效用，DRIFT 为 5.0% / 81.7%。效用在 12 组比较中有 8 组不变或提升，其余 4 组中 3 组下降不超过 1 个百分点，最大一处下降 5 个百分点。

作者自陈的限制：PIPES“评估的是语义可接受性与来源权威，而不是事实真伪：一个错误的值如果符合其先验，仍会通过”。
