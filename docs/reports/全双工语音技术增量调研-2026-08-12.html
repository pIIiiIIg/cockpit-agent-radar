一、先说结论

P0：直接命中当前工程短板

  1. 补“播放边界”这一层，并把它作为不可逆车控的授权前提。 PACE 的论文事实是：在其 108 条 GCM-Bench 上，仅取消生成的基线引用锚定正确率 25.0%，加入播放边界投影后为 96.3%（+71.3 个百分点，McNemar p<0.001，修好 78 条、引入 1 条回退）；在另取的 200 条 Full-Duplex-Bench v1 打断样本上，接管率都是 1.000，评分 4.975→4.995，打断后响应时延 0.771s→0.830s。编辑判断：项目当前连“用户听到了第几句”都没有记录，因此这不是选型问题，而是缺一层可观测量；应先落账本与撤销，再谈是否注入上下文。
  2. 把“工具执行期间的固定等待语”作为首音频的独立单变量。 论文/模型页事实：VoiceChat 为每个工具定义 on-hold 语，在生成触发工具的文本时立即播报。编辑判断：项目首动作已经在 700–1,094ms 完成，而首音频要 2.9–3.5 秒，这段静默可以用预合成音频填掉，且与 TTS 后端选型完全解耦；但必须分别报告“固定音频首包”和“真正内容首音频”，否则就是指标偷换。
  3. 用 pipecat 的 DGX Spark 部署记录校准自己的时延口径。 该仓库的一手记录：同一模型在浏览器端实测 voice-to-voice 1,470.7ms，Pipecat TTFB 732.341ms、TTFA 982.772ms（其中 250.431ms 是生成出来的前置静音），并写明当前仍未达到 400ms 目标；而模型页宣传的是“~450 ms”turn-taking 时延。编辑判断：这正是项目坚持“从 commit 起算、到真正出声为止”的理由，应把该仓库的分层归因表当作外部对照方法，而不是把 450ms 当成可达基线。

P1：适合形成下一阶段架构

  1. 参数与最终车态优先于工具名，这次有了外部同向证据。 VoiceChat 在口语化 FDB-v3 上工具选择 82.5%、参数正确率 44.2%、Pass@1 33%。编辑判断：一个自带工具通道的端到端全双工模型都出现“选得对、填不对”的量级落差，说明项目把严格工具名召回升级为参数 + 最终车态是必要的，而不是可选优化；同时也说明确定性执行器、参数校验和幂等不能因为换模型而移除。
  2. DuplexGen 的标注协议可以直接搬，语料和 LoRA 路线不要搬。 其可迁移部分是增量呈现、每样本 5 名标注者、listen/backchannel/take-floor 三分类与 KL 软标签；其英文语料、固定 0.16s 间隔与 0.64s 重叠是脚本化时序，不能当真实座舱分布。
  3. Evo-Bench 的“harness 敏感度筛选”值得借用来选评测样本。 它先用辅助任务进化找出真正对 harness 改动敏感的任务，再做敏感度分层切分。编辑判断：项目当前的 414/452 canary 与错误桶没有这层筛选，容易把模型强弱与 harness 收益混在一起。

P2：长期模型研究与明确的反例

  1. OasisKV 是本窗口最清楚的反例。 它的收益来自大批量、长上下文的服务吞吐；论文自己写明在 Qwen3-235B-A22B（TP8）低批量时 TPOT 高于 dense，只有到 B=32（16K）/B=16（32K）才反超。编辑判断：座舱是 batch=1、KV 约 2,500 的场景，引入它只会更慢；它也不触碰 MoE 路由同步。
  2. A-PACK 的可迁移结论是“别在进 LLM 前剪音频”，不是它的加速数字。 论文事实：audio token 的逐 token 重要性与多样性都高于 video token，因此它把音频保留到 LLM 内部再按查询相关性剪。其 78% prefill FLOPs 削减与 2.21× 解码吞吐提升都是离线长视频问答场景。
  3. Lychee-FD 的 v4 与 v3 没有实质变化，是同一工作的修订版。 逐词比对显示 v4 相对 v3 只多了一段 MOSS-Speech 相关工作和版本/日期变化，全部主表数值一致；它已在 2026-08-06 报告中覆盖，本次只补一条部署事实（多头低时延依赖跨 GPU 并行）。
  4. 本窗口的 TTS 新工作都不改变既定候选。 CtrlSpeech 只有英文评测、权重 CC-BY-NC；SemBridge 有中文 CER 但代码与权重未公开。

1. PACE: A Playback-Aligned Context Engine for LLM-Based Full-Duplex Voice Dialogue

论文（2026-08-07，Radar 于 2026-08-11 发现）：https://arxiv.org/abs/2608.07631v1 官方数据与评测代码：https://github.com/CodeForZzc/GCM-Bench

它是什么

阿里巴巴的一篇系统论文，提出并命名了一类全双工失效：服务端生成与对话状态推进得比客户端播放更快，用户后续话语可能被绑定到他根本没听到的助手内容。作者称之为 Generative Context Mis-anchoring（GCM），并把它定义为分布式一致性失效——识别结果和生成结果都可能局部正确，错的是输入被锚到了对话中的错误位置。PACE 是与提供方无关的中间件抽象，把模型可见上下文对齐到客户端播放边界。

核心方法

  • 服务端为每个助手轮次维护 OutputTurnLedger：turn_id、audio_copy（最多 W_max 秒）、可选 text_copy 与 semantic_spans、played_samples、生命周期 state。客户端持续上报 PlaybackAck = ⟨audio_turn_id, played_samples⟩。
  • 论文严格区分三种边界：物理播放边界 B^p（只声称哪些采样被渲染过）、语义提交边界 B^s（只有在运行时提供“音频时间→内容”的可靠映射、且 span 已 finalized 时才导出）、以及运行时特有的恢复边界。没有对齐信息时 B^s = ⊥，论文明确不从波形或流逝时间去猜语义边界。
  • 打断处理是四件事的定序：先同步关闭前向门（forward gate），再取消上游生成并置抑制标志、向客户端下发 Revoke⟨audio_turn_id, after_sample, reason⟩ 撤销缓冲音频，然后做上下文投影，最后按序释放被暂存的用户音频。保证模型看到的顺序是“最后一个打断前 tick → cancel → 注入上下文 → 暂存 tick → 新用户语音”。
  • 投影按运行时能力分三档：级联系统改写文本历史；黑盒实时语音 API 用“已播放音频再注入”（切取最近 L 秒已播放音频，重采样后拼接一段预合成分隔语，再送用户打断语音）；原生 S2S 若能给出 finalized transcript/semantic token 与输出采样端点，才计算 B^s 并回滚到检查点。
  • 设计原则里单列一条：投机生成可以，投机提交不可以——不可逆工具调用不得基于未落地播放的提案提交。

论文结果

  • 原型实现：浏览器 JS 客户端 + Python 异步中间件 + DashScope Qwen-Audio-Realtime 适配器，不修改模型服务。麦克风 100ms 一个 tick，主传输 WebTransport、WebSocket 兜底，乱序等待上限 50ms；上行 tick 头 33 字节携带 16 位 audio_turn_id 与 24kHz 下的 32 位 played_samples，下行 delta 头 27 字节。黑盒适配器切取不超过 5 秒已播放音频，24kHz float32 重采样为 16kHz PCM16，按不超过 192,000 字节分块注入。
  • GCM-Bench：12 个清单式场景 × 3 个打断延迟（12/16/20 秒）× 3 种指代操作 = 108 条。用户输入由 DashScope Qwen3-TTS-Flash（Cherry 音色）合成并固定时序，但助手生成、传输、浏览器播放和修复都是在线发生；播放边界来自真实浏览器 PlaybackAck。转写用 Qwen3-ASR（保留词级时间戳），判定用 ChatGPT 5.5，判定时只给它“已播放前缀”，不给标准清单。
  • 主结果：两种条件的 TOR 都是 100%，基线 27/108 = 25.0%，PACE 104/108 = 96.3%。配对结果为“两者都对 26 条、仅基线对 1 条、仅 PACE 对 78 条、都错 3 条”，McNemar 连续性校正 p<0.001。
  • 分操作：elaborate 从 1/36（2.78%）到 34/36（94.44%）；repeat 从 4/36（11.11%）到 35/36（97.22%）；next 从 22/36（61.11%）到 35/36（97.22%）。论文自己说明 next 的基线偏高，因为事后判定看不到“已生成但未播放”的后续项，所以把 elaborate 当作最干净的 GCM 修复证据。
  • 稳健性：12/16/20 秒延迟下 PACE 为 91.7%/100.0%/97.2%，且不单调；概念清单 97.2%、条件清单 100.0%、流程清单 91.7%。
  • 消融：固定 5 秒回看窗口时，三种分隔语 P1/P2/P3 为 96.30%/84.26%/91.67%（Cochran Q=8.897，p=0.012；Holm 校正后 P1 显著优于 P2，但不显著优于 P3）。固定 P1 时，回看 2.5s/5s/10s 为 95.37%/96.30%/65.74%（Q=51.561，p<1e-3；2.5s 与 5s 差 0.93 个百分点不显著）。论文说明 2.5s 与 10s 条件是在更晚的实时批次收集的，因此 2.5s 与 5s 的接近结果要谨慎解读。
  • 兼容性与代价：200 条 FDB v1 打断样本上 TOR 1.000→1.000，评分 4.975→4.995，平均响应时延 0.771s→0.830s，即 +58.7ms（配对 bootstrap 95% CI [24.8, 96.4] ms，Wilcoxon p=6.66e-7）。助手没有在播放时的请求走原路径，不增加 PACE 时延。
  • 错误分析：4 条 PACE 错误中 1 条是 next 重复了当前项，3 条发生在流程类场景、锚到了相邻子动作。

对 StreamingModelHarness 的帮助

编辑判断：项目应该先落三件与模型无关的机制——每轮播放账本（turn_id + played_samples）、客户端撤销、打断时的前向门与定序。这三件事本身就把“用户听到了哪一段”变成可记录量，能直接支撑项目下一步要求的多轮跟随、打断改口和取消/补偿评测。

编辑判断：PACE 的“不可逆动作门”与项目现有的候选授权、参数校验、幂等和最终车态验证是同一族约束，可以合并成一句可测规则：确认类车控只有在其提案音频已经播放完成时才允许提交。这一条比“注入已播放音频”更重要，因为它防的是错误执行而不只是错误措辞。

编辑判断：注入方式要按项目实际后端选：项目是自托管 Qwen3-Omni，理论上可以走比黑盒再注入更强的路径（文本历史改写或状态回滚）。但论文第 2.4 节列出的代价对项目同样成立——中途修改 KV 会破坏前缀缓存与批处理，边界还可能落在词或 token 内部。因此第一步只做“账本 + 撤销 + 门”，注入策略作为第二步的对照项。

编辑判断：GCM-Bench 不能直接当项目验收集。它是英文/中文清单式通用问答（场景为编程语言、番茄炒蛋、出国准备等），既没有车控动作，也没有座舱噪声与多乘员；项目要自建中文车控版“指代锚定”桶，才能得到可比数字。

2. NVIDIA NemotronLabs VoiceChat 11B 与它的单机部署记录

官方模型页（发布 2026-08-03）：https://huggingface.co/nvidia/NVIDIA-NemotronLabs-VoiceChat-11B 官方代码分支：https://github.com/NVIDIA-NeMo/Speech/tree/nemotron-labs-voicechat Radar 于 2026-08-11 发现的官方部署仓库：https://github.com/pipecat-ai/nemotron-voicechat-dgx-spark 派生量化权重：https://huggingface.co/pipecat-ai/NVIDIA-NemotronLabs-VoiceChat-11B-Spark

它是什么

VoiceChat 是 11B 的端到端实时全双工语音模型：Fast Conformer 语音编码器 + Nemotron Nano v2 9B 主干 + TTS 解码器，另有一条独立输出通道专门产生工具调用脚本。模型页称它是第一个支持工具调用的开放全双工模型，并且可以为每个工具定义 on-hold 语——一旦 LLM 生成会触发该工具的文本，就立刻播报这句等待语，从而在工具执行期间维持对话流。Radar 本次命中的是 pipecat 官方为 DGX Spark 做的部署仓库，不是模型首发；模型本身此前未进入任何一份项目报告。

核心架构

  • 输入 16kHz 音频 + 文本提示；输出助手文本、助手语音（22.05kHz）和用户转写。推理引擎 vLLM，模型页测试硬件为 H100，混合 Mamba/Transformer。
  • 部署仓库为了在一台 DGX Spark 上维持实时性做了三件事：Nano 权重 GPTQ W8、EarTTS W8A32、打补丁的 vLLM，并实现了“条件两帧 PAD 起草”。函数头保持全精度。
  • 该仓库的时序契约值得单独记下：Voicechat 持有连续的声学/模型状态，Pipecat 只负责麦克风轮次的开始/结束判定并发送显式的相关联 start/commit barrier；模型服务从不把上下文当作无状态 chat completion 重放。合格化的配置是单会话、batch=1。
  • 打字输入被有意设计成半双工：模型服务持有闸门，从接受打字任务到其 EOU 关闭期间收到的麦克风 PCM 被丢弃。

论文/官方页结果

  • 模型页 Highlights：11B、turn-taking 时延约 450ms、VoiceBench 在开放全双工模型中第 2、首个支持工具调用的开放全双工模型。训练音频约 550k 小时。
  • Full-Duplex-Bench 1.0（模型页给出的数值）：停顿处理 TOR 0.153（合成）/0.255（Candor）；平顺轮替 TOR 0.82、时延 448ms；用户打断 TOR 1、时延 480ms、GPT-4o 评分 4.33。

  • 部署仓库 docs/voice-to-voice-latency.md 的一手实测（状态自述为“已测量并定位根因，但当前运行时尚未达到 400ms 的末次人声到首次机器人声目标”）：浏览器端 voice-to-voice 1,470.7ms；Pipecat TTFB 732.341ms；TTFA 982.772ms，其中 250.431ms 是模型生成出来的前置静音。同一次相关联的麦克风 commit 中，6 个 settlement 位置到达十空白栅栏耗 517.914ms，随后是单独的 213.137ms BOS 位置，6 次模型调用本身合计 417.902ms；分层归因为感知 70.708ms、Nano 接口 186.495ms、EarTTS 96.836ms、单帧流水化的 codec 调用 45.012ms。

4. A-PACK: Deferred Audio Pruning with Local Audio–Visual Dynamics for Omni-LLMs

论文（2026-08-09，Radar 于 2026-08-11 发现）：https://arxiv.org/abs/2608.08794v1

它是什么

Sungkyunkwan University 与 AWS AI Labs 的工作，针对 omni-modal LLM 的长音视频序列的 prefill 与 KV 开销。它的立场是：跨 LLM 边界的模态特定压缩此前研究不足，token 相关性的判据在进入 LLM 前后是不同的——进入前只有模态特定特征，进入后才有以查询为条件的多模态上下文。

核心方法

  • 进入 LLM 前：保留音频，只压缩视频，并用“局部音视频动态”（短对齐窗口内的协同演化）而不是逐 token 相似度来分配视觉预算，同时去掉视频内部冗余。
  • 进入 LLM 后：按查询相关性渐进地剪掉低相关的音频与视觉 token 及其对应 KV 条目。7B/3B 分别从第 14/18 层开始，35%/25% 档位下每层丢弃 10%/15%。
  • 支撑观察：在 AVUT 与 WorldSense 上，音频 token 的逐 token 重要性（遮挡 KL）与多样性（有效秩）都显著高于视频 token；固定预算下保留音频一致更好，剪音频省得有限却可能丢掉紧凑而时间局部化的证据。

论文结果

  • 硬件与设置：Qwen2.5-Omni-7B/3B 公开权重、不微调、NVIDIA A6000 48GB；四个基准为 AVUT、WorldSense、Video-MME、DailyOmni；档位按相对 Full Tokens 的 prefill FLOPs 定义。
  • 7B、35% 档：保留 Full Tokens 平均相对准确率的 98.8%，prefill FLOPs 约降 66%，prefill 结束时 token 保留 16.8%；25% 档：97.0%，约降 78%，最终 token 保留 5.6%。3B 对应为 97.3% 与 95.5%。
  • AVUT、7B、25% 档效率（Table 2）：显存 21.7GB（Full 24.0GB），准确率 62.2（Full 64.5），prefill 加速 1.85×、端到端 1.96×；对照 OmniZip 为 21.9GB、59.3、1.75×、1.86×。
  • 解码吞吐 51.4 tok/s，对照 OmniZip 31.1、DyCoke 35.1；摘要中给出的“最高 2.21× 解码吞吐提升”与“AVUT 显存降低 2.3GB”是同一组实验的汇总说法。
  • 分阶段消融：A-PACK 的 LLM 前选择 + 随机内部剪枝优于随机前选择 + A-PACK 内部剪枝，即准确率增益主要来自 LLM 前阶段，查询感知的内部剪枝负责补回剩余性能并降低后续序列成本。

对 StreamingModelHarness 的帮助

编辑判断：唯一可直接采纳的是设计约束而不是加速手段——不要在进入 LLM 之前压缩音频 token。项目的 B 版方案是音频直接进 Qwen3-Omni 的 KV，未来若为省显存或省 prefill 想加“音频抽帧/降采样/前置剪枝”，这篇论文给出了反对它的一手证据（音频逐 token 信息密度高于视频、紧凑事件容易被剪掉）。

编辑判断：它的加速数字不能用于项目的 110ms/token。它的收益来自单次长音视频问答的 prefill 与随后被缩短的 KV，而项目已经实测速度不随 KV 长度变化、根因是 MoE 路由的 GPU→CPU 同步次数。把 prefill FLOPs 或 A6000 上的吞吐当作 batch=1 单 token 时延证据就是指标偷换。

局限与开放状态

  • 任务全部是离线的音视频问答，有完整的已知查询和短答案；没有流式、判停、打断、工具或多轮结果。
  • 主干是 Qwen2.5-Omni，不是项目在用的 Qwen3-Omni MoE；跨代结论未知。
  • FLOPs 为按 token 数解析估算，不是硬件计数器测量；部分对照方法在某些基准上 OOM（表中记为 -）。
  • 开放状态：论文公开。正文写明“代码将在录用后发布”，因此代码、权重与派生数据均未公开，许可证未知。本轮没有在作者页或任何官方仓库找到可用实现。

5. OasisKV: Scaling In-Decode KV Cache Beyond HBM with Lookahead Sparse Prefetching

论文（2026-08-08，Radar 于 2026-08-11 发现）：https://arxiv.org/abs/2608.08097v1

它是什么

Imperial College London、KAIST 与 Microsoft Research 的服务系统论文：把完整 KV 存储与 HBM 解耦，只把最相关 token 的 KV 留在 HBM 参与注意力，其余放在 host 或远端内存，并用投机解码起草的 lookahead token 预测“下一步会重要”的 KV 块并提前预取。实现基于 vLLM。

核心方法

后台注意力流水线用 draft token 识别重要 KV 块，从更高容量的内存层预取并在下一次解码步前落到 HBM；draft token 只作为预取信号，被强制拒绝，不用于加速采样本身。

论文结果

  • 精度：在 2,048 token 的 KV 预算下，lookahead 预测足够准，使精度与全注意力相差在 0.7 分以内。
  • 吞吐：在推理类工作负载上以 0.1 分精度损失换到相对 dense vLLM 的 1.69×；多 GPU 长上下文最高 2.1×（16K、最大并发 128 时 1,398 对 676 tok/s）。中等并发 16 时同时改善两者（836 对 649 tok/s，TPOT 17.7 对 23.5ms）。2,048 token 上界让 16K 下可并发 90–95 条请求，dense 只有 22 条。
  • Prefill–Decode 分离下约达 dense 的 2× 吞吐，同时每条请求准入的 KV 少 6.5–9.7×，decode 节点 host 内存少 2.2–2.6×。
  • 明确的负面条件：Qwen3-235B-A22B 在 TP8 下 KV 只占 GPU 内存一小部分，稀疏省得少而每步额外开销仍在，因此低批量时 TPOT 高于 dense，只有到 B=32（16K）与 B=16（32K）才反超，最高 1.9×（1,102 tok/s）。
  • 硬件：8×H100（80GB HBM3）。

对 StreamingModelHarness 的帮助

编辑判断：结论是不要引入。项目是单请求、batch=1、KV 约 2,500 的座舱场景，而这篇论文自己给出的低批量 MoE 结论正好相反——额外的预测与预取开销会让 TPOT 变差。它也完全不触碰项目定位到的每 token 约 816 次 GPU→CPU 同步。

编辑判断：它有一条可借用的方法论：论文把“Token-KV 强度 × KV 带宽”和批量/最小 TPOT 两条上限画成 roofline。项目在讨论 MoE fast path 时可以照这个思路把“理论带宽下限 3.0ms（5090）/1.1ms（H200）”与“同步次数导致的延迟性质开销”画在同一张图上，使判别实验（换卡后是否变快）的预期更明确。这属于表达方式，不构成候选。

6. Evo-Bench: Can Language Models Improve Agent Harness?

论文 v2（Radar 于 2026-08-11 以 Hugging Face 论文页命中）：https://arxiv.org/abs/2608.09096v2 Hugging Face 论文页：https://huggingface.co/papers/2608.09096 官方代码：https://github.com/RUCAIBox/Evo-Bench 官方数据：https://huggingface.co/datasets/RUC-AIBOX/Evo-Bench 榜单：http://evobench.org/

它是什么

中国人民大学与 BOSS 直聘的基准，测的是模型自主优化“agent harness”（系统提示、工具、循环等可执行脚手架）的内在能力，覆盖 Search、Office 和 General 三个域。注意术语：这里的 harness 指 agent 运行脚手架，与项目的 StreamingModelHarness 属于同一语义家族（都是模型外的执行脚手架），但它是纯文本/CLI 场景，没有流式、时延或语音。这与 2026-08-05 报告中出现过的“环境规模化”类工作里把训练脚手架称为 harness 的用法不同，不可混用。

核心方法

  • harness 敏感任务构造：先用辅助任务进化找出真正对框架改进敏感的任务，剔除非正向敏感度的任务，避免任务表现被基础模型强弱主导。
  • 敏感度感知的分层切分：保证验证集与评测集分布一致且互斥，防止针对具体任务过拟合。
  • 受控的长时程进化：固定 policy 模型，从同一个 CodeAct 种子 harness 出发，预算为 20 轮迭代、1,000 个 evolver step、48 小时，每次 policy rollout 上限 300 步。

论文结果

  • 9 个前沿与开放权重模型参评。GPT-5.6 Sol 排名第 1：Search 44.5（+32.8）、Office 41.6（+3.2）、General 59.4（+11.0）、Overall 46.3（+16.6）；Claude Opus 4.8 的总增益为 +16.1。人工工程基线 Artificial Harness 为 Search 46.7、Office 43.9、General 56.3、Overall 47.5。
  • 三条分析结论：进化行为存在“早期饱和”，模型很快找到高质量结构，随后几轮反而引入有害修改；增益强烈依赖域，Search 增益巨大、General 甚至超过人工工程，Office 因为需要高度特定的处理流程而困难；合成出的 harness 是可迁移的推理结构，在 Qwen、DeepSeek、GLM 等不同 policy 模型上都能带来一致增益。
  • 预算规模实验显示 24 小时/10 轮/500 步 → 48 小时/20 轮/1,000 步 存在正向缩放趋势；同时论文指出部分模型没有用尽预算（如某模型在 15 轮就停止、只用了约 200 步）。

对 StreamingModelHarness 的帮助

编辑判断：唯一值得借用的是选样本的方法，不是自动进化。项目现在用 414/452 的冻结 canary 与错误桶做零退化判定，但没有按“该样本是否对 harness 改动敏感”分层。借用它的做法可以让小收益候选（+1/+4 这一量级）更早显形，也能减少“模型本身强弱”对判定的干扰。

编辑判断：“早期饱和”对项目的直接含义是不要把连续多轮自动改写脚手架当作提升手段——论文观察到后续轮次会引入有害修改，这与项目自身的多条负结果（投机预取、工具清单压缩、强制 candidate-ID）方向一致。

编辑判断：它的分数不能与项目任何指标比较。它是文本/CLI agent 任务的综合分，没有语音、时延、判停或车控执行；不得把 +16.6 这类数字当作“harness 改动能带来的收益上限”。

局限与开放状态

  • 全部任务是文本/CLI 场景；没有流式音频、打断、判停、TTS 或带副作用的动作。
  • 评测依赖固定 policy 模型与来源基准的原生打分器；分数受被评模型版本与外部 API 变动影响。
  • 数据规模在 HF 上标为 n<1K，验证/评测两个 split；小规模基准上的名次差异需谨慎解读。
  • 开放状态（2026-08-12 复核）：论文公开；代码公开在 GitHub 并标 Apache-2.0，仓库含 construction anchors 等制品；数据集公开在 Hugging Face，卡内 license 为 CC-BY-4.0，语言 en/zh；另有公开榜单站点。

7. 本窗口的两篇 TTS 工作：CtrlSpeech 与 SemBridge

CtrlSpeech（2026-08-08，Radar 于 2026-08-11 发现）：https://arxiv.org/abs/2608.08362v1 ；作者项目页 https://zhishengzheng.com/ctrlspeech ；官方代码 https://github.com/zszheng147/ctrlspeech ；官方权重 https://huggingface.co/zhisheng01/CtrlSpeech SemBridge（2026-08-07，Radar 于 2026-08-11 发现）：https://arxiv.org/abs/2608.07462v1 ；demo 页 https://tiamojames.github.io/SemBridge_Demo/ ；仓库 https://github.com/ASLP-lab/SemBridge

它是什么

CtrlSpeech（UT Austin 与 Amazon，Interspeech 2026）在 DiTAR 架构上做“粗到细”可控表达性 TTS：全局说话人条件控音色，音素对齐的音高、音量、时长信号控局部韵律，并支持在第一遍生成之后只改其中一项再重合成。SemBridge（西北工业大学 ASLP 与 Soul AI Lab）是训练期专用的语义 token 锚定框架：用离散语义 token 直接监督连续隐空间自回归 LM 的状态，并用语义对齐的声学 VAE 组织连续目标空间，推理时完全保持连续、不引入量化。

论文结果

  • CtrlSpeech：0.1B 与 0.6B 两个变体，约 20,000 小时英文语音（Emilia 英文子集 + GigaSpeech 子集）预训练，8×A100 训练 5 epoch，推理 32 步、CFG 1.5。零样本 TTS：LibriSpeech-PC test-clean 上 0.6B 为 WER 2.46%、SIM-o 0.65、CMOS -0.16、SMOS 3.81（自行复现的 DiTAR 为 2.55%/0.61/-0.22/3.74，Ground Truth 为 2.40%/0.69）；Seed-TTS test-en 上 0.6B 为 WER 2.58%、SIM-o 0.63。去掉说话人条件后 SIM-o 掉到 0.07。可控性用音高/音量 RMSE 与音素级时长 MAE 报告。
  • SemBridge：零样本 TTS 在 Seed-TTS-Eval 上中文 CER 0.95、英文 WER 1.81、中文 hard 子集 CER 9.79；CV3-EVAL 上中文 CER 3.34、英文 WER 4.22、中文 hard 10.58、英文 hard 6.35。消融显示引入 SA-VAE 把英文 WER 从 2.46 降到 2.22、ZH-Hard CER 从 14.29 降到 13.72。中文 CER 用 Paraformer、英文 WER 用 Whisper-large-v3 计算。

对 StreamingModelHarness 的帮助

编辑判断：两篇都不改变 2026-08-10 已建的 omnivoice-local-tts-16step-v1 候选，也不新增 TTS 候选。原因是同一个：两篇都没有报告首包时间、流式 chunk 时间、取消或打断残留，而项目的问题是 commit→首音频约 3 秒，不是完整句的可懂度。

编辑判断：CtrlSpeech 里真正与项目相关的是“音素级时长可控 + 只改一项再重合成”这一接口形态。如果未来要做“已播放边界处精确截断并重说”，音素级时长与边界是必需信息；这条与第 1 节 PACE 的语义提交边界是同一需求的两端。目前只作为设计线索记录。

编辑判断：SemBridge 的中文 CER 数字看着与 OmniVoice 的 test-zh 口径值接近，但两者 ASR 评测器、测试子集与系统组成都不同，不能横向排名，更不能据此更换候选。

局限与开放状态

  • CtrlSpeech：评测全为英文（LibriSpeech-PC、Seed-TTS test-en、LJSpeech），中文能力未知；派生音素边界依赖 Montreal Forced Aligner 的 english_us_arpa 模型；论文未报告 RTF、首包或流式能力，记未知。开放状态为代码公开（仓库 LICENSE 文件为 MIT，GitHub API 的 license 字段显示 NOASSERTION）、权重公开在 HF 且卡内 license 为 CC-BY-NC-4.0，含 base-150m/600m、control-150m/600m 与 svae 等文件——与 OmniVoice 相同的陷阱：代码可商用不等于权重可商用。

9. flowcat：自托管实时语音运行时（工程参考，不进入候选）

仓库（Radar 于 2026-08-11 发现）：https://github.com/AreevAI/flowcat

它是什么

原生 Rust 的实时语音 agent 运行时，Apache-2.0，仓库自述为 pre-1.0。它刻意镜像 pipecat 的 FrameProcessor 图、Frame 类型体系、系统帧优先级/打断模型和 STT/TTS/LLM 服务接缝，但打包成单个自包含二进制，可在自有 VPC 或完全离网部署，进程内含 SIP/RTP。

值得记录的两点

  • 它的 ContextRelay 机制：把累积的音频上下文转成紧凑文本转写再重新播种会话，使模型重新注意的是廉价文本而不是音频（自述约 7× 更小、每 token 约 4× 更便宜），从而在长通话里不必靠滑动窗口丢弃最早的轮次；代价是被转换的轮次只保留词而丢失韵律，默认关闭。仓库提供了一份独立的评估文档。
  • 它在 README 中主动区分两类指标：单进程从 10 到 2,000 并发通话保持平坦 p99 是容量与运维余量，而端到端语音时延由 STT/LLM/TTS 提供方主导（数百毫秒量级），运行时本身改变不了。

对 StreamingModelHarness 的帮助

编辑判断：ContextRelay 的思路与项目已有的“上下文压缩 + 检索回执用完即弃”是同一族，可作为长时多轮座舱会话的对照设计；但“丢韵律换成本”对项目的判停与情绪相关判断是有害的一侧，必须在同一错误桶上验证而不是直接采纳。

编辑判断：它对“容量指标不等于会话时延”的表述可以直接借用到项目的口径文档里，与第 2 节的测量边界要求配套。

局限与开放状态

  • 自述 pre-1.0；本轮没有运行其任何代码，也没有独立复核 ContextRelay 的 7×/4× 数字与并发 p99 结论，这些均记为仓库自述而非已验证事实。
  • 它是编排运行时，不含全双工模型能力；AEC、声纹、多乘员与车控执行等项目关心的能力在本轮核验范围内未确认，记未知。

  1. 在项目自有回放里加一层 turn-local 播放账本：每个助手轮次记录 turn_id、已下发音频副本、played_samples，客户端按固定间隔回报播放进度，打断时快照边界并撤销尚未播放的缓冲音频。这一步只增加可观测量与撤销能力，不改变任何模型输入。
  2. 把口径文档补齐到可审计：每个时延数字都写清起点（commit 或末次人声）、终点（首 token / 首动作 / 固定音频首包 / 真正内容首音频）、时钟来源，并把“生成出来的前置静音”单列。对照方法照抄 pipecat DGX Spark 仓库的分层归因表结构。
  3. 继续原 HF MoE 与 index_select+bmm fast path 的 5090/H200 输出一致性与 ms/token 判别。本窗口的 KV 与剪枝论文都不替代这项实验。

第二阶段（两个单变量离线实验）

  1. tool-hold-message-first-audio-v1：只增加“工具触发时刻立即播放预合成固定等待语”这一个变量，冻结文本、工具选择、执行器、播放器与 100 条样本；分别记录固定音频首包与真正内容首音频的 P50/P90/P95，并验证工具选择、参数与最终车态逐条一致、固定音频可被立即打断。预计正确性修复数为 0，因此不请求 H20。
  2. playback-boundary-ledger-offline-v1：在第一阶段账本就位后，做“打断时是否注入已播放前缀 + 固定分隔提示”的单变量对照。需要先自建中文车控/清单式打断桶（借用 GCM-Bench 的数据格式与判定协议，但样本、语言与动作全部自造）。门槛是 414 canary 零退化、非打断样本逐条一致、新桶上引用锚定正确率显著提升、首动作时延不变。
  3. 既有 omnivoice-local-tts-16step-v1 保持不变，仍是仅离线、h20_request_allowed=false。本窗口的 CtrlSpeech/SemBridge 不替换它。

第三阶段（评测升级与长期对照）

  1. 把严格工具名召回升级为“工具选择 / 参数 / 最终车态”三层指标，并按 clean/20dB/音色分桶。VoiceChat 的 82.5% 对 44.2% 对 33% 只是外部同向证据，不作为目标值。
  2. 用 Evo-Bench 的敏感度分层思路，对现有错误桶做“是否对 harness 改动敏感”的标注与切分，让小收益候选更早显形。
  3. 若要评估原生全双工后端，把 Lychee-FD 与 VoiceChat 作为独立后端整体对照，并把 GPU 数量、头的放置方式、端点等待时间和语言限制写进实验记录；不拆代码进现有 Harness。

风险提醒

  • 指标偷换风险（本轮最高优先）：同一个 VoiceChat，模型页写约 450ms turn-taking，官方部署仓库量到 1,470.7ms 浏览器 voice-to-voice。任何引用都必须带测量边界。同理，A-PACK 的 prefill FLOPs 与解码吞吐、OasisKV 的并发吞吐都不是 batch=1 单 token 时延证据。
  • “固定等待语”不得掩盖真实首音频：加入 on-hold 语后必须继续报告真正内容首音频，否则首音频指标会被预合成音频人为压低。
  • 播放边界不等于用户理解：PACE 自己把播放当作可观测的保守代理——边界之后的内容不可能被听到，边界之前的内容只是被渲染过。项目不得据此声称用户已理解或已确认。
  • 不可逆动作风险：确认类车控只能在其提案音频已播放完成后提交；聚合意图存在未完成分支时不得提前口播成功。
  • 许可证风险：CtrlSpeech 代码 MIT 但权重 CC-BY-NC-4.0；jina omni 系列 CC-BY-NC-4.0；VoiceChat 与其派生量化权重为 OpenMDW-1.1，需独立审查。代码许可不传递给权重，第三方量化不消除上游限制。
  • 占位仓库风险：A-PACK 写“录用后发布代码”、SemBridge 仓库只有 README、DuplexGen 的 personaplex-finetune 仍是 1 个文件；论文正文的“已发布”措辞必须对着实际产物核验。
  • 修订版重复风险：arXiv:2607.06540v4 与 v3 在主表上完全一致，是 2026-08-06 已覆盖工作的修订版；不得当作新工作重新计数。
  • 重复实验风险：candidate-ID/CMTF、conditional top-2 verifier、投机预取、工具清单压缩、主模型自判停均已有负结果；参数化本体、云监督和 SoulX 只消费 result manifest。
  • 证据日期风险：本报告窗口跨 2026-08-10 至 2026-08-12，因为 2026-08-11 没有已提交报告；窗口内的 HF 论文页与量化镜像不等于当日新论文，报告未使用任何 2026-08-12 之后的证据。
