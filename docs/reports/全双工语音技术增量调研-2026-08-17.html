一、先说结论

今日有新论文，但它们全部来自 2026-08-14 的积压批次，而不是最近两天。 最近两天（08-15 02:30Z 之后）arXiv 全站依然是零投稿零修订。本轮最有决策价值的三件事：一个直接对着项目首音频瓶颈的 TTS 一手制品、一个把“小批量解码”这个词的含义钉死的反面判据、以及一次证明“索引冻结不等于没有论文”的流程验证。

P0：直接命中当前工程短板

  1. VoiceChat-TTS（2608.13831）是迄今第一个同时具备“流式 TTS + 显式打断 + 不重置 KV + 代码和权重都真实存在”的一手制品，直接对着项目首音频约 3 秒这个最大瓶颈。 论文事实：并发 1（即 batch=1，与项目口径一致）下在 RTX A6000 上，声学 token ITL 7.16ms、编解码 2.46ms、合计 9.62ms，而每帧对应 80ms 音频；同口径重测的 Qwen3-TTS-12Hz-1.7B 为 15.44 / 4.90 / 20.34ms。制品事实（本轮现场逐文件核实）：代码确实在 NVIDIA-NeMo/Speech（Apache-2.0、18,144 star）内，nemo/collections/speechlm2/models/duplex_ear_tts.py 等 31 个路径命中；权重在 nvidia/NVIDIA-NemotronLabs-VoiceChat-11B（OpenMDW-1.1、非门控）。编辑判断：这是本周唯一一个能把“本地流式 TTS”从纸面推进到可复核对象的更新，但它不能直接替换 Edge TTS，原因是两条硬事实——它只有英文评测，且 TTS 子模块（977M）被封在一个 44,382,749,892 字节的单一 model.safetensors 里，没有独立发布。详见第 1 节。
  2. DeaMoE（2608.14385）把“小批量解码”这个词的实际含义钉死了，这对项目是一条比任何加速方案都更有用的筛子。 论文事实：标题与摘要都主打 small-batch decoding，但图 3 的横轴从 batch 4 起步，加速比 batch 4 时 1.02×、batch 32 峰值 1.33×、batch 128 回落 1.03×，呈非单调；论文自述“加速比随 batch 由 4 增长到 32 而上升”。编辑判断：项目是 batch=1，位于该曲线起点之外且更低的一侧，按其自身趋势外推收益低于 1.02×，实质为零。更关键的是它是预训练期架构改动（自行预训练 7.3B、110B token），对既有的 Qwen3-Omni 权重不可用。这使它成为“KV/服务反模式家族”的第四个成员，但成因与前三个不同——不是“需要大 batch”，而是“最小可评测 batch 就不是 1”。详见第 2 节。
  3. CoRun（2608.14376）把“固定形状解码”与“输出可复现”绑在一起，这给 decode-loop-cudagraph-static-kv-v1 增加了一个此前没有考虑过、且不依赖时延成败的收益维度。 论文事实：CoRun 用隔离 prefill + 固定形状批量 decode + 固定尺寸 CUDA Graph 取得确定性输出，相对 batch-invariant 方案吞吐提升 15–324%，端到端时延分解为 Standard 19.4ms / Batch-invariant 88.4ms / CoRun 32.6ms。与项目最相关的一条：在其对照实验里，Qwen3-30B-A3B（MoE）的 rollback ratio 为 45.41%，接近同规模稠密模型 Qwen3-32B（24.25%）的两倍，论文解释为“一个很小的 router 扰动就可能改变被选中的专家，此后两条执行路径执行的是不同的计算，而不只是累积不同的低位比特”。编辑判断：项目基座 Qwen3-Omni-30B-A3B 同属 A3B MoE 族，这条机制性结论可迁移；但 45.41% 这个数值不可迁移（它是投机-验证框架下的候选拒绝率，不是“单次 batch=1 推理有 45% 概率不可复现”）。真正该做的是一个零成本自测：同一音频同一 seed 连续跑 N 次，逐 token 比对。详见第 5 节。
  4. 同一篇 DeaMoE 顺带给了 decode-loop-cudagraph-static-kv-v1 第三条独立旁证。 论文原文：“我们也为 DeaMoE 与所有基线启用了 vLLM 的 CUDA Graph 执行。由于解码本身对时延敏感且通常运行在小批量区间，采用 CUDA Graph 是业界降低 kernel 启动开销的通行做法。” 编辑判断：08-14 由 FlashDrive 提出、vToken 佐证的“图捕获兼容性是硬筛子”，现在有了第三个来源，而且是把它当作基线也必须启用的标配而非优化项。这提高了该候选的先验，但不改变执行顺序：仍然先做无同步 index_select+bmm 快路径，再把整环图捕获作为第二个独立变量。

P1：适合形成下一阶段架构

  1. VoiceChat-TTS 的“确定性静音帧”是一个可以脱离其模型单独借用的机制，直接落在项目两个在办候选上。 论文事实：打开 Force Silence 后 IOR@320ms 由 96.8% 升到 100.0%，平均停止时延由 228.3ms 降到 89.9ms，1 秒内泄漏由 169.1ms 降到 55.8ms，后续轮次的 AI-CER 由 0.255% 降到 0.095%，且全程不重置 KV cache。仓库事实（本轮逐行核实）：duplex_ear_tts.py 第 1193 行的 inference_force_speech_silence_on_eos 与 get_codec_silence_frame() 与论文描述逐字对应——编码 10 秒纯静音波形、对每帧的 31 个 token 组合计数、取出现频次最高的那一帧。编辑判断：这条机制的可迁移部分不是模型，而是“把收尾定义成一个确定性的静音写入动作，而不是等待自然衰减”，这正是 playback-boundary-ledger-offline-v1 缺的那一块。详见第 1 节。
  2. DuplexWorld 的数据集正式发布了，但发布的是场景规格而不是评测能力，这个区分必须写清楚。 制品事实：CentificAIResearch/Duplex-World 于 2026-08-15T16:50:32Z 创建，CC-BY-4.0、非门控，标注 arxiv:2608.10716；六个领域文件加 all.jsonl 共 10 个文件，总计 18 条（banking 3、healthcare 2、insurance 2、logistics 1、pathfinding 9、travel 1），all.jsonl 的字节数 103,426 与六个领域文件之和完全相等。每条约 10KB，含 decision_tree、evaluation_criteria、task_params 等 17 个字段。编辑判断：没有音频，没有 harness 代码——而 08-11 记录的 DuplexWorld 最有价值的结论恰恰是“三个 harness 旋钮对 Pass@1 的影响与换系统相当”，那部分依然不可复现。可借用的只有评测标准的字段结构。详见第 3 节。
  1. “用受约束解码去修工具弃权”这条路有了明确的负面证据，项目应当继续不走它。 论文事实（2608.13959，已全文核实）：把约束语法的两件事——规定生成在哪里停止、规定哪些 token 可发——分开测之后，相对无约束解码，弃权列按符号在六个单元格中的五个为负，其中四个区间不含零（0.6B KO 是 −0.5 [−9.5, +8.0]，区间含零），最差 −29.5 个百分点，而没有任何一个单元格出现区间不含零的正效果；分解到最小模型的韩语上是停止 token −20.0、enum +19.5、合计 −0.5；被修复的 698 条弃权中 545 条原本没有可读答案、0 条是评分器拒绝给出的判断。编辑判断：项目当前走的是候选工具集晚注入加确定性执行器校验（已拦住 45% 的失配大头），不是解码期语法约束；这篇支持维持现状。可复用的是它的实验设计——把“停止位置”与“可发 token 集合”当作两个独立变量分别测。注意它测的是弃权，作者说在“需要调用工具”的条目上效果全程为正，不得读成“约束解码总是有害”。详见 6.1。

1. VoiceChat-TTS：面向交互式 Agent 的低时延连续语音合成（NVIDIA）

论文（arXiv v1，2026-08-13T23:37:07Z 提交）：https://arxiv.org/abs/2608.13831

官方代码：https://github.com/NVIDIA-NeMo/Speech

官方权重：https://huggingface.co/nvidia/NVIDIA-NemotronLabs-VoiceChat-11B

它是什么

一个只做语音合成的流式 TTS 模块，由 LLM 的文本 token 流直接驱动，设计目标是在全双工交互中“一直在线”：没有文本可播时输出静音，收到中断控制 token 时立即转静音，并且跨轮次不重置 KV cache。作者为 NVIDIA，第一作者 Edresson Casanova。

同源关系必须先说清楚：这不是一项独立的新工作，而是 08-12 报告已记录的 NVIDIA NemotronLabs VoiceChat 11B 全双工模型的 TTS 组件的单独成文。论文自述“VoiceChat-TTS 的代码已在 NVIDIA NeMo Speech 中公开，模型 checkpoint 作为 NVIDIA-NemotronLabs-VoiceChat-11B 的一部分在 Hugging Face 上提供”。按去重纪律，本节记为同一技术脉络的组件级论文，不计为新的开源模型发布；08-12 记录的那些整机数字（FDB-v3 工具选择 82.5%、参数准确率 44.2%、Pass@1 33%、口语 BFCL-v3 平均 56.1%）与本节的 TTS 数字不可混用。

核心方法

  • 直接消费 LLM 文本 token 流。为解决 LLM 子词词表与 TTS 训练语料不匹配（很多子词在 TTS 语料中罕见或缺失），引入 Character-Aware Subword Encoder：每个输入子词先拆成字符序列再编码。使用 NVIDIA Nemotron Nano 2 的子词 tokenizer。
  • 连续时间轴上的静音建模。解码器跨会话时间持续运行，没有 agent 文本时产生静音，而不是停机等待。
  • 显式中断控制 token。中断以控制 token 注入；Force Silence 打开时，推理会在与中断 token 对齐的位置注入一帧固定的静音音频 token，把生成流确定性地推向静音。该静音帧的取法是：用 codec 编码一段较长的纯静音，取出现频次最高的那个 31-token codec 帧。
  • 不重置 KV cache。中断后模型继续在同一 KV 上生成下一轮，论文用 AI-CER 只统计后续 assistant 轮的方式验证了恢复能力。
  • 架构规模：全模型 977M 参数 = 778M 基于 Gemma 3 的流式 TTS 模块 + 199M codec 模型。输出 22kHz 波形，帧率 12.5Hz，31 个 codebook，每个音频 token 帧对应 80ms 音频。
源内命名不一致，本报告不代为取舍：对照模型的名字是 Qwen3-TTS-12Hz（12Hz），而论文正文两处均写“同样工作在 12.5 Hz”。两个值都记录。

训练配置（用于估计迁移代价）：第一阶段仅用单轮 TTS 数据预训练 1.4M 步、8 张 A100；第二阶段用完整混合数据微调 200k 步、32 张 H100。微调用 Lhotse 动态分桶，每批约 240 秒音频；数据配比为单轮 TTS 40%、词与专名列表 15%、真实对话 10%、合成全双工对话 35%。优化器 AdamW，学习率 4×10⁻⁵。

对 StreamingModelHarness 的帮助

分三层，且第三层是否定性的。

第一层，它是项目首音频瓶颈方向上第一个制品齐全的一手对象。 项目首音频 P50 为 2,918ms（A）／3,491ms（B），而首文本最快只要 131ms，瓶颈明确在 Edge TTS。此前 TTS 方向的候选 omnivoice-local-tts-16step-v1 一直卡在 Luna-TTS 项目页无代码、无权重、无许可证且页内自相矛盾（1.28s 块 vs 0.36s 块）的状态上，其 41.6ms 至今不可用于跨系统比较。VoiceChat-TTS 的不同之处在于代码与权重都能逐文件核到，并且它的时延是在并发 1 下测的，与项目 batch=1 的口径一致，不需要做并发折算。

第二层，Force Silence 是可以脱离模型单独借用的机制。 项目的 playback-boundary-ledger-offline-v1 与 tool-hold-message-first-audio-v1 都缺一个明确的“收尾动作”定义。VoiceChat-TTS 给出的形式非常具体：把收尾实现成在中断对齐位置确定性地写入一个预先算好的静音帧，而不是让声学流自然衰减；且写入后不重置 KV，模型仍能正常产出下一轮。它给出的收益量级是停止时延 228.3→89.9ms、1 秒泄漏 169.1→55.8ms。编辑判断：项目可以在自己的播报链路上实现同构的“确定性收尾写入”，但这两个数字不能借用为项目的预期值——它们是在英文 FDB 音频上、用该模型自己的 codec 帧测的。

第三层，它现在还不能替换 Edge TTS，有两条硬阻断。

2. DeaMoE：把“小批量解码”的下界钉在 batch 4（反面判据）

论文（arXiv v1，2026-08-14T15:25:32Z 提交）：https://arxiv.org/abs/2608.14385

它是什么

一个 MoE 架构改动：把专家分组为若干“部门（department）”，同部门专家共享大部分参数、各自只保留少量私有参数，并配一个两阶段路由（先路由到部门、部门内再分配到专家），目的是减少解码时反复加载专家权重的访存量。作者来自中国科学技术大学等。

本节把它写成反面判据，因为它对项目的价值不在于能不能用，而在于它精确定义了一个此前被含混使用的词。

核心方法

  • 专家按“专业领域”分组进部门，同部门共享公共骨干参数，每个专家仅保留少量私有参数以体现差异。
  • 两阶段路由：先把所有 token 路由到对应部门，部门一次性统一处理收集到的全部 token；再由部门把 token 分给具体专家做差异化处理。目的是提升单个解码步内跨 token 的权重复用。
  • 实现上集成进 vLLM v0.13.0，用 Triton 实现自定义算子，复用 vLLM 原生 fused MoE kernel 所用的 Grouped GEMM 原语，只改 token 索引逻辑。

论文结果

  • 摘要：相对 vanilla MoE，每步加载权重最多减少 50.9%；预训练 7B 模型在 A40 上端到端 TPOT 最高 1.33×；DeepSeek-V3 在 A40 与 H100 的微基准峰值分别为 2.00× 与 1.97×。
  • 端到端（图 3，单张 NVIDIA A40，vLLM，连续请求流）：加速比 1.02×–1.33×，随 batch 非单调变化。逐点标注为 batch 4→1.02×、8→1.14×、16→1.26×、24→1.32×、32→1.33×、40→1.30×、48→1.26×、64→1.20×、96→1.13×、128→1.03×。论文原话：“加速比随 batch 从 4 增长到 32 而上升（峰值 1.33×），随后逐渐下降，在 batch 128 时接近 1.03×。”
  • 吞吐口径：TPOT 预算 30ms 时基线与 DeaMoE 分别支撑 batch 64 与 96（1.50× 吞吐）；20ms 预算时为 24 与 44（1.83× 吞吐）。
  • 模型质量：自行预训练 7.3B 的 DeaMoE 与等预算标准 MoE，各用 110B token（RedPajama-v1）。困惑度 PTB 61.91 vs 64.33、WikiText-103 20.31 vs 20.18、WikiText-2 20.33 vs 20.43，论文结论是质量持平。
  • 微基准 batch 范围同样为 4 到 128。

对 StreamingModelHarness 的帮助

它的帮助是让项目少做一次评估，并给一个既有候选加一条旁证。

第一，它给出了一条可直接复用的筛子。 项目此前的反模式家族判据是“收益需要大 batch 或长上下文”（OasisKV、vToken）。DeaMoE 不属于这一类——它明确面向低时延交互、明确反对大 batch。但它最小的评测点就是 batch 4，且加速比在 batch 4 处仅 1.02×、并随 batch 减小而下降。项目是 batch=1，按其自身趋势外推收益低于 1.02×。编辑判断：应把家族判据从“需要大 batch”扩写为“最小可评测 batch 是否为 1；若不是，且收益随 batch 减小而单调下降，则直接否”——这条更普适，且能一次性挡掉整类以“small-batch”为卖点却从 batch 4 起步的工作。

第二，即使 batch 口径吻合，它对项目也是不可用的。 两条独立原因：(a) 它是预训练期架构改动，论文自述采取“pre-training-first”路线、从零预训练；项目用的是既有的 Qwen3-Omni 权重，无法套用。(b) 它攻击的瓶颈是访存带宽（专家权重加载），论文原话是“有效降低了每个解码步的访存流量，从而缓解 A40 GPU 上的带宽瓶颈”；而项目已实测自身瓶颈不是带宽——解码速度不随 KV 长度变化，实测 110ms 是按 config 实算的带宽下限（5090 口径约 3.0ms）的约 36 倍，根因是每 token 约 816 次 GPU→CPU 同步。同一个词“解码慢”，两边指的是完全不同的东西。

第三，它为 decode-loop-cudagraph-static-kv-v1 提供了第三条独立旁证，且是最强的一种形式。 论文在实现小节写：“我们也为 DeaMoE 与所有基线启用了 vLLM 的 CUDA Graph 执行。由于解码本身对时延敏感且通常运行在小批量区间，采用 CUDA Graph 是业界降低 kernel 启动开销的通行做法。” 编辑判断：这不是把图捕获当成一项优化来宣传，而是把它当作基线也必须具备的标配，否则对照不公平。这抬高了该候选的先验。但顺序不变：项目仍须先落地无同步 index_select+bmm 快路径，再把整环图捕获作为第二个独立变量单独测量，两步不得合并成一次结论。

一条仅供参考、不可直接相减的量级观察：DeaMoE 的基线（未经其架构改动的 vanilla MoE，vLLM，已开 CUDA Graph）在 A40 上于 20–30ms 的 TPOT 预算内可支撑 batch 24–64。项目在更强的 H20 上、batch=1、却是 110ms/token。四条免责必须同时写：模型不同（7.3B vs Qwen3-Omni 30B-A3B）、框架不同（vLLM vs HuggingFace）、硬件不同（A40 vs H20）、batch 不同（≥4 vs 1）。因此这不能作为“110ms 高出多少倍”的定量依据，只能作为一条与项目自身根因分析方向一致的定性佐证——即 110ms 更像实现问题而非硬件问题。

5. CoRun：固定形状解码同时买到确定性，这对项目的判定链路是一条新论据

论文（arXiv v1，2026-08-14T15:17:14Z 提交）：https://arxiv.org/abs/2608.14376

它是什么

一篇 cs.OS / cs.PF 的推理系统论文（南京大学 + 腾讯 Hunyuan）。它要解决的不是速度，而是同样的 prompt、同样的采样参数与随机种子，LLM 推理却给出不同 token 序列这一确定性问题。之所以纳入本报告，是因为它给项目在办候选 decode-loop-cudagraph-static-kv-v1 增加了一个此前完全没有考虑过的收益维度，并且顺带给出了一个关于项目所用模型族的具体数字。

按既有记忆的补漏规则，这篇是靠新增的 cat:cs.HC OR cat:cs.OS 第 14 组查询捞到的——它不在标准 13 组的覆盖范围内。

核心方法

  • 论文把非确定性的主因归为批次相关的 GPU 执行：动态输入形状会改变 kernel 的 tiling 与浮点归约顺序。
  • 既有做法是用 batch-invariant kernel，但论文测得这类 kernel“使时延增加 2 倍以上，并使服务吞吐下降最多 74%”。
  • CoRun 的观察是：多数 kernel 虽然不是 batch-invariant，却是 position-invariant。因此改为控制每个请求看到的执行形状，再保留更快的 position-invariant kernel。
  • 具体手段：隔离 prefill + 固定形状的批量 decode，decode 走固定尺寸的 CUDA Graph；decode 阶段关闭 attention Split-KV；对少数非 position-invariant 的算子使用确定性 collective；采样器与形状对齐。
  • 论文把这套保证写成一份端到端确定性契约，并明确该契约“不声称跨硬件的可复现性”，只在固定硬件、软件栈、模型与张量并行度下成立。

论文结果

  • 摘要：在 Qwen 与 DeepSeek 等不同架构上，CoRun 在保证确定性的同时，相对 batch-invariant 方案吞吐提升 15–324%，平均首 token 时延降低 51.8%、每输出 token 时延降低 48.6%。
  • 图 1(b) 的端到端时延分解（三档对照）：Standard 19.4ms、Batch-invariant 88.4ms、CoRun 32.6ms。
  • 确定性验证用 vLLM 自带的 batch-invariance 测试：每个模型生成 32 条 prompt，先以 batch size 1 执行、再作为 batch 32 的一部分执行，temperature 0.6、seed 42、每条最多 8 个输出 token，比较完整 token 序列与每步采样 token 的 log 概率。
  • 与项目直接相关的一条数字（图 14b，对照方案 LLM-42 在 ShareGPT 上、64 token 验证窗口下的 rollback ratio，定义为被拒绝的候选 token 数除以在非确定性快路径上生成的 token 总数）：Qwen3-8B 17.94%、Qwen3-32B 24.25%、而 Qwen3-30B-A3B（MoE）达到 45.41%，接近同等规模稠密模型 Qwen3-32B 的两倍。论文给出的解释是：“一个很小的 router 扰动就可能改变被选中的专家，此后两条执行路径执行的是不同的计算，而不只是累积不同的低位比特。”

对 StreamingModelHarness 的帮助

这篇的价值在于它把“图捕获”从一个纯时延议题，扩成一个同时关乎判定可信度的议题。

第一，它是 CUDA Graph 的第四条独立旁证，而且是唯一一条把固定形状与确定性绑在一起的。 08-14 的 FlashDrive 把图捕获写成前置条件、vToken 把兼容性写成硬约束、本轮的 DeaMoE 把它当作基线标配，三者都只谈性能。CoRun 说明：固定形状的 decode + 固定尺寸 CUDA Graph 同时是可复现输出的实现手段。

第二，这条与项目当前优先级第一的事项直接咬合。 项目最高优先级是判定器处理不变性检查（源于 2608.12880：只翻转与行为无关的元数据就改变了 180 条中的 31 条判定）。CoRun 指出的是同一问题的更底层一层：如果解码本身在数值上不可复现，那么“414 canary 零退化”这类判据就可能在测量噪声。编辑判断：项目的 KV 长度逐步增长，形状并非固定，因此 tiling 与归约顺序在每一步都可能变化；StaticCache + 图捕获会把这一维度钉死。这给了 decode-loop-cudagraph-static-kv-v1 一个此前没有的第二收益，且这个收益不依赖它在时延上是否成功。

第三，那个 45.41% 必须被非常谨慎地引用。 项目基座是 Qwen3-Omni-30B-A3B，与论文测的 Qwen3-30B-A3B 同属 A3B MoE 族。论文给出的机制性结论——router 扰动会改变专家选择，使两条路径执行完全不同的计算而非仅仅低位比特差异——是架构层面的，对项目的 MoE 同样适用，这是可迁移的部分。但那个 45.41% 本身不可迁移：它是在 LLM_42 的投机-验证框架下、ShareGPT 语料、64 token 验证窗口、高并发条件下测得的“被拒绝候选 token 占比”，不是“单次 batch=1 推理有 45% 概率不可复现”。项目若要知道自己的数值稳定性，只能自测——而这恰好是一个零成本、不需要 GPU 申请的实验：同一条音频、同一 seed、连续跑 N 次，逐 token 比较输出。

可执行动作（本轮新增建议项，不新增候选）：在做任何判定器审计之前，先做一次解码可复现性自测——固定输入与 seed 重复运行，记录 token 序列是否逐次一致、以及首次分歧出现在第几个 token。若存在分歧，则所有既有的 ±1/±4 结论都需要重新评估其显著性；若不存在，则记为一条有价值的负结果并写进判定协议。这条实验的单变量清晰、可测、无需 GPU 申请，但它测的是评测环境本身而非被测系统，因此按既定规则留在报告而不进入候选。

2608.14333 — Beyond Capacity / DASH（cs.AR，KAIST，13+ 页）。不采纳，但本轮必须更正一处我方此前的表述。

更正：此前把它与“需要大 batch”一类并列是不准确的。全文核实后：它明确评测了 B=1——图 9(a) 的批扫描包含 B ∈ {1, 4, 16, 64}，二十组序列长度扫描全部在 B=1，前瞻研究也在 B=1。因此批大小判据抓不住它。真正否掉它的是容量墙前提：论文立论是被调研 MoE 权重占用 281 GB–1.5 TB、专家权重占总权重 94.1–98.8%、单模型权重即超过 H100 的 80GB HBM，因而必须从闪存流式取专家。项目的 Qwen3-Omni-30B-A3B 在单张 96GB H20 上放得下，从不触碰这堵墙。

另两条独立否决：硬件不存在（DASH 是基于高带宽闪存 HBF 的仿真架构，论文自陈“公开的 HBF 资料未给出子阵列级并行度”“由于尚无具体 HBF 规格，我们把读时延 t_R 从 1 扫到 32µs”）；全部主结果是仿真输出，真实硬件只用于算子测速（一张 NVIDIA H100 PCIe 80GB 与一颗 Intel Xeon Platinum 8452Y）。

一处必须记录的源内不一致：摘要写“可达 1.94× 更高吞吐与 1.90× 端到端加速”，而 1.94× 这个值在全文正文中一次都没有再出现、也没有对应的条件说明；同时“1.90×”被归给两个不同条件——引言说是 B=4 下五模型几何均值、§VI-B 说是跨全部五模型与全部四个批大小的几何均值；端到端一侧则有三种说法：摘要的 1.90× 对应 47.4% 降幅、引言写 44.8%、§VI-B 写 42.2%。四个值全部原样记录。

一条值得单独留存的机制（与项目的既有负结果直接相关）：DASH 把路由 logit 重写为 P = α(P_base + P_attn)，其中 α = 1/RMS(·) 是同一 token 所有专家共享的正标量，因而只改变量级、不改变排序，于是 top-k 可以在残差相加与 RMSNorm 之前精确算出。这是非投机的——与项目已实测为负优化的投机预取性质不同，它不猜、结果与常规 top-k 完全一致。但它在论文里的收益是掩盖 NAND 读启动时延，B=1、t_R=3µs 时 Qwen3 的 TPOT 仅降 3.86%；项目没有闪存读要掩盖，预期收益约等于零。制品：无作者仓库；其基座仿真器 scale-snu/LLMSimulator 是 MIT 但版权属首尔大学、非本文 KAIST 作者，且不含任何 DASH 代码（4 次提交，最后一次 2025-10-14）。

规模与方法核实无误：8,135 条试验记录规范化，240 条开放编码记录中保留 238 个有效唯一标签，最终 12 种模式，528 组配对三元组（raw / workflow / skill 同任务）。技能相对 Workflow Memory 高 6.06 个百分点（61.9% 对 55.9%，自助 95% 区间 [+0.76, +11.36]）；程序性锚定占 65.7%、显式知识注入仅 4.5%。
