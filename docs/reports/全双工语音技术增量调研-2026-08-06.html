先说结论

P0：立即补入评测或前端对照

  1. Streaming Endpointer：直接命中 probe_turn_end 失败后的判停空缺。论文在固定 160ms 中位延迟下把单流 cutoff 从 12.23% 降到 7.01%，双流从 7.61% 降到 4.76%；但 SpokenWOZ 重叠少，Moshi 结果是模拟交互，必须重做中文座舱双讲。
  2. Audio2Tool + MIST 评价口径：前者补参数、改口、多轮和背景有效意图，后者用代码执行后的最终状态衡量成功，正好把当前“严格工具名”升级为“工具序列 + 参数 + 最终车态 + 误执行”。
  3. 增强强度扫描：论文证明增强器对听感和 ASR 的影响可相反，且最佳幅度强度依赖识别器。它适合成为 AEC/NS 上线前的诊断门，不是新的 AEC 算法。

P1：多人座舱与故障定位

  1. TPI-Bench：用同文本、单说话人硬负例检查模型是否真正利用声学说话人变化；最适合补第三方改参、取消、确认和背景插话回归。
  2. QiangDa：用同一真实双人混音分别提示 A/B，并要求输出切换目标身份，能发现“无论提示谁都输出最响者”的视觉旁路；但它是完整话语非因果提取，不能直接接在线链路。
  3. Model or Harness?：41 类交互故障适合作为现有 phase 埋点的归因结构。它只有 40 个说明性案例，不能当故障率基准。

P1/P2：服务层 shadow benchmark，暂不迁移主链

  1. M*：Walk Graph 能表达 Qwen3-Omni Thinker–Talker、codec 流和多组件调度，论文也给出 H200 上的吞吐优势；但该结果不是当前单请求 H20、中文车控或外挂 TTS 的证据。先做隔离对照，再决定是否迁移。

1. Streaming Endpointer：NAC 特征与标签延迟判停

来源：论文正文 / arXiv:2506.07081v2；作者机构发表页；作者官方仓库。

arXiv v2 与 ASRU 2025 同题论文、官方仓库属于同一工作，不重复统计。

论文事实：问题与方法

  • 固定静音 VAD 会增加不必要等待；低延迟帧级端点器又容易把句中停顿和填充词误判为话轮结束。
  • 单向 LSTM 逐帧预测 user、user-end、system、system-end 四类。
  • 输入可为 Mel，也可为冻结 EnCodec、AudioDec 或 Mimi 的流式码本向量。
  • 单流模型处理混合音频，并加入已知系统活动标记；双流模型分别处理用户与系统音频。
  • 标签延迟训练把监督目标后移若干帧。25Hz 下 τ=1/2 对应 40/80ms；推理不再额外添加固定等待规则。
  • 评测使用 SpokenWOZ 双声道对话，阈值扫描 0.7–0.99。ep50/ep90 只统计没有提前触发的样本，提前触发由 ep-cutoff 单独统计。

论文事实：明确结果

  • 固定 ep50=160ms，单流 Mel、τ=0 为 12.23% cutoff / 560ms ep90；Mimi、τ=2 为 7.01% / 560ms，cutoff 相对下降 42.7%。
  • 同一 ep50，双流 Mel、τ=0 为 7.61% / 520ms；Mimi、τ=1 为 4.76% / 600ms，cutoff 相对下降 37.5%，但尾延迟增加。
  • Mimi 编码器与量化器为 38.34M 参数；单流/双流端点器为 3.5M/6.9M。
  • 在 700 个模拟查询上接入 Moshi，温度 0.7 时中位响应延迟从表格所列 1,690ms 降到 412ms，ep90 从 4,575ms 降到 812ms，cutoff 从 46.51% 降到 21.15%。
  • 正文叙述曾把同一基线写为 1,640ms，本报告采用表格值，不把两个数字混用。

编辑判断：对当前项目的帮助

先比较三组，而不是直接引入完整 Mimi：

现有静音/语义门
Mel + label delay
Mimi + label delay

单流可把外挂 TTS 播放状态作为 system-activity；如果 AEC 能提供近端用户流和远端播放参考，再增加双流组。所有组都要在中文犹豫、导航槽位、20dB、真实座舱噪声、AEC 残留和双讲中同时报告 cutoff、ep50、ep90、GPU/CPU 占用和提前工具提交。

局限、开放状态与优先级

  • SpokenWOZ 的真实重叠很少；Moshi 实验为模拟交互，不是真实人机双讲。
  • 该方法只决定用户话轮结束，不识别第三方身份、附和或真正插话，也不降低当前 110ms/token。
  • 官方仓库为 Apache-2.0，含训练和指标代码；未见论文端点器权重或 Moshi 集成代码。论文为 CC BY 4.0。
  • 仓库后来增加 HumDial 英/中文支持，但论文没有中文结果；“有数据管线”不等于“已有中文可部署模型”。
  • 建议优先级：P0。

2. Where Speech Enhancement Hurts Recognition：增强强度诊断

来源：论文正文 / arXiv:2607.11157v1；实验所用 ClearerVoice-Studio 官方仓库。

ClearerVoice-Studio 是实验所用增强器的上游项目，不是本文诊断方法的代码发布。

论文事实：问题与方法

  • 语音增强能提高感知质量，却不一定降低 ASR WER；“伪影”和“过抑制”无法定位是幅度还是相位修改造成损失。
  • 对 STFT 复掩码 M=Ae^{jφ} 做推理时投影 M_{α,γ}=A^αe^{jγφ}，分别扫描幅度强度 α 与相位修正 γ。
  • 增强器与 ASR 都冻结，不进行联合训练。
  • 评测使用 VoiceBank+DEMAND 的 1,648 条 16kHz 测试音频、5 类噪声和 8 个 SNR；没有混响。WER 采用 micro-average，并做配对 bootstrap。

论文事实：明确结果

  • Whisper-large-v3 在未增强音频上的平均 WER 为 6.6%；六个增强器中只有 MossFormerGAN-SE 改善到 6.0%，其余为 6.7%–11.4%，尽管感知质量指标总体改善。
  • FRCRN 诊断中，Whisper 的最佳幅度强度为 α*=0.25；相对 noisy 显著改善，而 α=1 与 noisy 无显著差异。
  • wav2vec 2.0 随 α 增大近单调改善，说明最优强度依赖识别器。
  • 在各识别器最优 α 上加入所测相位修正会显著恶化 WER。
  • 从固定全局 α 到按 SNR oracle，wav2vec 2.0/Whisper WER 为 10.2%→10.0% 和 5.6%→5.4%；按句 oracle 可到 7.8%/3.7%。这些是 oracle 上界，不是可部署算法结果。

编辑判断：对当前项目的帮助

把 AEC/NS 后处理增加可扫的增强强度，并分别为“送 ASR/模型”和“给人听/录音回放”选参数。上线门槛必须包括中文 CER、数字与槽位、工具参数、最终车态和端点错误；PESQ/STOI 只能作为辅助指标。

如果 AEC 后处理不能表示为 STFT 掩码，则不能机械套用该投影。即使能表示，论文也没有验证非线性回声、双讲、流式因果性、RTF 和处理延迟。

局限、开放状态与优先级

  • 单一英文数据集、无混响；最佳 α 会随 ASR、增强器、噪声和域变化。
  • “相位无益”只适用于被测增强器的相位估计，不能外推为所有相位处理都无价值。
  • 本文方法代码、权重和许可证：未知。上游 ClearerVoice-Studio 的 Apache-2.0 不能自动视为本文方法的许可证。
  • 它不解决 AEC 本体、判停、TTS 或 110ms/token。
  • 建议优先级：P0 作为上线诊断，P2 才考虑研究性改造。

3. Audio2Tool：把语音工具失败拆成八级

来源：论文正文 / arXiv:2604.22821v2；作者官方项目页；官方数据页。

论文事实：问题与方法

  • 基准覆盖智能汽车、智能家居和可穿戴设备，共 152 个函数，并把任务分成八级：直接指令、参数、多意图、隐式推理、长音频中的有效指令、句中改口、4–8 轮对话、主说话人与背景有效意图混合。
  • 语音由 Qwen3-TTS、CosyVoice-3 和公开说话人参考合成，再加入汽车、室内、babble、mechanical hum 和 impulsive noise。
  • Tool Accuracy 检查工具名或有序工具序列；Exact Match 还要求全部参数归一化后正确；Slot F1 是参数级 micro-F1。

论文事实：明确结果

  • 论文正文给出约 29,680 条查询；官方 HF v1.0 卡片列出的查询条目和音频文件口径与正文没有完全对齐，因此不把二者混为同一精确规模。
  • Qwen3-Omni-30B 在 Tier 1 的 Acc/EM 为 92.4/92.4；Tier 7 的 Acc/EM/F1 为 54.6/16.3/26.8；Tier 8 为 41.7/12.4/19.9。
  • Whisper-v3 + Gemma-27B 在 Tier 8 为 50.5/15.7/25.6，高于 Qwen3-Omni-30B，说明端到端 SpeechLM 没有稳定压过强级联。
  • 工具准确率明显高于完整参数 EM，证明“工具选对”不能代表“动作可安全执行”。

编辑判断：对当前项目的帮助

优先把 Tier 2/3/6/7/8 映射到 52 组近义工具和现有 452/1,566 条语音池：

  • 参数与数字；
  • 聚合多意图和有序工具序列；
  • 句中改口、取消与补偿；
  • 4–8 轮状态；
  • 主说话人与背景有效指令混合。

指标必须扩成工具序列、参数、最终车态、误执行和失败阶段，不能只沿用严格 api_name。

局限、开放状态与优先级

  • 全部语音为合成，不含真实座舱回声、混响、阵列波束和自然重叠。
  • 论文主体查询规模与公开 v1.0 数据卡口径未解释对齐关系。
  • 官方 HF 数据为 CC BY-NC 4.0；底层语料受各自条款约束。官方 GitHub 主要是项目演示与少量脚本，完整 benchmark pipeline 及其许可证：未知。
  • 建议优先级：P0 借鉴分层和指标；公开数据仅作为研究参考。

4. MIST：数字孪生上的最终状态评测

来源：论文正文 / arXiv:2605.06897v1；作者官方项目页；作者官方仓库。

论文事实：问题与方法

  • MIST 在合成 Home State 数字孪生上评测语音工具代码、动态设备状态、空间约束、歧义澄清、冗余/no-op、纠正和 mixed-initiative 对话。
  • 论文报告 10,000 段对话、88.1 小时语音、平均 5.6 个用户轮次、50 类设备和 27 个 API。
  • 工具代码被实际执行并更新 Home State；Execution Match 比较执行后的最终状态，Exact Match 比较生成代码。

论文事实：明确结果

  • Qwen3-Omni 的 Execution Match/Exact Match 为 59.86%/47.19%，Gemini 2.5 Pro 为 79.53%/65.56%。
  • 对话动作 Macro F1/Accuracy：Qwen3-Omni 为 14.54/28.64，Gemini 2.5 Pro 为 46.00/66.73。
  • Previous State 基线达到 71.62%，因为约 71.6% 样本不需要改变设备状态；因此 Execution Match 单独使用会被 no-op 抬高。
  • 300 个样本的专家复核中，对话动作多数票正确率为 92.33%；141 个需要代码的样本中代码正确率为 92.91%。

编辑判断：对当前项目的帮助

将当前严格工具名升级为三层：

生成层：工具与参数是否符合 schema
执行层：执行器是否接受、是否幂等、是否触发补偿
环境层：最终车态是否达到目标，是否误改其他状态

同时设置 no-op、澄清、设备不存在、改口、撤销/补偿和 overtriggering 独立分桶，避免总体平均被“不执行即可正确”的样本抬高。

局限、开放状态与优先级

  • 数据、住宅和语音均为合成英语；噪声不覆盖真实座舱回声、多人或流式打断。
  • Execution Match 必须与 Exact Match、动作类型和安全错误同时报告。
  • 论文声称发布数据和生成框架，但官方仓库目前只有演示/少量样例，未见完整 10,000 段数据、生成器、评测实现或模型权重；许可证：未知。
  • 建议优先级：P0 借鉴最终状态和 no-op 口径，P1 等待可用工件。

5. TPI-Bench：第三方插话与声学硬负例

来源：论文正文 / arXiv:2604.17358v1；作者官方项目页；作者官方仓库；官方数据页。

论文事实：问题与方法

  • 模型可能把主用户与第三方的连续语音拼成一条指令，也可能依赖语义矛盾等文本捷径，而不利用声学说话人变化。
  • TPI 将插话分为 actionable 与 ignorable，覆盖 7 个上位类别、26 个细分场景。
  • hard negative 保持文本完全相同，但用主说话人的单一声音重合成，迫使模型区分“文本像插话”和“声学上确有换人”。
  • 基于 Qwen2.5-Omni-7B 做 LoRA SFT；任务是收到完整语音后输出文本，仍为 turn-based。

论文事实：明确结果

  • 论文将 TPI-Train 圆整为约 88K；官方 HF 当前元数据为 80,571 条双说话人训练样本与 7,519 条单说话人 hard negative。
  • TPI-Full 在 TPI-Test 上的 RSF/OH 为 0.83/4.16，Qwen2.5-Omni-7B 基线为 0.24/3.22。
  • Janus-Test 上 TPI-Full 的 RSF 为 0.16、OH 为 4.80；这里 RSF 是把单说话人误判为插话的比率，越低越好。原始基线 RSF 为 0.12，说明收益伴随误报权衡。
  • 100 条真实语音上，RSF 从 0.17 提到 0.60，OH 从 3.21 提到 4.25。
  • A/B 人评中 TPI-Full 获得 60.5% 偏好，基线 28.0%，平局 11.5%。

编辑判断：对当前项目的帮助

在 Harness 中显式记录 primary_speaker_id、interrupter_id、插话位置和可处理策略，并增加：

  • 同文本不同声纹与说话人交换；
  • 第三方参数注入、取消和确认；
  • overlap 期间提前 endpoint/提前工具提交；
  • 打断后恢复、改口和补偿。

actionable 只表示内容值得纳入回答，不表示第三方获得工具权限。第三方内容应默认 advisory_only；高风险动作仍要主用户 principal/capability 校验和重确认。

局限、开放状态与优先级

  • 论文明确为轮次式，不评估持续监听、何时说话和真正全双工调度。
  • 主体语料为 TTS 合成，真实测试仅 100 条；物理动作和视觉任务被排除。
  • 官方项目、数据和 pipeline 已公开，但许可证信息冲突：论文称 MIT，仓库 README 称 Apache-2.0，当前未见可核验的根 LICENSE，HF 数据卡也无许可证字段。因此代码和数据许可证均记为 未知。
  • 未见 TPI-Full 官方权重。
  • 建议优先级：P1；先移植反事实评测，不直接微调主模型。

6. QiangDa：音视频目标说话人的成对身份忠实度

来源：论文正文 / arXiv:2608.03964v1；VoxBlink2 官方项目页；VoxBlink2 官方仓库。

论文事实：问题与方法

  • 音视频目标说话人提取器可能忽略视频提示，无论提示 A 还是 B 都输出声学上占优的同一人。
  • QiangDa 共同录制中文双人重叠语音，每场景含 A-only、B-only 参考和 A+B 重叠段，并同步三机位视频。
  • 模型用冻结 AV-HuBERT 视觉特征，经投影后在 TF-GridNet 各 block 后以 FiLM 重新注入目标条件。
  • 推理使用完整话语、非因果处理，不是流式前端。

论文事实：明确结果

  • QiangDa 含 77 个场景、14 对说话人、7,598 个片段、11.84 小时；6,038 个混音可评。
  • 每个混音分别提示 A/B，因此形成 12,076 个目标输出行，不是 12,076 条独立录音。
  • VoxBlink2-AVSE 为从 VoxBlink2 派生的 250,828 对音频—嘴部 ROI、28,421 个身份、766.17 小时。
  • 最佳归档 checkpoint 的 CER 为 0.2261，strict correct 为 82.22%，wrong speaker 为 5.33%，both-output strict 为 69.53%。
  • both-output strict 的分母是 6,038 个混音，要求同一混音提示 A/B 时两次都通过严格身份判定。

编辑判断：对当前项目的帮助

把“同一混音切换目标提示必须切换输出身份”加入多人座舱前端回归，并单独测：

  • 目标身份与干扰身份相似度差；
  • 残留重叠；
  • 首包、目标切换和稳定时间；
  • 遮挡、离屏说话、座位变化和 chunk 边界。

它只能提供“当前声音更像哪个目标”的信号，不能证明真实身份或操作权限，不能直接作为车控授权凭据。

局限、开放状态与优先级

  • 仅中文朗读、固定位置双人、14 对说话人；依赖可见且同步的嘴部视频。
  • 完整话语非因果推理，没有流式延迟和增量稳定性数据。
  • 未见 QiangDa、VoxBlink2-AVSE 或最佳 checkpoint 的官方可下载页，因此开放状态和许可证为 未知。
  • 原始 VoxBlink2 官方仓库的 CC BY-NC-SA 4.0 不能自动证明派生数据已按同一条款发布。
  • 建议优先级：P1 作为前端评价；P2 才研究因果化。

7. Model or Harness?：交互边上的故障归因

来源：论文正文 / arXiv:2607.28802v1；Hugging Face 论文页。

HF 页面是同一 arXiv 工作的论文镜像，不是额外代码发布。

论文事实：问题、方法与结果

  • 系统级失败无法判断修复应落在模型、Harness、工具、环境还是 grader。
  • taxonomy 从最终失败沿因果链回溯，标注“最早且未恢复的故障”，并以交互边、责任侧和 failure mode 表示根因。
  • 共 41 类，其中 36 类归模型侧、5 类归周边组件侧。
  • 在 40 个说明性案例上，GPT-5.5 类别 exact match 为 0.80、macro-F1 为 0.69、相对人工标签 Cohen's κ 为 0.76；完整 failure-mode exact match/F1 为 0.72/0.64。
  • 四裁判至少三票一致时，类别 precision 0.83、coverage 90%；全票一致时 precision 0.96、coverage 68%。

编辑判断：对当前项目的帮助

给现有 phase 埋点补充：

edge: audio→endpoint / endpoint→model / model→search / search→candidate
      / model→call / call→executor / executor→vehicle / result→KV / text→TTS
fault_side: producer | consumer | environment | grader
first_unrecovered_failure
evidence
abstain_reason

这样可以区分 ASR 漏词、RAG 未召回、候选外工具、模型参数错、执行器拒绝、车态未落地和 TTS 超时，避免把同一个最终失败全部归到模型。

局限、开放状态与优先级

  • 40 个案例不能估计真实故障频率；taxonomy 也没有覆盖全部实时音频边。
  • 自动归因仍会错，事故和安全问题必须人工复核，证据不足时应 abstain。
  • 未找到作者发布的独立 taxonomy 数据包、代码或许可证，开放状态为 未知。
  • 建议优先级：P1，低成本引入日志与复盘规范。

8. M*：复合多模态模型的 Walk Graph 服务

来源：论文正文 / arXiv:2606.12688v2；作者官方项目页与文档；作者官方仓库。

论文事实：问题与方法

  • 围绕单一自回归循环设计的 serving 很难统一表达 Thinker–Talker、codec 流、扩散循环、CFG 并行和世界模型 rollout。
  • M* 把组件表示为有向图，把请求执行表示为命名 Walk；支持 Sequential、Parallel、Loop 和 DynamicLoop。
  • StreamingGraphEdge 提供固定 chunk、滑窗和左上下文策略；运行时负责组件放置、连续批处理、paged attention、CUDA graph、张量传输和异步调度。

论文事实：明确结果

  • Qwen3-Omni Seed-TTS 在 2×H200、batch 16 时，吞吐分别为 vLLM-Omni 和 SGLang-Omni 的 2.7×/4.0×；摘要报告 RTF 最多降低 2.9×。
  • BAGEL I2T 在单 H100、batch 16、64–256 输出 token 时，吞吐提高 32.7%，端到端延迟降低 25.5%。
  • V-JEPA 2 在 rollout horizon 30 时 p50 加速 12.5×。
  • 这些都是指定硬件、模型、并发和输出配置下的 serving 结果，不是回答质量或当前车控链路结果。

编辑判断：对当前项目的帮助

先做隔离 shadow benchmark：

  1. 固定 Qwen3-Omni revision、输入和输出。
  2. 比较当前 HF 与 M* 的单请求 ms/token、TTFT、显存和 GPU→CPU 同步。
  3. 再测 batch 16 的吞吐与 Seed-TTS RTF，避免把批量优势误写成单请求优势。
  4. 外挂 Edge TTS、endpoint、候选工具、执行器和补偿仍保持原样，以免同时改变太多变量。

只有输出一致且单请求延迟显著下降，才进入 Harness 适配评估。M* 的流式边是模型组件间张量流，不能单凭该抽象宣称具备对话全双工。

局限、开放状态与优先级

  • 论文只测单节点 H100/H200；没有跨节点、生产故障恢复或当前 H20 结果。
  • Qwen3-Omni 实验是 Seed-TTS，不是完整 speech-to-speech 工具调用。
  • 部分基线因正确性或性能问题被排除，比较范围有限。
  • 官方仓库公开，根 LICENSE 为 Apache-2.0；M* 本身没有专属模型权重。
  • 建议优先级：P1 做 shadow benchmark，P2 才考虑迁移。

今日建议路线

第一阶段

  1. 把现有 400 条文本和 1,566 条语音按 Audio2Tool 的参数、多意图、改口、多轮和背景意图重新分桶；补 MIST 的 no-op、澄清和最终车态。

  3. 以 Mel+标签延迟为低成本判停基线，再决定是否引入 Mimi；单流先用 TTS 播放状态，双流等 AEC 参考流可用后再测。
