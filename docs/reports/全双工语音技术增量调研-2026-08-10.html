StreamingModelHarness 当前进展与问题

项目状态快照仍生成于 2026-08-07，本次没有更新的 Harness 提交可供核验。以下“项目证据” 沿用该快照和前一日报告：A/B 的首音频 P50 分别为 2918/3491ms，当前主要瓶颈被定位为 外挂 Edge TTS；单 token 解码约 110ms，已定位到 HF MoE 路径每 token 约 816 次 GPU→CPU 同步；后续明确要求增加多轮跟随、打断改口和取消/补偿评测。前一日报告另记录 baseline 414/452、召回 443/452，以及条件式 Top-2 verifier 离线仅净修 4、未进 H20。

因此，今日新项目的价值主要在“交互状态机、打断评测、TTS 分块和实时服务边界”，不能被 解释成对 38 个工具失败或 110ms/token 根因的直接修复。

一、先说结论

今日没有新的论文级重大突破，也没有可信的新 AEC/降噪、空间听觉、多乘员身份解析或原生 全双工模型结果。Radar 的 9 个新增条目中，真正值得进入工程调研的是三个官方仓库； 其中只有 jax-realtime 提供了较完整的实验日志，且仍是作者自测而非同行评审结果。

P0：直接命中当前工程短板

  • jax-realtime：最值得借鉴的是“回复前续说”和“回复中打断”分流、按实际播放校准的

    • 回声底噪、Silero VAD 与能量打断双信号，以及把负结果保留在同一评测日志中。建议只移植 协议、埋点和回放用例，不直接移植浏览器模型栈。

P1：适合形成下一阶段架构

  • AoiVR：原生 C++ agent、Unity 前端、流式 TTS、滚动视觉/系统音频上下文和进程内

    • C ABI 的分层方式接近座舱“实时 UI 不被 agent 阻塞”的问题，但没有量化时延或打断证据。

  • ShipVoice Lite：可作为 WebRTC/SIP、worker 排空和组件可替换的服务参考，不是模型或

    • 全双工算法创新。

P2：长期模型研究

  • 今日无新增候选。第三方 Qwen3-Omni 镜像、GGUF 量化与来源不明的模型页不是作者官方发布，

    • 不进入结论；它们也没有新增的模型方法或可核验评测。

与前一日的明确差异

前一日重点是 HarnessOpt-Bench、CalibForge、MulRobBench、MASS、DataSpace 等“候选选择、 确定性验证和 handoff”证据；今日不重复这些工作。今日新增价值集中在语音交互运行时： 如何区分停顿续说与真正打断、如何避免助手听见自己、如何让工具播报可取消、以及如何防止 TTS 分块为了首声指标牺牲韵律。它补的是前一日报告未覆盖的交互状态机和可听评测层，不改变 前一日 verifier 已离线失败、不得进入 H20 的结论。

1. jax-realtime

  • 项目与代码：sachinkesiraju/jax-realtime
  • 作者实验日志：Benchmarks & latency hill-climb
  • 项目权重页：sachink98/jax-realtime-weights

它是什么

项目事实：这是浏览器内运行的英语级联语音助手，组合 Whisper base.en、SmolLM2-360M、 Pocket TTS/Mimi、Silero VAD 和可选 D-FINE 视觉检测。仓库将约 150ms 的策略 tick、流式 ASR、LLM、TTS、视觉和天气/Wikipedia/计算器/时钟工具组织为一个确定性微轮次状态机。 它不是端到端语音模型，也没有论文。

核心方法（或核心架构）

项目事实：

  1. 监听阶段用 Silero VAD v5 的 TypeScript 移植版做起声、静音和 phantom-turn 判断；

    2. 回复阶段仍用能量打断，因为作者观察到 Silero 会把扬声器回声也判为语音。

  2. 回声底噪只在 TTS 分析器确认“实际有声播放”时采样；连续约两个 tick 超过

    3. max(绝对门槛, 回声底噪×1.8) 才打断。这样避免在首音频前的静默区错误校准。

  3. 若 endpoint 后 700ms 内、首音频前恢复说话，则取消未被听见的回复，把前后两段转写

    4. 合并为一轮；窗口外或第二次恢复则走普通 barge-in。工具播报和定时提醒也有独立 AbortController，可被同一打断路径停止。

  4. LLM prefill 采用固定 256-token shape bucket，并把历史限制在 8 条消息；TTS 在加载期

    5. 预热常见长度。TTS 只在标点处分块，避免在词边界截断时生成“句末降调+停顿”。

  5. 工具请求可以先播 holding line，再后台查询并在下一次静音后返回；动作、回复和工具播报

    6. 都经过同一可取消音频通道。

论文结果

本项没有论文。以下均为作者仓库自报实验，不是独立复现：

  • Silero 移植与 ONNX Runtime 参考在状态序列上的最坏绝对差为 6.2e-7；作者报告每

    • 32ms 帧约 2.3ms CPU 开销。

  • Cycle 22 的 12 轮固定假麦克风回放报告 turn latency P50/P95 为 1418/1540ms，

    • 12/12 转写一致；60 秒键盘输入从能量基线的 20–21 次 phantom discard 降为 0。

  • 700ms 的 continuation-merge 在作者的 mid-pause 用例中 3/3 完整合并；无限窗口曾让

    • 噪声取消回复并拼坏转写，因此被收紧且每轮只允许一次。

  • 只按标点切 TTS 后，作者报告 sentence P50 从 217ms 增至 460ms、整轮 P50 从

    • 1324ms 增至 1585ms；这是为了韵律主动接受的时延代价。

  • 预填充投机在单 WebGPU 上因与 ASR 争用而变慢，早期实验从 1731ms 增至

    • 2012–2425ms，已撤回。这个负结果说明“并行启动”不等于“关键路径重叠”。

对 StreamingModelHarness 的帮助

编辑判断：

  • 第一优先级不是换模型，而是把 endpoint-fired、first-audio、continuation-resume、

    • barge-detected、tts-aborted、tool-committed 写成统一事件。这样可明确区分“用户只是 续说”和“用户撤销/修改已听见的回复”，也能验证旧 action 是否真的停止。

  • 回声底噪必须以播放端实际有声为采样门，而不是以“回复状态已开始”为门。建议加入真实

    • 扬声器→麦克风回环、不同音量、车内音乐和双讲用例；这比只在静音 WAV 上测 barge-in 更接近 座舱。

  • 可复用其负结果纪律：首声指标不能奖励无意义 filler；单卡上 ASR/LLM/TTS 的“并发”必须

    • 由阶段时间线证明。对当前 110ms/token 问题，应先消除 HF MoE 同步，再讨论 shape bucket 或 KV；两者不能混为一个根因。

  • TTS 候选应同时报告首音频、句间空洞、截断残音和韵律盲听。当前项目约 3 秒首音频可先把

    • jax-realtime 的字段设计当作测量模板，但其浏览器数字不能与 H20/5090 直接横比。

建议优先级：P0（协议与评测）；不建议直接替换 Harness 推理栈。

局限与开放状态

  • 项目事实：代码仓库为 MIT；作者权重页可访问，但没有 model card，页面未给整包许可证。

    • 仓库说明各底层权重仍服从各自许可证，因此“所有权重可商用”未知。

  • 项目事实：当前 ASR 是 base.en，不代表中文座舱；视觉只做 COCO 对象检测，不处理

    • 多乘员身份、说话人定位或空间听觉。

  • 项目事实：实验日志说明假麦克风会静音播放，现有探针不能测真实扬声器泄漏；可听

    • loopback 仍是待办。仓库公开了日志和运行代码，但日志提到的部分 bench clip/harness 是本地产物或 gitignored，完整逐项复现材料不齐。

  • 编辑判断：其“full-duplex”是可打断的级联系统，不是模型同时听说；AEC、远场降噪和

    • 双讲质量仍未知。

2. AoiVR

  • 项目与代码：keybodhi/AoiVR

它是什么

项目事实：AoiVR 是 Windows/SteamVR 助手，使用 Unity overlay 展示界面，并把 LLM、ASR、流式 TTS、系统音频转写、VR 截图和工具放进 C++20 原生 agent DLL。Unity 与 agent 通过进程内 C ABI 交换长度前缀 JSON；仓库声明 agent 循环不阻塞 Unity 渲染线程。

核心方法（或核心架构）

项目事实：音频层使用环形缓冲和分块 SSE PCM，支持串行句子播放和 abort；环境层按 时间窗口处理最新视觉帧、限制并发描述、归档过期上下文，并把视觉时间线和系统音频分区。 协议层为消息设置类型、ID 和时间戳，并拒绝畸形或超 64MB 消息。

论文结果

没有论文，也没有官方仓库给出的端到端时延、ASR 准确率、打断成功率、帧率影响或并发压力 数字。仓库中的 feature/test 文件说明预期行为和单元测试范围，不能等同于量化结果。

对 StreamingModelHarness 的帮助

编辑判断：其价值是座舱形态参考：把 UI/渲染、agent 状态、流式音频和低优先级视觉任务 解耦，并为每条消息保留 ID/时间戳。可将 VR 控制器映射为座舱显示/旋钮，把截图与系统音频 映射为相机和媒体流，测试视觉任务背压是否影响车控 action。建议只抽取协议和压力测试思想， 不运行或接入该陌生仓库。

建议优先级：P1（多模态运行时参考）。

局限与开放状态

  • 项目事实：代码为 MIT，仓库包含原生、Unity、feature 和测试文件；依赖外部 LLM/TTS

    • 服务，未发布专属模型权重。

  • 项目事实：仓库没有给出 AEC、降噪、语义判停、barge-in、多说话人归属或空间音频方法。
  • 编辑判断：持续视觉和系统音频并不自动构成多乘员智能座舱；在没有资源隔离、隐私门和

    • 说话人/座位绑定前，只能算单用户多模态助手。

3. ShipVoice Lite

  • 项目与代码：mahimailabs/shipvoice

它是什么

项目事实：这是 LiveKit 语音 agent 模板，将 Python worker、FastAPI token 服务和 React 前端拆开，默认串联 Deepgram STT、Cerebras LLM、Inworld TTS、Silero VAD 和 LiveKit 多语言 turn detector，同时支持 WebRTC 与 SIP。

核心方法（或核心架构）

项目事实：worker 可显式 dispatch，并在 SIGTERM 时排空正在进行的会话；模型供应商可 替换，工具通过 @function_tool 或 AgentTask 接入。仓库也明确提示：backend 默认无认证， LiveKit signing secret 会以未加密形式进入 Postgres，不能直接暴露公网。

论文结果

没有论文，也没有公开的首音频、打断、丢包、并发、成本或工具成功率结果。所谓“可用于生产” 只能视为项目定位，不能视为已经通过座舱实时门。

对 StreamingModelHarness 的帮助

编辑判断：可借鉴 transport/worker/会话排空的服务边界，并用同一 Harness 驱动本地与 WebRTC 路径，比较网络抖动、断连重入和取消语义。它不解决当前 110ms/token、TTS 首音频或 38 个工具错误；默认云服务也不适合作为离线座舱基线。

建议优先级：P1（实时服务与故障注入）。

局限与开放状态

  • 项目事实：仓库 LICENSE 对项目自有代码授予 MIT，但 vendored UI、品牌和部分图片另有

    • 范围说明；依赖服务与模型的许可证需分别审计。

  • 项目事实：默认 backend 无认证且 signing secret 未加密，是明确安全风险。
  • 编辑判断：在补齐认证、密钥存储、离线降级和确定性 action verifier 前，不应直接用于

    • 车控生产链路。

候选去重与未纳入项

  • genpark-realtime-voice-duplex-conversational-copilot-skill 虽是今日最高 Radar 分，但官方

    • 仓库只有极薄客户端；client.py 固定返回示例 URL、user_interrupted: false 和 latency_ms: 95。这不是实测全双工或 95ms 证据，许可证也未知，故不纳入技术建议。

  • mlinmg/Qwen3-Omni-30B-A3B-Instruct、两个 Qwen/OmniVoice GGUF 与 Barbados fused 页面

    • 都不是原作者官方模型页；它们是既有模型的镜像、融合或量化，不计作新模型。

  • AoiVR、jax-realtime 和 ShipVoice 是三个独立项目，没有发现同一论文改名或修订关系。
  • 今日没有可核验的新 AEC/降噪、空间听觉、多乘员、流式音视频 benchmark 或原生全双工论文；

    • 继续跟踪，但不以无来源数字填充。

今日建议路线

第一阶段

先在现有 Harness 增加统一交互事件和四类离线回放：首音频前 700ms 内续说、首音频后打断、 工具播报打断、真实扬声器回环自打断。只改评测和协议，不动模型；与 452 冻结任务一起检查 action 是否 exactly-once。

第二阶段

把 TTS 测试从“首声”升级为多目标：首音频、句间间隙、取消后残音、标点韵律盲听。并行 比较本地 TTS 与现有 Edge TTS，但不得把不同硬件上的 jax-realtime 数字当目标值。

第三阶段

建立低优先级视觉/系统音频任务与 action 主通道的资源隔离和过期策略；随后再用 WebRTC/SIP 故障注入验证断连、排空、恢复和重复 action。多乘员与空间音频必须等待有说话人/座位真值的 新数据或论文，今日无足够证据启动。

风险提醒

  • GitHub README 和项目实验日志是作者自报，不是论文结果；本报告已按“项目事实”标注。
  • “full-duplex”标签可能只表示可打断级联，不代表模型同时听说，也不代表已有 AEC。
  • 能量打断在真实车舱会受 AGC、音乐、路噪和扬声器位置影响；没有可听 loopback 就不能发布。
  • TTS 首声、整轮时延和自然度存在直接冲突；任何优化都必须同时过数值门与盲听门。
  • shape bucket/KV 技巧不能替代当前已定位的 HF MoE 同步修复；根因不同，必须分别测量。
