方向：打断上下文锚定 PACE（当前问题：项目连“用户听到了第几句”都没有记录，多轮打断改口与取消/补偿评测仍缺位；PACE 用 turn-local 播放账本 + 客户端撤销 + 前向门定序，把模型可见上下文对齐到真实播放边界，在其 108 条 GCM-Bench 上引用锚定正确率从 25.0% 升到 96.3%，200 条 FDB v1 上接管率不变、评分 4.975→4.995、时延 +58.7ms；先在项目自有回放里落账本与撤销，再做“是否注入已播放前缀”的单变量对照，门槛是 414 canary 零退化）

方向：工具执行期的固定等待语（当前问题：首动作已在 700–1,094ms 完成，首音频却要 2,918/3,491ms，中间 1.8–2.8 秒纯静默；NVIDIA VoiceChat 模型页的 per-tool on-hold 语在生成触发工具的文本时立即播报；只加“工具触发即播预合成固定音频”这一个变量，冻结文本/工具/执行器/播放器，分别记录固定音频首包与真正内容首音频，预计正确性修复数为 0 故不请求 H20）

方向：时延口径校准（当前问题：项目需要防住用别人的宣传数字当基线；同一个 VoiceChat，模型页写约 450ms turn-taking，pipecat 官方 DGX Spark 仓库在浏览器端实测 voice-to-voice 1,470.7ms、TTFB 732.341ms、TTFA 982.772ms 且其中 250.431ms 是生成出来的前置静音，并自述未达 400ms 目标；照抄它的分层归因与边界定义，把“生成静音”单列进项目口径文档）

方向：参数与最终车态优先（当前问题：严格工具名召回 80.49%/79.27% 偏保守，参数与最终车态尚未成为主指标；VoiceChat 在口语化 FDB-v3 上工具选择 82.5%、参数正确率 44.2%、Pass@1 33%，其部署仓库另记录 15 个保留会话中 5 个选了无关工具；把三层指标写进现有回放并按 clean/20dB/音色分桶，同时保留确定性执行器与参数校验）

方向：全双工模型修订版去重（当前问题：Radar 以论文标题命中 arXiv:2607.06540v4，易被当成新工作；逐词比对显示 v4 相对 2026-08-06 已覆盖的 v3 只多一段 MOSS-Speech 相关工作，主表数值全部一致；本轮只补一条部署事实——它的 570ms 停止时延依赖自定义 vLLM 的 DAG 流水并行把语义/声学/控制头放到不同 GPU，单卡串行会引入论文自述的时延瓶颈，做对照时必须记录 GPU 数量与头的放置）

方向：音频 token 不可前剪（当前问题：未来若为省显存想在进 LLM 前压缩音频；A-PACK 实测音频 token 的逐 token 重要性与多样性都高于视频 token，因此保留音频、只压视频，再在 LLM 内部按查询相关性剪；采纳其设计约束，但它的 78% prefill FLOPs 与 2.21× 解码吞吐是 A6000 上离线长视频问答，不能解释 110ms/token，代码写“录用后发布”故未公开）

方向：KV cache 明确反例 OasisKV（当前问题：容易把 KV 论文误当解码加速；它靠投机 draft token 预取稀疏 KV，在 2,048 token 预算下精度差 0.7 分内、并发吞吐最高 2.1×，但论文自己写明 Qwen3-235B-A22B 在 TP8 低批量时 TPOT 高于 dense，要到 B=32 才反超；座舱是 batch=1、KV 约 2,500，引入只会更慢，也不触碰约 816 次/token 的 GPU→CPU 同步；只借用它的 roofline 表达方式）

方向：harness 敏感度分层 Evo-Bench（当前问题：414/452 canary 与错误桶没有区分“对 harness 改动敏感”的样本，小收益容易被模型强弱淹没；它先用辅助任务进化筛出敏感任务再做敏感度分层切分，代码 Apache-2.0、数据 CC-BY-4.0；借用选样本方法，不引入自动 harness 进化——论文观察到“早期饱和”，后续轮次反而引入有害修改）

方向：TTS 参考但不换候选（当前问题：首音频瓶颈在 Edge TTS，既有候选 omnivoice-local-tts-16step-v1 仍待离线验证；CtrlSpeech 提供音素级音高/音量/时长控制与二次重合成，LibriSpeech-PC 上 0.6B 为 WER 2.46%、SIM-o 0.65，但全为英文评测、权重 CC-BY-NC-4.0；SemBridge 有中文 CER 0.95 与 ZH-Hard 9.79，但仓库只有 README、代码权重未公开；两者都没有首包/流式/取消数据，故不新增 TTS 候选，只把“音素级时长可控”记为将来精确截断重说的设计线索）

方向：打断标注协议 DuplexGen（当前问题：自建中文打断桶时“该不该现在接话”没有唯一正确答案；其可迁移部分是增量呈现、每样本 5 名标注者、listen/backchannel/take-floor 三分类与 KL 软标签；不可迁移的是英文语料与脚本化时序——固定 0.16s 间隔、0.64s 重叠会把答案预先写进数据。2026-08-12 现场复核：duplexgen-code 为 Apache-2.0、131 个文件的真实实现，personaplex-finetune 仍只有 1 个 README）

方向：不得用音频 LLM 当打断裁判（当前问题：新增打断桶后会想用模型自动判定恰当性；arXiv:2608.06718 的反事实审计显示多数音频语言模型原生逐条判定接近随机，含 Qwen-2.5-Omni-7B 的 50.0/47.1；打断评测继续用确定性口径：stop latency、残留音频、取消后车态、重复执行）

方向：持续跟踪不重启的项目（Qwen3-Omni MoE 无同步 fast path 仍是本周期唯一的解码时延实验，本窗口没有命中可替代它的新内核；omnivoice-local-tts-16step-v1 保持仅离线；聚合意图 typed assignment/branch/return gate 只等既有参数化本体 result manifest；candidate-ID/CMTF、conditional top-2 verifier、投机预取、工具清单压缩、主模型自判停的负结果不重跑；参数化本体、云监督与 SoulX 不重复启动）

今日新增 handoff 候选：tool-hold-message-first-audio-v1（工具触发即播预合成等待语，仅离线，h20_request_allowed=false）与 playback-boundary-ledger-offline-v1（打断时是否注入已播放前缀，仅离线，需先自建中文车控打断桶）。两者预计正确性修复数均为 0，因此本轮都不请求 H20。
