P0：X2Streaming-TTS —— 迄今为止最贴近项目首音频瓶颈的一篇，且硬件平台完全对得上

论文事实。 2608.18661《X2Streaming-TTS: Causal Token-Level Text-to-Speech from Streaming Text with Speech-State Inheritance》，X Square Robot，投稿 2026-08-19T08:05Z，v1，11 页，cs.CL。它做的是严格零前瞻的 token 级流式 TTS：上游语言模型每吐一个 text token，TTS 就可以在不看任何未来 token 的前提下决定是否发声。正文自述的目标是"many systems wait for sentence-level text and are therefore only pseudo-streaming"。

它是什么

一套架在 Qwen3-TTS 之上的严格因果流式 TTS 框架。论文给出的因果性定义是一条硬约束（式 1）：第 u 个声学 token 只能依赖于其生成时刻之前已观测到的文本、此前已生成的声学 token、以及从上一段继承来的语音状态。换言之，前瞻为零——这一点与既有工作的分界线，论文在 §2 讲得很清楚：LiveSpeech / SyncSpeech / SpeakStream 用的是固定前瞻，MagpieTTS-LF 用的是标点感知分块加历史文本，"these methods reduce sentence-level waiting but still depend on future tokens, so their latency remains coupled to the upstream generation rate"。

论文用来支撑"零前瞻是负担得起的"这个前提的论证很干净：文本信息密度高，语音时间上冗余。它定义声学-文本膨胀比 ρ = 声学解码步数 / 文本 token 数，指出 ρ 通常远大于 1，因此"把当前已有的文本先念出去"这件事本身就为后续 token 的到达争取到了时间。

核心方法（或核心架构）

选 Qwen3-TTS 作骨干的理由，论文写得很具体，是三条工程属性而非效果：可计数的声学输出、可迁移的解码状态、可观测的剩余容量（"its KV-cache-aware decoder exposes the remaining capacity in cache positions"）。

（一）Causal Commitment（因果提交），管"什么时候可以开口"。 分两个耦合部件：

  • 不确定性感知的语义就绪判定。 前端维护一个待定后缀 U_t，凡是发音仍可能被后续字符改写的跨度就压住不发。论文自己的例子是英文的 He finished 3——后续可能变成 3 laps（读 three）或 3rd（读 third），两者在词还没写完之前就已分叉，而已经播出去的音频无法撤回。规则覆盖数字、单位、符号、缩写、标点；一旦释放就永不修改；输入结束时残余后缀按同一套规则闭合。
  • 容量自适应、标点感知的分段（CAPS）。 把分段建成一个带约束的最优化问题：边界分 1/2/3/Hard 四档（句末 / 从句级 / 更弱标点 / 非标点硬切），代价 c(1)<c(2)<c(3)<c(Hard)，约束是每段的 KV cache 占用 G(S;ξ) 不得超过可用容量 B，目标是段数罚项 λ_seg 与边界代价之和最小。离线解由动态规划给出（式 4），复杂度 O(n²)，或段长上界为 C 时 O(nC)。在线侧用 EMA 估计 ρ̂：初值 6.0，β 常态 0.1、溢出后 0.5，ρ̂ 截断到 [2, 10]，(α₁,α₂,α₃)=(0.7, 0.8, 0.9)，因而段数因子上界 10/7≈1.429。实现是前端里的一个 token 驱动有限状态机，容量上限 B 直接从已加载的引擎读出。最多允许 2 个文本段排队，声学解码严格串行。

（二）Causal Speech-State Inheritance（因果语音状态继承），管"下一段从什么状态接着说"。 两条独立状态通路：

  • 完整 Code2Wav 状态包跨段搬运，含其 KV cache、卷积状态、转置卷积状态与帧索引，用来热启动下一段的波形解码。
  • 末尾 H 个 token 对齐的 Talker 状态作为有界历史记忆。H 是与流长度无关的全局超参，实验中固定 H = 4，因此继承的声学上下文被界定在 O(H)。

两条通路都受一个健康检查门控：前一段必须收到完整输入、消费完所有已释放文本、声学解码正常终止、实现膨胀比 ρ_k ∈ [1, 12]、且 Code2Wav 快照完整；任一不满足则两条状态全部清零、从默认状态重启。

注意力侧用一个固定因果先验（式 10）：偏置 b(d) 在 0≤d≤4 时为 −d²/8，d≥5 时为 log 0.1，d<0 时为 −∞，因此未来位置权重恒为零；在内容相似度相等时，当前位置相对于距离≥5 的位置有 10:1 的先验优势。注入是有界的：门控分数 s_u 取归一化注意力集中度 ∈[0,1]，增益 g_u = 0.015(0.5+0.5·s_u)，故 0.0075 ≤ g_u ≤ 0.015，扰动满足 ‖z′_u − z_u‖ ≤ 0.015·max‖m_j‖。

编辑判断：这两个"有界"是这篇论文在工程上最讲究的地方。 H 固定为 4、增益夹在 0.0075–0.015 之间、ρ̂ 截断在 [2,10]、健康检查一票清零——每一处都把"跨段继承"这件本质上会累积漂移的事情限死在常数代价内。项目若要借鉴，先借这套边界纪律，再谈具体数值。

对 StreamingModelHarness 的帮助

第一，它是目前唯一一篇同时满足"中文有正文指标 + 有首包时延 + 硬件与项目同级"的 TTS 工作。 追踪表上此前的三种缺口它各补了一块：Luna-TTS 无制品且首包时延要多卡；VoiceChat-TTS 是纯英文，且其 9.62ms 是 ITL 不是 TTFA；FireRedTTS3 中文与制品都过关但零时延数字。X2Streaming-TTS 的中文 CER 0.78% 与 15.8ms TTFT 出自同一篇、同一套系统。

第二，可以直接搬进项目的是三个机制，而不是三个数字。

  1. "不确定性感知缓冲"直接对应中文场景里最容易出错的一类。 论文用英文序数词举例，但同一问题在中文里更常见也更严重：车控场景的"打开空调 26"到底是"二十六度"还是"二六"、"降到 3 档"、"播放第 2 首"——在数字后面那个字到达之前，读法是不确定的。项目目前的外挂 Edge TTS 走的是整句合成，天然回避了这个问题；一旦转向 token 级流式，这个问题会立刻出现。这条机制应当在切流式之前就设计进去，而不是等出问题再补。
  2. CAPS 把"分段"从纯文本问题改造成"文本 × 声学容量"的联合问题。 它的核心不是那个 DP，而是那条约束：段的 KV cache 占用不得超过引擎实际可用容量，而这个容量是从已加载引擎读出来的、不是写死的常数。项目自己正在处理 MoE 解码与 KV 账本，这条"容量从引擎读、不从配置猜"的做法可以直接借鉴到判停与分段逻辑上。
  3. 状态继承给了一个可算的成本上界。 论文只抽象地说"完整 Code2Wav 状态包"，而同机构仓库里的一份官方设计文档把这笔账算死了（见下）。

第三，那份状态尺寸文档是本轮意外收获，可能比论文本身更实用。 Qwen3TTS-Streaming 仓库的 docs/dev/investigation/code2wav_state_size.md 给出 Code2Wav 的状态构成与字节数（这是官方仓库的一手文档，不是论文正文，引用时必须区分）：

  • 解码器配置：num_hidden_layers 8、num_key_value_heads 16、hidden_size 1024、head_dim 64、latent_dim 1024、decoder_dim 1536、KV 滑动窗口 72（来自 Qwen3TTSTokenizerV2DecoderConfig 的官方默认 sliding_window=72）。
  • KV cache：单层单路 K+V = 2×16×72×64 = 147,456 元素 = 294,912 字节（BF16）；8 层单路 2,359,296 字节 ≈ 2.25 MB。
  • 卷积历史：17 个状态共 131,752 元素，单路 263,504 字节 ≈ 0.257 MB。
  • 转置卷积重叠：4 个状态共 9,120 元素，单路 18,240 字节 ≈ 0.018 MB。
  • 单路合计 ≈ 2.53 MB（BF16），且与解码长度无关（滑动窗口固定 72 步）；16 路合计 ≈ 40.3 MB；存 FP32 则翻倍至约 80.6 MB。

编辑判断：这条"跨段继承的状态成本是每路 2.53MB 且与长度无关"是可以直接进项目设计文档的数字。 它同时回答了两个项目问题：其一，若要在打断后保留而非重置语音状态（PACE 的 playback boundary ledger 与 VoiceChat-TTS 的 "KV never reset" 都指向这个方向），代价是可计算且有界的；其二，滑动窗口 72 步意味着声学侧的历史依赖本来就只有约 6 秒，跨越 6 秒的状态继承在架构上没有意义。

第四，那份 README 的时延方法论比论文严谨，应当照抄进项目自己的埋点规范。 详见"局限与开放状态"。

README 里还有两条方法论警告，应当直接搬进项目自己的时延埋点规范：

  1. 服务端 TTFT 与客户端 TTFT 不可混用。 README 明确说 WebUI 并发面板报的是服务端侧适配器 TTFT——"计时从模型开始处理该请求时才开始，因此客户端连接建立、分发展开、处理前排队、首帧回程全部被排除在外"——在同一硬件上该面板在 128 路时读数约 100–170ms，而对外可引用的客户端突发口径是 242–275ms。同一系统同一时刻，两种口径差出一倍以上。
  2. 突发到达与斜坡到达不可混用。 README 说明其 128 路数字是"同时突发"这一最坏情形，"staggered arrivals see lower TTFT"。

该 README 还给出一组论文里没有的吞吐数字（一手仓库文档，非论文）： 经三轮解码优化后，RTX 5090 上 128 路并发的解码步为 42.1ms / 80ms 音频帧，RTF ≈ 1.90（约 47% 实时余量）；优化前为 119.8ms/帧，RTF ≈ 0.67，低于实时；64 路时为 24.5ms/帧，RTF ≈ 3.3。README 自己给了一句很克制的话："128 streams is the tested ceiling, not a safe production target."

这里出现 CUDA Graph 的第五次独立佐证。 README 列出的三轮优化中，2026-07-06 那轮明写为 "CP in-graph KV + CUDA-graph decode replay + arena-ized KV gather"，2026-07-07 为 "batched burst admission + per-slot state pooling + serving hot-path slimming"。此前四次分别是 FlashDrive（前置条件）、vToken（硬约束）、DeaMoE（方法与基线的公平性前提）、CoRun（确定性）。本次是第五次，且是第一次来自一个可读源码的生产级 TTS 引擎，而非论文。 项目既定顺序不变：先落地无同步 index_select+bmm 快路径，再把整环图捕获作为第二个独立变量。

另有一条与项目直接冲突的部署前提。 该仓库的运行路径依赖 NVIDIA NGC 容器（nvcr.io/nvidia/tensorrt、nvcr.io/nvidia/tritonserver），NOTICE 写明这是"专有 NVIDIA 软件，受 NVIDIA EULA 约束"，且 README 写明"拉取 NGC 镜像即构成接受 NVIDIA EULA"。硬件要求为 NVIDIA GPU、建议 ≥16GB 显存，磁盘约 20–40GB。另外 TensorRT 引擎"绑定特定 GPU/驱动/TensorRT 组合，一台机器上构建的 .plan 无法可靠地在另一台上运行"。编辑判断：这对车机侧是实打实的工程约束，不是许可证细节。

  2. 文本 token 按固定速率喂入。 论文自己声明："Text tokens are supplied at a fixed rate for controlled evaluation; a deployed upstream language model may exhibit variable token-generation latency."上游是我们自己的 MoE 主模型，其 110ms/token 且抖动未知，因此论文的 ρ 论证（"声学侧的时间足以掩盖文本到达"）在项目条件下不能默认成立——ρ 掩盖不掩盖得住，取决于上游吐字速度与声学速度之比，而项目的上游比论文的实验条件慢得多。这是项目采纳该方法前必须自测的第一件事。

2. X2-Turn v1→v2（2608.10878）：一次只改两行、却翻转开放状态的修订

  • 论文：https://arxiv.org/abs/2608.10878（v2，published 2026-08-11T12:54:52Z，updated 2026-08-19T03:16:50Z）
  • 代码：https://github.com/X-Square-Robot/X2-Turn（Apache-2.0）
  • 权重：https://huggingface.co/x-square-robot/X2-Turn-4B-0812（Apache-2.0，非门控）

内容见"一、先说结论"中的 P0（并列）一节，此处只补两条方法学记录。

第一，这是追踪表上第三个完成的 v1→v2 逐版差分，也是三者中差分最小、影响最大的一个。 三次的结果各不相同：StreamTTT（2608.13416）改了 184 行、结论不变；Ambisonics（2608.14097）只改了 2 字节，且改的是标题里一个漏掉的字母 l；本次 X2-Turn 只加了一句话，却把一项挂了 8 天的开放状态判定整个翻转。

08-19 记下的规律"差分大小完全预测不了结论是否改变"，本次是第三次印证，且提供了一个新的极端：内容改动量最小的一次，带来的判定改变最大。 由此追加一条操作规则：逐版复核时，除了重跑原判定所依赖的字词/数字计数，还必须单独比对两版的 URL 集合（超链接注解 + 裸 URL）——本次的全部实质变化就藏在裸 URL 从 4 条变成 5 条这一个差别里，而任何只看数值 token 的比对都会漏掉它（数值 token 只从 364 变成 365，且新增的那个是页边日期戳，纯属噪声）。

第二，论文结论未变这件事必须与开放状态分开写。 v2 没有新增任何实验、没有改动任何数字。08-19 记录的三条局限原样保留：联合训练损害 ASR（AISHELL-1 从 2.57 劣化到 3.94）；EasyTurn-zh 在 τ=480ms 下的 91.00/93.00/96.00 与 288ms 时延是相对词尾而非相对说话结束的口径；判停头与 ASR 头并行、不回灌解码。

3. 其余候选与筛查结论

4. 术语与同名/同源辨析（本轮新增）

  • X2-Turn 与 X2Streaming-TTS 是同一机构、同一技术脉络的两个半边，共享 5 名作者与同一通讯作者，按一条脉络记录。这与 08-19 的 DuplexGen 同名案恰好相反：那里是两篇毫无关系的论文用了同一个名字，这里是两篇不同名的论文属于同一个栈。"名字相同"与"工作相同"两个方向的误判都会发生，判据一律是作者/机构重合 + 是否互相引用 + 投稿间隔。
  • X2Streaming-TTS（论文名）与 Qwen3TTS-Streaming（仓库名）疑似同一系统的两个名字，但两边互不引用，在得到作者确认之前不合并记录。
  • TTSD-FAR（2608.18386）里的 TTSD 不是 TTS。 其展开为 Test-Time Self-Distillation，论文主题是缺失模态下的情绪识别。关键词扫描的又一个缩写级假阳性，与已记录的 RTF＝relative transfer function、HRTF 内含 RTF、wall-clock＝视频时间轴位置同类。
  • 2608.19013 "Harness Continual Learning" 里的 harness 既不是训练脚手架也不是执行脚手架，而是动词"驾驭"。"harness" 的第三种义项，加入术语陷阱清单。

5. 今日建议路线

第一阶段（零 GPU，可立即做）

  1. 把 X2Streaming-TTS 的三条"有界纪律"写进项目的流式 TTS 设计文档：固定 H、夹紧增益、状态健康检查一票清零。先落纪律，不落数值。
  2. 把"不确定性感知缓冲"的中文场景清单列出来：数字后缀（度/档/首/号/路）、单位、序数、时间、车控参数。这件事必须在切 token 级流式之前做完，否则一定会以"念错档位"的形式在线上暴露。
  3. 把仓库 README 的时延方法论抄进项目埋点规范：服务端 TTFT 与客户端 TTFT 分开记；突发到达与斜坡到达分开记；prefix-cache 命中与否分开记；冷通道额外成本单列。项目当前的首音频 P50/P90 属于哪一种口径，需要先自查。
  4. 判定器处理不变性检查（优先级仍为最高，来自 2608.12880，与本轮无关但未完成）。

第二阶段（单卡可做）

  1. 离线复现 X2-Turn：权重与代码都已开放且非门控，先测 EasyTurn-zh 中文判停，再测项目自己的 452 条基准音频。这是本轮唯一一项可以立刻动手、无需任何谈判或申请的实验。
  2. 测上游 token 速率：X2Streaming-TTS 全部论证建立在"声学侧膨胀比 ρ 足以掩盖文本到达"之上，而项目上游是 110ms/token 的 MoE。先测出项目自身的 ρ 与 token 到达抖动，再决定 token 级流式是否成立。 这一步不需要任何外部代码。

第三阶段（需要环境评估）

  1. 评估 TensorRT/Triton 链路是否可接受，包括 NGC EULA、.plan 与 GPU/驱动绑定、20–40GB 磁盘。在这一步完成之前，不把 X2Streaming-TTS 的任何时延数字写进项目预期。
  2. 跟踪 X-Square-Robot/X2Streaming-TTS 是否出现。 若出现，重新做一次完整开放状态核实；若两周内仍为 404，则按"声称发布、地址失效"定案。

风险提醒

  1. 不要把 15.8ms 当成项目可获得的首音频。 它是首个音频 *token*、客户端侧中位数、暖引擎、prefix-cache 命中、本地链路、单请求、RTX 5090、BF16。项目的门槛管的是首个音频到达听者，且首句必然是冷的。这两个量之间隔着至少四层未测量的成本。
  2. 不要把"论文没有训练章节"读成"论文证明了无需训练"。 论文只说了离线参考与流式版本使用相同权重。
  3. X2Streaming-TTS 论文声明的仓库地址目前不存在。 在它出现之前，任何"代码已开放"的表述都是错的。同机构那个 MIT 仓库是疑似实现，两边互不引用。
  4. TEN VAD 的 "Apache-2.0 WITH ADDITIONAL CONDITIONS" 含竞业限制条款。 虽然默认关闭且非捆绑，但对商业车机项目属实质性风险，选型文档必须点名。
  5. NGC 容器与 TensorRT 引擎绑定是部署侧的硬约束，不是许可证细节：.plan 不能跨机器复用，且拉取 NGC 镜像即接受 NVIDIA EULA。
  6. X2-Turn 的开放状态变了，论文结论一个字都没变。 联合训练损害 ASR（2.57→3.94）这条依然成立，复现时必须同时测 ASR 退化，不能只测判停指标。
  7. 12 Hz 与 12.5 Hz 的不一致已经在两个独立来源上出现。 凡由帧率推导时长的换算，一律标注所用取值。
  8. 本轮 50 篇的窗口不代表低产。 上一轮 235 篇是四批积压，本轮是单批常态。用篇数判断"有没有重大新增"是错的——本轮篇数只有上轮的 21%，却出了近若干轮质量最高的一条 P0。
