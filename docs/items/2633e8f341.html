LongHorizon-Harness: Advancing Long-Horizon Agents for Real-World Tasks

论文Paper · hf · 2026-08-02 · ◈ 6
摘要Summary
LongHorizon-Harness 用 Manage–Execute–Audit 循环和环境证据维护外部任务状态，让每轮执行器在新上下文中工作，WeaveBench PassRate 由 51.8% 提升至 80.7%。它适合 Harness 的异步工具任务、恢复和最终状态验证，但不解决同一生成中的晚注入、语音判停或外挂 TTS。 Large language model (LLM) agents increasingly undertake long-horizon tasks that require sustained reasoning, tool use, and revision across many interdependent steps. However, existing agent harnesses maintain task execution, task state, and completion assessment within a growing context, making the state difficult to track and allowing incorrect self-assessments to propagate into later decisions. We reformulate long-horizon execution as a task-state management problem and propose LongHorizon-Harness, which maintains the task state explicitly outside execution and updates it only with facts independently verified from the environment. Its Manage-Execute-Audit(MEA) loop uses a manager to maintain the task state and determine the next subtask, a fresh-context executor to perform it, and a read-only auditor to verify the resulting environment state before the next round. A lightweight AgentAdapter supports interchangeable model and harness backends without modifying their native agent loops. LongHorizon-Harness improves Qwen~3.7-Plus from 51.8% to 80.7% on WeaveBench, from 69.7% to 77.2% on Terminal-Bench~2.1, and from 2.8% to 8.3% on OSWorld~2.0. It also raises Claude Opus~4.7 from 20.0% to 34.3% on an OSWorld2.0 subset, demonstrating consistent gains across models, harnesses, and interaction domains.

深度讲解Deep dive

LongHorizon-Harness 把长任务变成 Manage–Execute–Audit 循环：状态只由环境审计证据推进，执行器每轮使用新上下文。

它解决什么问题Problem

单一不断增长的代理会话同时承担执行、状态维护和完成判断，容易产生上下文退化、目标漂移、状态丢失，并把错误的自我完成声明传播到后续步骤。

核心方法Core method

Manager 只读取目标、结构化状态和审计报告并生成有边界的子任务契约；Executor 在预算受限的新上下文中修改环境；Auditor 用只读工具独立检查结果。只有审计支持的事实进入持久状态，AgentAdapter 保留底层代理原生循环。

怎么工作How it works

  1. Manager 从 requirements、artifacts、facts 和历史审计证据中选择未完成目标。
  2. 生成含目标、依赖、边界和验收标准的子任务契约，并选择 GUI 或 CLI 执行器。
  3. Executor 在新上下文中执行并提交报告，原始轨迹不进入下一轮上下文。
  4. Auditor 独立检查环境并输出完成状态、证据和剩余缺口。
  5. Manager 只据审计更新状态并决定 execute、done、blocked 或 ask。

论文报告了什么Reported findings

  • 相同主干和 Claude Code 后端下，WeaveBench PassRate 由 51.8% 升至 80.7%，Overall 由 0.702 升至 0.835。
  • Terminal-Bench 2.1 成功率由 69.7% 升至 77.2%。
  • OSWorld 2.0 全集 Binary 由 2.8% 升至 8.3%，Partial 由 21.5% 升至 35.2%。
  • 相对基线，WeaveBench token 为 2.3×、OSWorld 输出 token 为 3.6×，而 Terminal-Bench token 减少 24%。
对 StreamingModelHarness 的帮助（编辑判断）Fit for StreamingModelHarness (editorial analysis)
  • 编辑判断：MEA 适合 StreamingModelHarness 中耗时工具任务的持久状态、分轮恢复和独立验收，尤其适合作为异步任务模式。
  • 编辑判断：工具集合在每轮开始前配置，最多支持下一轮重新路由；它没有解决同一生成过程中的晚注入工具。
  • 编辑判断：框架与音频传输、判停、响应音频和外挂 TTS 正交，不会使系统变成原生全双工；逐轮审计还会增加对话延迟。

边界与局限Limits

  • OSWorld 基线使用 single-action GUI，而 Harness 使用 hybrid GUI+CLI，结果不能纯粹归因于状态管理。
  • 两个基准分别增加至 2.3× token 和 3.6×输出 token，较弱主干还可能触发更多恢复轮次。
  • 视觉定位、数学、算法等原子能力不足时，审计不能补齐能力，误解契约时仍可能验证错误答案。
  • 三个角色通常使用同一主干，独立主要来自权限和上下文隔离；未报告审计器准确率、显著性或置信区间。
