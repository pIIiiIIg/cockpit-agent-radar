Zero-Mem: Zero-Token Memory Operations for LLM Agents

论文Paper · hf · 2026-07-30 · ◈ 5
摘要Summary
Zero-Mem 保留原始 trace，以实体图、时间层级、双路检索和规则校准完成最终 QA 之外的零 LLM-token 记忆操作，相对生成式 baseline 将该部分耗时降低 57.6%。它适合作为 Harness 的跨会话外部文本记忆，不修复流内音频 KV 或 MoE 解码；官方仓库目前只有发布占位 README。 LLM agents need memory to act consistently over long interactions, yet many systems use additional LLM calls to operate that memory. Generating intermediate records and mediating their retrieval adds recurring token and time costs, while omitted or merged details can obscure the original evidence. We ask whether structured memory access requires generation at all. Zero-Mem introduces zero-token memory operations: no step outside final question answering invokes an LLM or consumes LLM input or output tokens; encoder computation is accounted for separately. Zero-Mem preserves original interaction traces as its source of record. It organizes the traces in two complementary ways. An entity--context graph exposes connections across interactions, while a temporal hierarchy preserves conversational locality and session state. For each query, Zero-Mem weighs the two views, retrieves from both, and follows their structure to recover supporting relations or surrounding context. Deterministic calibration first discards conflicting evidence and then keeps the reader's answer grounded in the retrieved traces. Only the final-QA reader invokes an LLM. Across long-memory and long-context question-answering benchmarks, Zero-Mem achieves competitive performance while eliminating LLM calls and LLM-token consumption from memory operations. With the same final-QA reader and context budget, it reduces memory-operation time cost by 57.6\% relative to the fastest compared baseline. Ablations support the contribution of the two views and their query-dependent coordination. Overall, the results show that structured agent memory need not generate an intermediate representation of the past. After peer review, the code and implementation details will be available at blue{https://github.com/TheMoon0815/Zero-mem}.

深度讲解Deep dive

Zero-Mem 保留原始交互文本，以实体图和时间层级进行非生成式检索、闭包与规则校准，使最终 QA 之外的记忆操作不调用 LLM。

它解决什么问题Problem

生成式 memory 反复调用 LLM 做摘要、更新和检索规划，增加 token/延迟并可能丢失原始证据；纯向量检索又容易混淆实体、时间和会话边界。

核心方法Core method

系统保留带 source ID、session time 和 boundary 的原始 trace，用 spaCy NER 建立 entity-context 二部图与相邻边，同时建立 turn→window→episode→local-span 时间层级。BM25 与 BGE-M3 提供词法和密集访问；query profile 提取 subject、keywords、answer type、temporal cues 和 boundary，规则选择主视图。图视图用实体匹配、共现传播和 Personalized PageRank，层级视图粗到细检索；融合后补 graph bridge 与局部邻居，规则过滤冲突和越界证据，只在最终 reader 调用一次 LLM。

怎么工作How it works

  1. 从原始交互构建 provenance trace、实体图和时间层级。
  2. 为 query 构建结构化 profile，并确定主检索视图。
  3. 执行双视图检索、加权融合和 evidence closure。
  4. 规则过滤后调用一次最终 QA reader，再做非生成式答案校准。

论文报告了什么Reported findings

  • LoCoMo/GPT-4o-mini 的平均 F1/BLEU-1 为 59.15/52.96，GAM 为 53.75/47.51。
  • LoCoMo/Qwen2.5-14B 为 57.57/51.41，GAM 为 52.70/46.55。
  • HotpotQA 448K 上 GPT-4o-mini 为 65.04、GAM 59.81；Qwen2.5-14B 为 61.02、GAM 57.87。
  • 统一四线程设置中，记忆操作为 0 LLM token、334.77 秒总计/0.22 秒每 query；LightMem 为 877,086 token、788.76 秒/0.51 秒，时间减少 57.6%。
  • HotpotQA-56K 消融中完整模型 72.07/69.66；graph-only 62.50/59.90、hierarchy-only 54.88/51.40、无 closure 67.90/65.43。
对 StreamingModelHarness 的帮助（编辑判断）Fit for StreamingModelHarness (editorial analysis)
  • 编辑判断：更适合作为跨会话外部文本记忆；endpoint 后按用户 query 检索少量历史 trace，再与晚注入工具一起送入 Qwen3-Omni。
  • 编辑判断：它不修复流内 B-path KV 损失，要求文本、实体和时间元数据，无法保存声学细节，追加检索文本还可能增加 context attraction。
  • 编辑判断：57.6% 是相对生成式 memory baseline 的记忆操作耗时，不包含共享最终 reader，不能外推为 110 ms/token 解码加速。

边界与局限Limits

  • “zero-token”只指最终 QA 之外不使用 LLM token；BGE-M3、NER、索引、PageRank、存储和最终 reader 仍有成本。
  • 只评估 LoCoMo 与整理后的 HotpotQA QA，没有真实 agent action、工具调用、流式音频或在线更新实验。
  • episode 划分、query profile、冲突过滤、候选抽取和答案校准缺少可执行细节；无代码时无法区分架构收益与任务规则收益。
