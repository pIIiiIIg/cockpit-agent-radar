Ouroboros: A Self-Developing Frontier Coding Agent with Reviewed Core Evolution

论文Paper · hf · 2026-08-07 · ◈ 6
摘要Summary
Ouroboros 把 agent 的提示、工具、上下文组装和核心实现都纳入版本控制，通过受审查的提交让后续任务运行在改进后的 harness 上。它既支持以自我改进为任务的递归演化，也能从日常任务和用户反馈中提炼维护变更，并用治理边界约束自修改。 We present Ouroboros, a self-developing agent harness whose tools, prompts, context assembly, and core implementation improve through reviewed commits that become the runtime for later work. Core evolution proceeds in two modes. In recursive free evolution, improvement is itself a task, and completing one evolution cycle can schedule the next. In experience-driven core evolution, ordinary work and social interaction expose bugs, rough edges, and inefficient context construction that lead to reviewed structural changes. On Terminal-Bench 2.1, an Opus 5 run scores 86.74%, the best result reported on the benchmark. On OSWorld-Verified, an Opus 5 run reaches 90.69%, exceeding the best previously reported score. A five-rollout CL-Bench campaign achieves a normalized reward of 0.2301, setting a new state of the art. Hope is the longest-running publicly documented Ouroboros deployment. It is a 161-day living agent experiment in free evolution under governed human communication across seven surfaces. Human interaction surfaces faults and generates proposals, but the agent decides which changes to pursue. Because a self-developing agent may rewrite its own code and select new model APIs, operational safety becomes a primary design problem: guardrails must remain authoritative under evolutionary and public social pressure. Benchmark campaigns use frozen system snapshots, while Hope continues live evolution on a separate lineage.

深度讲解Deep dive

Ouroboros 展示的是“可审计、自修改的 agent harness”：模型可以提出并实现核心改动，但只有通过版本化提交与审查门后才成为下一轮运行时；这套治理思想比放任线上 agent 自改代码更值得车舱系统借鉴。

它解决什么问题Problem

长周期 agent 的实际能力由模型和 harness 共同决定，但多数 harness 在设计后冻结，任务中暴露的上下文缺陷、工具摩擦和恢复失败不能沉淀为核心改进。允许 agent 修改自身又会带来权限扩张、控制弱化、模型 API 更换和成本失控等安全风险。

核心方法Core method

Ouroboros 把源码、提示、工具、上下文装配、审查逻辑和核心实现置于版本仓库。递归自由演化把“检查当前系统并改进它”本身设为任务，完成后可调度下一周期；经验驱动演化则从普通工作、反思、审查阻塞、仪表数据和社会反馈中记录持久错误类，再发起维护变更。所有变化经过 staged diff 审查和提交门，宪法加载、治理文件保护、外部开销限制与操作员停止权保持在演化权限之外。

怎么工作How it works

  1. 运行普通任务或专门的自我改进任务，收集失败、上下文缺陷、低效工具路径和用户建议。
  2. agent 判断问题是否值得进入核心维护，并形成可复用的错误类别与修复方案。
  3. 在受控工作区修改提示、工具、上下文装配或核心代码，并生成 staged diff。
  4. 通过审查、治理保护和提交门后，将变更写入可审计版本历史。
  5. 后续任务使用获批提交作为新的运行时；若为递归模式，可再调度下一轮改进。
  6. 基准评测冻结种子与运行配置，持续部署的 Hope 则在独立谱系上继续演化。

论文报告了什么Reported findings

  • Terminal-Bench 2.1 的 Opus 5 活动在 89 个任务上各运行 5 次，原始成绩为 387/445（86.97%）；轨迹审计移除一个利用弱验证器的样本后为 386/445（86.74%）。
  • OSWorld-Verified 的 Opus 5 运行在标准非 Google Drive 集上取得 327.39/361（90.69%）。
  • CL-Bench 的 Sonnet 4.6 活动在六个域上使用 1 个无状态基线和 5 个有序有状态 rollout，归一化奖励为 0.2301。
  • SWE-bench Pro 上 Ouroboros+GPT-5.6 Luna 为 58.2%，对照 Codex 为 59.4%；GAIA 上 Ouroboros+Sonnet 5 为 78.2%，对照 Claude Code 为 78.8%。
  • Hope 是论文记录的 161 天持续部署实验，跨 7 个通信界面保留记忆并演化实现。
对 StreamingModelHarness 的帮助（编辑判断）Fit for StreamingModelHarness (editorial analysis)
  • 对 StreamingModelHarness 最有价值的是版本化改进闭环：把 ASR 错误、端点误判、RAG 失败、工具超时和 TTS 问题沉淀为可审查变更，而不是只在单次对话中反思。
  • 架构 A 与 B 都可使用冻结种子、轨迹审计、staged diff 和回滚谱系；尤其应把车控、拨号、外部开销与隐私策略置于 agent 不可修改的治理层。
  • 论文不提供原生音频全双工机制；其 benchmark 成绩来自编码/计算机使用 harness，不能证明语音打断、低延迟或并行听说能力。
  • 车舱场景不宜照搬持续自主核心演化。更稳妥的编辑判断是保留经验驱动的问题发现，但让发布、模型更换和权限变化始终经过人工及自动安全门。

边界与局限Limits

  • 持续部署研究只有一条长运行谱系，而非多个独立演化 agent 的受控总体。
  • SWE-bench Pro 存在公开参考泄漏和任务缺陷。
  • LLM 审查者可能与执行 agent 共享盲点。
  • 低上下文审查模式会遗漏全仓库范围的检查。
  • 自修改和远程工作区能力具有双重用途，治理边界本身仍需独立验证。
