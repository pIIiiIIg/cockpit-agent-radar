Allocation Before Ranking: Decoupled Token Compression for OmniLLMs

论文Paper · arxiv · 2026-08-03 · ◈ 6
摘要Summary
Macer 先显式分配音视频 token 预算，再在模态内排序，25% 保留率下保留 Qwen2.5-Omni-7B 全 token 性能的 98.7%。当前 StreamingModelHarness 以音频为主且已有流式 KV，不宜直接集成；更适合作为未来摄像头+麦克风版本的容量分配原则。 Token compression in OmniLLMs is typically posed as a single saliency-ranking problem: score each multimodal token, keep the top-K. We argue this abstraction is mis-specified. The same attention score simultaneously decides two things: how much retained capacity each modality receives, and which tokens within a modality are kept. A shared top-K rule therefore inherits this audio-favoring allocation prior, spending retained capacity on audio before video tokens have a chance to compete. We propose Macer, a training-free compressor that first assigns explicit audio and video budgets, then performs allocation-normalized ranking within each modality at modality-specific shallow layers. Macer significantly reduces token cost while preserving accuracy across audio-grounded, audio--video joint, visual-dominant, and video-centric benchmarks. At 25 % retention, Macer preserves 98.7 % of full-token performance on Qwen2.5-Omni-7B and 97.3 % on Qwen2.5-Omni-3B. On Qwen2.5-Omni-7B, this 25 % setting reaches OmniZip-level performance at 45 % retention while using lower FLOPs. On OmniVinci-9B, the same allocation-before-ranking principle improves over shared top-K ranking by up to 12.9 points.

深度讲解Deep dive

Macer 先显式分配音频和视频 token 预算，再在各模态内部排序，避免共享 top-K 的音频偏置挤占视频容量。

它解决什么问题Problem

OmniLLM 的全局 top-K 同时决定模态间容量和模态内 token 选择；共享注意力偏向音频时，视频 token 可能在真正参与竞争前就失去预算。

核心方法Core method

Macer 按总保留率和固定音频份额 α 分配音视频预算，用模态内归一化注意力分别排序，并在单次 prefill 的不同浅层先剪音频、后剪视频。视频选择加入递减时间覆盖奖励，文本 token 始终保留；方法无需训练、改权重或第二次前向。

怎么工作How it works

  1. 由保留率计算总多模态预算并按 α 分给音频和视频。
  2. 在浅层读取并模态内归一化音频注意力，剪除音频 token。
  3. 继续同一次前向，在后续浅层选择视频 token。
  4. 施加时间覆盖奖励后按原顺序合并保留 token，完成剩余 decoder 层。

论文报告了什么Reported findings

  • 25% 保留率下，7B/3B 分别保留全 token 归一化性能的 98.7%/97.3%，OmniZip 为 91.6%/95.5%。
  • WorldSense 上 Macer 25% 得分 44.80、耗时 9.17 秒、显存 25 GB；全 token 为 46.80、10.5 秒、41 GB。
对 StreamingModelHarness 的帮助（编辑判断）Fit for StreamingModelHarness (editorial analysis)
  • 当前 Harness 以流式音频为主，没有音视频模态预算竞争；Macer 还依赖 endpoint 后 query attention，难直接压缩已经形成的流式 KV。
  • 未来摄像头+麦克风版本可采用“先分模态容量、再模态内选择”的原则，但它不改善晚工具注入或外挂 TTS。

边界与局限Limits

  • 音频份额、读取层和覆盖权重按模型规模固定校准，不能按查询动态分配。
  • 仅适用于音频和视频进入同一 decoder 的架构；在同为 25% 保留率时其 FLOPs 也高于 OmniZip，优势不是所有成本口径都成立。
