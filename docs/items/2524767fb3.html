Omni-Prune: Query-Aware Unified Token Pruning for Efficient Omnimodal Large Language Models

论文Paper · arxiv · 2026-07-26 · ◈ 13
摘要Summary
Omni-Prune 按音频事件分窗，并用显著性、查询相关性、音视配对和多样性代表免训练剪枝；7B 在 35% 保留率下保持 99.0% 归一化表现，prefill 由 899ms 降至 277ms。它适合 Harness 判停后的完整输入 prefill，不加速判停前流式阶段，也不处理外挂 TTS。 Omnimodal large language models (OmniLLMs) are rapidly extending multimodal reasoning to cover synchronized audio and video. 深度讲解Deep dive

Omni-Prune 在 LLM 前按音频事件自适应分窗，并结合编码器显著性、文本相关性、音视配对和多样性代表免训练剪枝。

它解决什么问题Problem

视觉专用剪枝忽略同步音频、跨模态关联和用户问题；单向用一种模态指导另一种，又可能保留响亮但无关内容或丢掉静音却关键的视觉证据。

核心方法Core method

方法先平滑音频编码器注意力并以峰值划分时间窗口，再在每个窗口内联合编码器显著性与文本相关性，建立音视频关系图并成对保留高相似 token，最后按模态和窗口用最远点优先 medoid 补回少量多样性代表。

怎么工作How it works

  1. 把音频 token 对齐到视频帧，计算平均音频注意力并用核大小 3 的一维平均池化平滑。
  2. 以局部音频显著性峰值划分窗口，边界最小间隔为 2 帧。
  3. 在窗口内按编码器显著性和文本相关性排序 token。
  4. 以跨模态相似度门限联合保留相关音频—视频 token 对。
  5. 从剩余 token 中按模态执行最远点优先选择，补充低显著但多样的上下文。

论文报告了什么Reported findings

  • Qwen2.5-Omni-7B 保留 45% token 时五基准归一化平均为全模型的 99.2%，保留 35% 时仍为 99.0%。
  • Daily-Omni、单张 A6000、FlashAttention 条件下，7B 在 35% 保留率时 prefill 由 899ms 降至 277ms，峰值显存由 28.7GB 降至 22.3GB。
  • 3B 在 35% 保留率时保持 97.5% 归一化表现，prefill 由 567ms 降至 156ms，峰值显存由 18.4GB 降至 12.8GB。
  • 7B、35% 保留率下移除残差聚类后，VideoMME 由 66.3 降至 64.5，Daily-Omni 由 60.4 降至 59.2。
对 StreamingModelHarness 的帮助（编辑判断）Fit for StreamingModelHarness (editorial analysis)
  • 编辑判断：该方法在 LLM 前一次性剪枝，更适合 Harness 判停后对完整音视频输入做 prefill，不会加速判停前的持续输入。
  • 编辑判断：官方评测使用 return_audio=false，与文本输出再接外挂 TTS 的链路相容，但不提供原生语音全双工、抢话或 Talker 加速。
  • 编辑判断：当前代码把所有非音视频 token 都用于文本相关性；晚注入工具 schema 可能吸走剪枝预算，接入时应显式限定用户问题。

边界与局限Limits

  • 只评估五个视频问答基准，未验证开放式生成、多轮对话、工具调用或端到端语音链路。
  • 效率只在 Daily-Omni、单张 A6000 和 FlashAttention 下测量，没有编码器成本、解码吞吐或并发数据。
  • 论文公式称音视频显著性联合归一化，公开代码却先分别归一化再拼接，结果影响未知。
  • 仓库不含基准数据、锁定依赖、release 或实验提交标记，五个评测脚本仍使用本地占位路径。
