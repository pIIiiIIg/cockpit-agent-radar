PACE: A Playback-Aligned Context Engine for LLM-Based Full-Duplex Voice Dialogue

论文Paper · arxiv · 2026-08-07 · ◈ 25
摘要Summary
PACE 是面向全双工语音服务的播放对齐上下文中间件，用客户端实际播放边界修复被服务端预生成内容提前推进的对话状态。它不要求原生模型层全双工，因此与 StreamingModelHarness 的外部 TTS、客户端播放和打断链路高度相关，但前提是补充逐轮音频账本与播放确认。 LLM-based full-duplex voice services allow users to speak while the assistant is responding. Because servers can generate output and advance dialogue state faster than clients can play it, subsequent user speech may be interpreted based on content the user never heard. We call this failure Generative Context Mis-anchoring (GCM). To address GCM issues, we present PACE, a provider-independent middleware layer that anchors model-facing context to the client playback boundary, a system-observable proxy for what the user could have heard. After an interruption, PACE repairs this context to exclude assistant content that never reached playback, while preserving low-latency generation across heterogeneous voice runtimes. We implement PACE's audio-only projection path end to end in a browser-based realtime voice assistant using a black-box speech model, without modifying the model service. We also construct GCM-Bench, a new controlled benchmark dataset of 108 playback-relative referent-anchoring cases. On GCM-Bench, PACE raises Referent Anchoring Accuracy from 25.0% to 96.3% over a cancellation-only baseline. On 200 Full-Duplex-Bench v1 interruption samples, it preserves interruption response quality. These results show that grounding model-facing context in actual playback is a practical way to maintain consistency in full-duplex voice dialogue.

深度讲解Deep dive

PACE 用“用户实际播放到哪里”而非“模型生成到哪里”提交上下文，避免打断后指代落到用户尚未听到的内容。

它解决什么问题Problem

全双工服务中的生成速度通常快于播放速度，服务端历史可能已经写入多句未播放内容；用户打断并说“那里”或“下一项”时，即使 ASR 和生成各自正确，模型也会在错误的上下文位置解析指代，论文称之为生成式上下文错锚（GCM）。仅停止播放或取消生成不能撤销已经推进的模型上下文。

核心方法Core method

PACE 将边界跟踪与上下文投影解耦：服务端为每个助手轮次维护输出音频账本，客户端回报最新已渲染采样点；确认打断后冻结该边界、暂存新用户音频、取消生成并抑制迟到输出、撤销边界后的客户端缓冲，再按运行时能力重写文本历史、调用供应商截断接口，或向黑盒语音模型重注入最近已播放音频。

怎么工作How it works

  1. 为助手生成的音频建立逐轮账本，并持续接收客户端播放采样点确认。
  2. 确认用户打断时快照播放边界，关闭用户音频前向门并取消当前生成。
  3. 丢弃迟到输出与尚未播放的客户端缓冲，只保留边界前可被听到的内容。
  4. 通过文本重写、供应商截断或已播放音频重注入完成上下文投影。
  5. 修复完成后释放暂存的用户音频，继续识别与生成。

论文报告了什么Reported findings

  • GCM-Bench 含 108 个播放相对指代锚定样例；PACE 将 RAA 从仅取消基线的 25.0% 提升到 96.3%（104/108）。
  • 在 200 个 Full-Duplex-Bench v1 打断样例上，基线与 PACE 的响应率均为 1.000，平均质量分分别为 4.975 和 4.995。
  • 打断路径平均响应延迟由 0.771 秒增至 0.830 秒，论文报告额外开销为 58.7 毫秒。
  • 5 秒回看为 104/108（96.30%），2.5 秒为 103/108（95.37%），10 秒降至 71/108（65.74%）。
对 StreamingModelHarness 的帮助（编辑判断）Fit for StreamingModelHarness (editorial analysis)
  • 编辑判断：这是本批次与 StreamingModelHarness 最直接的系统层改造方向；外部 TTS 使播放进度可观测，也使生成历史领先播放的风险真实存在。
  • 编辑判断：可在架构 A 的 ASR、RAG 与迟到工具注入之外增加 playback commit；工具结果及其生成文本也应在真正播放后再视为面向用户的已提交语义。
  • 编辑判断：它修复的是打断后的分布式一致性，不提供端到端同时听说、回声消除、端点检测或自然 backchannel。

边界与局限Limits

  • 论文指出 GCM-Bench 使用 TTS 构造的用户轨迹，集中于列表任务，并只采用一个评审器和一个实时模型。
  • 播放边界只证明音频已渲染，不证明用户确实注意或理解；缺少可靠音频—语义映射时只能做采样级承诺。
  • PACE 的四个错误中，三个出现在流程型场景并错锚到相邻子动作，细粒度语义边界仍困难。
