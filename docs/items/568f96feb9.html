Metronome: Bound the Cache, Keep the Beat for Real-Time Interaction Model Serving

论文Paper · arxiv · 2026-07-02 · ◈ 12
摘要Summary
Metronome 用有界滑窗 KV、attention sinks 和 AIMD 准入控制防止长期实时会话突然耗尽缓存；5 分钟测试把无界 KV 的 14/20 次崩溃降为 0/20。当前 Harness 判停后才生成，主要应借鉴长会话上限、活性监控和分钟级压力测试，而非直接套用 209 会话容量。 Real-time interaction models -- Moshi, MiniCPM-o, Qwen-Omni -- turn serving into a periodic real-time task: on every frame a session ingests streaming audio and must respond by a recurring wall-clock deadline, while its KV cache grows monotonically and stays pinned for the whole conversation. This regime hides a dangerous failure mode. On a real full-duplex stack, sustained load does not degrade serving gracefully: i

深度讲解Deep dive

Metronome 用“最近 W 个 token 加固定 attention sinks”的有界 KV 和逐帧延迟驱动的 AIMD 准入控制，避免实时交互模型长期驻留时突然耗尽 KV block pool。

它解决什么问题Problem

逐帧接收音频并持续 prefill/decode 的会话会让 KV 单调增长并长期驻留；block pool 饱和后所有请求会一起等待，而空帧仍按时返回，使常规延迟指标看不见服务已失活。

核心方法Core method

系统在 vLLM decoder 启用滑动窗口，只保留最近 W 个 token，并固定最前 S 个 attention-sink token 以减轻窗口滑动后的生成退化。Gateway 按 frame budget 批量 Step，再依据逐帧实际延迟运行 AIMD admission controller；负载有余量时加性提高并发，接近目标时乘性降低。

怎么工作How it works

  1. 客户端持续发送小音频块，Gateway 按帧预算合并到期会话。
  2. GPU worker 对长期 resumable request 做小段 prefill 和有限 decode。
  3. KV manager 释放窗口前 block，同时保留 sink block。
  4. Gateway 用逐帧延迟更新准入上限，超过容量的会话直接拒绝。

论文报告了什么Reported findings

  • Figure 4 与 Appendix Table 1 中，5 分钟测试的无界 KV 共 14/20 次撞墙，窗口 KV 为 0/20。
  • Figure 6 中 Qwen3-Omni-30B 饱和时间预测 145 秒、实测 148 秒；MiniCPM-o 预测 99 秒、实测 114 秒。
  • Figure 7 中以 8 sessions/s 提供 512 个会话时，控制器收敛到约 209 个并发，稳态 p99 为 12ms。
  • Appendix Table 2 中两种策略的 turn-based QA 均为 96/96 会话答对，但 W=512、S=32 的连续生成质量会退化到 0%，窗口过小不能靠 sink 补救。
对 StreamingModelHarness 的帮助（编辑判断）Fit for StreamingModelHarness (editorial analysis)
  • 编辑判断：当前 Harness 在 endpoint 后才生成，通常没有论文所述每帧自回归 KV 无限增长；仍应对长历史和晚注入工具后的上下文设置上限，并做分钟级压力测试。
  • 编辑判断：若未来改为长期 resumable generation，再引入 per-session KV window、活性指标和 admission control；不能直接套用论文的 209 会话容量。

边界与局限Limits

  • 实验只用一张 RTX PRO 6000 Blackwell，admission 与质量实验主要只覆盖 Qwen3-Omni-30B。
  • 多数容量和 MiniCPM 长时实验是单次 fresh run，主要服务实验实际只启用 window、没有完整 sink kernel。
  • 论文不评真实 turn-taking、barge-in 或工具调用，固定窗口也无法回忆窗口外内容。
