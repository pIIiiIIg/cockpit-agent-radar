UEmbed: Unified Sparse and Dense Multimodal Embeddings

论文Paper · hf · 2026-08-02 · ◈ 6
摘要Summary
UEmbed 用一次因果多模态前向同时生成稠密向量和可倒排索引的稀疏词项向量，9B 在 MMEB-v2 得到 71.8/71.0。它可作为 Harness 在 endpoint 后的候选检索 sidecar，但不能增量编码流式输入，也不负责工具授权、外部 TTS 或全双工调度。 Sparse retrieval underpins modern search systems, from web search to retrieval-augmented generation. Existing work has introduced Learned Sparse Retrieval (LSR) to push beyond exact lexical matching toward richer semantics. Yet LSR has so far remained tied to encoder-style bidirectional architectures, and its extension to multimodal settings still relies heavily on auxiliary cross-modal modules. To address these limitations, we introduce UEmbed (Unified Embedding), a decoder-only multimodal embedding model that produces both sparse lexical and dense representations in one causal forward pass. UEmbed appends N learnable special tokens to the input and partitions the vocabulary into N disjoint subsets. Each token's causal hidden state predicts sparse weights over its assigned subset, and the N subsets are concatenated into the full sparse vector. Trained on public data, we release UEmbed at 2B, 4B, and 9B scales. UEmbed-9B reaches 71.8 (dense) and 71.0 (sparse) on MMEB-v2, outperforming multimodal embedding models trained on publicly available data (e.g., RzenEmbed). On BEIR, UEmbed also remains competitive with strong dense and sparse baselines. Furthermore, we demonstrate the practical utility of UEmbed across three dimensions: effectiveness, efficiency, and agentic applications. Overall, UEmbed offers a new paradigm: it unifies dense and sparse embeddings in one model, while further extending sparse retrieval to unify text and multimodal inputs.

深度讲解Deep dive

UEmbed 用一个因果多模态骨干同时生成稠密向量和可进入倒排索引的稀疏词项向量；9B 版本在 MMEB-v2 得到 71.8/71.0，稀疏模式在代理搜索中还能减少检索轮次。

它解决什么问题Problem

学习式稀疏检索通常依赖双向文本编码器；因果解码器的中间位置看不到后续 token，传统最大池化难以获得全局表示。多模态稀疏方案又常需额外跨模态模块，增加训练与部署复杂度。

核心方法Core method

模型先把 248320 个 tokenizer 条目规范化为 184016 个词项，再用语义 k-means 分成 16 个子词表。输入末尾追加 16 个可学习 token，每个 token 通过独立稀疏头预测一个子词表并拼接成 SPLADE 式向量；此前的 EOS 隐状态作为稠密向量。训练联合使用稠密/稀疏 InfoNCE、查询/文档 FLOPS 正则，并用 Qwen3-VL-Embedding-8B 挖掘多模态困难负例。

怎么工作How it works

  1. 把文本、图像、视频或混合输入整理为带任务指令的多模态序列。
  2. 在序列末尾追加 16 个稀疏 token，并保留 EOS 作为稠密表示位置。
  3. 执行一次因果 Qwen3.5 多模态前向，让末尾 token 汇总完整输入。
  4. 读取并归一化 EOS 稠密向量，拼接 16 个稀疏头的词项权重。
  5. 使用余弦、稀疏内积或按模态调权的混合分数检索。

论文报告了什么Reported findings

  • MMEB-v2 的 78 个数据集上，UEmbed-9B 稠密/稀疏总分为 71.8/71.0；公开数据对照 RzenEmbed-V2-7B 为 71.1，但使用专有数据的 Qwen3-VL-Embedding-8B 为 77.8。
  • 2B、4B、9B 的稠密总分为 66.5/70.4/71.8，稀疏总分为 65.5/69.7/71.0，各规模双表示差距不超过 1.0 分。
  • 九个 BEIR 数据集平均 nDCG@10 中，9B 稠密为 56.3，稀疏为 55.2。
  • BrowseComp-Plus 上，9B 稀疏与稠密准确率同为 49.76%，但平均搜索轮次由 33.68 降至 31.05。
对 StreamingModelHarness 的帮助（编辑判断）Fit for StreamingModelHarness (editorial analysis)
  • 编辑判断：UEmbed 适合作为 Harness 的检索 sidecar；它不能随流式输入增量维护表示，宜在 endpoint 后、generation 前编码已定稿轮次。
  • 编辑判断：迟到工具结果可以重新编码和重排，但会增加一次前向；该模型只提供候选证据，不负责工具授权、调度或副作用控制。
  • 编辑判断：模型没有音频或声码器能力，外挂 TTS 路径不受影响；因果编码也不等于原生全双工。

边界与局限Limits

  • 训练语料偏向英文和中文，其他语言的稀疏词项覆盖有限。
  • 超大词表会激活异常或非标准 token，生产环境仍需剪枝与后处理。
  • 长视频、动作识别和时序定位仍弱，混合评分收益也较小且需按模态调权。
  • 论文未给出大规模倒排索引的端到端延迟、显存和吞吐实验。
