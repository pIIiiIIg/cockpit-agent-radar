RestoreKV: Recovering Full-Cache Behavior Under Aggressive Query-Agnostic KV Cache Eviction

论文Paper · hf · 2026-08-01 · ◈ 6
摘要Summary
RestoreKV 在固定总预算内，以一次 LoRA 适配的八 token 前向从完整缓存生成恢复 KV，再与保留的原 KV 合并；Qwen3-4B 的 5% KVzip RULER-4K 由 38.2 升至 73.2。它适合实验性修复 Harness B 路径端点后的激进压缩损失，但需训练 Qwen3-Omni adapter，且不解决 context attraction 或 MoE 同步。 Query-agnostic KV cache eviction compresses a context once and reuses the resulting cache for arbitrary future queries, but performance can collapse under tight budgets. Existing methods primarily improve which original KV pairs are retained. We introduce RestoreKV, which complements this selection-based formulation with learned restoration under the same total KV budget. Our key insight is that, although the information lost through eviction is context-specific, the mechanism for generating its compact complement can be shared across contexts. After context prefill, a few restore tokens attend to the full KV cache in a single LoRA-adapted pass, generating a compact, context-conditioned restore cache. The base importance scorer and eviction rule remain unchanged, and the adapters are disabled for all subsequent queries and decoding. RestoreKV is trained through parameter-efficient self-distillation from the frozen full-cache model, optimizing only 0.4% of the parameters and requiring no task-specific tuning. Across four backbones and four long-context benchmarks, RestoreKV substantially reduces compression-induced degradation. On Qwen3-4B, it improves 59 of 60 paired, budget-matched settings across five base eviction methods; at a 5% budget, it raises KVzip from 38.2 to 73.2 on RULER-4K. Applied to KVzip+, RestoreKV reaches 86.4 RULER accuracy at 16times compression on the KVPress Benchmark, while adding less than 0.5% one-time cache-construction overhead in a 32K-context evaluation. Our project page is available at https://paper.pnu-cvsp.com/RestoreKV/

深度讲解Deep dive

RestoreKV 在固定总 KV 预算内，用一次 LoRA 适配的八 token 恢复前向生成上下文相关 KV，再与保留的原始 KV 合并，缓解激进、查询无关驱逐造成的准确率损失。

它解决什么问题Problem

查询无关驱逐必须在未来问题未知时压缩上下文；现有方法只优化保留哪些原 KV，在 5% 等极低预算下性能显著崩溃。论文改为在驱逐前用完整缓存生成少量合成 KV，补足即将丢失的信息。

核心方法Core method

完整 prefill 后，八个可学习 restore embeddings 通过 rank-8、α=16 的 LoRA 前向访问完整 KV，产生 8LH 个恢复 KV；基础驱逐器只保留 B-8LH 个原始 KV，两者拼接后总量仍为固定预算 B，原 KV 保留原 RoPE 相位。离线训练以冻结 full-cache 模型为教师，在相同 query/teacher answer 上最小化双向对称 KL，只更新 restore embeddings 与 LoRA；推理时 LoRA 仅在恢复 pass 开启，随后关闭，压缩缓存可供未知 query 重复使用。

怎么工作How it works

  1. 离线以 full-cache 教师为每个 backbone/evictor 蒸馏恢复模块。
  2. 在线完整 prefill，并用基础方法计算 KV 重要度。
  3. 运行一次八 token LoRA restore pass，再按固定总预算驱逐并拼接。
  4. 关闭 LoRA，以冻结原模型处理后续 query 和生成。

论文报告了什么Reported findings

  • Qwen3-4B、5% KV 预算下，KVzip 在 RULER-4K 从 38.2 提升到 73.2；QASPER 18.0→28.7、QuALITY 46.3→52.4、LongHealth 61.0→67.5。
  • 五种驱逐方法、四任务、三预算的 60 个配对设置中改善 59 个；唯一退步是 SnapKV/QuALITY、10% 预算的 53.0→51.8。
  • 查询末 token 对非 sink 上下文平均注意力为 full cache 2.73%、KVzip 0.56%、RestoreKV 1.30%；最终预测分布差异由 7.3 降至 3.8。
  • 5% 预算消融中，仅学习 embeddings 得 42.1，固定 embeddings+LoRA 得 71.9，只适配 q/k/v 得 72.4，完整配置 73.2。
  • Llama-3.1-8B、32K 上下文的恢复 pass 增加 0.03–0.04 秒、低于总压缩时间 0.5%，峰值显存增加 84 MB；推理 KV 内存与基础方法相同。
对 StreamingModelHarness 的帮助（编辑判断）Fit for StreamingModelHarness (editorial analysis)
  • 编辑判断：适合作为 B-path 22 点损失的端点后恢复实验：音频结束时完整 KV 仍在，未来 query/工具尚未知；但必须训练 Qwen3-Omni 专用 adapter。
  • 编辑判断：它恢复 full-cache 行为，不会自动消除 context attraction；若完整缓存本身过度吸引旧音频，恢复缓存可能保留该偏差。
  • 编辑判断：论文的无额外 query-time KV 成本不是 MoE 加速；DynamicCache KV=2500 仅约 0.2 ms，110 ms/token 瓶颈仍在 GPU–CPU 同步。

边界与局限Limits

  • 必须在完整 KV 尚未丢弃时运行，不能恢复已经在线删除的历史状态。
  • 恢复器依赖训练时驱逐器：5% 预算下 SnapKV 训练、KVzip 推理只得 42.0，匹配训练为 73.2。
  • 只验证文本 decoder；长期真实任务收益小于合成 RULER，也没有 Qwen3-Omni、音频、晚注入工具或 MoE offload 实验。

代码与模型开放情况Code and model availability

部分开放Partial   RestoreKV 推理实现已合入 Apache-2.0 的 KVPress，Qwen3-8B/Llama-3.1-8B 四套 PEFT adapter 以 CC BY-NC 4.0 发布；但蒸馏训练代码、精确 6,248 样本和论文 Qwen3-0.6B/4B adapter 未发布。
