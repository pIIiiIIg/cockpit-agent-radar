AnovaX: A Local, Multi-Agent Voice Assistant with LLM Planning, Typed Executors, and Adaptive Recovery

论文Paper · arxiv · 2026-07-16 · ◈ 13
摘要Summary
AnovaX 用 JSON 规划、白名单安全检查、类型化执行器、资源锁和有界恢复编排桌面语音任务，但只做单机手工定性验证。其工具调度可借给 Harness 的晚注入执行层；默认仍依赖 Google ASR、Gemini 和外挂 TTS，且没有模型级全双工。 Desktop voice assistants are still dominated by cloud pipelines that ship raw audio off the machine and expose a fixed set of skills. We describe AnovaX, a small local-first assistant that runs entirely on the user's computer and treats the desktop itself as its action surface. 深度讲解Deep dive

AnovaX 把桌面语音助手拆成转写、JSON 规划、安全检查、类型化本地执行器和有界恢复循环，重点是可控工具编排而非新语音模型。

它解决什么问题Problem

传统语音助手技能封闭且执行过程不透明；简单的线性 LLM 工具链又会因单步阻塞、焦点竞争或错误环境假设而让整条计划失败。

核心方法Core method

单个 Python 进程整合唤醒、语音识别、Gemini JSON 规划、记忆、执行器和 pyttsx3。提示规则与 Python 白名单、拒绝词和计划预算形成两层安全检查；工具映射到带 TTL、重试和资源锁的 ChildAgent，核心步骤失败后才进入有界 ReAct 恢复。

怎么工作How it works

  1. 把唤醒词或文本请求与会话、应用和持久事实合并为规划上下文。
  2. Gemini 生成固定 JSON 计划；无 API key 时退化到正则规则。
  3. 每个计划及递归子计划都经过工具白名单、参数拒绝词和预算检查。
  4. 编排器按资源锁和只读性分批运行类型化执行器。
  5. 核心步骤失败时启动有界恢复，结束后由外部 TTS 播报并推送状态。

论文报告了什么Reported findings

  • 能力表覆盖 13 类请求；每个示例手工运行 5 次，至少成功 4 次才标记 works，表中操作类均为 works，删除请求被正确拒绝。
  • 论文日志给出的语音识别、Gemini 规划和十词 TTS 时延分别约为 0.6–1.4 秒、0.7–2.0 秒和 1.2–2.0 秒，安全检查加调度低于 0.05 秒。
  • 关闭 Gemini 后正则回退覆盖 13 类中的 8 类；关闭键鼠锁后，复合任务约每 5 次出现 1 次按键抢跑。
  • 错误应用名案例通过额外一次恢复往返改用网页搜索完成；预执行剩余只读操作约减少 0.7 秒感知恢复时间。
对 StreamingModelHarness 的帮助（编辑判断）Fit for StreamingModelHarness (editorial analysis)
  • 编辑判断：其“转写→一次规划→工具执行→外挂 TTS”与 StreamingModelHarness 的工程形态接近，类型化执行器、锁、TTL 和恢复循环可用于晚注入工具调度。
  • 编辑判断：执行成功仍需由确定性车控层和实际车态回执验证；论文执行器不观察屏幕，也不证明动作已经生效。
  • 编辑判断：它没有连续输入上的模型内流式推理、生成中监听或双向语音通道，不能作为原生全双工能力证据。

边界与局限Limits

  • 仅在单台笔记本上做手工定性检查，没有标准任务集、对照系统、统计显著性或长期可靠性评估。
  • 默认语音识别调用 Google、规划调用 Gemini，因而“完全本地”的表述与具体实现不一致。
  • 手机端使用 PIN over HTTP，没有传输加密、限速或轮换；MJPEG 还会暴露完整屏幕。
