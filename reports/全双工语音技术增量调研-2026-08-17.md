## 一、先说结论

**今日有新论文，但它们全部来自 2026-08-14 的积压批次，而不是最近两天。** 最近两天（08-15 02:30Z 之后）arXiv 全站依然是零投稿零修订。本轮最有决策价值的三件事：一个直接对着项目首音频瓶颈的 TTS 一手制品、一个把“小批量解码”这个词的含义钉死的反面判据、以及一次证明“索引冻结不等于没有论文”的流程验证。

### P0：直接命中当前工程短板

1. **VoiceChat-TTS（2608.13831）是迄今第一个同时具备“流式 TTS + 显式打断 + 不重置 KV + 代码和权重都真实存在”的一手制品，直接对着项目首音频约 3 秒这个最大瓶颈。** 论文事实：并发 1（即 batch=1，与项目口径一致）下在 RTX A6000 上，声学 token ITL 7.16ms、编解码 2.46ms、合计 9.62ms，而每帧对应 80ms 音频；同口径重测的 Qwen3-TTS-12Hz-1.7B 为 15.44 / 4.90 / 20.34ms。制品事实（本轮现场逐文件核实）：代码确实在 `NVIDIA-NeMo/Speech`（Apache-2.0、18,144 star）内，`nemo/collections/speechlm2/models/duplex_ear_tts.py` 等 31 个路径命中；权重在 `nvidia/NVIDIA-NemotronLabs-VoiceChat-11B`（OpenMDW-1.1、非门控）。编辑判断：这是本周唯一一个能把“本地流式 TTS”从纸面推进到可复核对象的更新，**但它不能直接替换 Edge TTS**，原因是两条硬事实——它只有英文评测，且 TTS 子模块（977M）被封在一个 44,382,749,892 字节的单一 `model.safetensors` 里，没有独立发布。详见第 1 节。
2. **DeaMoE（2608.14385）把“小批量解码”这个词的实际含义钉死了，这对项目是一条比任何加速方案都更有用的筛子。** 论文事实：标题与摘要都主打 small-batch decoding，但图 3 的横轴从 **batch 4** 起步，加速比 batch 4 时 1.02×、batch 32 峰值 1.33×、batch 128 回落 1.03×，呈非单调；论文自述“加速比随 batch 由 4 增长到 32 而上升”。编辑判断：项目是 batch=1，位于该曲线起点之外且更低的一侧，按其自身趋势外推收益低于 1.02×，实质为零。更关键的是它是**预训练期架构改动**（自行预训练 7.3B、110B token），对既有的 Qwen3-Omni 权重不可用。这使它成为“KV/服务反模式家族”的第四个成员，但成因与前三个不同——不是“需要大 batch”，而是“最小可评测 batch 就不是 1”。详见第 2 节。
3. **同一篇 DeaMoE 顺带给了 `decode-loop-cudagraph-static-kv-v1` 第三条独立旁证。** 论文原文：“我们也为 DeaMoE 与所有基线启用了 vLLM 的 CUDA Graph 执行。由于解码本身对时延敏感且通常运行在小批量区间，采用 CUDA Graph 是业界降低 kernel 启动开销的通行做法。” 编辑判断：08-14 由 FlashDrive 提出、vToken 佐证的“图捕获兼容性是硬筛子”，现在有了第三个来源，而且是把它当作**基线也必须启用的标配**而非优化项。这提高了该候选的先验，但**不改变执行顺序**：仍然先做无同步 `index_select`+`bmm` 快路径，再把整环图捕获作为第二个独立变量。

### P1：适合形成下一阶段架构

1. **VoiceChat-TTS 的“确定性静音帧”是一个可以脱离其模型单独借用的机制，直接落在项目两个在办候选上。** 论文事实：打开 `Force Silence` 后 IOR@320ms 由 96.8% 升到 100.0%，平均停止时延由 228.3ms 降到 89.9ms，1 秒内泄漏由 169.1ms 降到 55.8ms，后续轮次的 AI-CER 由 0.255% 降到 0.095%，且**全程不重置 KV cache**。仓库事实（本轮逐行核实）：`duplex_ear_tts.py` 第 1193 行的 `inference_force_speech_silence_on_eos` 与 `get_codec_silence_frame()` 与论文描述**逐字对应**——编码 10 秒纯静音波形、对每帧的 31 个 token 组合计数、取出现频次最高的那一帧。编辑判断：这条机制的可迁移部分不是模型，而是“把收尾定义成一个确定性的静音写入动作，而不是等待自然衰减”，这正是 `playback-boundary-ledger-offline-v1` 缺的那一块。详见第 1 节。
2. **DuplexWorld 的数据集正式发布了，但发布的是场景规格而不是评测能力，这个区分必须写清楚。** 制品事实：`CentificAIResearch/Duplex-World` 于 2026-08-15T16:50:32Z 创建，CC-BY-4.0、非门控，标注 `arxiv:2608.10716`；六个领域文件加 `all.jsonl` 共 10 个文件，**总计 18 条**（banking 3、healthcare 2、insurance 2、logistics 1、pathfinding 9、travel 1），`all.jsonl` 的字节数 103,426 与六个领域文件之和**完全相等**。每条约 10KB，含 `decision_tree`、`evaluation_criteria`、`task_params` 等 17 个字段。编辑判断：**没有音频，没有 harness 代码**——而 08-11 记录的 DuplexWorld 最有价值的结论恰恰是“三个 harness 旋钮对 Pass@1 的影响与换系统相当”，那部分依然不可复现。可借用的只有评测标准的字段结构。详见第 3 节。

## 1. VoiceChat-TTS：面向交互式 Agent 的低时延连续语音合成（NVIDIA）

论文（arXiv v1，2026-08-13T23:37:07Z 提交）：https://arxiv.org/abs/2608.13831

官方代码：https://github.com/NVIDIA-NeMo/Speech

官方权重：https://huggingface.co/nvidia/NVIDIA-NemotronLabs-VoiceChat-11B

### 它是什么

一个**只做语音合成**的流式 TTS 模块，由 LLM 的文本 token 流直接驱动，设计目标是在全双工交互中“一直在线”：没有文本可播时输出静音，收到中断控制 token 时立即转静音，并且跨轮次不重置 KV cache。作者为 NVIDIA，第一作者 Edresson Casanova。

**同源关系必须先说清楚**：这不是一项独立的新工作，而是 08-12 报告已记录的 **NVIDIA NemotronLabs VoiceChat 11B 全双工模型的 TTS 组件**的单独成文。论文自述“VoiceChat-TTS 的代码已在 NVIDIA NeMo Speech 中公开，模型 checkpoint 作为 NVIDIA-NemotronLabs-VoiceChat-11B 的一部分在 Hugging Face 上提供”。按去重纪律，本节记为**同一技术脉络的组件级论文**，不计为新的开源模型发布；08-12 记录的那些整机数字（FDB-v3 工具选择 82.5%、参数准确率 44.2%、Pass@1 33%、口语 BFCL-v3 平均 56.1%）与本节的 TTS 数字不可混用。

### 核心方法

- **直接消费 LLM 文本 token 流**。为解决 LLM 子词词表与 TTS 训练语料不匹配（很多子词在 TTS 语料中罕见或缺失），引入 **Character-Aware Subword Encoder**：每个输入子词先拆成字符序列再编码。使用 NVIDIA Nemotron Nano 2 的子词 tokenizer。
- **连续时间轴上的静音建模**。解码器跨会话时间持续运行，没有 agent 文本时产生静音，而不是停机等待。
- **显式中断控制 token**。中断以控制 token 注入；`Force Silence` 打开时，推理会在与中断 token 对齐的位置**注入一帧固定的静音音频 token**，把生成流确定性地推向静音。该静音帧的取法是：用 codec 编码一段较长的纯静音，取出现频次最高的那个 31-token codec 帧。
- **不重置 KV cache**。中断后模型继续在同一 KV 上生成下一轮，论文用 AI-CER 只统计后续 assistant 轮的方式验证了恢复能力。
- 架构规模：全模型 977M 参数 = 778M 基于 Gemma 3 的流式 TTS 模块 + 199M codec 模型。输出 22kHz 波形，帧率 12.5Hz，31 个 codebook，**每个音频 token 帧对应 80ms 音频**。

> 源内命名不一致，本报告不代为取舍：对照模型的名字是 `Qwen3-TTS-12Hz`（12Hz），而论文正文两处均写“同样工作在 12.5 Hz”。两个值都记录。

训练配置（用于估计迁移代价）：第一阶段仅用单轮 TTS 数据预训练 1.4M 步、**8 张 A100**；第二阶段用完整混合数据微调 200k 步、**32 张 H100**。微调用 Lhotse 动态分桶，每批约 240 秒音频；数据配比为单轮 TTS 40%、词与专名列表 15%、真实对话 10%、合成全双工对话 35%。优化器 AdamW，学习率 4×10⁻⁵。

### 对 StreamingModelHarness 的帮助

分三层，且第三层是否定性的。

**第一层，它是项目首音频瓶颈方向上第一个制品齐全的一手对象。** 项目首音频 P50 为 2,918ms（A）／3,491ms（B），而首文本最快只要 131ms，瓶颈明确在 Edge TTS。此前 TTS 方向的候选 `omnivoice-local-tts-16step-v1` 一直卡在 Luna-TTS 项目页无代码、无权重、无许可证且页内自相矛盾（1.28s 块 vs 0.36s 块）的状态上，其 41.6ms 至今不可用于跨系统比较。VoiceChat-TTS 的不同之处在于**代码与权重都能逐文件核到**，并且它的时延是在**并发 1** 下测的，与项目 batch=1 的口径一致，不需要做并发折算。

**第二层，`Force Silence` 是可以脱离模型单独借用的机制。** 项目的 `playback-boundary-ledger-offline-v1` 与 `tool-hold-message-first-audio-v1` 都缺一个明确的“收尾动作”定义。VoiceChat-TTS 给出的形式非常具体：把收尾实现成**在中断对齐位置确定性地写入一个预先算好的静音帧**，而不是让声学流自然衰减；且写入后不重置 KV，模型仍能正常产出下一轮。它给出的收益量级是停止时延 228.3→89.9ms、1 秒泄漏 169.1→55.8ms。编辑判断：项目可以在自己的播报链路上实现同构的“确定性收尾写入”，**但这两个数字不能借用为项目的预期值**——它们是在英文 FDB 音频上、用该模型自己的 codec 帧测的。

**第三层，它现在还不能替换 Edge TTS，有两条硬阻断。**

- **只有英文。** 训练与评测语料是 LibriTTS、Fisher 及内部英文对话，全文没有任何中文数据或中文指标。项目是中文车控，跨语种泛化未知。
- **TTS 子模块没有独立发布。** 本轮逐文件核实：`nvidia/NVIDIA-NemotronLabs-VoiceChat-11B` 仓库里只有**一个** `model.safetensors`，大小 **44,382,749,892 字节**；论文所述的 977M TTS 模块以 `config.json` 中 `model/speech_generation/*` 子树的形式存在（`codec_config.num_quantizers = 31`、`data.frame_length = 0.08`、`target_sample_rate = 22050`，与论文完全对应），但**没有单独的权重文件**。HF 上以 `VoiceChat-TTS`、`voicechat_tts` 检索均返回 0 条，不存在独立的 TTS 模型页。也就是说，要用这个 TTS，当前只能先取回约 44.4GB 的整包。

**可执行动作（本轮不新增 H20 候选，只新增一条只读前置任务）**：对 `NVIDIA-NeMo/Speech` 中 `duplex_ear_tts.py`、`nemotron_voicechat.py` 与 `examples/speechlm2/conf/nemotron_voicechat.yaml` 做只读审阅，回答两个可判定的问题——(a) 977M TTS 子模块能否在不加载 11B 主干的前提下单独实例化与推理；(b) 其 codec 与项目现有音频链路的采样率（22,050Hz vs 项目 16kHz）如何对接。这两个问题有明确答案之前，不进入单变量替换实验。

## 2. DeaMoE：把“小批量解码”的下界钉在 batch 4（反面判据）

论文（arXiv v1，2026-08-14T15:25:32Z 提交）：https://arxiv.org/abs/2608.14385

### 它是什么

一个 MoE **架构**改动：把专家分组为若干“部门（department）”，同部门专家共享大部分参数、各自只保留少量私有参数，并配一个两阶段路由（先路由到部门、部门内再分配到专家），目的是减少解码时反复加载专家权重的访存量。作者来自中国科学技术大学等。

本节把它写成反面判据，因为它对项目的价值**不在于能不能用，而在于它精确定义了一个此前被含混使用的词**。

### 核心方法

- 专家按“专业领域”分组进部门，同部门共享公共骨干参数，每个专家仅保留少量私有参数以体现差异。
- 两阶段路由：先把所有 token 路由到对应部门，部门一次性统一处理收集到的全部 token；再由部门把 token 分给具体专家做差异化处理。目的是提升单个解码步内跨 token 的权重复用。
- 实现上集成进 vLLM v0.13.0，用 Triton 实现自定义算子，复用 vLLM 原生 fused MoE kernel 所用的 Grouped GEMM 原语，只改 token 索引逻辑。

### 论文结果

- 摘要：相对 vanilla MoE，每步加载权重最多减少 **50.9%**；预训练 7B 模型在 A40 上端到端 TPOT 最高 **1.33×**；DeepSeek-V3 在 A40 与 H100 的微基准峰值分别为 **2.00×** 与 **1.97×**。
- 端到端（图 3，单张 **NVIDIA A40**，vLLM，连续请求流）：加速比 **1.02×–1.33×**，随 batch 非单调变化。逐点标注为 batch 4→1.02×、8→1.14×、16→1.26×、24→1.32×、32→**1.33×**、40→1.30×、48→1.26×、64→1.20×、96→1.13×、128→1.03×。论文原话：“加速比随 batch 从 4 增长到 32 而上升（峰值 1.33×），随后逐渐下降，在 batch 128 时接近 1.03×。”
- 吞吐口径：TPOT 预算 30ms 时基线与 DeaMoE 分别支撑 batch 64 与 96（1.50× 吞吐）；20ms 预算时为 24 与 44（1.83× 吞吐）。
- 模型质量：自行预训练 7.3B 的 DeaMoE 与等预算标准 MoE，各用 **110B token**（RedPajama-v1）。困惑度 PTB 61.91 vs 64.33、WikiText-103 20.31 vs 20.18、WikiText-2 20.33 vs 20.43，论文结论是质量持平。
- 微基准 batch 范围同样为 **4 到 128**。

### 对 StreamingModelHarness 的帮助

**它的帮助是让项目少做一次评估，并给一个既有候选加一条旁证。**

**第一，它给出了一条可直接复用的筛子。** 项目此前的反模式家族判据是“收益需要大 batch 或长上下文”（OasisKV、vToken）。DeaMoE 不属于这一类——它明确面向低时延交互、明确反对大 batch。但它**最小的评测点就是 batch 4**，且加速比在 batch 4 处仅 1.02×、并随 batch 减小而下降。项目是 batch=1，按其自身趋势外推收益低于 1.02×。编辑判断：应把家族判据从“需要大 batch”扩写为**“最小可评测 batch 是否为 1；若不是，且收益随 batch 减小而单调下降，则直接否”**——这条更普适，且能一次性挡掉整类以“small-batch”为卖点却从 batch 4 起步的工作。

**第二，即使 batch 口径吻合，它对项目也是不可用的。** 两条独立原因：(a) 它是**预训练期架构改动**，论文自述采取“pre-training-first”路线、从零预训练；项目用的是既有的 Qwen3-Omni 权重，无法套用。(b) 它攻击的瓶颈是**访存带宽**（专家权重加载），论文原话是“有效降低了每个解码步的访存流量，从而缓解 A40 GPU 上的带宽瓶颈”；而项目已实测自身瓶颈**不是带宽**——解码速度不随 KV 长度变化，实测 110ms 是按 config 实算的带宽下限（5090 口径约 3.0ms）的约 36 倍，根因是每 token 约 816 次 GPU→CPU 同步。**同一个词“解码慢”，两边指的是完全不同的东西。**

**第三，它为 `decode-loop-cudagraph-static-kv-v1` 提供了第三条独立旁证，且是最强的一种形式。** 论文在实现小节写：“我们也为 DeaMoE 与所有基线启用了 vLLM 的 CUDA Graph 执行。由于解码本身对时延敏感且通常运行在小批量区间，采用 CUDA Graph 是业界降低 kernel 启动开销的通行做法。” 编辑判断：这不是把图捕获当成一项优化来宣传，而是把它当作**基线也必须具备的标配**，否则对照不公平。这抬高了该候选的先验。但**顺序不变**：项目仍须先落地无同步 `index_select`+`bmm` 快路径，再把整环图捕获作为第二个独立变量单独测量，两步不得合并成一次结论。

一条**仅供参考、不可直接相减**的量级观察：DeaMoE 的基线（未经其架构改动的 vanilla MoE，vLLM，已开 CUDA Graph）在 A40 上于 20–30ms 的 TPOT 预算内可支撑 batch 24–64。项目在更强的 H20 上、batch=1、却是 110ms/token。四条免责必须同时写：模型不同（7.3B vs Qwen3-Omni 30B-A3B）、框架不同（vLLM vs HuggingFace）、硬件不同（A40 vs H20）、batch 不同（≥4 vs 1）。因此这**不能**作为“110ms 高出多少倍”的定量依据，只能作为一条与项目自身根因分析方向一致的定性佐证——即 110ms 更像实现问题而非硬件问题。

## 风险提醒

1. **不要把 VoiceChat-TTS 的 9.62ms 当成首包时延。** 它是 **ITL**（稳态下产出一帧声学 token 的墙钟时间，每帧对应 80ms 音频）。论文在引言里讨论 TTFA，但**结果部分从未报告自己的 TTFA/首包数字**，该值记为未知。项目的瓶颈恰恰是首音频（P50 2,918ms），两者不是同一个量。
2. **不要把 VoiceChat-TTS 读成“可以替换 Edge TTS 了”。** 两条硬阻断：全文只有英文评测，无任何中文数据或指标；977M 的 TTS 子模块**没有独立权重文件**，被封在 44,382,749,892 字节的单一 `model.safetensors` 内，HF 上不存在独立的 TTS 模型页。
3. **“更快”不等于“更好”。** 同一张表里 Qwen3-TTS-12Hz-1.7B 在 CER 0.34%、WER 1.01%、SECS 0.827、Squim-MOS 4.45 四项上全面优于 VoiceChat-TTS 的 1.00%/2.00%/0.757/4.380，论文自己也写“常规 TTS 系统取得了最好的单轮可懂度、说话人相似度与预测整体语音质量”。任何替换实验必须同时报时延与质量两侧。另注意 Squim-MOS 是非侵入式**预测**质量，不是主观 MOS。
4. **代码许可证不传递给权重，这次是 Apache-2.0 与 OpenMDW-1.1。** NeMo 代码为 Apache-2.0，VoiceChat-11B 权重为 OpenMDW-1.1。**本轮未逐条阅读 OpenMDW-1.1 正文**，其义务记为未知；实际使用前必须先读许可证正文。
5. **DeaMoE 的“small-batch”下界是 4，不是 1。** 加速比 batch 4 时仅 1.02×、batch 32 峰值 1.33×、batch 128 回落 1.03×，且随 batch 减小而下降；项目是 batch=1，按其自身趋势外推收益低于 1.02×。此外它是**预训练期架构改动**且攻击的是**带宽**瓶颈，而项目实测瓶颈不是带宽（速度不随 KV 长度变化，与带宽下限差约 36 倍，根因是每 token 约 816 次主机同步）。三条理由各自独立成立。
6. **不要用 DeaMoE 的基线 TPOT 反推项目的 110ms 高出多少倍。** 模型、框架、硬件、batch 四项全部不同（7.3B vs 30B-A3B、vLLM vs HuggingFace、A40 vs H20、≥4 vs 1）。它只能作为方向一致的定性佐证。
