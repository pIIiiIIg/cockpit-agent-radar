### 核心方法（仓库确认与新增的实现细节）

论文侧方法 08-13 已记录，不重复。以下是**仓库公开后才可核实、论文正文未给出**的实现级事实，全部来自 README 与 `recipes/KD1/KD1.yaml` 文本：

- **STFT 配置**：`sampling_rate: 16000`、`n_fft: 400`、`hop_size: 100`、`win_size: 400`。即 25ms 分析窗、**6.25ms 跳步、160 帧/秒**。README 说明 STFT/iSTFT 两侧均为 `center=False`，算法时延因此被一个 25ms 窗界定。
- **因果化改动逐项**：卷积用非对称因果 padding（左侧补 `K-1` 个零、右侧不补，`_get_causal_padding_2d`）；`InstanceNorm2d` 换成沿时间因果的 `ChannelLayerNorm2d`；时间轴 Mamba 单向、无前瞻；**频率轴 Mamba 仍是双向**（README 原话：“the frequency axis is not a causal axis”，与 08-13 从论文记下的一致）；每个 cTF-Mamba 块后额外加一个 MLP。
- **三个固定大小的推理状态被点名**：帧缓冲（保存因果时间卷积所需的前 `K-1` 帧）、`conv_state`（SSM 前深度可分离一维卷积的 `d_conv - 1` 步）、`ssm_state`（循环隐状态 `h_t`）。切换接口是 `SEMamba.set_streaming(True)`，跨句清理是 `reset_streaming_state()`。
- **两种流式模式**：`--streaming_mode realtime` 为一帧一次前向，`chunked` 为整块一次前向；`--chunk_size` 默认 **1600 采样（100ms @ 16kHz）**。`inference_KD1.sh` 的默认组合是 `--streaming True --streaming_mode realtime --chunk_size 1600`。
- **PCS 后处理默认关闭**：`--post_processing_PCS False`，`KD1.yaml` 中 `use_PCS400: False`。
- **KD1 模型配置**：`hid_feature: 64`、`compress_factor: 0.3`、`num_tfmamba: 1`、`d_state: 16`、`d_conv: 4`、`expand: 4`、输入 2 通道（幅度 + 相位）、输出 1 通道。
- **训练配置**（用于估计迁移代价）：1,200 epoch、batch 2、`segment_size: 40000`（2.5s @ 16kHz）、AdamW、初始 lr 5e-4、默认 2 GPU；蒸馏 `lambda_out: 0.5`、`lambda_feat: 0.1`、ramp 为前 10% 步数、教师块输出取 8 层均值、两侧逐样本归一化，并在前 2% 步数冻结由教师初始化的 `dense_encoder`/`mask_decoder`/`phase_decoder`。

**第二层，CPU/MPS 推理路径改变了这个候选的部署算术。** 08-13 与 08-14 都写过同一条反对意见：RTF 0.11–0.29 是在 RTX 5090 上测的，前端要与主模型抢同一张卡。仓库公开后，`mamba_install_mps` 提供了跳过 CUDA 编译的纯 PyTorch 路径，README 支持矩阵把 CPU 与 MPS 的推理都标为可用。编辑判断：如果 KD1（1.05M 参数、20.56 GMACs/s）能在座舱主机的 CPU 上实时跑，前端就不占用主模型的 GPU，整个候选的成本结构完全改变。但这是**假设不是结论**——见下方局限。

## 风险提醒

1. **不要把“RT-SEMamba 发布代码”读成“可以上前端了”。** 它今天获得的是**可验证性**，不是有效性。全仓库没有一个下游 ASR CER 或工具正确率数字；“PESQ 3.18 能让车控更准”在今天之后依然是零证据的推测。分桶归因没做完就上前端，会同时改变噪声致错与理解致错两类误差，且无法归因。
2. **25ms 不是它给项目增加的时延。** 25ms 是由 `win_size: 400` 与 `center=False` 界定的**模型算法时延**；`inference_KD1.sh` 的默认管线块长是 `--chunk_size 1600`，即 100ms；实测每帧墙钟耗时另算。三个数必须分开报，混成一个会低估约 100ms 量级，而项目首动作 P50 只有 700–1,094ms。
3. **“支持 CPU/MPS”不等于“CPU/MPS 上能实时”。** README 只给了 RTX 5090 上的 RTF，并明确声明不对其它设备作保证；CPU 与 MPS 的 RTF **未知**。且 MPS 上因固定约 32ms 的每次调用开销，`rt_enhance.py` 改为按 100ms 块整批前向，**逐帧性质在该后端实际被放弃**——这与 08-13 定下的“1 帧进 1 帧出”硬要求在该后端上不再成立。
