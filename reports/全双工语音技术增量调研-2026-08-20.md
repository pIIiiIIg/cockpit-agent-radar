### 它是什么

一套架在 Qwen3-TTS 之上的**严格因果**流式 TTS 框架。论文给出的因果性定义是一条硬约束（式 1）：第 u 个声学 token 只能依赖于**其生成时刻之前已观测到的文本**、此前已生成的声学 token、以及从上一段继承来的语音状态。换言之，**前瞻为零**——这一点与既有工作的分界线，论文在 §2 讲得很清楚：LiveSpeech / SyncSpeech / SpeakStream 用的是固定前瞻，MagpieTTS-LF 用的是标点感知分块加历史文本，"these methods reduce sentence-level waiting but still depend on future tokens, so their latency remains coupled to the upstream generation rate"。

论文用来支撑"零前瞻是负担得起的"这个前提的论证很干净：**文本信息密度高，语音时间上冗余**。它定义声学-文本膨胀比 ρ = 声学解码步数 / 文本 token 数，指出 ρ 通常远大于 1，因此"把当前已有的文本先念出去"这件事本身就为后续 token 的到达争取到了时间。

### 核心方法（或核心架构）

选 Qwen3-TTS 作骨干的理由，论文写得很具体，是三条工程属性而非效果：**可计数的声学输出、可迁移的解码状态、可观测的剩余容量**（"its KV-cache-aware decoder exposes the remaining capacity in cache positions"）。

**（一）Causal Commitment（因果提交），管"什么时候可以开口"。** 分两个耦合部件：

- **不确定性感知的语义就绪判定。** 前端维护一个待定后缀 U_t，凡是发音仍可能被后续字符改写的跨度就压住不发。论文自己的例子是英文的 `He finished 3`——后续可能变成 `3 laps`（读 three）或 `3rd`（读 third），两者在词还没写完之前就已分叉，而**已经播出去的音频无法撤回**。规则覆盖数字、单位、符号、缩写、标点；一旦释放就永不修改；输入结束时残余后缀按同一套规则闭合。
- **容量自适应、标点感知的分段（CAPS）。** 把分段建成一个带约束的最优化问题：边界分 1/2/3/Hard 四档（句末 / 从句级 / 更弱标点 / 非标点硬切），代价 c(1)<c(2)<c(3)<c(Hard)，约束是每段的 KV cache 占用 G(S;ξ) 不得超过可用容量 B，目标是段数罚项 λ_seg 与边界代价之和最小。离线解由动态规划给出（式 4），复杂度 O(n²)，或段长上界为 C 时 O(nC)。在线侧用 EMA 估计 ρ̂：初值 **6.0**，β 常态 **0.1**、溢出后 **0.5**，ρ̂ 截断到 **[2, 10]**，(α₁,α₂,α₃)=(**0.7, 0.8, 0.9**)，因而段数因子上界 10/7≈1.429。实现是前端里的一个 token 驱动有限状态机，**容量上限 B 直接从已加载的引擎读出**。最多允许 2 个文本段排队，声学解码严格串行。

**（二）Causal Speech-State Inheritance（因果语音状态继承），管"下一段从什么状态接着说"。** 两条独立状态通路：

- **完整 Code2Wav 状态包**跨段搬运，含其 KV cache、卷积状态、转置卷积状态与帧索引，用来热启动下一段的波形解码。
- **末尾 H 个 token 对齐的 Talker 状态**作为有界历史记忆。H 是与流长度无关的全局超参，**实验中固定 H = 4**，因此继承的声学上下文被界定在 O(H)。

两条通路都受一个**健康检查**门控：前一段必须收到完整输入、消费完所有已释放文本、声学解码正常终止、实现膨胀比 ρ_k ∈ **[1, 12]**、且 Code2Wav 快照完整；任一不满足则两条状态全部清零、从默认状态重启。

注意力侧用一个**固定因果先验**（式 10）：偏置 b(d) 在 0≤d≤4 时为 −d²/8，d≥5 时为 log 0.1，**d<0 时为 −∞**，因此未来位置权重恒为零；在内容相似度相等时，当前位置相对于距离≥5 的位置有 **10:1** 的先验优势。注入是**有界**的：门控分数 s_u 取归一化注意力集中度 ∈[0,1]，增益 g_u = 0.015(0.5+0.5·s_u)，故 **0.0075 ≤ g_u ≤ 0.015**，扰动满足 ‖z′_u − z_u‖ ≤ 0.015·max‖m_j‖。

**编辑判断：这两个"有界"是这篇论文在工程上最讲究的地方。** H 固定为 4、增益夹在 0.0075–0.015 之间、ρ̂ 截断在 [2,10]、健康检查一票清零——每一处都把"跨段继承"这件本质上会累积漂移的事情限死在常数代价内。项目若要借鉴，**先借这套边界纪律，再谈具体数值**。

### 对 StreamingModelHarness 的帮助

**第一，它是目前唯一一篇同时满足"中文有正文指标 + 有首包时延 + 硬件与项目同级"的 TTS 工作。** 追踪表上此前的三种缺口它各补了一块：Luna-TTS 无制品且首包时延要多卡；VoiceChat-TTS 是纯英文，且其 9.62ms 是 ITL 不是 TTFA；FireRedTTS3 中文与制品都过关但零时延数字。X2Streaming-TTS 的中文 CER 0.78% 与 15.8ms TTFT 出自同一篇、同一套系统。

**第二，可以直接搬进项目的是三个机制，而不是三个数字。**

1. **"不确定性感知缓冲"直接对应中文场景里最容易出错的一类。** 论文用英文序数词举例，但同一问题在中文里更常见也更严重：车控场景的"打开空调 26"到底是"二十六度"还是"二六"、"降到 3 档"、"播放第 2 首"——**在数字后面那个字到达之前，读法是不确定的**。项目目前的外挂 Edge TTS 走的是整句合成，天然回避了这个问题；一旦转向 token 级流式，这个问题会立刻出现。**这条机制应当在切流式之前就设计进去，而不是等出问题再补。**
2. **CAPS 把"分段"从纯文本问题改造成"文本 × 声学容量"的联合问题。** 它的核心不是那个 DP，而是那条约束：**段的 KV cache 占用不得超过引擎实际可用容量，而这个容量是从已加载引擎读出来的、不是写死的常数**。项目自己正在处理 MoE 解码与 KV 账本，这条"容量从引擎读、不从配置猜"的做法可以直接借鉴到判停与分段逻辑上。
3. **状态继承给了一个可算的成本上界。** 论文只抽象地说"完整 Code2Wav 状态包"，而同机构仓库里的一份官方设计文档把这笔账算死了（见下）。

**第三，那份状态尺寸文档是本轮意外收获，可能比论文本身更实用。** `Qwen3TTS-Streaming` 仓库的 `docs/dev/investigation/code2wav_state_size.md` 给出 Code2Wav 的状态构成与字节数（**这是官方仓库的一手文档，不是论文正文，引用时必须区分**）：

- 解码器配置：`num_hidden_layers` **8**、`num_key_value_heads` **16**、`hidden_size` **1024**、`head_dim` **64**、`latent_dim` 1024、`decoder_dim` 1536、**KV 滑动窗口 72**（来自 `Qwen3TTSTokenizerV2DecoderConfig` 的官方默认 `sliding_window=72`）。
- KV cache：单层单路 K+V = 2×16×72×64 = 147,456 元素 = **294,912 字节**（BF16）；8 层单路 **2,359,296 字节 ≈ 2.25 MB**。
- 卷积历史：17 个状态共 131,752 元素，单路 **263,504 字节 ≈ 0.257 MB**。
- 转置卷积重叠：4 个状态共 9,120 元素，单路 **18,240 字节 ≈ 0.018 MB**。
- **单路合计 ≈ 2.53 MB（BF16），且与解码长度无关**（滑动窗口固定 72 步）；16 路合计 ≈ 40.3 MB；存 FP32 则翻倍至约 80.6 MB。

**编辑判断：这条"跨段继承的状态成本是每路 2.53MB 且与长度无关"是可以直接进项目设计文档的数字。** 它同时回答了两个项目问题：其一，若要在打断后**保留**而非重置语音状态（PACE 的 playback boundary ledger 与 VoiceChat-TTS 的 "KV never reset" 都指向这个方向），代价是可计算且有界的；其二，滑动窗口 72 步意味着声学侧的历史依赖本来就只有约 6 秒，**跨越 6 秒的状态继承在架构上没有意义**。

**第四，那份 README 的时延方法论比论文严谨，应当照抄进项目自己的埋点规范。** 详见"局限与开放状态"。

2. **文本 token 按固定速率喂入。** 论文自己声明："Text tokens are supplied at a fixed rate for controlled evaluation; a deployed upstream language model may exhibit variable token-generation latency."**上游是我们自己的 MoE 主模型，其 110ms/token 且抖动未知，因此论文的 ρ 论证（"声学侧的时间足以掩盖文本到达"）在项目条件下不能默认成立**——ρ 掩盖不掩盖得住，取决于上游吐字速度与声学速度之比，而项目的上游比论文的实验条件慢得多。**这是项目采纳该方法前必须自测的第一件事。**
3. **两个自建评测集均未命名未发布**，Table 2/3/4 第三方不可复现。
4. **模型命名与帧率存在未解的不一致，且是第二次遇到。** 论文表 1 写 `Qwen3-TTS-12Hz-1.7B`；仓库 README 的吞吐口径写"每 **80ms** 音频帧"（对应 **12.5 Hz**）；而 `code2wav_state_size.md` 写"滑动窗口 72 约合 12 Hz 编解码器下的 6 秒上下文"（对应 **12 Hz**）。**08-19 已经在 VoiceChat-TTS 上记过完全同形的一处（基线名 `Qwen3-TTS-12Hz` 而正文两次写 12.5 Hz）。两处独立出现，说明这是 Qwen3-TTS 生态自身的命名与实际帧率脱节，不是单篇笔误。** 本报告不替其选择，两个值都记为并存，**凡由帧率推导的任何时长换算一律标注所用取值**。
5. **Table 4 的最弱基线处于崩坏区间**（CosyVoice 2-S 完全正确朗读率 0.0%、语义保持 0.00%），与 08-19 对 2608.14812 的告诫同理：**崩坏区间的改善幅度不可外推到精细区间**。
6. **主观评测 120 名听众，但论文未说明母语构成、未报告评分者间一致性、未做显著性检验。**
7. **Table 2 的"纯标点"策略硬切数记为 1（而非百分比），与同列其余三行的百分比口径不同**，论文未加说明。按原样记录。
8. **全文没有给出总参数量**，也没有给出训练成本——因为论文没有训练章节。

**综合判断：进入"只读审阅 + 离线实测"，不进入线上替换，也不列为候选。** 理由有三：论文声明的代码地址失效；疑似实现依赖 NGC/TensorRT 这条项目尚未评估的部署链；以及第 2 条——上游 token 速率这个前提在项目条件下未经验证。**但它是本轮唯一一篇值得排到首音频待办最前面的工作。**

## 2. X2-Turn v1→v2（2608.10878）：一次只改两行、却翻转开放状态的修订

- 论文：`https://arxiv.org/abs/2608.10878`（v2，published 2026-08-11T12:54:52Z，updated 2026-08-19T03:16:50Z）
- 代码：`https://github.com/X-Square-Robot/X2-Turn`（Apache-2.0）
- 权重：`https://huggingface.co/x-square-robot/X2-Turn-4B-0812`（Apache-2.0，非门控）

内容见"一、先说结论"中的 P0（并列）一节，此处只补两条方法学记录。

**第一，这是追踪表上第三个完成的 v1→v2 逐版差分，也是三者中差分最小、影响最大的一个。** 三次的结果各不相同：StreamTTT（2608.13416）改了 184 行、结论不变；Ambisonics（2608.14097）只改了 2 字节，且改的是标题里一个漏掉的字母 `l`；本次 X2-Turn 只加了一句话，**却把一项挂了 8 天的开放状态判定整个翻转**。

**08-19 记下的规律"差分大小完全预测不了结论是否改变"，本次是第三次印证，且提供了一个新的极端：内容改动量最小的一次，带来的判定改变最大。** 由此追加一条操作规则：**逐版复核时，除了重跑原判定所依赖的字词/数字计数，还必须单独比对两版的 URL 集合（超链接注解 + 裸 URL）**——本次的全部实质变化就藏在裸 URL 从 4 条变成 5 条这一个差别里，而任何只看数值 token 的比对都会漏掉它（数值 token 只从 364 变成 365，且新增的那个是页边日期戳，纯属噪声）。

**第二，论文结论未变这件事必须与开放状态分开写。** v2 没有新增任何实验、没有改动任何数字。08-19 记录的三条局限原样保留：联合训练损害 ASR（AISHELL-1 从 2.57 劣化到 3.94）；EasyTurn-zh 在 τ=480ms 下的 91.00/93.00/96.00 与 288ms 时延是**相对词尾**而非相对说话结束的口径；判停头与 ASR 头并行、不回灌解码。

## 3. 其余七篇的细读结论

本节记录本窗口 50 篇中进入细读的其余七篇，全部完成全文核实与制品一手核查。**七篇里没有一篇进入候选序列**，但其中三条结论对项目的最高优先级事项有直接影响，因此不是纯粹的否决记录。

### 3.0 先说本节最重要的一条：判定器/脚手架敏感性在同一个窗口里拿到了两条独立佐证

**这是本轮除两条 P0 之外最有价值的发现，且它直指项目优先级最高的未决事项（判定器处理不变性）。**

论文事实（SemaPLC，2608.18565）：**7 个后端模型 × 2 个条件（有脚手架 / 无脚手架），同一批 117 个任务、同一个判定器。** 固定模型、加上脚手架，指标提升 **8.5 至 33.3 个百分点，均值 +17.3**；而固定脚手架、换模型，指标跨度是 **37.6 个百分点**（bare 列 34.2 到 71.8）。

论文事实（ComponentBench，2608.18307）：**同一个 harness、同一个模型、同一批任务，只改变观察与动作空间**，GPT-5 mini 的通过率从 AX-tree 的 **83.1% 掉到 Pixel 的 48.9%**，摆幅 34.2 个百分点。作者另给出一个更细的例子：在 clutter=none 时 GPT-5.4 的 Pixel（86.1%）胜过 AX-tree（81.6%），而 clutter=medium 时反转成 AX-tree 领先 9.7 个百分点——**"哪种观察空间更好"这个结论本身会被一个场景参数翻转**。

**编辑判断：算上 DuplexWorld（2608.10716），"脚手架挪动指标的幅度与换模型同量级"这条现在有三条独立佐证，且本轮两条都比 DuplexWorld 强——SemaPLC 是 7×2 的完全析因，ComponentBench 的 harness 与全部原始运行记录是 MIT 开放的（4,264 个 blob + 40.97GB 运行归档，291 次下载，非门控），而 DuplexWorld 至今只有 18 条场景规格、无音频、无 harness 代码。** 这把项目的排序结论钉死了：**下一个评测周期应当花在判定器与 harness 的构造效度上，而不是换模型。**

**但同等重要的反向记录：这三篇没有一篇验证了自己的归因方法。** SemaPLC 的判定器是作者自己重写的（下详）；ComponentBench 的失效归因有两套标注，一套是"确定性"的但**以组件类型先验为起点**（原文：每条轨迹"从一个组件驱动的类别先验出发"，再由轨迹证据修正），另一套直接是 GPT-5.4 读日志，而唯一的复核者是另一个 LLM（Claude Opus 4.8，20 个案例、单次非确定性采样、**改标 5 个即 25%**）；LEDGER 则完全没有验证。**三篇的人工一致性统计（kappa / 一致率 / 注入故障召回）全部为零。** 所以：**它们强化了"必须做判定器审计"这个结论，但没有一篇能替项目把这件事做掉。** 这正是 2608.12880 那条教训的第二种形态——确定性买到的是可复现，不是构造效度；一个以"滑块任务默认归为连续标定误差"为先验的标注器，报出来的连续标定占比（20.2%）里有一部分是定义带来的。

### 3.1 SemaPLC（2608.18565）——TRACK，但它自己重写了判定器

**术语先定：这里的 `harness` 是执行脚手架（Evo-Bench 义），不是训练脚手架。** 全文无训练、无微调、无梯度，七个后端都是第三方 API。**另注该论文自己在实验描述里用了 `harness` 的第二个义项**（程序被部署进去的 ST 外壳），一篇之内两义并存。

它是什么：一个 PLC（可编程逻辑控制器）代码生成的验证门控执行脚手架，五个部件通过一个 16 工具的 MCP 工具层作用于环境。**核心机制是三条门不变量**，逐条抄录，因为这三条是可以直接搬进项目工具/动作通道的：**有界重试**（每项检查最多 2 轮修复）、**编辑失效**（任何修改作废此前全部verdict、全部检查重跑，"verdict 附着在确切的字节上"）、**挣得的声明**（每个结果都是机器可读哨兵并与工具调用日志交叉验证，"未记录的声明降级为未检查"）。作者的总结句是：**"交付的程序与挣得每一项已报告通过的候选完全相同，且没有任何自报通过能在缺少工具日志的情况下存活。"**

论文结果：功能轨道严格通过率均值 **72.6%**（最强基线 Agents4PLC 63.9%），且**最差的 SemaPLC 模型 67.5% 高于每一条基线的均值**；项目上下文轨道动态行为均值 **52.2**（最强基线 31.4）。**层次消融（Table 3）是本轮唯一一处把门的代价测出来的地方**：验证层从无到全，动态分 23.1 → 30.3 → 43.7 → 54.1，而每任务 token 从 34k 涨到 **129k**、请求数从 8.9 涨到 **47.8**——**即 3.79 倍 token、5.37 倍请求买到 +31.0 分。**

**对项目的帮助，只有一条，但这一条形状对：** 那套完成纪律（终止必须有已记录的外部验证；编辑作废此前 verdict；每一条声称的通过都要与日志交叉核对）是对"模型说它做完了"这个问题的一个精确且可实现的回答。项目的对应物是**播报前的动作门**：把发出的工具名与参数对照实时车态与工具 schema 做确定性校验，未记录的自我断言不得移交 TTS。**关键在于 SemaPLC 的检查器不是模型调用**——是编译器与运行时——**这是唯一可能塞进时延预算的形状。任何座舱版本同样必须是确定性校验，不能是 LLM 审阅者。**

**局限与开放状态（这一段决定了它只能 TRACK）：**

- **判定器是作者自己重写的。** 原文：其发布的 oracle"包含会让正确实现失败的缺陷验证属性与任务描述，因此 PLC 工程师审计并修复了受影响的任务（**117 个中的 43 个**）"；附录写明改动 53 个样本、属性数 **629 → 607**。作者的缓解措施异常认真（三轮审计、独立平行复核、布尔逻辑用穷举真值表重新推导、盲审第三轮裁决、只修两轮以上确认的缺陷、无依据的属性直接删除而非编造阈值、所有方法都在同一份修复数据上评测）——**内部可比性成立，但与任何此前发表的 Agents4PLC 数字的可比性被彻底破坏，而论文没有说这一点，也没有在原始 oracle 上给出对照消融，更没有发布修复后的数据。** 编辑判断：这是 2608.12880 的新形态——不是意外的标志位，而是**有意的、有记录的、未发布的重写**。
- **最强基线是作者自己的复现实现**（"Agents4PLC ... 一个忠实的重新实现"）。8.8 分的头条优势是对着获胜方自己写的代码取得的。
- **形式化验证对有状态、跨时间的构造完全失明**：**32 个含定时器（TON）的程序、174 条属性，结论性判定为 0，全部 100% inconclusive。** 编辑判断：这条负面结果可以直接迁移——静态判定与实际执行行为会分叉，这正是项目应当坚持端到端播放边界与判停时序实测、而不是静态打分的理由。
- **全文未声明任何硬件，连运行时本身都没命名**（只写"a live runtime"），而它的头条指标恰恰是运行时测量。它因此加入 CoRun、AATC、DuplexGen-B、2608.17972 的无硬件名单。
- 开放状态四分：**代码公开（`midea-ai/SemaPLC`，MIT + 署名条款 + 下游 Docker 镜像 copyleft 义务），但公开的是产品不是实验**——README 全文不提论文、不提 arXiv、不提任何一个数字；**权重不适用**；**数据：论文写"The released data ..."却在全文任何位置都没给 URL，属第三档 unverifiable**，且发布的 skill 目录里缺了论文 Table S3 列出的 `benchmark-verify`、也缺了论文枚举的六条领域公理。
- **一条应当明确给出的正面记录：全篇没有 LLM-as-judge。** 判定用 PLCverif + nuXmv + RuSTy 编译器与确定性断言。**项目关于"不得采纳 LLM 判定器作为阈值"的既定规则在这篇上不触发。**

### 3.2 DART-SD（2608.18524，字节跳动）——REJECT

**在项目真正测量的那个轴上，它几乎没动。** RoTBench 工具选择（最接近项目严格工具名召回 80.49% 的公开对应物）在 8B 上是 **75.52 → 75.83，即 +0.31**，而同表的 FTRL-GRPO 是 **77.02**，比它高。4B 上它的 72.02 只是与两个 MatchTIR 变体打平；参数正确率一列在 4B 上 **42.38 输给普通 SFT 的 44.40**。

**它自己的消融拆穿了自己的标题。** 固定 Qwen3-8B，逐项累加：普通自蒸馏 **+14.62**，CTB 定位 **+1.41**，渐进 SFT +4.42，ISTG **+1.73**。**总增益 22.18 里，普通自蒸馏贡献 66%，而标题命名的两项机制合计 3.14 分、占 14%。**

其余否决理由：**按构造不可能改善时延**（纯训练期方法，无任何推理期组件，全文零时延、零硬件、零吞吐，推理批大小从未评测）；**沉默式未发布**（无代码、无权重、无数据，且从未声称过要发布）；**写出每一条训练目标的 `AugGen` 组件从头到尾没有命名**，信息原子的"语义阶段"标注器同样没有命名，加上 ISTG 消融的对照臂本身就是一个 LLM 判定器——**训练信号的来源整体不可复现**。BFCL 多轮（最标准的多轮工具调用基准）是它最弱的一项：8B 上 27.63，输给 FTRL-GRPO 的 35.25，也远低于教师的 54.5。

**唯一值得留下的是一个想法而非系统：把损失掩码限制在出错之后的恢复片段、保护有效前缀。** 若项目将来微调自己的工具调用数据，这是训练脚本上的两行改动；但它在这里的实测边际价值只有 +1.41，单次运行、无置信区间。

**一条口径警告：不要引用它的 `Avg.` 列。** 它是九个数值列的无权重平均，其中 FTRL 占 3/9 且第三列是前两列的导出量（等于三重加权且有一列重复计数），而 RoTBench TS 一列在所有行（包括未训练的基座）都落在 60.36–77.02 的窄带里，注入了一个近似常数的偏置，压缩了所有方法间差异。另：**该论文报告的 Solve-F1 在全部 18 行上都不等于其报告的 Solve-P 与 Solve-R 的调和平均**（例如 8B DART-SD 应为 47.30 而报 45.66），方向一致偏低，最可能是按任务先算 F1 再宏平均，**但论文从未声明聚合顺序**，按原样记录。

### 3.3 WhiteMatter（2608.18486，USC）——REJECT

**否决理由一句话：它是从零预训练的架构改动，而它的全部代价都记在 prefill 上——3.05 至 3.30 倍于原版的 prefill FLOPs——而 prefill 正是项目的首音频瓶颈。** 它无法以任何代价加装到现有 Qwen3-Omni 上；即便可以，换来的是一个从未做过墙钟测量的约 1.0 倍解码 FLOP 曲线（0.99–1.03×），代价是把项目最需要缩短的那条路径变成三倍贵。它自己的消融证明这笔代价躲不掉：去掉深到浅反馈的 depth-causal 变体"训练与 prefill 代价与原版相近"，但困惑度从 34.71 劣化到 37.30——**迭代本身就是机制**。

其余边界：全部是 48.7M–约 100M 的稠密小模型、8B token 预算，**全文 `MoE` 出现 0 次**；无解码墙钟、无解码批大小、无制品（**沉默式未发布**：全文对代码/权重/数据不作任何声明，14 条裸 URL 全是参考文献）。

**值得留下的一条工程技巧：为了让注意力对角线不可读又不破坏 FlashAttention-2，它在 KV cache 前面预置了一个可学习的哑元 token，把 cache 相对 query 偏移一位**，而不是去掉对角线掩码。原文：掩掉对角线"与 FlashAttention-2 之类的 kernel 不兼容"。这个技巧可迁移到任何需要 cache 偏移的场合。另一条可留的论证方式：它为"每层只读一个通道"给出的理由是 HBM 带宽——密集读取"将要求每一层从 HBM 流式读取全部 k 路 key 与 value 通道"——与项目对 MoE dispatch 的每层固定代价推理同构。

### 3.4 Pre-Compiled Pipeline Shards（2608.19147，Intel）——REJECT，但带走一个直接可用的原语

**否决理由：它的全部价值主张是用网络跳数换聚合显存，而项目既没有第二台机器，也没有第二个用户。** 头条数字全部需要多个物理节点（43.97 tok/s 要两台、64.67 要三台、70B 要四个云实例）。更关键的是**用在单机上它是净负的**：它自己的表显示把 8B 模型在一台机器上切成多段要付 11–15% 的开销，而它的并发机制在单用户处反转——OpenVINO 的连续批处理"在并发度 1 上损失 8–15%"。**座舱在任一时刻只有一个人在说话。** 两条次要否决理由，写下来以免日后按错误理由重新litigate：整个栈是 Intel iGPU/NPU + OpenVINO，**CUDA 内容为零**，与项目的 CUDA Graph 与 MoE dispatch 工作毫无交集；目标模型全是稠密模型。

**明确不以批大小否决：这篇论文全程把批固定为 1 并反复强调，批大小判据在此静默，引用它会是一次错误否决。**

**但它有一个直接对得上项目打断路径的原语，值得单独记：掩码式 KV 回退。** 不去物理裁剪 KV cache，而是把作废位置的 attention mask 置零，同时让 `position_ids` 跟踪**逻辑**序列长度（回退前的计数）而非物理 cache 长度。论文实测：与物理裁剪**逐位等价**（修正后 logits 最大绝对差 **0.0000**，fp32 机器精度相等），代价在 K=3 时**低于每步墙钟的 1%**，而物理裁剪一次要 **约 48ms**；生成到 2048 token 时 cache 膨胀收敛到 **1.02 倍逻辑长度**。

**编辑判断：这正是"在不改变形状的前提下撤回已写入 cache 的 token"这个问题的答案，而这个问题就是项目打断/撤回路径的核心问题，也是 CUDA Graph 捕获的解码环所要求的形状（固定形状、无主机分支）。** 它与既有的 PACE playback boundary ledger、VoiceChat-TTS 的 "KV never reset" 属同一族，但**前两者给的是协议，这一条给的是可实现的原语与代价数字**。配套必须记下一个陷阱，项目自己的掩码代码要遵守：**空闲行必须在自己的 query 列上开一个口，不能整行掩掉——整行被屏蔽的行会让 softmax 产生 NaN 并污染共享同一次推理的其它活跃行。**

另有两条外部佐证值得带走：其一，**INT8 KV cache 在其硬件上比默认慢 4%**（20.86 对 21.74 tok/s，"反量化开销超过内存带宽节省"），这是"不要指望 cache 量化带来每 token 带宽收益"的独立证据；其二，其剖析结论"用户 Python 占墙钟 0.6%（4521ms 中的 27ms），`req.infer()` 占 99.3%"，与项目 host-sync 工作所依据的"开销在运行时内部而不在你的循环里"是同一条教训。

**开放状态：这是本轮第三个"给了 URL 而 URL 失效"的实例**，且带一个新形态。论文两处印出 `github.com/labscommunity/pipeline-sharded-inference-paper` 并二十余次引用 `reproduction/` 下的具体文件名，该仓库 **404**（注意：已认证的 `gh` 对私有仓库同样返回 404，因此 404 不能区分"不存在"与"存在但私有"，但两种情况下今天都不可核实）。**新形态在于那个"近似命中"的仓库是真实且实质的**：同组织的 `labscommunity/cascadia`（Apache-2.0，884 条目/712 blob/12,280,772 字节，22 stars）在**论文投稿前 17 分钟**推送，实现了本文的技术并逐字提到本文的制品名（"Requires **v5 shards** ... v3 shards are rejected at load time"）——**但它不是论文承诺的那个包**（全树 `reproduction` 出现 0 次，且它是 Rust 而论文引用的每个基准脚本都是 Python），**且两边互不引用**。

### 3.5 ComponentBench（2608.18307，Duke + Amazon）——TRACK，只借协议

结论见 3.0。此处补三条可直接照搬的做法与一条否决理由。

**可照搬的三条：**

1. **把"判定器输入隔离"做成可测试的不变量。** 它的成功谓词存放在 React 组件闭包里，测试用 DOM 属性由一个实时 MutationObserver 剥除，并且**有一个 CI 就绪的扫描器验证全部 2,910 个页面上没有任何此类属性存活**。项目的 452 条自建判定没有任何等价的泄漏扫描器。
2. **把聚合稳定性与逐条翻转分开报告。** 原文实例：GPT-5 mini 在 Pixel 上两次运行的通过率完全相同（52.5%），**却有 17.3% 的任务结果翻转，pass→fail 与 fail→pass 在聚合上互相抵消**。在通过率旁边同时公布一致率与 Jaccard 是零成本的，且**直接适用于项目的 80.49% 严格工具名召回**。
3. **把"设计意图难度"与"实测实现难度"分开记录。** 与 08-19 从 DuplexGen-B 得到的"合成重叠数据系统性偏易"是同一条纪律，项目的合成音频集需要它。

**否决为技术候选的理由：** 浏览器 GUI 组件，无语音、无中文、无工具调用语义、无每轮时延；它自己的范围声明也承认"它测量的是组件级能力，不是长程规划"。另注其硬件只在一句里出现且**从未命名 GPU 型号**，且七个模型经由五种不同的服务通道（Google AI Studio、OpenAI API、Duke LiteLLM 代理、本地 vLLM FP8、Amazon Bedrock），**跨模型时延比较因此不成立**——论文自己也拒绝相信自己的时长："我们把效率结论建立在动作计数而不是受时延污染的时长上。"

### 3.6 LEDGER（2608.18398，CMU + LLNL）——REJECT

**否决理由一句话：全文零数字。** 没有错误率、没有时延、没有稳定性、没有人工一致性、没有基线、没有用户研究、没有节点或边的计数——**不是藏在图里，是不存在**。正文中仅有的数字是章节号、参考文献序号、两个邮编与若干资助编号。

**针对"它是不是 PIPES 那一族、有没有补上 PIPES 的两个缺口"这个问题：两问都是否。** PIPES 是在**运行时**把溯源挂在工具回执上并给出了实测效果（ASR 致错率 84.7% → 2.3%），缺的是时延与代码；LEDGER 是一个**事后的人工审阅面板**，没有运行时强制、没有任何错误率指标、**同样没有时延、同样没有代码**。相似之处只有"溯源"这个词。

**唯一值得留下的是一条设计纪律而非系统：显式的层次信任分离。** 它把审计记录的每个字段标记为"确定性捕获"还是"模型推断"，原文："这一区分之所以重要，是因为审阅者需要把被捕获的证据与图构造期间被推断出来的结构区分开。"**项目的判定器工作正需要这条规则，且它与 playback boundary ledger 是同一精神：采纳规则，忽略那张图。** 值得记一笔的是该论文对自己的诚实——它自己写明"这些选择可能是不完整的、不稳定的、或错误的"，并自己点名了缺失的实验（"重复运行研究还应当测量同一会话在重建下是否产生稳定的节点、边与声明支持路径"）。开放状态属"从未声称发布"这一最诚实的一档。

### 3.7 Task-Conditioned Least-Privilege Learning（2608.18351，Purdue Northwest）——TRACK（有条件），并且它更正了项目的一个假设

**它的价值在于：这是名单上第一篇同时测量了权限效应与任务准确率效应、并发现二者不冲突的论文。** MetaTool 通用工具选择准确率 **81.9% → 83.6%（+1.7 个百分点，p = 4.55×10⁻⁴）**，同时越权下降；内部任务成功率 68.92% → 99.27%。论文自己点破了项目一直担心的那个失败模式："一个只测越权的安全指标可以通过让 agent 更不作为、普遍拒绝来轻易改善……这是自我挫败的，因为它降低能力。"

**但它更正了项目从 2608.14036 推出的那条假设，这一点必须写清楚。** 项目此前记的推论是："既然技能池从 5 涨到 100 会让实际使用精度从 29.6% 崩到 3.3%，那么任何能合法缩小可达工具集的东西都可能提升准确率而不只是安全性。" **这篇论文不缩小可达工具集**——原文明写"模型看到的是一份完整的工具清单"，broker 在环境侧且对模型不可见，训练的是让策略去**选择**更低权限的动作。**因此它不能作为那条假设的证据，那个问题仍然开放，而这不是回答它的论文。**

**两条阻止它成为候选的理由：**

1. **它优化的指标不是座舱需要的那个。** "越权成功"这一列按定义等于（任务成功 − 安全成功），即**分子只统计成功的 episode**；基座策略另外约 900 个失败 episode 的越权行为从未被报告。**在失败轮次中发生的越权动作——正是车辆执行场景中最危险的那一类——在这套指标里一次都没被计入。** 另注论文摘要把这个数写成"把越权错误事件从 4.56% 降到 0.79%"，而结论段写的是"**成功的**越权事件"，后者才是准确的。
2. **定义"越权"的那个充分权限包络本身没有被验证。** 论文自己承认"权限维度、权重与充分包络编码了可能并不完全正确的判断"，而任务与包络是 LLM 生成的（致谢：仓库代码与任务撰写"大部分是合成的，由 Codex 与 Claude Code 的工具在人工监督下生成"）。**无标注者间一致性、无 kappa、无人工审计抽样、无注入故障召回率、无风险向量消融**（最后一项论文自己列为缺失）。

其余阻塞：**推理时延与 broker 开销全部为零测量，而这条 broker 恰恰内联在工具执行路径上**（对座舱而言那是 LLM 与执行之间的一个内联阶段）；只有一个 4B 模型与一个适配器族；**头条是三个种子里被挑出的那一个**（routine 集上三个种子分别是 85.98 / 97.63 / 86.29，约 11.6 个百分点的跨种子摆幅，而 500 任务集上根本没报种子方差）；开放状态为 unverifiable（正文暗示存在仓库却全文无 URL），唯一能归属到作者的制品是 Hugging Face 上一个**空的 MIT 占位库**（两个文件，README 只有 21 字节的许可证前置块，0 下载）。

**现在就能零成本借走的两条：** 其一，**"尝试"与"被允许"分开记录**——即便门拦住了，也要记下策略**请求过**不正当权限（原文："被阻止的命令因此不会造成外部损害，但仍会被记录为该策略请求了不正当的权限"）。项目目前不做这个测量，它不需要任何模型改动，而且它是"只靠门防御"会掩盖掉的那个先行指标。其二，**提示词消融的设计**（完整提示 / 去掉安全措辞 / 一行提示，同一评测集、两个策略同跑）是判断某个行为是被内化了还是被提示词撑着的廉价而有说服力的检验，本轮它给出了最干净的对比：训练后的策略跨三种提示只动了 0.24 个百分点，基座动了 3.70。

## 风险提醒

1. **不要把 15.8ms 当成项目可获得的首音频。** 它是首个音频 *token*、客户端侧中位数、暖引擎、prefix-cache 命中、本地链路、单请求、RTX 5090、BF16。项目的门槛管的是首个音频**到达听者**，且首句必然是冷的。**这两个量之间隔着至少四层未测量的成本。**
2. **不要把"论文没有训练章节"读成"论文证明了无需训练"。** 论文只说了离线参考与流式版本使用相同权重。
3. **X2Streaming-TTS 论文声明的仓库地址目前不存在。** 在它出现之前，任何"代码已开放"的表述都是错的。同机构那个 MIT 仓库是**疑似**实现，两边互不引用。
4. **TEN VAD 的 "Apache-2.0 WITH ADDITIONAL CONDITIONS" 含竞业限制条款。** 虽然默认关闭且非捆绑，但对商业车机项目属实质性风险，选型文档必须点名。
5. **NGC 容器与 TensorRT 引擎绑定是部署侧的硬约束**，不是许可证细节：`.plan` 不能跨机器复用，且拉取 NGC 镜像即接受 NVIDIA EULA。
6. **X2-Turn 的开放状态变了，论文结论一个字都没变。** 联合训练损害 ASR（2.57→3.94）这条依然成立，复现时必须同时测 ASR 退化，不能只测判停指标。
7. **12 Hz 与 12.5 Hz 的不一致已经在两个独立来源上出现。** 凡由帧率推导时长的换算，一律标注所用取值。
