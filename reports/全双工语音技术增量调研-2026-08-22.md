#### 1.6 最重要的一条限定：归并的方向是"多召回"，不是"漏召回"

**必须把这条写清楚，否则本节会被过度解读。** 词干归并让一个查询匹配到**更多**文档，从来不会让它匹配到更少。因此：

- **此前所有记录为 `totalResults = 0` 的零结果，全部仍然有效。** 一个被人为放宽了的查询若仍返回零，那个零比原本更强，不是更弱。08-13 以来 AEC 的十轮为零、空间听觉的连续为零、流式 ASR 的连续为零，都不受本节影响。
- **受影响的是精度，不是召回。** 此前记录的"某组返回 N 篇、N 篇全是假阳性"这一整类观察，现在有了机制解释。
- **因此"全双工组存在系统性盲区"这个结论只有一半被解释。** 该组的**噪声**来源清楚了（`interruption` 一词就带来 2,491 篇全库量级的词干污染，且 08-21 该组返回的 3 篇假阳性正是 `abs:"interrupt"` 族最新的 3 篇：2608.19893、2608.19887、2608.19622，逐条吻合）。**但"漏掉真正的全双工进展"这件事，词干归并解释不了**——归并只会多给，不会少给。**两个缺陷必须继续分开记录：精度损失已归因，召回损失仍未归因。**
- 同理，`interrupt` 词根的三个假阳性（并行机排程、统计学 "Interrupted Time Series"、`2608.19893` "Interrupting the Loop"）**应从"三次巧合"改记为"一个机制的三次显形"**。

**时延按四种口径分别记账（这是本项目的硬要求，本篇正好把第四种暴露为缺口）：**

| 口径 | 值 | 说明 |

**否决理由（作为可采用系统），三条，且第一条是决定性的：**

1. **637 ms 是 3–4 张 GPU 的结果，而这一点只写在附录里。** 正文断言 `our architecture incurs no computational overhead`，而附录 Algorithm 1（DAG Pipeline Parallelism）显示：共享骨干在 GPU 0，随后 `NCCL_Broadcast(Hshared → GPU_T, GPU_A, GPU_C)`，三个头"strictly in parallel across different devices"。附录自己说明这是承重的：`Forcing this multi-head architecture into a single GPU or a linear pipeline would result in the sequential execution of the specialized heads, introducing severe latency bottlenecks that disrupt the fluidity of real-time conversation.` **座舱只有一张加速卡。更要紧的是：每 token 一次跨设备集合通信，正是本项目已实测根因（每 token 约 816 次 GPU→CPU 同步）最不该走的方向。**
2. **哪一个时钟未声明**，因此 637 ms 不能直接对着"首音频 P90 ≤ 1,000ms"这道门记账。沿用既定判据（同一系统的服务端与客户端 TTFT 曾相差 2 倍以上），**它只能记为"算法加测评框架"口径，不是客户端观测值**。
3. **效率声明建立在 GFLOPs 上**，而 GFLOPs 恰好看不见本项目解码中占主导的那两类开销。

**但作为架构参照必须接受，因为它给出了项目自己那条负面结果的机制解释。** 项目已实测"主模型自己判停不可行"并据此把旁路放到音频通路之外；Lychee-FD 的 `w/o Param-Sep` 消融正是它的机制版本——**S→S 准确率崩到 27.6%**，论文解释为深层参数共享导致"the optimization landscape becomes dominated by semantic modeling, effectively suppressing the learning of acoustic features in deep layers"。**这是一条来自完全不同方向的、量化的独立佐证。**

**四条可直接搬的原语：**

- **带早退路径的专用控制流，是本轮三篇里对项目最有价值的一条。** 仓库 README 逐字：控制头`also uses an early-exit path, allowing interruption, stop-speaking, and listen/respond decisions to be produced **before full speech generation completes**`。**这正是项目为判停与打断所要求的那个形状的一个可运行实例**，其控制词表 `Y_C = [<Start>, c_1, ···, <Stop>]` 可直接照搬编码方式。
- **梯度冲突诊断是一件可复用的量具，而不只是一个结论。** 逐层计算声学与语义梯度的余弦相似度（论文观察到它"drops sharply, turning negative and fluctuating in the deeper layers"），**可以用来定位任何多头流式模型该在哪一层切分，而不是靠猜**。
- **"语义稀释"是一条关于帧率对齐的具体警告。** 用 padding 把约 3 Hz 的文本流对齐到 25 Hz 音频会"consistently suppress the magnitude of semantic gradients"。**项目任何把稀疏控制流或文本流时间对齐到密集音频帧的设计，都应预期该稀疏流被训练不足**——其 `w/o Sem-Channel` 消融代价为 S→T 5.6 分、S→S 5.4 分。
- **FSED 是首音频这件事的正确指标名**，并自带一张可对位的基线表。项目今后报自己的首音频时应采用这个已发表定义，**但必须注明自己的时钟**。

**必须原样并存的五处不一致：**

1. **摘要的 `+28.5%` 是两个指标的均值，没有任何单项指标接近这个改进幅度。** 它等于 mean(IRR, BRR) 的 73.50 减 Freeze-Omni 的 45.00；而 IRR 相对最佳基线只 +17.0、BRR 只 +6.0。**属"摘要级最高级只在聚合上成立"这一既有形态。**
2. **正文说单卡会造成"severe latency bottlenecks"，而仓库明确提供了单卡模式。** README 默认是 token2wav 与主后端**各占一卡（两张，不是四张）**，并另给 `For a single-GPU machine:` 配置。**部署形态（多流 vLLM 服务管线 + 控制头早退）与论文附录的 DAG-PP 并不是同一个东西。**
3. **仓库报了两个论文里没有的数字**：`about 2.96x speedup in speaking rounds` 与 `reduces incremental GPU memory growth by about 23%`。不矛盾，但**仓库的性能故事与论文的性能故事不是同一个故事**。

### 3.2 S2-MoE（`2608.15018` v2）—— 否决，但两条否决理由都不是通常那两条

**v1 → v2 是一次真正的空修订，且是本项目记录到的最纯粹一例。** 逐页内容流**逐字节相同**（合计 213,096 字节）、10 个图 XObject **MD5 全部相同**、提取字符数与行数完全一致（75,752 / 1,669）、裸 URL 集合相同、注解 URI 集合除自指戳记外相同。**全文文本差异只有一行**：`arXiv:2608.15018v1 [cs.AI] 15 Aug 2026` → `v2 [cs.AI] 19 Aug 2026`。唯一变化的二进制对象是 `/ArXivWatermark`（102 → 125 字节）。**因此无任何判定可能改变。** 这与既有记录一致："修订的体量预测不了任何东西"——StreamTTT 改了 184 行而判定不变，X2-Turn 只加一句话却翻转了一个开放状态判定，本篇则一个字都没改。

**否决理由两条，且都不是批大小、也不是缓存命中：**

1. **瓶颈不对。** 项目 blocker 是每 token 约 816 次 GPU→CPU 同步，根因是**主机同步**。本篇对 `synchroniz` / `cuda graph` / `kernel launch` / `launch overhead` / `host-side` / `d2h` / `h2d` **命中数全部为 0**。它优化的是**卸载条件下的显存带宽与专家流量**——另一个瓶颈。**而在 H20 上这四个模型都不需要专家卸载，因此它所利用的机制在项目服务端硬件上根本不存在。**
2. **收益是显存饥饿的函数，且随饥饿缓解单调衰减。** 平均加速比 **2.500（16 GB）→ 1.926（32 GB）→ 1.718（64 GB）**；唯一的"装得下对装不下"受控对照（DeepSeek/HumanEval）**从 3.76× 崩到 1.65×**。外推到完全不需要卸载的设备，所剩不多。**5.3× 这个头条在 H20 上不可达。**

**必须写明不以哪两条理由否决，否则日后会被按错理由重估：**

- **批大小规则在本篇沉默。** 论文侧属第四态（正文与 Table 1 均未报批大小），**但官方仓库把它定到了第一态**：README 代表性命令含 `--parallel 1`，配置文件含 `"parallel": 2`（**两者不一致，原样并存**），而 1.2–5.25× 的收益正是**为这个区间**报的。**本篇恰是通常那个陷阱的反面：它论证的是竞品在批 1–2 时收益消失，而自己是针对该区间的修法。**
- **缓存命中陷阱在本篇清除，方向还是有利的。** 唯一相关段落写明现有卸载方法"their ideal operating regime corresponds to scenarios with high cache hit rates. Such settings are effectively equivalent to memory-relaxed configurations, which we explicitly evaluate (e.g., 64GB memory budgets)"——即它**同时报了宽松档与紧张档，而头条来自紧张档**。**论文自己从未声明测量时的缓存/预热状态（这个缺失本身是发现），而仓库回答了它**：每个配置都设 `"no_warmup": true` 与 `"no_mmap": true`，README 命令带 `--no-warmup --no-mmap`，**即冷测**，正是车机第一句话需要的条件。残留一处不对称：`docs/baselines.md` 的基线命令只有 `--no-mmap` 而**没有** `--no-warmup`，即基线跑热而本方法跑冷；**该不对称对作者不利（热基线更快、会压低报出的加速比），故记为低严重度。**

**本篇最严重的问题在外部，且是"论文与自家仓库在方法学声明上相反"的第三个实例。** 论文写 `For Cascade [35], we implement its core policy in llama.cpp **following the method described in their paper**, and integrate it into the same evaluation pipeline for **a fair comparison**.`；而仓库的 `MOE_UTILITY_SPEC.md`（中文）写的是实现了一个**"简化版"**，并补充说完整论文在 vLLM 等服务框架上的实现与此不同，此处是**用"observable statistics to approximate"收益与验证成本之比**。该文档还暴露搜索空间极小：候选草稿长度仅 `{0, 1, max(2, cap/2), cap}` 四个值，`test_iters=4` / `set_iters=16`。**即最强基线比论文声称的更弱。**

**另四处不一致，原样并存：**

- **672 个附录加速比格里有 12 个不等于自己的 `T/s ÷ Auto(T/s)`，而 112 个 S2-MoE 格全部自洽——12 个错格全在基线行**（Cascade、EAGLE3、ES、LS）。多个错格共享一个与印出的 `Auto` 行不同的隐含分母（Table 8/MT 印 Auto = 1.60，而 Cascade 与 LS 都反推出约 1.377；Table 8/HE 印 1.68 而两者都反推出约 1.80）。误差达 16% 且双向，读作记账错误而非方向性偏差。
- **OLMoE 的 S2-MoE 吞吐在 32 GB 与 64 GB 两张表间像是复用而非重测**：7 个任务中有 5 个末位数字完全相同，而每个基线方法的吞吐都有小幅移动。加速比列印证了机制：HumanEval 印 2.38（32 GB）与 2.37（64 GB），而 74.32/31.27 = 2.3767、74.32/31.36 = 2.3699，**即处理组吞吐被固定、只重测了基线**。
- **仓库报了论文完全没有的两个基线（DFlash、Domino），而其 S2-MoE 数字与论文任何一格都对不上。** 我核对了全部 112 格：DeepSeek/64 GB 的 (1.60×, 2.50) 与 OLMoE/32 GB 的 (1.87×, 2.56) 都无法匹配（该模型该档的论文加速比区间为 1.42–1.83、接受长度 3.45–5.50，README 的 2.50 低于整个区间，而 README 自称其接受长度**含**目标 token、本应更大）。**但要写清这条省略对作者不利**：Domino 在两格都低于 1.0×，即论文漏掉了两个自己能赢的基线。
- **仓库独有的测量参数，论文一个字没提，而它们直接决定可信度**：采样是随机且单种子的（`--temp 1 --min-p 0.01 --top-k 4 -s 42`，另一配置 `"temp": 0.8`），生成长度按配置在 64 与 640 之间变化，**最要紧的是每个数据集只评 3 到 5 条 prompt**（`"questions_limit": 5` / `3`、README `--n-questions 5`）。**论文无种子、无重复、无误差棒。**

**开放状态为第二档，但带一处第七档尾巴与一处成分许可证缺口。** 代码在 `https://github.com/angerybob/S2-MoE`，是 llama.cpp 的 fork（1,956 条树条目），MIT——`LICENSE` 1,078 字节且版权行是 `Copyright (c) 2023-2024 The ggml authors`，**本应触发聚合许可证陷阱，但 README 把它补上了**：`This project is built on llama.cpp. The implementation retains its MIT license; see LICENSE.` **成分许可证仍未覆盖**：仓库随附 `datasets/*.jsonl`（gsm8K、human-eval、mt_bench、specbench 等第三方评测数据），而单一 MIT LICENSE 未涉及其各自条款，无 `NOTICE`、无 `COPYING`。**第七档尾巴**：`spec_config_qwen3.json` 需要 `hot_experts.json`，而全树递归搜索 `hot_expert` **零命中**；不过生成它所需的四份逐层专家激活剖面已随仓库发布，**即该派生物缺失但可重建**。另：`When memory permits, we further keep frequently activated experts resident in device memory based on offline profiling.`——**离线剖析成本被使用却从未计入任何地方。**

**硬件也有一处矛盾**：论文两处明确写 `Jetson Orin NX 16GB`，而仓库两处写 `a Jetson AGX Orin under a 16 GB memory budget`，且 `spec_config_olmoe2.json` 硬编码 `"bandwidth": 204.8`（AGX Orin 的值；Orin NX 16 GB 为 102.4）。**这很重要，因为 5.25× 的最大值完全来自 16 GB 档**——按仓库的读法，该档是同一台设备被人为限容，**于是头条变成纯粹的显存容量效应而不是设备效应**。两种读法原样并存。

**干净的部分要说明，它校准其余各条：** 全部头条数字都能从附录复现，包括"about 2.0× on average"落在 112 格均值 **1.9907**；**摘要没有藏聚合值——它把均值与最大值并列披露**；Table 3 的"acceptance rates increase by up to 79%"复现为 33.01 → 59.09（+79.01%）；Table 4 复现；**仓库的专家剖面独立佐证了论文 Table 1**（最大 `expert_id`+1 得 64/64/128/128，四个模型全部吻合，层数也与真实架构一致，且每条 `count/total_activations == frequency` 零失配）；消融 Figure 8 诚实报告了单靠自投机会**变慢**（0.2–0.8×）；README 链接了 arXiv 与 BibTeX 并复述了头条数字，**因此"README 不提论文也不提数字"这个陷阱不触发**。

**三条可带走的原语：**

- **硬件校准的成本模型是本篇最可迁移的资产。** 把每个新激活专家折算成"一个硬件校准的时延单位"（`expert_bytes / bandwidth`，拟合 R²=0.981、MAPE 2.3%），**是"用实测设备常数而不是启发式来做调度判断"的干净范式**，项目可以把同样的形状用到自己的解码预算上。
- **上下文对齐的自投机**——草稿与目标共享同一份 KV cache——带来 **+23% 到 +79%** 的接受率，且不需要额外训练、不需要第二个模型。**对一个时延受限的单用户座舱助手，这是本篇性价比最高的想法。**
- **一条方法学教训，其价值超出本篇：决定一个加速比是否可信的那些测量参数（批大小、预热、种子、prompt 条数、生成长度）全部缺席于论文而齐备于仓库的配置文件。** 因此**"读随仓库发布的配置文件"应成为本项目论文初筛的常规步骤**——本篇的批大小状态、缓存状态与样本量三件事，全部是靠它才查清的。
- **另附一条对项目最高优先级事项的校准数据点**：DeepSeek 的 Qasper 从 27.40 涨到 32.72（+5.32）、四个模型的平均任务准确率全部改善，而论文把这些差异描述为"small and non-systematic"。**在单种子随机采样、每任务 3–5 条 prompt 的条件下，这是噪声呈现为信号**——**这是"单次运行的头条数字不可靠"的又一条独立佐证，与项目自己的 80.49% 同源。**

### 3.3 `2608.06718` v2 —— 既有判定不变，但措辞需要收紧，而且这次修订正好修掉了一处旧矛盾

**判定不变：不得把音频语言模型当作打断/情绪恰当性的自动判定器。** 证据基础完全没动。**Table 7 的原生 POINTWISE / No-Cue 一档是决定性的：11 个判定器里只有 Gemini-3-Pro 一个的置信区间排除了 50%，而且只是勉强排除（55.2 [50.1, 60.1]）。** 其余全部统计上等于随机，含全部开放模型；Qwen2.5-Omni-7B 恰好 **50.0**。Table 6 的协议差（配对 bootstrap 95% CI）显示 Gemini 家族从对照式格式获得 **+21.3 到 +29.2** 分，而每个非 Gemini 模型的区间都包含零。

**但措辞必须收紧，因为论文比"一律禁止"要窄。** 最直接支持该判定的原句是：`Cueing is a diagnostic intervention, so a judge whose conclusion depends sharply on prompt wording may be useful in a scaffolded pipeline, but **should not be treated as a plug-and-play evaluator**.` 以及 `similar aggregate accuracies can hide different failure modes ... ALM judges should not be evaluated by accuracy alone, instead requiring thorough behavioral audits before deployment.`

**因此被支持的判定是："不得把音频语言模型当作即插即用的判定器"，而论文明确留下了"在有脚手架的管线里可能有用"这一条**——而那正是 PAIRWISE 下 Gemini 家族达到 74–91% 的地方。**这条区分值得保留，因为它指向一个可用设计而不只是一条禁令。**

**两条不可忽略的迁移限制**：审计**只有英语**，且作者自陈`relies primarily on synthesized speech ... it limits external validity`。另有一条对中文部署尤其不利的构造效度提示：**最低的单轮得分来自非母语英语者**，即该基准的题目对听者母语背景敏感。**开放状态为第三档**：只有将来时的 `will be released`，全文没有任何作者制品 URL（唯一裸 URL `talkarena.org/cava` 是第三方源数据集，30 条注解 URI 全是参考文献）。

**这次修订恰好修掉了一处存在于我们形成判定时那一版里的内部矛盾，这是版本通道的一次实打实的价值证明。** v1 的 §4.3 正文写人评一致性 `88-92%`，而附录 E 同一档写 `88.0–100.0`；**v2 把附录改成 `88.0 – 92.0`，与正文对齐。** 其余实质编辑三处：**Voxtral-Mini-3B 被整体删除**（v1 三张附录鲁棒性表里有它，v2 零次出现，即少评了一个模型）；标注者人数下修，`We recruited ten graduate students` → `We recruited nine students`；以及一批引用更正（其中 NOESIS-II 的第一作者由 `Kummerfeld et al., 2019` 改为 `Gunasekara et al., 2020`），连带掉了两条 arXiv 超链接。合计 −1,645 字符、49 个差异块。**Table 6 与 Table 7 这两张承载全部证据的表逐字节未动，因此没有任何数字级的判定变化。**

**一处残留的轻微歧义，原样并存**：v2 说"nine students"，同时又说每个任务"five independent annotators"、而任务有两个（十个标注位），附录表也列 5 名标注者。**九人填十位意味着有一人兼做两个任务，论文未说明；v1 的"ten"在这一点上是自洽的，即这次更正引入了该歧义。**

**四条可带走的原语：**

- **反事实审计的构造方式，是本轮三篇里对项目最高优先级事项最直接可用的一条。** 固定转写文本不变，只改与被测行为相关的那一个通道，要求判定器随之翻转。**这正是项目那个"只翻转与行为无关的元数据即改变 180 条中的 31 条"实验的正向推广版**，而**造一套中文的打断恰当性反事实集是一个自足、可立刻动手的后续项。**
- **POINTWISE 对 PAIRWISE 的协议差本身就是一件诊断量具。** 任何只在两个候选同时可见时才表现良好的判定器，**都不在测量它的聚合分数所暗示的那个东西**。做起来便宜，而它检出了单看准确率会被掩盖的失效。
- **(P, O, J) 三态分解，尤其是"Potemkin"这一态**——感知与响应映射都过关、最终判断仍失败。**这给项目一套给自己判定器失效分类的词汇，取代单一召回率。**
- **报 Wilson 或 bootstrap 区间，不要报点准确率。** 本篇的结论之所以可读，全靠每个数字都带区间；**项目的 80.49% 是单次运行且不带区间，这恰恰是它现在不被信任的原因。**

## 八、方法学固化（本轮新增，建议写入长期规则）

1. **`abs:` 做词干归并。** 任何单词探针实际匹配的是它的词干，因此：不要用"删掉某个宽泛单词"来提精度（无效）；缩略词若以 S 结尾会被剥成另一个词（`TTS`→`tt`）；短语内的成分词同样被归并（`echo cancellation` = `echo cancel`）。**提精度的唯一有效手段是改用多词短语。**
2. **归并只会多召回，不会少召回。因此所有历史零结果依然有效，受影响的只有精度。** 不得用本发现去回溯质疑任何一条已记录的零结果。
3. **每次改写查询都必须做同窗口 A/B 并记录两个总数。** 本轮正是靠 A/B 才发现 08-21 的建议无效——若只换写法不做对照，会把"改写生效"当成既成事实带进后续若干轮。
4. **提出一个新查询词时，先测它的全库 totalResults。** `abs:"turn-end detection"` = 0 说明它永远不会命中；一个全库为零的词进了查询组，会让该组看起来比实际覆盖得更宽。
5. **逐版复核的输入集合必须机械提取，不得人工维护。** 依据是本轮 47→173 的对比。
6. **窗口起点绑定"最后一篇实际覆盖到的投稿时刻"，而不是上一轮的时钟时刻。** 本轮覆盖 0 篇，所以起点不前移。**这是索引冻结日必须显式处理的一步，否则会永久丢批。**
7. **区分"方向为零"与"索引为零"。** 前者是领域没产出，后者是检索源没推进；两者的后续动作完全不同（前者继续等，后者下一轮必须把窗口起点保持不动并预期回填）。
8. **经过身份认证的 `gh` 返回 404，默认读法是"尚未公开"，不是"不存在"。** 该类条目的后续动作是发布观察，**不得设死线**。本轮的 `X2Streaming-TTS` 是这条规则的第一个实证案例，而它恰好落在一个已按错误读法设了死线的条目上。判定私有转公开的可用线索是 **`updated_at` 前移而 `pushed_at` 不动**，且必须写明 GitHub REST API 不暴露可见性变更事件，因此这是推断而非官方陈述。
9. **`pushed_at`、star 数与"README 里出现了 `arxiv`"三者都不是进展信号。** 本轮五个动了的仓库，五次全是 README / 引用编辑，四次集中在同一个 34 小时窗口内（论文投稿后的引用整理潮）。**以这三者为触发条件的流水线本轮会报四到五个假阳性。** 判断进展必须落到文件级：制品关键词在全树路径中的命中数。
10. **架构/能力支持的 grep 必须限定到项目自己的目录。** FlashPrefill V2 全树搜 `sm_?120` 有 23 处命中，**23 处全在第三方 CUTLASS 头文件里，实例化目录下为 0**。
11. **`11,357 字节`只能当作 Apache-2.0 的快速线索，不能当作硬相等条件。** X2-Turn 的 LICENSE 为 11,374 字节，但归一化空白并剥掉开头的版权行后与规范文本逐字节相同。**判定靠归一化比对，不靠字节数。**
12. **随仓库发布的配置文件是判断一个加速比是否可信的必读材料，应列为论文初筛的常规步骤。** S2-MoE 的批大小、预热状态、随机种子、每任务 prompt 条数（**只有 3 到 5 条**）与生成长度**全部缺席于论文而齐备于仓库配置**。本轮该篇的批大小状态、缓存状态与样本量三件事全靠它才查清。
13. **批大小四态的判定，论文侧与仓库侧可以落在不同的态，必须分别记。** S2-MoE 论文侧是第四态（从未报告），而仓库把它定到第一态（`--parallel 1`，且收益正是为该区间报的）⇒ **规则沉默，不得否决**。**这是四态规则的一个新用法：先看论文，再让仓库把状态定死。**
14. **一次修订可以披露初版未显示的产业方参与。** `2607.06540` 的 v1→v3 调换了作者顺序，并新增了一个 v1 中完全不存在的第四单位（腾讯 PCG），五位作者从无任何单位标记变为归属该单位。**逐版差分的价值不限于数字与结论。**
15. **一次修订也可以只是让步优先权。** `2607.06540` 的 v3→v4 只 +235 字符，实质就是承认一篇并列工作提出了基本相同的核心洞见，**软化了正文反复出现的"For the first time"声明**。这类修订不改数字却改可信度归属。
16. **"空修订"是一种应当明确记录的结果。** `2608.15018` 的 v1→v2 逐页内容流逐字节相同、10 个图 MD5 全同、全文文本只差 arXiv 戳记那一行。**与既有记录一致：修订体量预测不了任何东西**（StreamTTT 改 184 行判定不变；X2-Turn 加一句话翻转了一个开放状态判定；本篇一个字未改）。
17. **一次"仓库确实在被编辑却依然缺少承诺物"，比"仓库停滞"是更强的负面证据。** 本轮两个实例：ReCache 的作者 08-21 在改 README 却仍未加 LICENSE；FlashPrefill V2 的 α 矛盾在两次刻意的 README 润色之后依然存活，**因此该矛盾应从"待澄清"改记为"既成的方法学矛盾"**。
