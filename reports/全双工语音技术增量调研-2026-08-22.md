#### 1.6 最重要的一条限定：归并的方向是"多召回"，不是"漏召回"

**必须把这条写清楚，否则本节会被过度解读。** 词干归并让一个查询匹配到**更多**文档，从来不会让它匹配到更少。因此：

- **此前所有记录为 `totalResults = 0` 的零结果，全部仍然有效。** 一个被人为放宽了的查询若仍返回零，那个零比原本更强，不是更弱。08-13 以来 AEC 的十轮为零、空间听觉的连续为零、流式 ASR 的连续为零，都不受本节影响。
- **受影响的是精度，不是召回。** 此前记录的"某组返回 N 篇、N 篇全是假阳性"这一整类观察，现在有了机制解释。
- **因此"全双工组存在系统性盲区"这个结论只有一半被解释。** 该组的**噪声**来源清楚了（`interruption` 一词就带来 2,491 篇全库量级的词干污染，且 08-21 该组返回的 3 篇假阳性正是 `abs:"interrupt"` 族最新的 3 篇：2608.19893、2608.19887、2608.19622，逐条吻合）。**但"漏掉真正的全双工进展"这件事，词干归并解释不了**——归并只会多给，不会少给。**两个缺陷必须继续分开记录：精度损失已归因，召回损失仍未归因。**
- 同理，`interrupt` 词根的三个假阳性（并行机排程、统计学 "Interrupted Time Series"、`2608.19893` "Interrupting the Loop"）**应从"三次巧合"改记为"一个机制的三次显形"**。

### 2.4 本轮制品通道最重要的方法学发现：`pushed_at`、star 数与 README 里的 `arxiv` 全都不能作为进展信号

**五个动了的仓库，五次全是 README / 引用编辑，四次集中在同一个 34 小时窗口内。** 一条以 `pushed_at` 前移、star 增长、或"README 里出现了 `arxiv`"为触发条件的流水线，**本轮会报出四到五个假阳性**——其中最危险的一个是把 Thinkingbox 新增的论文链接读成"发布产品不发布实验"这个形态被打破，**而它的制品关键词命中数全部仍为 0**。

**三条配套的扫描陷阱，全部来自本轮实测：**

1. **star 数可以在代码零变化时暴涨。** EnvHarness 9 → 104，11.6 倍，同期只有一次 README 标题修改。
2. **架构支持的 grep 必须限定目录。** FlashPrefill V2 全树搜 `sm_?120` 有 **23 处命中，23 处全部在 `csrc/cutlass/include/` 下的第三方 CUTLASS 头文件里，没有一处在 `flashprefill_ops/instantiations/` 下**。不限定目录就会把"厂商头文件里提到过 sm120"误读成"新增了 sm120 支持"。
3. **`11,357 字节`这个 Apache-2.0 判据不能当成硬相等条件。** X2-Turn 的 LICENSE 是 **11,374 字节**，看似不符；但逐行归一化空白并剥掉开头那行 `Copyright 2026 X Square contributors` 之后，**与 apache.org 的规范文本逐字节相同（两侧都归一化为 10,222 字节，`cmp` 无差异）**。**结论：字节数只能用作快速线索，判定必须靠归一化比对。**

## 七、方法学固化（本轮新增，建议写入长期规则）

1. **`abs:` 做词干归并。** 任何单词探针实际匹配的是它的词干，因此：不要用"删掉某个宽泛单词"来提精度（无效）；缩略词若以 S 结尾会被剥成另一个词（`TTS`→`tt`）；短语内的成分词同样被归并（`echo cancellation` = `echo cancel`）。**提精度的唯一有效手段是改用多词短语。**
2. **归并只会多召回，不会少召回。因此所有历史零结果依然有效，受影响的只有精度。** 不得用本发现去回溯质疑任何一条已记录的零结果。
3. **每次改写查询都必须做同窗口 A/B 并记录两个总数。** 本轮正是靠 A/B 才发现 08-21 的建议无效——若只换写法不做对照，会把"改写生效"当成既成事实带进后续若干轮。
4. **提出一个新查询词时，先测它的全库 totalResults。** `abs:"turn-end detection"` = 0 说明它永远不会命中；一个全库为零的词进了查询组，会让该组看起来比实际覆盖得更宽。
5. **逐版复核的输入集合必须机械提取，不得人工维护。** 依据是本轮 47→173 的对比。
6. **窗口起点绑定"最后一篇实际覆盖到的投稿时刻"，而不是上一轮的时钟时刻。** 本轮覆盖 0 篇，所以起点不前移。**这是索引冻结日必须显式处理的一步，否则会永久丢批。**
7. **区分"方向为零"与"索引为零"。** 前者是领域没产出，后者是检索源没推进；两者的后续动作完全不同（前者继续等，后者下一轮必须把窗口起点保持不动并预期回填）。
8. **经过身份认证的 `gh` 返回 404，默认读法是"尚未公开"，不是"不存在"。** 该类条目的后续动作是发布观察，**不得设死线**。本轮的 `X2Streaming-TTS` 是这条规则的第一个实证案例，而它恰好落在一个已按错误读法设了死线的条目上。判定私有转公开的可用线索是 **`updated_at` 前移而 `pushed_at` 不动**，且必须写明 GitHub REST API 不暴露可见性变更事件，因此这是推断而非官方陈述。
9. **`pushed_at`、star 数与"README 里出现了 `arxiv`"三者都不是进展信号。** 本轮五个动了的仓库，五次全是 README / 引用编辑，四次集中在同一个 34 小时窗口内（论文投稿后的引用整理潮）。**以这三者为触发条件的流水线本轮会报四到五个假阳性。** 判断进展必须落到文件级：制品关键词在全树路径中的命中数。
10. **架构/能力支持的 grep 必须限定到项目自己的目录。** FlashPrefill V2 全树搜 `sm_?120` 有 23 处命中，**23 处全在第三方 CUTLASS 头文件里，实例化目录下为 0**。
11. **`11,357 字节`只能当作 Apache-2.0 的快速线索，不能当作硬相等条件。** X2-Turn 的 LICENSE 为 11,374 字节，但归一化空白并剥掉开头的版权行后与规范文本逐字节相同。**判定靠归一化比对，不靠字节数。**
12. **一次"仓库确实在被编辑却依然缺少承诺物"，比"仓库停滞"是更强的负面证据。** 本轮两个实例：ReCache 的作者 08-21 在改 README 却仍未加 LICENSE；FlashPrefill V2 的 α 矛盾在两次刻意的 README 润色之后依然存活，**因此该矛盾应从"待澄清"改记为"既成的方法学矛盾"**。
