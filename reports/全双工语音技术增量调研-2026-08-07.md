## 一、先说结论

以下“论文结果”只采用论文正文、作者项目页、官方仓库和官方模型页。Radar 摘要只用于
发现候选。项目数字是 StreamingModelHarness 已实测事实；成功门槛、优先级和接入方式
是面向项目的编辑判断。

### P0：直接命中当前工程短板

1. **LedgerMind** 最值得先转成 Harness 自己的轻量证据契约。它新增的价值不是再做一份
   日志，而是给 evidence 设置 Active/Stale/Conflicted/Dropped 生命周期、依赖边和有限
   repair operator。项目已有 phase 和回执埋点，下一步应让每个口播与车控结论只能引用
   当前有效的执行证据。
2. **SpatialSTALE** 把“记忆是否过期”和“过期记忆是否真的造成危险动作”拆成两个指标。
   对 Harness，应直接构造旧车态与当前 CarSim 状态冲突的成对测试；必须保留 no-memory
   对照，因为论文显示过滤后的记忆并不天然优于不用记忆。
3. **Sparse Event-KV** 直接挑战“删除音频/工具源 span 就清除了影响”的假设。它最适合
   做 context attraction 的 donor-pair 因果诊断，而不是立即作为生产 memory 技术。

### P1：适合形成下一阶段架构

1. **OneDayAgent** 只借鉴 verification-only，不照搬小时级 decomposition。其论文消融中
   verification-only 与 decomposition-only 得分相同，但额外耗时明显更低；这与当前约
   80% 工具准确率下“先验证最终车态、不要盲目加调用”一致。
2. **CloudEdgeVLA** 提供“慢路径只给稳定任务信息、快路径始终使用当前观察”的架构类比。
   对 Harness 的可执行部分是结果年龄、latest-result 非阻塞接口和本地安全门，不是训练
   一套 VLA，也不能把机器人 step 延迟结果外推成语音毫秒结果。

### P2：长期模型研究

1. **RestoreKV** 只在项目未来明确采用激进、查询无关 KV 驱逐时进入候选。当前 KV=2500
   的复制成本约 0.2ms，且 110ms/token 根因是 MoE 同步；现在接入 RestoreKV会优化错层。
2. 今天没有能直接替代无同步 MoE fast path、本地 TTS、独立语义端点器或确定性车控执行
   层的新技术。已有负面结果继续有效，不能因新论文而重启无约束投机预取或主模型判停。

## 1. LedgerMind：把工具轨迹变成有生命周期的证据状态机

来源：[论文正文 / arXiv:2607.28374v1](https://arxiv.org/abs/2607.28374v1)。

### 它是什么

LedgerMind 是套在冻结多模态模型外的 evidence runtime。工具输出先被规则映射为结构化
账本项；后续 State Claim 和 Decision Claim 只能引用 active evidence。它试图捕获四类
最终答案指标看不到的错误：无支撑的中间推理、引用存在但实体/数字是编造的
Phantom Grounding、简单问题被过度推理改坏，以及自由修复时继续放大幻觉。

### 核心方法

- 每条账本项有 11 个字段，包括来源、证据类型、时间戳、规则化事实、置信度、
  Active/Stale/Conflicted/Dropped 状态、TTL、替代项和反向依赖。
- grounding 分三层：support coverage、Entity Consistency Check 和 Numeric Coherence
  Check；Derivation 不允许自证，必须递归落到 Perception/Retrieval 叶子证据。
- Direct/FullPipe dispatcher 避免所有问题都走昂贵多步流程。
- Tool Anomaly、Stale Reference、Conflict、Confidence Drop、Unsupported Decision 和
  Phantom Grounding 才触发 repair。
- repair 被限制为 Drop、Refresh、Retry、Switch、Acquire、StopAndAnswer、Abstain，
  新证据必须来自工具输出。论文只保证来源不被修复放大，不保证工具输出本身正确。

### 论文结果

- 论文报告 VTC-Bench 上 LedgerMind(Gemini-3-Flash) 为 58.90%；相对同 backbone
  baseline 增加 12.43 个百分点。
- Hard-200 的六个 backbone 总体增益为 11.25–19.74 个百分点；该集含 25 条未公开的
  RealCAR，不能当完全公开复现结果。
- EMMA 上 Gemini-3.1-Pro 配置 Overall 为 58.29，相对对应 baseline 增加 9.58 个百分点；
  Coding 子项反而下降 0.18 个百分点。
- MMMU-Pro 消融中完整系统为 68.89，去掉 ledger 为 53.50，去掉 typed repair 为
  60.40，去掉 ECC/NCC 为 63.70。

### 对 StreamingModelHarness 的帮助

编辑判断：把现有 phase/token/engine/真正车态埋点统一为：

```text
音频/文本请求版本
→ 候选工具证据
→ typed call + 参数 + 前置条件
→ 执行器接受/拒绝
→ CarSim 最终状态版本
→ 回执
→ 对用户的口播声明
```

工具回执和车态改变时，只重验依赖它们的声明。参数、设备、座位、温度、百分比和时间等
字段用确定性类型检查；失败时只允许 refresh/retry/abstain，不允许模型自由改写出新的
参数。该建议扩展了昨日 VAmoS 的证据账本：VAmoS 给验收断言，LedgerMind 给证据生命
周期和有限修复状态机。

### 局限与开放状态

- 论文只研究静态图文 VQA，没有音频流、增量解码、真实有副作用工具、车态事务或 TTS。
- ECC/NCC 依赖规则抽取与小型别名表；可追溯不等于事实正确。
- 论文未统一报告 ledger、重复读取、搜索和 repair 的延迟、token 与 API 成本。
- 论文公开；截至报告生成时未核验到官方实现、Hard-200 完整资产或专属模型。
- 代码、权重、数据和许可证：未知。

## 2. SpatialSTALE：在动作前审计旧记忆与当前状态冲突

来源：[论文正文 / arXiv:2608.04574v1](https://arxiv.org/abs/2608.04574v1)。

### 它是什么

SpatialSTALE 是动态 FrozenLake 评测。它先让模型判断 64 条持久空间记忆是否与当前
8×8 地图冲突，再让同一模型依据 raw、filtered 或 no memory 导航。这样能区分“过期项
检测失败”和“检测正确但动作选择仍失败”。

### 核心方法

- 原地图约 25% 是 hole，并保证至少一条可行路径；每个格子有 SAFE/DANGER 文字记忆。
- L1 随机翻 5–7 格，L2 在局部翻 12–16 格，L3 每五步可能在线翻两格。
- 当前观察用坐标文本或 384×384 图片，记忆始终是文字。
- NoMemory、NoFilter、SelfVerify、OMCD 四组共享当前真实观察；OMCD 每批审计 10 条，
  删除 stale 项，L3 在事件后重审。
- Oracle 使用真实 stale 标签，判断后续瓶颈是否仍在审计精度。

### 论文结果

- 检测共 1,800 次；四个导航模型的文本模式共 12,000 回合。
- 视觉 stale 检测平均 F1 从 Qwen 的 0.887 到 GLM-5.1 的 0.067；文本可解不能证明视觉
  证据真的被使用。
- GPT-4o 的 L2 文本导航中，NoFilter 成功/死亡为 14.4%/74.4%，NoMemory 为
  28.8%/28.0%，OMCD 为 32.8%/31.6%。
- GPT-4o 文本条件下，detection F1 与 OMCD success 的 Pearson `r` 只有
  0.005–0.060，均 `p>0.67`；Oracle 也没有检测到进一步收益，说明剩余错误转移到动作
  选择，但论文没有做等价性证明。
- batch 从 1 增至 10 后，每实例调用从 64 降到 7，F1 从 0.941 降至 0.914。

### 对 StreamingModelHarness 的帮助

编辑判断：为 CarSim 和工具结果增加 `source_version/observation_version/valid_at/ttl`。
构造相同请求下的四组：

```text
no-memory
raw stale state
audited state
oracle-audited state
```

让旧回执声称“副驾屏已打开”、当前 CarSim 则显示“光场屏请求尚未执行”，或反向构造。
评分必须同时看 stale 检出、typed call、参数、最终车态和未授权副作用。只有 audit
准确但执行仍错时，才能把瓶颈归到动作选择。

### 局限与开放状态

- 环境是完全可观测的符号化 8×8 网格，不含真实传感噪声、连续状态或车控权限。
- 视觉导航只有 10 seeds×3 episodes，是探索性结果。
- 论文不证明过滤普遍优于 no-memory；部分设置中 no-memory 更安全。
- 正文声称发布代码、50 组 seeds、轨迹和复现流水线，但正文没有给出可核验 URL。
- 代码、数据和许可证：截至报告生成时未知；没有专属模型。

## 3. Sparse Event-KV：删掉源事件不等于删掉语义影响

来源：[论文正文 / arXiv:2607.23693v1](https://arxiv.org/abs/2607.23693v1)；
[作者官方仓库](https://github.com/oklen/Compute-Globally-Materialize-Locally)。

### 它是什么

该工作研究 sparse event-KV 的“语义物化”：全局 prefill 时，下游事件的 KV 可能已经
携带上游源事件计算出的紧凑状态；服务时即使删掉源事件，下游 KV 仍会让答案随隐藏源值
变化。它不是普通文本 RAG，因为被服务文本本身没有写出该值。

### 核心方法

- donor pair 的两条轨迹在所有被服务 token、位置、decoy 和 query 上字节相同，只翻转
  被删除源事件中的值。
- 全局 prefill 后按 event 选择 KV block，保留原位置/RoPE；与同文本独立重编码对照。
- 将 memory contract 拆为 Trigger、Landing、Access：什么措辞会写入、状态落在哪个
  event、未来 query 能读出多少。
- 用 root、reference edge、carrier、菜单/logit readout 和多种 serve set 排除文本泄漏、
  decoy 排除和位置偏差。
- 还测试显式 patch：新版本作为追加事件被 query-scoped 选择，而不是原地编辑旧 KV。

### 论文结果

- Qwen3-8B root-only 的 donor-sensitive 输出 follow:anti 为 99:0，`p=3.2×10⁻³⁰`；
  256-pair 复现中为 130 follow、0 anti、125 const、1 个无法评分。
- 16 种构造的完整文本理解均值为 0.98、最低 0.77，但 write-through 从接近 chance 到
  0.95；不同 checkpoint 没有通用写入语法。
- 二元状态恢复为 0.934；四分类 0.223、八分类 0.156，三位数精确恢复为 0/192。
- Qwen3 的主动自然语言 compute carrier 把 donor-aligned recovery 从 11/192 提高到
  97/192；显式文本为 192/192。
- REALTALK/LoCoMo 的被动自然提及没有显示相对独立重编码的收益，不能把合成正结果
  外推成自然对话 memory。

### 对 StreamingModelHarness 的帮助

编辑判断：这项工作的首要价值是诊断上下文引力。构造“光场屏/副驾屏”“主驾/副驾”
“旧车态/新车态” donor pair，在完整 prefill 后删除源音频或源工具事件，只服务固定的
下游 KV、工具候选和 query。若 typed call 仍随不可见 donor 翻转，就证明旧状态已物化
到后续 KV。

生产设计应优先使用显式、版本化、可审计状态，而不是依赖隐式 carrier。新车态通过
append-only patch 写入，并让当前查询只路由到新版本；历史查询才可读取旧版本。

### 局限与开放状态

- 这是紧凑状态通道，不是通用压缩：字符串逐字迁移只有 9.7%，较大类别和数字接近失败。
- trigger、readout、绝对位置、serve set 和 checkpoint 都会改变结果。
- 自然对话被动 harvest 没有显示收益；主动结果主要来自合成 donor-pair。
- 论文和官方仓库公开；仓库说明提供复现代码。Radar 正文复核记录显示仓库为 MIT，
  含环境、模型 revision 和实验脚本，但未提交完整结果输出。
- 无专属权重；REALTALK、LoCoMo 和外部模型各自遵循独立许可证。

## 4. OneDayAgent：优先借鉴 verification-only，而非加长工具链

来源：[论文正文 / arXiv:2608.05013v1](https://arxiv.org/abs/2608.05013v1)；
[作者官方仓库](https://github.com/zjunlp/OneDayAgent)。

### 它是什么

OneDayAgent 是小时级跨网页、文件、代码和多模态工具的 long-horizon harness。它把原始
请求保留为 global intent，最多拆为六个子任务，以 compact execution memory 跨子任务
传状态，最后检查真实 deliverable 并做定点修复。

### 核心架构

- 子任务各自运行 ReAct，只提交摘要、证据和结果文件句柄，不传全部低层轨迹。
- 搜索、长网页和文件先做 bounded summary；上下文到 90% 时 LLM 压缩并保留 system、
  原始任务和最近三轮，95% 时确定性裁剪。
- synthesis 后，verifier 对照原任务、子任务结果和实际附件检查最终产物。
- 失败时最多三次 targeted repair，不从头重跑全部任务。
- 同一 harness 在多个 backend 上使用，不把效果只归因于单一模型。

### 论文结果

- GLM-5.2 在 104 个 AgentIF-OneDay 任务上总分 0.821；同一 harness 的五个 backend
  全部完成 104/104，得分 0.613–0.821。
- DIRECT、仅 decomposition、仅 verification、FULL 分别为
  0.771/0.804/0.804/0.821。
- 平均耗时分别为 27.6/38.1/29.7/53.6 分钟；verification-only 只比 DIRECT 多约
  2.1 分钟，却达到 decomposition-only 同样的 0.804。
- 95/104 项首次验证通过；9 项进入 repair，6 项修复成功、3 项仍失败。
- 35/104 项触发 context compression；最高压力任务累计约 350K token，但 memory 始终
  开启，没有独立消融。

### 对 StreamingModelHarness 的帮助

编辑判断：第一阶段只做 verification-only。聚合车控执行后，把“原始用户意图、所有
typed call、执行顺序、最终 CarSim state、口播”交给确定性 verifier；发现漏展开时才
允许生成缺失子动作，并设置修复上限。这样可以先验证最终状态，而不因 decomposition
增加约 60% 工具调用并扩大当前约 20% 的工具错误面。

若未来扩展跨分钟任务，再考虑 subtask checkpoint；短车控不应套小时级 ReAct。

### 局限与开放状态

- 论文只在 AgentIF-OneDay 验证，且官方 baseline 与新结果使用不同 Gemini judge；作者
  测得新 judge 低 3.12 个百分点，跨 judge 比较仍有混杂。
- 没有 ASR、音频 KV、endpoint、语音生成、打断或车态事务。
- 实现允许宿主机 shell 且无 workspace isolation；网页注入还可能经压缩记忆传播。
- 官方 GitHub 仓库和 MIT LICENSE 已存在，但当前核验到的公开内容主要是 README、
  图片和发布说明，harness 源码/prompts 尚未完整开放。
- 官方轨迹资产约 8.24GB，但其独立数据许可未明确；无专属模型权重。

## 5. CloudEdgeVLA：慢路径结果可晚到，但不能直接支配当前动作

来源：[论文正文 / arXiv:2608.00569v1](https://arxiv.org/abs/2608.00569v1)。

### 它是什么

CloudEdgeVLA 将慢速云端 7B VLA 与快速边缘动作头分开。边缘端不等待特定云请求，而是
始终消费“最近到达的云特征”并结合当前本地图像闭环。论文把网络延迟问题转成表示学习
问题：云特征保留慢变任务信息，本地支路负责当前状态。

### 核心架构

- 云端 OpenVLA-OFT 输出高层 planning feature，边缘冻结 SigLIP-Base 读取当前图像。
- 训练为同一当前动作构造 fresh/stale 两路：云 backbone 分别读当前帧和随机历史帧，
  两路都与当前 edge feature 融合并监督当前动作。
- 部署时异步发送观察，云结果到达即覆盖 `latest feature`；本地控制循环从不阻塞。
- 一次输出 8 步×7 维动作块；训练历史窗口长度为 21 step。

### 论文结果

- LIBERO 的 40-step uniform-delay 下，四套件成功率为
  76.4%/75.6%/78.0%/63.8%，宏平均 73.5%；VLASH 同条件最高 6.4%。
- normalized delay AUC 为 90.8%，40-step 时同步成功率保留率为 76.5%。
- 120k checkpoint 在固定 20-step offset 下把 backbone drift 从 0.391 降至 0.160，
  action drift 从 0.423 降至 0.047。
- 额外 1000ms RTT 的单项实机 pilot 中，CloudEdgeVLA 静态/动态成功率为 80%/70%，
  VLASH 为 0%/0%；每格只有 10 次。
- 补充 counterfactual 是重要负面结果：把 edge 图像从旧帧换成当前帧几乎不改变 action
  drift，主要收益更像 backbone 稳定化与 head 衰减，而非本地图像主动纠错。

### 对 StreamingModelHarness 的帮助

编辑判断：只借鉴接口，不外推模型结果。Harness C 的 RAG、state 和工具回执必须带来源
请求、输入版本和年龄；模型可消费 latest valid result，但确定性执行器必须用当前
CarSim 状态重新验证参数和权限。超过 TTL 的结果丢弃或降级为只读提示，不能直接触发
车控；已交给 TTS 的旧口播也不能依靠晚到结果“事后纠正”。

### 局限与开放状态

- 论文是机器人 VLA，不是语音、工具代理或模型原生全双工系统。
- delay 用 environment step 表示，没有可外推的控制频率；不能与 227ms RAG 或
  110ms/token 直接比较。
- paired-frame 训练需要两次云 backbone 前向；长期断网仍需 timestamp 和本地 fallback。
- 实机只有一个 Franka 任务，所谓 edge 是 RTX 5080，不是座舱端侧硬件证据。
- 论文和静态项目材料公开；截至报告生成时未核验到官方代码、checkpoint、配对训练数据
  或实机日志。许可证未知。

## 6. RestoreKV：只为未来的激进 KV 驱逐保留

来源：[论文正文 / arXiv:2608.01247v1](https://arxiv.org/abs/2608.01247v1)；
[作者项目页](https://paper.pnu-cvsp.com/RestoreKV/)；
[官方 KVPress 仓库中的实现](https://github.com/NVIDIA/kvpress/blob/main/kvpress/presses/restorekv_press.py)；
[作者官方模型集合](https://huggingface.co/collections/higokri/restorekv-6a747ef7f486dc9e08d1de4c)。

### 它是什么

RestoreKV 针对 query-agnostic KV eviction：未来 query 尚未知时先把长 context 压成固定
预算。它不只选择保留哪些原 KV，而是在完整 cache 尚存在时，用少量 restore token
生成 context-conditioned 补充 KV。

### 核心方法

- 默认 8 个 restore embedding 通过 rank-8、`alpha=16` 的 LoRA 前向访问完整 KV。
- restore KV 占用固定总预算的一部分，基础 evictor 用剩余预算选择原 KV；总 KV 预算不变。
- 冻结 full-cache 模型作 teacher，在相同 query 和 teacher answer 上最小化双向对称 KL；
  只训练约 0.4% 参数。
- LoRA 仅在一次 restore pass 中开启，后续 query 和 decoding 使用原冻结 backbone。
- 每个 backbone/evictor 需要匹配训练；训练时和推理时 evictor 不匹配会显著掉点。

### 论文结果

- Qwen3-4B、5% KV budget 下，KVzip 的 RULER-4K 从 38.2 提升到 73.2；QASPER
  18.0→28.7、QuALITY 46.3→52.4、LongHealth 61.0→67.5。
- 五种 evictor、四任务、三预算的 60 个配对设置中改善 59 个；SnapKV/QuALITY 的
  10% budget 从 53.0 降到 51.8，是唯一退步。
- 32K Llama-3.1-8B 上 restore pass 增加 0.03–0.04 秒和 84MB peak memory；该数字包含
  在论文指定 RTX PRO 6000 环境中，不能直接外推 Qwen3-Omni。
- KVzip+RestoreKV 在 KVPress RULER 的 16× compression 达到 86.4。
- SnapKV-trained restore 在 KVzip 5% 推理时只有 42.0，匹配训练为 73.2。

### 对 StreamingModelHarness 的帮助

编辑判断：当前不接入。只有当长会话 KV 超过 10,000、项目建立 full-cache 与具体
eviction baseline，并确认显存/attention 而非 MoE 同步成为瓶颈后，才训练
Qwen3-Omni 专用 restore adapter。测试必须用相同语音、相同工具注入和相同 CarSim 初态，
同时评分参数、最终车态和 context attraction。

RestoreKV 恢复的是 full-cache 行为；如果 full cache 本身被旧音频吸引，它可能把偏差
一起恢复。因此它不能替代 SpatialSTALE 或 Sparse Event-KV 的冲突/因果测试。

### 局限与开放状态

- 只验证文本 decoder，没有 Qwen3-Omni、音频 KV、晚注入工具或 MoE offload 实验。
- 必须在完整 KV 丢弃前运行，不能恢复已经在线删除的历史状态。
- 训练依赖具体 evictor，且主要收益集中在极端压缩；当前 Harness 并未采用该设定。
- 推理实现已进入 Apache-2.0 的 NVIDIA KVPress；官方 HF 提供部分 Qwen3-8B/
  Llama-3.1-8B adapter，Radar 复核记录其模型许可为 CC BY-NC 4.0。
- 蒸馏训练代码、精确 6,248 样本资产和论文全部规模的 adapter 未完整开放。

## 今日建议路线

### 第一阶段

1. 先把 `22edce8`、`768c60e`、`0a1d84e` 的现有埋点映射为最小 evidence ledger：
   `request/version/source/params/status/ttl/dependencies/final_state/claim`。
2. 在现有 400 条文本和语音映射中加入 stale-state 成对样本，运行 no-memory、
   raw-memory、audited、oracle-audited 四组；先找“旧状态直接导致错误车控”的证据。
3. 构造 context-attraction donor-pair：所有服务 token、位置、工具候选和 query 固定，
   只翻转被删除源音频中的屏幕/乘员/状态，检查 typed call 是否仍随 donor 翻转。
4. 聚合意图先做 verification-only：执行后比对原始意图和最终 CarSim 状态，限制修复
   次数；暂不增加小时级 decomposition。
5. 继续既定 MoE 无同步 fast path、本地 CosyVoice 和独立语义端点实验；今天候选不能
   替代这些直接实验。

### 第二阶段

1. 为 Harness C 的 RAG、state、tool receipt 统一增加 request ID、source version、
   age、TTL 和 cancel 状态；做 blocking/latest-valid/drop/fallback 四组。
2. 只允许异步预取只读候选；任何车控都必须在当前 CarSim state 上重新做权限、前置条件、
   参数和幂等校验。
3. 把 ledger repair 限制为 refresh/retry/drop/abstain 等有限操作；每次修复记录额外
   调用、P50/P90、成功与新副作用。

### 第三阶段

1. 当且仅当 KV>10000 并出现真实显存或 attention 瓶颈时，建立 full-cache、具体
   eviction 和 RestoreKV 的离线对照；不得跳过 Qwen3-Omni 专用训练与许可审查。
2. 长会话状态使用显式版本化文本/结构记录作为真源；隐式 KV carrier 只作机制研究，
   不作安全关键车控依据。
3. 扩大到全部 1,566 条语音、多轮跟随、打断改口和取消/补偿后，再判断账本与审计是否
   在最差桶也不退化。

## 风险提醒

- 今天没有项目新提交或新 P50/P90，不能声称 LedgerMind、SpatialSTALE、Sparse Event-KV、
  OneDayAgent、CloudEdgeVLA 或 RestoreKV 已改善 Harness。
- LedgerMind 的 provenance non-amplification 只保证 repair 新增内容来自工具，不保证
  工具正确；Harness 仍需查询最终 CarSim state。
- SpatialSTALE 显示 audit 可靠后仍可能选错动作；stale F1 不能代替最终车态成功率。
- Sparse Event-KV 的正结果主要是合成二元状态；自然对话被动 harvest 没有显示收益，
  且数字载荷为 0/192，不能把隐式 KV 当数据库。
- OneDayAgent 的 FULL 方案平均耗时和工具调用都明显增加；对短车控应先做
  verification-only，避免把 20% 左右的工具错误面扩散到更多步骤。

  消除 context attraction；当前接入会优化错层。
- 今日候选已按同一工作去重：Sparse Event-KV 的论文与 GitHub 是同一工作；RestoreKV

  是同一 harness；未把镜像或配套资产重复计数。
