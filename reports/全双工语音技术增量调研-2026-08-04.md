## 1. Cocktail-Talker：多人环境中的“是否该说”

来源：[论文正文 / arXiv:2607.27756](https://arxiv.org/abs/2607.27756)；[作者官方代码仓库](https://github.com/xi-j/Cocktail-Talker)。

### 它是什么

普通语音助手通常假设单用户、干净环境和轮流说话。Cocktail-Talker 面向多人及背景噪声并存的场景：当前语音可能对助手说、对其他乘员说，或完全无关，因此模型需要同时决定“是否响应”和“响应什么”。

它与前一日报告的 M3-DuplexBench 不重复：M3-DuplexBench 评测多轮 `SHIFT`、`PAUSE`、`BACKCHANNEL`、`BARGE_IN` 等连续对话事件；Cocktail-Talker 在固定话轮末做受话对象和响应动作决策，两者不能互相替代。

### 核心方法

- 在回答前生成三个动作之一：`<|respond|>`、`<|listen|>`、`<|ignore|>`。
- 基于 Qwen2.5-Omni-7B thinker–talker；冻结音频编码器和 talker，以 LoRA 微调 thinker。
- 输入是截至固定话轮结束的完整混合音频前缀和角色元数据；没有说话人分离、降噪或在线分块。
- Cocktail-DialogGen 生成 3/4 人对话，由 Qwen3-TTS 合成不同说话人的语音，再与不同 SNR 背景声混合。
- 训练包含 14,400 个独立对话，经五种噪声条件得到 72,000 个混合音频，约 1,280 小时；先对 580,100 个话轮做 SFT，再做 2,000 步 GRPO。

### 论文结果

由于其他模型没有 `LISTEN`/`IGNORE` 区分，横向比较将二者合并为 Silent：

| 模型 | 已见环境 macro-F1 | 未见环境 macro-F1 |
|---|---:|---:|
| Qwen2.5-Omni | 0.512 | 0.504 |
| Cocktail-Talker SFT | 0.903 | 0.907 |
| Cocktail-Talker SFT + GRPO | **0.928** | **0.930** |

SFT+GRPO 的 Respond/Silent 准确率在已见、未见环境分别为 0.931、0.933。回答内容指标显示，GRPO 主要提高“该回答时确实回答”的惩罚分；只在已经回答的样本上，条件分基本持平或略降。因此论文支持的是动作决策改善，不是回答内容全面改善。

### 对 StreamingModelHarness 的帮助

不要用它替换现有 FastTurn/SoulX 判停。更合适的接法是增加一个独立的“是否对助手说”动作头：

```text
AEC/NS → 说话人/座位线索 → 流式语义判停
                           → RESPOND / LISTEN / IGNORE
                           → 仅 RESPOND 进入 ASR/RAG/Action
```

应先构造驾驶员、副驾、后排、助手回声和广播声混合的回放集，测误唤醒、漏响应、打断恢复及动作首包时延。

### 局限与开放状态

- 作者明确说明当前系统**不是流式系统，并假设固定话轮边界**。
- 只有音频；没有利用座位、视线和唇动判断受话对象。
- 数据和测试来自模拟对话及合成/混合音频，没有真实座舱结果。
- 公开横向表只支持 Respond/Silent 二分类结论，不能证明三动作完整分类优于基线。
- 代码：作者仓库已存在。
- Cocktail-Talker 权重：**未知**。
- 生成数据：**未知**。
- 代码、模型和数据许可证：**未知**。

## 2. ECCD：TTS 幻觉的训练自由解码控制

来源：[论文正文 / arXiv:2608.00722](https://arxiv.org/abs/2608.00722)。

### 它是什么

自回归语音 LM 会出现偏离目标文本的误读、替换、遗漏、重复和意外续说。论文将其中一类错误归因于脆弱转换点上文本对齐支持不足。ECCD 是一种不需要再训练、在解码时增强文本对齐证据的方法；它应作为本地 TTS 的解码插件，而不是独立 TTS 候选。

### 核心方法

每个 acoustic-token 解码步运行同一模型的两个分支：

- expert：保留声学提示、历史、提示文本和目标文本；
- amateur：保留相同声学上下文和历史，但移除文本条件。

ECCD 只在 expert 的 top-k 可信候选中增强 `log p_expert - log p_amateur > 0` 的 token，并用 amateur 在该候选集中的概率质量动态校准增强强度。默认 `α=1, k=25`。方法不需要再训练，但需要模型暴露 logits，并在每步完成两个条件分支。

### 论文结果

SeedTTS-Eval 上，原生解码到 ECCD 的错误率变化如下：

| 模型 | test-zh CER | test-en WER | test-hard CER |
|---|---:|---:|---:|
| CosyVoice2 | 1.34 → **0.95** | 2.98 → **2.08** | 8.10 → **6.91** |
| CosyVoice3 | 1.19 → **0.92** | 3.01 → **1.82** | 6.92 → **6.19** |
| Llasa | 8.66 → **3.95** | 6.83 → **3.03** | 26.26 → **14.27** |
| GLM-TTS | 1.01 → **0.97** | 2.12 → **1.94** | 11.11 → **9.70** |

- 12 个模型/子集组合全部改善；最大相对降幅是 Llasa test-en 的约 55.6%。
- CV3-Eval 的 25 个模型/语言组合中改善 24 个；例外是 CosyVoice2 日语 WER 9.46% → 9.71%。
- CosyVoice2 的 test-hard 主观测试由 25 位母语听者评价、每种方法 30 条：ECCD 的 CMOS 为 `+0.644±0.091`，原生解码为 0。
- 常规 contrastive decoding 将 test-hard CER 从 8.10% 恶化到 8.72%；完整 ECCD 为 6.91%，说明“只做正向对齐增强”和动态校准是必要组成。

### 对 StreamingModelHarness 的帮助

前一日报告将本地 TTS 列为 P0。应在 CosyVoice2/3 本地 TTS 上实现 ECCD 小规模 A/B，同时记录首音频 P50/P95、RTF、峰值显存、CER、重复/漏词率和中断后的残留音频。若双分支使首包延迟不可接受，可以实验只在低置信转换点触发，但这一优化尚无论文证据。

### 局限与开放状态

- 正文没有报告双分支带来的首包时延、RTF、显存或吞吐。
- 主观实验只覆盖 CosyVoice2 的 test-hard。
- 一个日语组合退化；较大的 `α=4` 同时损害 CER 和说话人相似度。
- 错误边界定位依赖 ASR 时间戳近似，论文明确表示相关分析不能建立因果关系。
- ECCD 实现：**未知**，正文未给代码链接。
- 独立模型权重：不适用；方法无需训练。
- 许可证：**未知**。

## 3. SpeechParaling-Bench：副语言语音生成评测

来源：[论文正文 / arXiv:2604.20842](https://arxiv.org/abs/2604.20842)；[作者官方项目页](https://speechparaling-bench.github.io/)。

### 它是什么

SpeechParaling-Bench 是副语言语音生成基准，评测三种能力：

1. 指定音色、情绪、语速、音量等细粒度特征；
2. 在一句话内完成渐变或切换；
3. 从用户年龄、情绪、态度和非语言发声中推断合适的回答风格。

它补的是语音输出风格，与前一日报告的 OmniVideo-100K 音视频联合数据任务不同，不作重复项；也不能替代 M3-DuplexBench 的连续对话评测。

### 核心方法

数据含 1,001 个中英平行样本、13 个维度。正文 Table 1 和附录写 104 个特征，但 Table 2 写 101 个，数字存在内部不一致。评测用 Gemini 3 Pro 作为音频 judge，将候选与固定基线成对比较；中文基线是 Doubao Realtime Voice，英文基线是 Gemini Audio。

### 论文结果

- 中文总分最高是 Doubao Realtime Voice 70.84；英文最高是 Gemini Audio 64.97。
- 所有受测模型的 Dynamic Variation 初始平均分为 56.51/100，低于 Situational Adaptation 的 68.64 和静态控制的 66.01。
- 人工验证覆盖 5%、共 416 对响应；自动 judge 与人工偏好的 Spearman 相关在中文、英文分别为 0.90、1.00。
- Gemini Audio 在中文情境适配的 190 个样本中失败 67 个，其中 43.3% 被归因于忽略用户语音中的副语言信息。

### 对 StreamingModelHarness 的帮助

将其转成外挂 TTS 的“表达层”回归集，重点保留儿童安抚、驾驶告警、导航播报、后排娱乐和耳语/高噪声补偿；把文本正确率、音频首包和可打断性作为额外硬门槛。不要用其总分替代 M3-DuplexBench。

### 局限与开放状态

- 官方项目页提供数据集下载入口；数据许可证：**未知**。
- 评测代码和 judge pipeline 是否开放：**未知**。
- 查询主要由模型生成并由 TTS 合成，虽有人审，不等于自然用户分布。
- 主结果依赖单一 LALM judge、固定基线和默认 API 解码参数。
- 没有流式首包、判停、打断或实时稳定性指标。

## 4. Qwen-UI-Agent：统一 Action 与持久 Harness

来源：[论文正文 / arXiv:2607.28227](https://arxiv.org/abs/2607.28227)；[作者官方项目页](https://tongyi-mai.github.io/Qwen-UI-Agent/)。

### 它是什么

Qwen-UI-Agent 是统一操作 GUI、CLI 和 API 的跨平台 Agent。论文明确称其是 MAI-UI 的延续，应按同一技术谱系记录；本次只记录真实设备、统一 Action、主动服务和跨平台 harness 等新增内容，而不是把所有结果视为全新独立系统。

相较前一日报告中的 iFLYTEK-Embodied-Omni 和 ARDena，它新增了更具体的统一 Action schema、批动作、确认门和跨端状态编排；机器人或动态场景策略不能替代这些座舱执行安全机制。

### 核心方法

- 统一观察 GUI 截图、CLI 输出和 API 结构化响应，并保留完整交互历史。
- 统一动作含 GUI 操作、`cli_command`、`api_call`、`ask_user` 和 `terminate`；单次决策可发有序批动作。
- 支付、敏感数据和 CAPTCHA 等场景要求确认或用户接管。
- 主动服务按 `notification → event → affair → task` 组织，结合事项状态、用户画像记忆和反馈记忆。
- 跨平台 harness 维护持久 planner、session、workspace 和 tool registry，并支持依赖感知子任务与设备间 artifact transfer。
- 训练环境支持超过 10,000 个并发 sandbox；真实移动集群超过 100 台设备、150 个应用。

### 论文结果

- Qwen-UI-Agent-27B：MobileWorld 82.1%、MobileWorld-Real 92.2%、AndroidDaily 97.5%。
- OSWorld-Verified 为 79.5%，低于 Claude Opus 4.8 的 83.4%。
- OSWorld-v2 partial progress 为 40.0%、binary completion 为 13.9%；对应 Claude Opus 4.8 为 54.8%、20.6%。
- Action RL 使总体任务成功率提高超过 7%，推理 token 减少 21.3%，但交互步数增加 8.4%。
- Online RL 后，含验证动作的轨迹比例提高 14.7%，false-stop 降低 11.2%。
- 主动服务和跨平台 harness 只有案例，没有成功率、延迟或用户研究。

### 对 StreamingModelHarness 的帮助

可把 Harness C 的工具通道从“模型直接发 JSON”升级为：

```text
流式模型 → typed Action batch
         → schema / 权限 / 前置条件 / 幂等检查
         → 低风险并行准备，高风险 ask_user
         → 执行结果与最终车态回写
         → terminate 前强制验证
```

车控不需要复刻 GUI Agent；最有价值的是批动作、显式确认、持久事项和执行后验证。

### 局限与开放状态

- 真实设备结果依赖准确率为 92.8% 的 AutoJudge，仍有判断误差。
- 数据飞轮仍需大量人工监督；长流程逐步观察、推理和执行的延迟仍是部署障碍。
- 需要更系统的安全评测、可解释性和用户记忆控制。
- 没有语音流、音频打断或实时座舱结果。
- Qwen-UI-Agent 专用代码、权重、MobileWorld-Real 和 harness 许可证：**未知**。
- 官方页面提供演示，但不能据此标记为已开源。

## 5. StreamingClaw v2：流式视觉 Agent 框架

来源：[arXiv v2:2603.22120](https://arxiv.org/abs/2603.22120v2)；[作者官方项目页](https://jackyu6.github.io/StreamingClaw-Page/)。

### 它是什么

StreamingClaw v2 是面向连续视频流的 Agent 框架，将增量感知、外部记忆、主动事件和工具/技能执行组织为闭环。相较前一日报告的 Mage-VL codec 事件稀疏化，它补充 Agent、记忆和工具框架；相较 Voice Memory、AdaMM、ReflectWorld-MM 等外部记忆工作，它补充层次流式记忆，但没有实验证明优于前一日方案。

### 核心方法

- 新视频块到达后增量编码和推理，以动态滑窗限制上下文。
- 复用增量 KV cache；按注意力贡献裁剪视觉 token，并以余弦相似度跳过冗余视觉写入，但没有给保留率或阈值。
- 路由到直接流式推理、历史记忆检索或主动交互。
- 记忆节点保存压缩视频、摘要、描述和时间戳，并从片段演化为动作和事件。
- 主动交互可用持续监控节点，或由场景专用 trigger token 在一次 forward 中发出多个事件信号。
- 工具/技能执行结果回写上下文，形成感知—决策—动作闭环；项目页展示 DMS 和车辆迎宾 skill。

### 论文结果

正文**没有**报告数据集、基线、准确率、消融、硬件、帧率、端到端时延、TTFT、吞吐或 KV 保留率。因此“real-time”“low latency”是设计目标，不是已验证结果。

### 对 StreamingModelHarness 的帮助

可以借鉴“短窗 KV + 外部层次记忆 + 主动事件 + skill”四层接口，但不能据此选择运行时或制定时延预算。必须先在真实座舱视频上复现吞吐、事件漏检/误报、KV 增长和工具闭环成功率。

### 局限与开放状态

- 论文承认当前主要是视觉+文本，音频输入、音视频精细对齐和端到端联合生成仍不足。
- StreamingClaw 自身代码和模型权重：**未知**。
- 数据和许可证：**未知**。
- 官方项目页有架构和案例展示，但没有代码下载证据。
- 本次 Radar 命中的是 arXiv `v2`；正文没有说明 v1→v2 的具体变更，按同一论文修订版去重，不建立第二条技术记录。

## 6. Audio-Visual Flamingo：长音视频联合理解

来源：[论文正文 / arXiv:2607.16107](https://arxiv.org/abs/2607.16107)；[作者官方项目页](https://avflamingo.pages.dev/)；[NVIDIA 官方模型页](https://huggingface.co/nvidia/nemotron-labs-audio-visual-flamingo-hf)。

### 它是什么

Audio-Visual Flamingo（AVF）是长音视频联合理解和带时间戳推理模型。它与前一日报告的 OmniVideo-100K 音视频联合数据相关但任务不同：AVF 面向长视频联合理解，不作为重复项。它补充了 StreamingClaw 未覆盖的音视频联合理解，但没有证明音视频在线到达时的因果增量推理。

### 核心方法

- SigLIP 视觉塔与 AF-Whisper 音频编码器分别提取特征，再按时间块交错并加入 CRTE 绝对时间信息，送入 Qwen2.5-7B。
- 音频为 16 kHz 单声道，以 30 秒非重叠块独立编码后拼接。
- 训练课程从最长 5 分钟/16K token 扩展到 15 分钟/32K token，再以带时间戳的音视觉交错推理链做 SFT 和 GRPO。
- AV-Skills 含约 7M 个 caption/QA 实例，其中约 4.8M 是 QA；训练使用 512 张 H100。
- 文本子词可驱动可选流式 TTS；正文没有描述音视频在线到达时的因果增量推理。

### 论文结果

- WorldSense：AVF-Think 51.6，OmniVinci 48.2。
- DailyOmni：73.9，对比 OmniVinci 66.5。
- Video-MME 无/有字幕：70.7/71.2，对比 OmniVinci 67.3/68.6。
- LongVideoBench：60.1，低于 OmniVinci 62.0。
- MMOU：60.2，低于 Gemini-2.5 Pro 64.2。
- 正文没有推理硬件、采样帧率、分辨率、吞吐、TTFT、端到端延迟或 TTS RTF。

### 对 StreamingModelHarness 的帮助
